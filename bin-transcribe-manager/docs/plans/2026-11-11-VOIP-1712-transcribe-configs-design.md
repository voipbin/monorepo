# VOIP-1712: transcribe_configs with request-time AWS key resolution

## 1. Ticket review (against origin/main 5526516e6)

The only consumers are the two `streaminghandler.NewStreamingHandler(..., AWSAccessKey, AWSSecretKey)` calls (`cmd/transcribe-manager/main.go`, `cmd/transcribe-control/main.go`, one each).
- The constructor creates the GCP client (ADC), and the AWS client once when both strings are not empty. With neither client it returns `NewDisabledStreamingHandler()`. `awsClient` is read in `getProviderFunc` (`start.go`), `awsRun` and `awsInit` (`aws.go`). `STT_PROVIDER_PRIORITY` is not in the code (only in `k8s/deployment.yml` and an old plan).
- `migrations/` holds `000001_baseline` only, so the next numbers are 000002 and 000003. There is no open or merged PR in this scope, and no open sibling PR (tts, message) at the time of writing.
- Corrected: (a) "two keys as an atomic group" is not possible with the shared library: an atomic group needs exactly one secret as its anchor (`confighandler/registry.go`, `findAnchor`), and a non secret access key could not be written (the admin API and the CLI write secrets only). The library is not changed. (b) The call sites are one in each `cmd`, not three.

## 2. Baseline (what must stay the same when the database has no row)

- Start up: GCP client from ADC; AWS client only when both keys are set; no client at all gives the disabled handler (`Run` warns and returns nil, `Start` and `Stop` return `STT_NOT_CONFIGURED`, Unavailable).
- `Start`: creates the streaming record, starts the external media, connects the WebSocket, then `go runSTT` picks the providers (the requested one first, then GCP, then AWS; a provider without a client is skipped).
- `Stop`: an unknown session is `STREAMING_NOT_FOUND` (NotFound), wrapped. `transcribehandler.isSafeToConsiderStopped` treats NotFound and `STT_NOT_CONFIGURED` alike as "safe to consider stopped". `Run` of the real handler is a silent no-op, and `runStreaming` turns a `Run` error into a failed start.
- One key set only: AWS is silently unavailable (debug log).

## 3. Decisions

D1. Two independent secret keys `aws.access_key` (env `AWS_ACCESS_KEY`) and `aws.secret_key` (env `AWS_SECRET_KEY`), at most 512 bytes, table prefix `transcribe`. The access key id is an identifier in AWS terms, but it is declared secret so that no value reaches the API, the history or a log, and because the admin API writes secrets only.

D2. Pair rule (replaces the atomic group). `internal/transcribeconfig.AWSKeys` reads both keys and hands the pair out only when both have a value from the same source: both `db` or both `env`. Every other state is "AWS not available": one key only (as before), one from the database and one from the environment, none. A pair is never assembled from two sources, and the environment never fills a database gap, which is the rule of the atomic group (a database value for the credential means the group is read from the database only). A state that involves a database row logs a warning with key names and sources only; the all environment cases keep the old debug level. A read error (database error, undecryptable value) is an error (`ErrKeyUnavailable`), never "not configured" and never the environment value.

Both keys are always read (access key first), so every state that involves a database row is seen and logged, including a secret stored before its access key. The two reads are not one transaction: a `config set` between them can give a mixed pair that still counts as "same source". The client cache is keyed by the pair, so the next `Start` recovers; a test covers it.

Consequence for operators, documented: entering the first pair takes two `config set` commands, and between them AWS is unavailable (GCP serves; with no GCP, streaming start is refused). Rotating an existing pair takes two commands as well, and between them the pair is mixed (new id with the old secret) and is accepted by the rule. AWS rejects such a credential only inside the asynchronous `runSTT`, after `Start` has returned success, so the failure is delayed and silent to the caller: with GCP present the stream falls back to GCP (a customer who asked for provider AWS gets GCP, as when the AWS client cannot be built today), with no GCP the session never produces a transcript. Run the two commands back to back (the window is seconds), keep the old key valid at AWS, and check one transcribe start afterwards.

D3. Request-time resolution, no disabled handler. `NewStreamingHandler` takes `awsKeys AWSKeyFunc` (`func(ctx) (accessKey, secretKey string, err error)`) instead of the two strings and always returns the real handler. The GCP client is still made once at start up (it has no stored key). The AWS client is resolved in `Start` by `awsClientFor(ctx)`: read the pair (one 2 second bound for both reads), and reuse the cached client when the pair is the one it was built from, otherwise build a new client and replace the cache (a mutex guards the cache: the pair is read outside the lock, and the lock covers the comparison and, only when the pair changed, the client build; no new type). The 2 second bound is below the RPC timeout of the caller. A client build failure keeps the old meaning: AWS not available (warning); it does not update the cache, so the same pair is built again at the next `Start` and warns again. The cache holds the pair that built the client, in memory only, like the configuration did.
- A deployment that has the key only in the database is not pinned: nothing is decided at start up, so it works from the first `Start` after the value is stored, with no restart. The constructor resolves once to log the old start up lines (provider initialized, or "no provider available now"); a read failure there is a warning and never stops the start.
- `Start` resolves the providers before the streaming record and the external media: GCP nil and no AWS client means `STT_NOT_CONFIGURED` at once, no side effect (the baseline of the disabled handler); GCP nil and a read error means a new Unavailable reason `STT_KEY_UNAVAILABLE` (a configuration that cannot be read is not "not configured"); GCP present and AWS unavailable (not configured, incomplete or read error) continues with GCP, as before with an AWS client that failed to build (this includes a request that names `provider` `aws`: while the credential cannot be read it is served by GCP with the existing "requested provider not initialized" warning, where before the environment pair would have served it); a read error or an incomplete pair that involves a database row logs one warning per `Start` (key names and sources only), so a read failure is not mistaken for "not configured". The resolved client is passed to `runSTT`, `getProviderFunc` and `awsRun`/`awsInit` as an argument (the `go runSTT` goroutine must not read a field that another `Start` replaces).
- Deliberate deviations from the baseline when no row exists (the behavior is otherwise the same): (a) every `Start` now reads the configuration (two reads of about a millisecond each, bounded by 2 seconds in total); (b) a deployment that has AWS keys in the environment only, no GCP client, and a database outage or timeout now gets `STT_KEY_UNAVAILABLE` where it worked before, because a read error is never treated as "no row" (the same rule as ai-manager and email-manager: a store error is an error); with GCP present such a deployment keeps working through GCP; (c) the warning of the disabled handler's `Run` goes away because the handler is always the real one (`Run` is a silent no-op); the constructor logs the "no provider available now" line instead.
- `Stop` and `Run` do not read the database. `Stop` never returns the new reason and needs no entry in `isSafeToConsiderStopped`. The `STT_NOT_CONFIGURED` branch of `isSafeToConsiderStopped` stays as a defensive branch (no `Stop` produces it after this change) and only its comment, which points at the removed disabled handler, is corrected. A session without a provider cannot exist, so `Stop` of an unknown id returns `STREAMING_NOT_FOUND`, which `isSafeToConsiderStopped` treats as safe, exactly like `STT_NOT_CONFIGURED` (the only visible difference is the reason text in a log line; a test pins that a transcribe still reaches done). `transcribehandler.Start` returns the `Start` error unchanged, so the typed error reaches api-manager.
- A key change does not touch a running stream: the stream keeps the client it was started with, and the next `Start` uses the new pair. A transcribe of direction "both" starts two legs with two `Start` calls, so a change between them gives two clients; this is harmless, and a read failure on the second leg makes `transcribehandler` stop the first as it does for any `Start` error. AWS validates the credential when a stream is opened, so a revoked old key ends the running streams at AWS, which is the operator's choice (rotation steps in `docs/operations.md`).
- `transcribe-control` calls the same constructor with the same supplier, so its `transcribe start` follows the same rule.
- `disabledStreamingHandler` and `NewDisabledStreamingHandler` lose their last caller and are removed with their test; the error helper and the reason constant stay (`disabled.go` becomes `errors.go`).

D4. Master key list `TRANSCRIBE_CONFIG_ENCRYPTION_KEYS`, environment only (no flag), parsed like ai-manager: a malformed or empty list is logged without the value, secrets cannot be stored (`ENCRYPTION_KEY_NOT_CONFIGURED`), and the service starts and keeps using the environment keys (the same policy as ai-manager: the stored secret feature is off, the environment keys keep working). `internal/config.EnvValue` serves the two environment names to the registry (same lookup as the direct read).

D5. Container definition: one line in `bin-transcribe-manager/komodo/docker-compose.yml`: `TRANSCRIBE_CONFIG_ENCRYPTION_KEYS=[[BIN_MANAGER__TRANSCRIBE_MANAGER_CONFIG_ENCRYPTION_KEYS]]` (the ai-manager precedent maps `BIN_MANAGER__AI_MANAGER_CONFIG_ENCRYPTION_KEYS` to `AI_CONFIG_ENCRYPTION_KEYS`). Without the variable the service starts normally. `k8s/deployment.yml` also lists the AWS variables but production is Docker and Komodo, so it is not changed (the ai-manager change did not touch it either).

D6. Admin API: allow `transcribe` in `serviceConfigServices`, map it to `QueueNameTranscribeRequest` with the label `transcribe/configs` in `requesthandler`, mount `configrpc.NewServer(configHandler, serviceName)` in the transcribe-manager listener (before the request log entry exists, with the guard, recover and fixed 404 of the ai-manager listener), add `transcribe` to the OpenAPI enum (`ServiceConfigServiceNameTranscribe`), docs and generated files. The config requests arrive on the shared queue only (api-manager sends them there); `processRequest` is shared with the per host queue, so both queues answer them.

D7. Store: `pkg/dbhandler/config_store.go` is the ai-manager implementation (the table names come from `internal/configkeys`). It is wired by calling `dbhandler.NewConfigStore(sqlDB)` directly in `cmd/transcribe-manager` and `cmd/transcribe-control`; the `DBHandler` interface and its mock are not changed, so there is no mock regeneration and no `go generate` drift (the ai-manager added `ConfigStore()` to its interface; it is not needed here).

## 4. Dual input with tts-manager

The same AWS credential is read by bin-tts-manager from its own environment. In the Komodo definitions both services take the credential from the same variables (`BIN_MANAGER__AWS_ACCESS_KEY`, `BIN_MANAGER__AWS_SECRET_KEY`), so rotating those variables moves both at once, and the environment value is a rollback only while the variable still holds the old key; going back from the database to the environment takes `config clear` on both keys (with only one cleared the pair is "not available", and between the two commands AWS is off, which refuses a transcribe start on a deployment that has no GCP). Each service has its own configs (design D2, D3), so the source of the credential is two places: the environment variables of the two services, and, once each of them adopts configs, the two tables. Nothing keeps them equal. Risks: moving one service to the database and not the other leaves the other on the environment value; rotating in one service only leaves the other on the old key, and revoking the old key at AWS then breaks that one. Mitigation (a procedure, no code): `docs/operations.md` states it. Rotate both services before the old key is revoked, check a transcribe start and a TTS call after the change, revoke the old key last, and keep the old key valid until both checks pass (the environment value is the rollback). If the two services use different IAM users nothing is shared. No abstraction in code: the sibling's implementation is not read as a dependency and is not changed.

## 5.1 Code level design

- `internal/configkeys`: `Table = "transcribe_configs"`, `HistoryTable = "transcribe_config_histories"`, `KeyAWSAccessKey = "aws.access_key"`, `KeyAWSSecretKey = "aws.secret_key"`, `Keys()` (secret, string, `MaxLen` 512, env names as above), `NewRegistry()`.
- `internal/config`: `EnvConfigEncryptionKeys = "TRANSCRIBE_CONFIG_ENCRYPTION_KEYS"`, field `ConfigEncryptionKeys` (viper env binding only, no flag), `func (c *Config) EnvValue(name string) (string, bool)` for the two AWS names (the value viper resolved, flag or environment, as the direct read did), `ResetForTest` only if a test needs it.
- `internal/transcribeconfig`: `New(cfg, store, opts...) (confighandler.Handler, error)` (`secretcrypto.New(cfg.ConfigEncryptionKeys, WithMaxPlaintext(2020))`; a failure is logged without the value and replaced by an empty cipher), `ErrKeyUnavailable`, `AWSKeys(h) func(ctx) (accessKey, secretKey string, err error)` (D2, a fixed 2 second bound, reads on every call, keeps nothing), `LogSources(ctx, h)` (key and source only; an unset key is info, because AWS is optional).
- `pkg/streaminghandler`: `type AWSKeyFunc = func(ctx context.Context) (accessKey, secretKey string, err error)`; `NewStreamingHandler(reqHandler, notifyHandler, transcriptHandler, awsKeys AWSKeyFunc) StreamingHandler`; struct fields `awsKeys`, `muAWS sync.Mutex`, `awsClient`, `awsAccess`, `awsSecret` (the cache); `awsClientFor(ctx) (*transcribestreaming.Client, error)`; `runSTT(st, provider, awsClient)`, `getProviderFunc(p, awsClient)`, `awsRun(st, awsClient)`, `awsInit(ctx, st, awsClient)`; `getProviderFunc(p, awsClient)` keeps its return type `func(*streaming.Streaming) error` (for AWS it returns a closure that binds the client), so the `runSTT` loop is unchanged; the client factory is a handler field `newAWSClient func(accessKey, secretKey string) (*transcribestreaming.Client, error)` set to `awsNewClient` by the constructor, so tests inject a loopback client (the existing `newUnreachableAWSClient`) and never reach AWS; `errors.go` (was `disabled.go`) keeps `ErrSTTNotConfiguredReason`, `newErrSTTNotConfigured` and adds `ErrSTTKeyUnavailableReason`, `newErrSTTKeyUnavailable`. A nil `awsKeys` means "no AWS".
- `pkg/listenhandler`: `NewListenHandler(..., configServer *configrpc.Server)`, a nil server answers config URIs with 404; `processRequest` routes `h.configServer.Match(m) || configrpc.LogSafe(m) != m` to `processConfig` before the log entry is built.
- `cmd/transcribe-manager`: `run` builds `transcribeconfig.New(config.Get(), dbhandler.NewConfigStore(sqlDB))`, calls `LogSources`, passes `transcribeconfig.AWSKeys(configHandler)` to `NewStreamingHandler` and `configrpc.NewServer(configHandler, serviceName)` to `runListen`. `cmd/transcribe-control`: the same for the handler, and a `config` command group (copy of `ai-control config`: `list`, `set --key --actor-id` with the value on stdin, `clear`; history source `cli`; the root `PersistentPreRunE` of `transcribe-control` only binds flags and loads the configuration and opens no connection, so the group needs no `PersistentPreRunE` of its own and works with the database and the master key list only).

## 6. Impact analysis (schema change)

1. Destructive operations: none. Two new tables, `CREATE TABLE IF NOT EXISTS`, one statement per file; no DROP, TRUNCATE, type change, rename, default change, UPDATE, DELETE or INSERT SELECT; no constraint on existing data (the CHECK constraints belong to the new empty tables). Not `[DESTRUCTIVE]`. The down files drop the new tables and carry `-- DOWN-LOSSY`. MySQL 8.0 and MariaDB 12.3 are the tested engines; no ClickHouse change.
2. Rolling deploy: an old image ignores the tables; the new image applies them before it listens, so it never meets the old schema. `grep -rn "transcribe_configs\|transcribe_config_histories" /bin-*` finds no other user. An old replica ignores a stored value, so a value must be entered only after every replica runs the new image (documented).
3. Locks and duration: creating an empty table; no existing data, no lock on a table in use.
4. Rollback: deploy a revert; the tables stay and old code ignores them; the migration helper skips a database version ahead of the image. A service migration revert never edits `migrations/`.
5. Data loss: none for a new table; `down` removes stored settings and history. Old code on the new schema: works (ignores). New code on the old schema: cannot happen (migrations run before listening).

## 8. Frontend contract (after merge)
