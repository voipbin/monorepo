# VOIP-1685 PR2: bin-number-manager uses the shared secretcrypto

> Superseded in part (VOIP-1688): the additional authenticated data described below was removed. A stored ciphertext is plain AES-256-GCM and is not bound to its row; ciphertexts written with the data no longer decrypt and the secret must be entered again.

## 1. Ticket review (against origin/main d43e84007)
- `bin-common-handler/pkg/secretcrypto` is on main (`Crypto`, `New(raw, ...Option)`, `Encrypt(pt, aad []byte)`, `Decrypt(blob, version, aad []byte)`, `AADLiteral`, `WithMaxPlaintext`, sentinels `ErrKeyNotConfigured`, `ErrTooLong`, `ErrDecrypt`, `ErrInvalidKeySet`). The signatures differ from the service copy (`aad` is `[]byte`, errors are library sentinels), so the service needs a thin adapter.
- With this PR the shared library has two consumers (email-manager, number-manager). This is not a precedent for other packages.
- Users of the service copy: `cmd/number-manager`, `cmd/number-control`, `pkg/providerhandler` (`admin.go` Encrypt, `resolve.go` Decrypt, `main.go` field and constructor). No other package imports it.
- Behavior differences found by reading both implementations (none touches stored data):
  1. A list with only empty entries (for example `,`): service copy returns "no key" without an error; the library returns `ErrInvalidKeySet`. The adapter keeps the old result.
  2. Decrypt with a nil receiver, no key at all, or an unknown key version (the old code had three texts): old text "encryption key version N is not configured", new `ErrDecrypt`. The library gives `ErrKeyNotConfigured` for the first two and `ErrDecrypt` for the last. Both only reach a log line and both give `db_undecryptable`.
  3. Every parse error text changes: the service copy says `encryption key entry N is malformed` or names the key version (`encryption key version N is not valid base64`), the library says `invalid encryption key list: entry N ...` and names only the position, wrapping `ErrInvalidKeySet`. It is only logged (daemon) or printed by the CLI; no code or test matches it. This is the one stated exception to "error text unchanged"; the error still never holds key text.
  4. Encrypt without a key: old `provider.ErrSecretKeyNotConfigured`; the adapter maps `ErrKeyNotConfigured` to it (same text). Too long: old `provider.ErrInvalidArgument` with the text "the secret is longer than 1024 bytes"; the adapter rebuilds the same text from `ErrTooLong`.

## 2. Design
- New `pkg/providerhandler/secret.go`: `maxSecretBytes = 1024`; `NewSecretCrypto(raw) (*secretcrypto.Crypto, error)` (a list is blank-only when every comma-separated entry is empty after `TrimSpace`; it becomes `New("")`, which needs no limit because Encrypt fails on the missing key first; otherwise `New(raw, WithMaxPlaintext(maxSecretBytes))`); `encryptSecret(c, secret, name)` and `decryptSecret(c, blob, version, name)` using `AADLiteral(string(name))` and the error mapping above. `NewProviderHandler` keeps its signature and takes `*secretcrypto.Crypto` of the common package.
- `admin.go`/`resolve.go` call the two helpers; the existing 1024 pre-check in `UpdateSecret` stays and is the path that answers a long secret (400 "secret is too long"); the mapped `ErrTooLong` is a second line that tests reach directly. The order stays: length pre-check (400) before the key check (503), and the library checks the key before the length, as the old code did. `cmd/*` call `providerhandler.NewSecretCrypto`; the daemon still continues on a parse error (fail closed, `New("")`), the CLI still rejects it.
- Delete `pkg/secretcrypto` (tests too). Update `CLAUDE.md` and `docs/architecture.md`. Schema and data untouched.

## 3. Verify items
- Fixed vectors: ciphertext hex constants made once by running the old `pkg/secretcrypto` code in a scratch run, before it is deleted, under fake keys (byte patterns built in the test code, never a real key). The constants are literals in the test, so the proof is of the old ciphertext, not of the new library. Keys: version 1 = bytes 0x40+i, version 2 = bytes 0x90+i. Five vectors, already generated with the old code (scratch run, kept outside the repo until step 1): A telnyx and B twilio at version 2 under the two-key list; C telnyx ASCII, D twilio with a non-ASCII plaintext, and E telnyx with a 1024-byte plaintext (the limit) at version 1 under the one-key list. They decrypt through `decryptSecret`; a wrong provider name, a removed key version and a damaged blob fail with an error (the `db_undecryptable` path).
- Adapter tests: blank-only list including `, ,` and a mixed list `1:key,,`, a 12..27 byte blob giving `db_undecryptable`, malformed list errors and no key text in the message, error mapping with `errors.Is`, 1024 accepted and 1025 rejected, nil crypto.
- The existing tests pass with their assertions unchanged. The allowed fixture edits are only: the import path; the 5 `secretcrypto.New(x)` fixture calls (`main_test.go` 124, 144, 358, 378, `twilio_test.go` 25) become `NewSecretCrypto(x)` so the tests run with the production configuration (1024 limit, blank-only list); and the AAD argument of the 4 `Encrypt` calls (`main_test.go` three times, `twilio_test.go` once), which becomes `secretcrypto.AADLiteral(...)`.
- Coverage: no package other than the deleted one loses covered statements; the measured total is given in the coverage result below.
- `go build`, `go vet`, golangci-lint, `go test ./...`, grep shows no reference to the deleted package.
- Coverage result (replaces the earlier top-up plan): the total moved from 2790/3451 (80.85%) to 2738/3397 (80.60%); without generated mocks from 93.44% to 93.38%. The whole drop is the 66 covered statements of the deleted package, whose tests now live in `bin-common-handler/pkg/secretcrypto` (the library has its own suite and the compatibility vectors). No other package fell, and `providerhandler` rose from 76.4% to 77.3%. The statements that are still uncovered in the service were checked one by one and cannot be reached by a test without padding: the error branches of `json.Marshal`, `url.Parse`, `http.NewRequest` and the SQL builders, the `VoipbinError` and `ErrNotFound` cases of the listen handler default error switch (no handler path returns such an error unconsumed: the raw errors are only `url.Parse` and JSON unmarshal errors, all others are consumed by `errorResponse`), the viper bind errors, a random-number duplicate and the `initNumberHandler` of `number-control` (it needs RabbitMQ and Redis; its key-list check is the same `NewSecretCrypto` call that is tested). ## 4. Implementation plan (interfaces)
```go
// pkg/providerhandler/secret.go
const maxSecretBytes = 1024
func NewSecretCrypto(raw string) (*secretcrypto.Crypto, error)            // exported: used by cmd/*
func encryptSecret(c *secretcrypto.Crypto, secret string, name number.ProviderName) ([]byte, int, error)
func decryptSecret(c *secretcrypto.Crypto, blob []byte, version int, name number.ProviderName) (string, error)
```
- `encryptSecret`: `c.Encrypt(secret, secretcrypto.AADLiteral(string(name)))`; `ErrKeyNotConfigured` -> `provider.ErrSecretKeyNotConfigured` (returned as is); `ErrTooLong` -> `fmt.Errorf("%w: the secret is longer than %d bytes", provider.ErrInvalidArgument, maxSecretBytes)`; any other error (cipher or nonce failure, not reachable in a test) is returned by one plain `if err != nil` branch next to the `errors.Is` cases, with no extra branch. `decryptSecret` only forwards with the AAD (the error is logged and decides `db_undecryptable`).
- Steps: (1) add `secret.go` and its test, with the five literal vectors from the scratch file (the old package is deleted only in step 3, after the vectors are in the test), (2) switch `main.go`, `admin.go` (also its `secretcrypto.MaxPlaintextBytes` pre-check becomes `maxSecretBytes`, the one constant for both limits), `resolve.go`, the 2 test fixture files (`main_test.go`, `twilio_test.go`) and both `cmd` files, (3) delete `pkg/secretcrypto`, (4) measure coverage, (5) docs: `CLAUDE.md` (Provider dispatch line), `docs/architecture.md` (tree line and component table row). The adapter test also checks that the daemon fallback `NewSecretCrypto("")` has no key and that `encryptSecret` then gives `provider.ErrSecretKeyNotConfigured`. Each step builds and tests.
- Vector provenance: the old `pkg/secretcrypto/main.go` is unchanged on origin/main d43e84007; the test comment names plaintexts, key patterns and provider names. Before step 3 the old package decrypts the five literal vectors once more to confirm they match.
- Diff review items: after the switch the daemon still replaces a failed parse by `NewSecretCrypto("")` and continues, and the CLI still wraps the error and returns it (the `cmd/*` branches have no unit tests; the diff is read for this).
