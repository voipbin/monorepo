# bin-transfer-manager 단위 테스트 커버리지 90% 상향 설계 (VOIP-1663)

미커버 125 중 cmd/transfer-control 54, cmd/transfer-manager 61 이 대부분입니다. 이전 레인(VOIP-1652)은 sock, DB Connect 에 주입 지점이 없어 cmd 의 연결 이후 구간을 제외했으나 이제 `sockhandler.SetRabbitFactory`, `databasehandler.SetConnectFunc` 가 있어 그 구간에 도달할 수 있습니다. 열린 PR 과 중복 없음. 제품 코드(비테스트 .go)는 바꾸지 않습니다.

## 3. 변경 계획 (테스트 파일만, go.mod/go.sum 변경 없음)
세 주입 지점을 `t.Cleanup` 으로 복원하고 `t.Parallel` 을 쓰지 않습니다. DB 는 `sql.Open("mysql", <존재하지 않는 unix 소켓 DSN>)` 로 만든 지연 연결 핸들(Ping 이 없어 접속하지 않음), Redis 는 miniredis, sock 은 `MockSockHandler`(Connect 는 기대 호출)를 씁니다. 네트워크와 외부 비용 호출이 없습니다.
- control, 새 테스트: initHandler 성공(factory 가 설정의 RabbitMQAddress 를 받고 Connect 가 1회 호출됨), initTransferHandler, runGetByCall 과 runGetByGroupcall(miniredis 에 cachehandler 로 저장한 전이를 출력 JSON 으로 단언, 없는 id 는 오류 접두사 `failed to retrieve transfer`, 잘못된 UUID 는 `failed to resolve ...`), runServiceStart(입력 검증 오류 4종, 통화 조회 실패 전파, 통화 조회와 flow 생성이 성공한 뒤 알 수 없는 transfer type 오류), Execute 경유 PersistentPreRunE(플래그로 Redis 주소를 지정해 get-by-call 실행, config.LoadGlobalConfig 가 sync.Once 이므로 Execute 와 main 을 지나는 테스트는 모두 같은 값을 플래그로 넘김), main(`--help` 인자, 출력의 `Voipbin Transfer Management CLI` 단언).
- manager, 새 테스트: run(성공, subscribe 실패, listen 실패. 성공 경로의 Consume 호출은 채널로 완료를 기다림), runDaemon(성공: chDone 을 미리 채워 종료, DB 성공 뒤 cache 실패, run 실패), main(completion 서브커맨드, 출력의 `bash completion` 단언, 표준 출력은 읽는 고루틴이 있는 파이프(captureStdout 방식)로 받음).
- 전역 상태 규칙: (1) config.LoadGlobalConfig 는 프로세스 전역 sync.Once 라 Execute 와 main(completion)을 지나는 테스트는 `-count`, `-shuffle` 에서 Once 소비 여부가 달라집니다. 따라서 이 테스트들은 시작 때 `setConfig` 로 값을 넣고 같은 값을 플래그로 넘겨 Once 소비 여부와 무관하게 같은 결과가 나오게 하며, 설정 반영 여부 대신 출력 JSON 과 서브커맨드 로컬 플래그의 `viper.GetString` 을 단언합니다. (2) main 테스트는 os.Args 를 완전히 교체하고 `t.Cleanup` 으로 복원하며 Execute 가 nil 을 반환하는 인자(`--help`, `completion bash`)만 씁니다. 단언 대상은 help 출력의 `Voipbin Transfer Manager Daemon` 등 표준 출력 내용입니다. Bootstrap 이 바꾸는 logrus 포매터와 레벨은 저장 후 복원합니다. (3) runDaemon 계열 테스트는 시작 때 chDone 을 비우고(남은 initSignal 고루틴이 있어도 chDone 에는 true 가 최대 1회만 쌓이므로 비운 뒤의 단언은 순서와 무관), `t.Cleanup` 에서 `signal.Stop(chSigs)` 를 호출하며, 종료 뒤 chDone 이 비었음을 단언합니다. (4) Consume 고루틴이 시작되는 모든 경로(성공과 listen 단계 실패 포함)에서 호출된 ConsumeMessage 와 ConsumeRPC 를 각각 채널로 기다린 뒤 테스트를 끝내 gomock 종료 뒤 호출을 막습니다(기존 Test_runSubscribe 의 consumed 패턴 재사용).
- 기존 헬퍼는 패키지별로 다릅니다(별개 test binary). control 은 setConfig, resetViper, startFakeDatabase, testUnreachableDSN, captureStdout 을 재사용하고 testWaitTimeout, hookLog, checkRunError 는 없어 새 파일에 필요한 만큼만 `_seam` 이름으로 정의합니다. manager 는 setConfig, hookLog, checkRunError, testWaitTimeout, testUnreachableDSN 을 재사용하고 resetViper, captureStdout 은 없어 새 파일에 정의합니다. 새 테스트 이름은 기존 `Test_initHandler_*`, `Test_runDaemon_*` 와 겹치지 않게 `_seam` 접미사를 붙입니다.
- requesthandler.NewRequestHandler 는 호출마다 prometheus 기본 registerer 에 MustRegister 해 프로세스당 1회만 호출할 수 있습니다(두 번째 호출은 panic, `-count` 에서도 동일). initTransferHandler, run 등 이를 거치는 모든 테스트는 NewRequestHandler 를 부르기 전에 매 호출 단위(서브테스트마다)로 헬퍼 `isolateMetrics(t)` 를 호출합니다(부모 테스트에서 한 번만 부르면 같은 registry 에 중복 등록되어 panic). 헬퍼는 새 `prometheus.NewRegistry()` 를 `prometheus.DefaultRegisterer` 에 넣고 `t.Cleanup` 으로 원복하며 DefaultGatherer 는 건드리지 않습니다(기존 initProm 테스트 영향 없음). 직접 검증 항목으로 호출마다 isolateMetrics 를 부르면 같은 경로를 2회 연속 호출해도 panic 이 없음을 테스트합니다(isolate 없이 두 번 부르면 panic 이 나는 것이 정상 동작).
- runDaemon 계열 테스트의 config 는 PrometheusEndpoint 와 PrometheusListenAddress 를 빈 값으로 고정해 initProm 이 DefaultServeMux 에 등록하지 않게 합니다.
- 환경변수 누출 방어: Execute 와 main 테스트는 Bootstrap 이 읽는 환경변수 키(AutomaticEnv, BindEnv 대상 7개)를 `t.Setenv(key, "")` 로 비우고 viper 를 초기화(`viper.Reset`, 정리 시 다시 Reset)합니다.
- control 의 입력 검증 4종(transfer-type 빈 값, transferer-call-id 빈 값 또는 UUID 형식 오류, transferee-addresses 빈 값, addresses JSON 파싱 오류 `failed to parse transferee addresses JSON`)도 initHandler 가 먼저 실행되므로 지연 DB 핸들, miniredis, mock sock(Connect 기대)이 모두 필요합니다. unknown type 경로의 RequestPublish 응답은 `sock.Response{StatusCode: 200, DataType: "application/json"}` 에 CallV1CallGet(GET /v1/calls/<id>, confbridge_id 가 nil 이 아닌 call JSON)과 FlowV1FlowCreate(POST /v1/flows, flow JSON)를 URI 와 메서드로 구분해 단언합니다.
- get-by-* 근거: dbhandler 의 TransferGetByTransfererCallID 와 TransferGetByGroupcallID 는 cache 만 읽어 DB 핸들(지연 sql.Open)은 쓰이지 않습니다. ServiceStart 는 transferInit 단계까지만 reqHandler(mock sock 의 RequestPublish)를 쓰며, DB 가 필요한 BlindTransfer, AttendedTransfer 본문은 범위 밖입니다. cache 실패는 기존 테스트처럼 닫은 miniredis 주소를 씁니다.
- 시간, 외부 상태 비의존: 대기는 채널과 제한 시간으로만 하고 고정 sleep 을 쓰지 않습니다. 기존 테스트 파일과 이름이 겹치지 않게 새 파일 `main_seam_test.go` 를 각 cmd 에 둡니다.
- 빈 호출과 자기비교 금지. 단언은 오류 접두사와 errors.Is, 출력 JSON, 호출 인자(factory 인자, RequestPublish 의 URI 와 메서드)로 합니다. 합성 값만 씁니다(203.0.113.x, 가짜 UUID, DSN 에 비밀번호 없음).

## 4. 도달 범위 평가
주입 지점으로 sock, DB 연결 뒤 구간이 열려 수기 약 +100 statement 가 도달 가능하며 예상 합계는 약 935/950 입니다(구현 뒤 실측은 932/950, 98.1%)(실제 값은 구현 뒤 재측정). 목표 90.5%(860) 에 큰 여유가 있어 block 사유가 없습니다.
