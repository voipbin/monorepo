## 1. Goal

Make the admin-surface `GET /v1.0/transcripts?transcribe_id=...&page_size=&page_token=`
return the requested page, exactly as the agent surface and the OpenAPI contract already
do. No behaviour change for callers that send neither parameter (they still get the
newest 100 lines).

## 2. Design

### 2.1 Service handler signature

`TranscriptList` gains the two pagination arguments in the same position the agent
method uses, so the admin and agent methods read identically:

```go
// before
TranscriptList(ctx context.Context, a *auth.AuthIdentity, transcribeID uuid.UUID) ([]*tmtranscript.WebhookMessage, error)
// after
TranscriptList(ctx context.Context, a *auth.AuthIdentity, size uint64, token string, transcribeID uuid.UUID) ([]*tmtranscript.WebhookMessage, error)
```

Files: `pkg/servicehandler/main.go` (interface), `pkg/servicehandler/transcript.go`
(implementation), `pkg/servicehandler/mock_main.go` (regenerated by `go generate`,
never hand-edited), `server/transcripts.go` (caller).

### 2.2 Empty token defaults in api-manager

As `TranscribeList` (`pkg/servicehandler/transcribe.go:82-84`) and
`ServiceAgentTranscriptList` (`serviceagent_transcript.go:38-40`) do:

```go
if token == "" {
    token = h.utilHandler.TimeGetCurTime()
}
```

placed exactly where the agent method places it: right after the log fields, **before**
`transcribeGet` and `hasPermission`. Consequence for tests: every call with an empty
token, including a permission-denied one, expects one `TimeGetCurTime()` call.
transcribe-manager would default it too, but setting it here keeps the three
api-manager list methods consistent and makes the token the service handler sends fully
determined by its inputs (testable with the util-handler mock). `utilHandler` is wired in
production by `NewServiceHandler` (`main.go:1243`).

### 2.3 Handler

`server/transcripts.go` already computes `pageSize` (default 100; any value `<= 0` or
`> 100` is reset to 100, `:33-36`) and `pageToken`; the only change is passing them:
`h.serviceHandler.TranscriptList(c.Request.Context(), a, pageSize, pageToken, transcribeID)`.
Cleanup while the files are touched: the error log at `transcripts.go:48` currently uses
the package-level `logrus.Errorf` and so drops the `func`/`request_address`/`agent`
fields built at `:14-27`; it becomes `log.Errorf("Could not get transcripts. err: %v", err)`
on the field-scoped logger, as `server/accesskeys.go`, `activeflows.go`, `agents.go` and
others in this package do. `server/service_agents_transcripts.go:48` has the identical
package-level call (`log` is in scope there at `:15`) and is switched to
`log.Errorf("Could not get transcripts. err: %v", err)` in the same change; in `transcript.go` the doc
comment at `:16-18` ("TranscriptGets … list of transcribes") becomes "TranscriptList
sends a request to transcribe-manager to get a list of transcript lines for one
transcribe session", the `"func": "TranscribeGets"` log field at `:25` becomes
`"TranscriptList"`, and `size`/`token` are added to the log fields as in
`serviceagent_transcript.go:34-35`. Everything else (auth, `IsDirect` rejection,
permission check on the fetched transcribe's customer, `next_page_token` from the last
row's `tm_create`, `GenerateListResponse`) is unchanged.

### 2.4 Out of scope

- `next_page_token` on the last page (platform-wide list convention; VOIP-1480 description
  notes it as a separate candidate).
- square-admin `transcripts_list.js` / `transcribes_detail.js` pagination: SQUARE-62
  (monorepo-javascript).
- Any OpenAPI change: `page_size`/`page_token` are already declared
  (`paths/transcripts/main.yaml:7-8`).

### 2.5 Docs (RST sync rule)

Analysis 2.4 lists seven RST mentions of the endpoint; four sentences among them promise
completeness ("All transcripts are available…" at `transcribe_struct.rst:123`, "Query all
transcripts…" at `quickstart_realtime.rst:137` and `quickstart_transcribe.rst:304`,
"retrieve the full transcript" at `quickstart_transcribe.rst:357`), which is only true for
a caller that pages. Four steps in `docsdev/source/`:

1. `transcribe_tutorial.rst`: in the `GET /v1.0/transcripts` sample response (`:163-182`)
   add the field the endpoint always returns, as the last key of the object:
   `"next_page_token": "2024-04-01T07:17:27.208337Z"`. The handler emits the **last**
   row's `tm_create` (`tmps[len(tmps)-1]`, `server/transcripts.go:53-58`) in the
   `2006-01-02T15:04:05.000000Z` layout; this sample is already newest-first, so its last
   row (`:179`) is the oldest. In the same object, re-render the two rows' `tm_transcript`
   and `tm_create` values in the format the API really emits: `*time.Time` marshals as
   RFC 3339 with `T` and `Z` **and with trailing fractional zeros omitted**
   (`encoding/json` uses `time.RFC3339Nano`), so the four values become
   `"0001-01-01T00:01:04.44116Z"`, `"2024-04-01T07:22:07.229309Z"`,
   `"0001-01-01T00:00:43.11683Z"`, `"2024-04-01T07:17:27.208337Z"`. Note the token
   format differs from the rows on purpose: the handler renders it with the fixed
   `.000000` layout (six digits, zero-padded), while rows drop trailing zeros; the two
   coincide here because the tokens' microseconds (`.208337`, `.233415`) end in a
   non-zero digit. Do not "fix" one side to match the other. Then,
   directly after that response and before `**Find All Transcribes for a Call:**`:

```rst
Transcripts are returned newest first, up to ``page_size`` (default and maximum 100)
lines per call. For longer transcripts, pass the ``next_page_token`` from the previous
response as ``page_token`` to fetch the next (older) page. The final page returns an
empty ``result``; stop when it is empty (``next_page_token`` is still set on the last
non-empty page).

.. code::

    $ curl --location --request GET 'https://api.voipbin.net/v1.0/transcripts?token=<YOUR_AUTH_TOKEN>&transcribe_id=8c5a9e2a-2a7f-4a6f-9f1d-debd72c279ce&page_size=100&page_token=2024-04-01T07:17:27.208337Z'
```

2. `quickstart_transcribe.rst:365-384`: the second sample response of the same endpoint.
   Its two rows are currently oldest-first (`out` at `10:02:05.233415`, then `in` at
   `10:02:10.100000`), which contradicts both the endpoint (`ORDER BY tm_create DESC`,
   `bin-transcribe-manager/pkg/dbhandler/transcript.go:159-166`) and the paragraph added
   in step 1. Swap the two row objects so the `in` row (`10:02:10.100000`) comes first,
   then add `"next_page_token": "2026-02-18T10:02:05.233415Z"` as the last key of the
   object: the last row after the swap is the `out` row, whose `tm_create` is
   `2026-02-18 10:02:05.233415`. Re-render that sample's `tm_transcript`/`tm_create`
   values the same way (trailing zeros omitted): `in` row `"0001-01-01T00:00:15.5Z"` /
   `"2026-02-18T10:02:10.1Z"`, `out` row `"0001-01-01T00:00:08.99184Z"` /
   `"2026-02-18T10:02:05.233415Z"`. Both samples then agree that the field is always
   present, that rows are newest-first, and on the timestamp format.

3. `quickstart_realtime.rst:137`: that page has no link to the tutorial, so append to
   the `data.transcribe_id` bullet: `` Transcripts are paginated; see the
   :ref:`Transcribe tutorial <transcribe-tutorial>`. `` (`quickstart_transcribe.rst:407`
   and `transcribe_struct.rst:27` already link to the tutorial.)

4. Rebuild and force-add the HTML, per bin-api-manager CLAUDE.md:
   `cd bin-api-manager/docsdev && rm -rf build && python3 -m sphinx -M html source build`,
   `git add -f bin-api-manager/docsdev/build/`; commit sources and build together.

(r11) `transcribe_struct.rst:164-165` carries its own separate example with the same
stale space-separated timestamps; it is re-rendered as `"0001-01-01T00:05:04.44116Z"`
and `"2024-04-01T07:22:07.229309Z"` alongside the steps above, while the equivalent
example in `transcript_struct_transcript.rst` is left for VOIP-1483.

The other mentions are left unchanged; with pagination documented in the tutorial and
reachable from every page that promises completeness, they are accurate.

## 4. Risk

Low. Signature change is internal to bin-api-manager (single caller). Behaviour for
callers that omit the parameters is unchanged. Callers that already send `page_token`
or `page_size` (the `vn` CLI, the `voipbin-go` SDK, and the `voipbin-python-sdk`, whose
`list_all()` cannot terminate today) now get the page and size they asked for;
square-admin's two transcript views send `page_size` above 100 and see no change
(SQUARE-62). The api-validator's STT poller (`stt/conftest.py:116-155`) sends
`page_token` from five live tests and today receives every transcript line twice before
its circular-token guard stops it; after this fix it pages correctly and returns each line
once. Operational consequence: the STT accuracy and event assertions in
monorepo-monitoring will run on de-duplicated text after deploy. `test_stt_events.py:299`
asserts `len(transcript_events) == len(transcripts)`, which cannot pass today (N events
against 2N lines) and is expected to turn green; the STT suite should still be watched on
its first run after the merge to confirm that direction. The two api-validator
scenarios that omit the required `transcribe_id` are inert before and after (analysis 2.4). No OpenAPI, CLI or SDK change: the wire contract is
unchanged and was already declared; the only docs changes are the three RST edits in 2.5
(tutorial sample + paragraph, quickstart_transcribe sample field, quickstart_realtime
cross-reference) and the rebuilt HTML.
