# bin-direct-manager unit test coverage 85% (VOIP-1659)

## 1. Analysis

- Baseline (origin/main 320acbfc2): hand-written 81.75% (932 of 1140 statements); raw 72.6%. Hand-written excludes `mock_*.go` and generated files. All figures below use the hand-written view unless stated; per package raw figures are lower (for example `cachehandler` 60.8% and `dbhandler` 67.7%) only because of the mock files.
- Measured with `GOFLAGS=-mod=mod go test -count=1 -coverprofile=cp.out ./...`. The target is 85.0% (969 statements, +37) or more, 85.5% recommended (+43).
- Of 208 uncovered statements, 176 are in `cmd/`, 17 in `pkg/listenhandler`, 8 in `pkg/dbhandler`, 5 in `pkg/directhandler` and 2 in `internal/config`. In the hand-written view the `pkg/` packages are at 93% or higher (`dbhandler` 93.0%, `listenhandler` 93.6%, `directhandler` 97.8%, `cachehandler` and `subscribehandler` 100%).
- Uncovered and reachable without any external connection:
  - `cmd/direct-control`: the `initHandler` failure branch of every subcommand and the failing database connect in `initHandler` (the driver rejects a syntactically invalid DSN while opening, before any network access), and the root `PersistentPreRunE` (except the flag binding error return), and the `migrate` command's migrator constructor failing on the invalid DSN.
  - `cmd/direct-manager`: `run` up to the database connect failure (and the config init failure for a command without the service flags), and `initProm` including its listen retry branch (the final `break` after a successful serve is not reachable).
  - `pkg/listenhandler`: the consume error log branch of `Run`, and the `errorResponse` branch for a typed error whose details cannot be marshaled.
- Uncovered and not reachable without changing signatures or a real service: statements that need a live database, cache or broker (`runService`, `initDirectHandler`, the path after a successful connect), `main`, and error branches of calls that cannot fail for the types and values used (flag and env binding, query builders, random source, JSON marshal of the direct models, the `errorResponse` calls in `processRequest` that no handler can reach). A few `dbhandler` field preparation errors may be reachable with an unmarshalable value and are taken only if cheap.
- Process wide state that tests must respect:
  - `config.LoadGlobalConfig` uses a `sync.Once`. Only the first call in a process loads viper values, so the subcommand run functions are called directly with `*config.Get()` set. At most one `Execute()` case is used, for `PersistentPreRunE`, and it does not rely on the config loaded by the once.
  - `initProm` registers its endpoint on `http.DefaultServeMux`; a repeated endpoint panics, so every call to `initProm`, and every call to `run` that reaches `initProm`, uses a unique endpoint and a loopback ephemeral listen address (the default `:2112` would bind a real port). The goroutine it starts retries once per second while the port is taken, then serves until the process exits. The `Run` consume error is logged from a goroutine, so it is observed through a channel or hook with a bounded wait.
- Estimated reachable gain is about 49 to 52 statements against the +37 (85.0%) and +43 (85.5%) needed.

## 2. Design

Only test files are added or changed. No product code, signature or exposure changes. Synthetic values only; the invalid DSN is the literal `not-a-dsn` (rejected by the driver while opening, before any network access). A DSN must never be empty, because an empty DSN parses and would dial the default local address.

Shared helpers (test files only):
- `cmd/direct-manager`: a `resetState` equivalent that restores viper (`viper.Reset`), `*config.Get()`, and the logrus hooks, and clears `DATABASE_DSN` and related variables with `t.Setenv` so `AutomaticEnv` cannot leak the developer environment, and marks the flags as changed with `Flags().Set` so a flag value always wins over the environment. (`cmd/direct-control` needs no such clearing: its arguments are flags, which already take precedence.) A package level atomic counter builds unique metrics endpoints (`/metrics-test-<n>`), so repeated runs in one process (`-count`, `-shuffle`) never re-register a pattern. Listen address is always `127.0.0.1:0` or a listener the test owns.
- Log capture uses a small test-local logrus hook that sends matching entries (message `Contains` plus level) into a buffered channel with a non-blocking send; the hooks are restored with `ReplaceHooks` as `pkg/listenhandler/logsecret_test.go` does. Waiting is on that channel with a bounded timeout. Failure messages print expected and actual values.
- State order rule for `cmd/direct-control`: `config.LoadGlobalConfig` is once-guarded. In the first `Execute()` of a process it replaces the whole global config from viper (so a pre-set value is lost); in later ones it does nothing and the global config keeps whatever the test set. Therefore: tests that call a run function directly set `*config.Get()` DSN to `not-a-dsn`; every `Execute()` test both passes `--database_dsn not-a-dsn` as an argument and pre-sets `*config.Get()` to `not-a-dsn`, so the DSN is the invalid literal in either state and no order (`-shuffle`) can leave an empty or default DSN. The existing `resetState` of that package is reused (it restores viper and the config, not the environment, which is fine because flags take precedence). It runs before `initCommand()` so the flag bindings start from a clean viper.

Tests:
- `cmd/direct-control/main_test.go`:
  - `Test_run_initHandlerFailure` (table: create, get, list, delete, regenerate): set `*config.Get()` DSN to `not-a-dsn`; for create also set valid synthetic customer, resource type and resource id in viper first (the validation runs before `initHandler`). Call the run function directly and assert the error contains `failed to initialize handlers` and `could not connect to the database`, and that stdout stays empty.
  - `Test_initCommand_execute` (case `direct create`): `root.SetArgs([]string{"direct", "create", "--customer-id", <synthetic uuid>, "--resource-type", "extension", "--resource-id", <synthetic uuid>, "--database_dsn", "not-a-dsn"})` (args isolated from `os.Args`), root `SetOut`/`SetErr` to buffers and `SilenceUsage`/`SilenceErrors` so nothing is printed; assert the connect error. `runCreate` validates the viper values before it connects, so without the pre-run flag binding the run would fail earlier with a required-value error; this test therefore fails if the binding is removed.
  - `Test_initCommand_execute` (case `migrate`): execute `migrate status --database_dsn not-a-dsn` with silenced output and assert the error contains `could not parse the database dsn` (the migrator construction error), not a connection error.
- `cmd/direct-manager/main_run_test.go` (new file):
  - `Test_run_configError`: a bare `cobra.Command` without the service flags; assert `failed to initialize config`. Returns before `initProm`.
  - `Test_run_databaseError`: a command carrying the seven service flags, DSN `not-a-dsn`, listen address `127.0.0.1:0`, a unique endpoint; assert the connect error is returned.
  - `Test_initProm_retriesWhileBusy`: occupy a loopback port with a test owned listener, call `initProm` with a unique endpoint and that address; wait for the `Could not start prometheus listener` entry; close the listener; then poll `GET` on the endpoint (bounded, 10 seconds) until it answers 200, which proves the loop retried and started serving. The goroutine lives until the process exits and is accepted.
- `pkg/listenhandler/consume_error_test.go` (new file):
  - `Test_Run_consumeError`: mock `QueueCreate` ok and `ConsumeRPC` (same arguments as the existing `Test_Run`) returning a fixed error; wait for the `Could not consume the request message correctly` entry through the hook and assert the logged error text, plus that `Run` itself returned nil.
  - `Test_errorResponse_unmarshalableDetails`: a typed `*cerrors.VoipbinError` whose details carry a channel value; assert status 500 and an empty body. A neutral comment only.

Mutation sample on a scratch copy only, restored and confirmed by an unchanged diff afterwards: (a) drop the wrap text of the `initHandler` connect error; (b) replace the `viper.BindPFlags` call in `PersistentPreRunE` with `errBind := error(nil)` (kills the Execute create test); (b2) in the `migrate` closure discard the error of `migrationhandler.New` and return `nil, nil` (a nil dereference panic counts as a failure); (c) replace the `run` config error return with `_ = fmt.Sprint(err)` so the file still compiles (the continued run reaches `initProm("", ...)` and panics, and a panic that fails the package counts as a failure); (d) remove the `initProm` retry `continue`; (e) remove the consume error log in `Run`; (f) in `errorResponse`, return the (nil) `resp` instead of `simpleResponse(500)` on `ToResponse` failure; the test checks `resp == nil` first and fails on that, so the failure is an assertion, not a nil dereference; (g) make `run` ignore the `Connect` error: the `Test_run_databaseError` assertion therefore requires the connect-stage text `database open error` and rejects the migration-stage text `could not parse the database dsn`, because the continued run would otherwise return a different DSN error that a loose `invalid DSN` check accepts.
