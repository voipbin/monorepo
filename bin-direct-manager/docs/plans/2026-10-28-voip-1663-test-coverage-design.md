# bin-direct-manager unit test coverage to 90% (VOIP-1663) - design

Scope: `_test.go` files only, inside bin-direct-manager. No go.mod change expected (sqlite3, sqlmock and miniredis are already required). No non-test change. Target: hand-written total at least 90.5% (+48 statements); the plan below covers about 130 statements (+130 against the +48 needed). The two `main()` functions are not exercised (the test binary arguments are not a valid command line).

## Shared helpers (test files, per package)

- `useFakeServices`: swaps `prometheus.DefaultRegisterer` for a fresh registry; installs `SetConnectFunc` (returns a database prepared by the test), `SetRabbitFactory` (returns a `MockSockHandler`), and for direct-manager `SetEngineFunc` (a fake `Engine` recording `Up`/`Close`, whose `Version` returns no version and no error and whose maximum version is not behind it, so that `Up` runs); returns nothing and registers the restores with `t.Cleanup` in reverse order. Never `t.Parallel()`. The preparation runs once per subtest and each subtest calls one `run*`/`runService` at most once, because a second construction fails the `Connect` expectation and, without the registry swap, panics on the duplicate collector; multi-step scenarios seed rows directly with SQL.
- sqlite (the test imports the sqlite3 driver): `sql.Open("sqlite3", "file:<counter based unique name>?mode=memory&cache=shared")` (never the subtest name, which can hold characters the driver rejects), one connection, schema from `scripts/database_scripts_test/directs.sql`, closed by the test.
- mock sock expectations (always accepted, `AnyTimes`): `TopicCreateWithKind(event exchange, "topic")` (called by the notify handler and must never fail, because a failure ends the process), `EventPublish`, and for `runService` the `QueueCreate`/`QueueBind` calls with the exact queue names; the two consumer methods take eight arguments, so the matcher and the `DoAndReturn` signature copy the existing `runListen`/`runSubscribe` tests. `Connect` is expected exactly once per service construction. Consumer calls (`ConsumeRPC`, `ConsumeMessage`) run in goroutines: the test waits on a channel closed by the call before it ends.
- `chDone` safety: a `t.Cleanup` drains `chDone` without blocking (`select` with `default`) in every `run` test, because failure paths return before the receive; the wait on the request consumer in the subscribe failure case is a required assertion with a bounded `select`, and the comment of the existing signal test is updated, because the new tests use `chDone` too (never `chSigs`).
- direct-control additions: blank the connection environment variables as the direct-manager `resetState` does; stdout is captured with the existing helper.

## Test files and verify items

1. `cmd/direct-control/run_test.go`
   - `initHandler`: cache connect failure (closed miniredis) is wrapped ("could not initialize the cache"), the database was connected and the broker untouched (`Connect` not called); success returns a handler whose `Create` writes a row visible in the database.
   - `initDirectHandler`: success; `Connect` called once.
   - `runCreate`, `runGet`, `runList`, `runDelete`, `runRegenerate`: success prints the JSON of the stored row (compared with a raw `select` on the test's own sqlite handle of customer, resource type, resource id and hash, never with the handler's own getter); unknown id is reported with the operation context ("failed to retrieve direct", "failed to delete direct", "failed to regenerate direct"); invalid id after a successful init; list passes a pagination token later than the seeded rows, honors limit with at least three rows and the customer filter (a second customer's row is not returned); delete hard-deletes the row (raw `count(*)` is 0) and removes the cached hash key that the test seeded in miniredis first; regenerate changes the stored hash; create with an existing resource reports "failed to create direct"; a list against a database without the table reports "failed to retrieve directs".
2. `cmd/direct-manager/run_full_test.go`
   - `run` after the database step (flags marked changed through `newServiceCommand`, extended to set the redis address, miniredis address, port 0 metrics address, unique endpoint, `chDone` pre-filled): migration failure is returned and the database connection is closed (sqlmock expects close); cache failure is returned; full success asserts that the engine `Up` and `Close` were called, both queues were declared and both consumers started, and that `chDone` was drained.
   - `runService`: success; failure of the subscribe step is returned (the queue-name based `QueueCreate` expectation fails only the event queue; `ConsumeMessage` is then never called, so only the request consumer is awaited).
3. `pkg/listenhandler` and `pkg/dbhandler`: table-driven cases for the 500 answer when the mocked domain result cannot be JSON encoded (creation time in year 10000) for each of the six handlers that encode a result, and for the field preparation of the update call when a value holds a type the JSON encoder rejects (`chan` inside a slice); the error text is asserted.

Mutation sampling (scratch copy): drop the migration error return in `run`, swap the customer filter field of `runList`, drop the limit, drop the cache invalidation in the delete path, drop the 500 answer on encoding failure, drop `defer Close` of the database in `run`, reverse the listen and subscribe steps in `runService`, keep the old hash in regenerate; each must fail a new test.

Conventions: `Test_` names, gomock controller `mc`, synthetic UUIDs and hashes, synthetic credential values only, built at run time and never next to an address, no network, bounded channel waits only, `go test -race -shuffle=on -count=1` clean (the existing signal test needs `-count=1`).
