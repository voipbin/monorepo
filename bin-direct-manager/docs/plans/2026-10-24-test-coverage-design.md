Findings that shape the plan (function level coverage checked with `go tool cover -func`):
- Not unit testable without product code changes: `cmd/direct-manager` `main`, `run` (it dials MySQL, runs migrations, connects Redis), `runService` (dials RabbitMQ through `sockHandler.Connect()`), and `cmd/direct-control` `main`, `initHandler`, `initDirectHandler`, and `runGet`, `runList`, `runDelete`, `runRegenerate` (each calls `initHandler()` before validating input, so even their validation failures sit behind a MySQL/RabbitMQ connection). Only `runCreate` validates before `initHandler()`. `initProm` starts a listener on a fixed port and registers on `http.DefaultServeMux`, so a second call panics; it is not called from tests. `init()` in cmd/direct-manager runs `signal.Notify` and sets the logrus formatter at package load; this side effect applies to any test added to that package. `init()` also starts `go signalHandler()`, which blocks on `chSigs` and consumes the first value only; `chDone` has a buffer of 1. A test must therefore never call `signalHandler` directly (it would race with the `init` goroutine for the same `chSigs` value and could leak a blocked goroutine). The single signal test sends exactly one value to `chSigs`, lets the `init` goroutine consume it, and reads `chDone` with a timeout, once per process (the test cannot be run with `-count=2` or more; the CI command uses `-count=1`). `signal.Notify` also changes the default SIGINT behaviour of the test binary; this is limited to that package and the test never sends a real OS signal.
- Testable in cmd: `direct-manager` `runListen` and `runSubscribe` take `SockHandler` and `DirectHandler` as arguments (gomock), `signalHandler`, covered through its consumer (see the signal note below); `direct-control` `resolveUUID`, `printJSON`, `initCommand`, `cmdXxx`, the validation failure returns of `runCreate`, and `initCache` (miniredis, after setting `config`).
- pkg/cachehandler (45 stmts) is Redis only. `github.com/alicebob/miniredis/v2` v2.36.1 is already used by other modules (ai, sentinel, webhook, customer, contact managers) together with the same go-redis v8.11.5, so a test-only go.mod addition is enough.
- internal/config (78 stmts): `LoadGlobalConfig` uses `sync.Once`, so it applies only once per process and cannot be reset; tests cover it once and cover `Bootstrap` and `InitConfig` (which reassigns `globalConfig` on each call) in isolation. `Bootstrap` registers PersistentFlags (redis_database as String) while `InitConfig` reads `cmd.Flags()` (cmd/direct-manager registers redis_database as Int); a test must not mix the two paths on one command. Each test calls `viper.Reset()` and uses `t.Setenv`, and none uses `t.Parallel()`.
- Asynchrony: `processEventRun` and `Run` start goroutines. Tests synchronize with a channel or WaitGroup and fix mock call counts, and run under `-race`. The prometheus collectors are registered once in `init()` of each package; tests never re-register them.
- Current state of the other packages: listenhandler `processRequest` is already 96.4 %; the misses are `NewListenHandler`, `Run`, and error branches of each `processV1*` (`errorResponse` 84.6 %). subscribehandler `Run` is 75 % (existing `Test_Run_sequencing` and `binding_golden_test.go` cover the success sequence); the misses are the three failure returns, `processEventRun` and `processEvent`. directhandler misses `NewDirectHandler`, `EventCustomerDeleted` (0 %) and error branches. dbhandler misses `NewHandler` and error branches.

Reachability: config about 70, cachehandler 45, subscribehandler 27, directhandler about 45, listenhandler about 50, dbhandler about 18, cmd (runListen, runSubscribe, signalHandler, resolveUUID, printJSON, initCommand and subcommand constructors, initCache) about 60. Total about 315 against the +173 needed. The target is reachable without any non-test change. No product code change is needed: every item above uses existing exported or package level symbols from `package` internal tests.

## 2. Plan

Scope: `_test.go` files and `go.mod`/`go.sum` (miniredis, test only) inside bin-direct-manager. No non-test .go change. Target: hand-written total >= 61 %.

Conventions for every new test: `Test_<func>` names, gomock controller named `mc`, synthetic values only (fake UUIDs, `abcdef123456` style hashes, fake DSN and passwords), no `t.Parallel()` in packages that touch viper, `chSigs`/`chDone` or prometheus, and constructor tests assert behaviour, never only non-nil. Before writing listenhandler cases, list the cases already covered by `TestProcessV1*` and `error_response_test.go` and add only the missing branches.

Files and verify items (each asserts an observable result: returned error, status code, stored Redis state, mock call arguments and counts):
1. `pkg/cachehandler/handler_test.go` (miniredis): set then get round trip returns an equal Direct; the stored key is `direct:hash:<hash>` with TTL 24h (`miniredis.TTL`); get of a missing key returns `redis.Nil`; a corrupted JSON value returns an unmarshal error; delete removes the key and deleting a missing key is not an error; `Connect` succeeds against miniredis and fails after `Close`; `NewHandler` is verified through behaviour: with `RequireAuth` set, a handler built with the wrong password fails `Connect` and one with the right password succeeds, and a handler built with DB 3 writes into miniredis DB 3 (not DB 0).
2. `internal/config/config_test.go`: `Bootstrap` registers all 7 flags with the documented default values (read back from the command flags); its two error returns are unreachable (a second call on one command panics in pflag with `flag redefined`, the lookup of a just registered flag is never nil and `BindEnv` does not fail for a non-empty key), so they are excluded from the estimate; env variables override defaults through `viper` after `Bootstrap`; `LoadGlobalConfig` is called in one test function only (sync.Once), asserts the loaded fields, and restores `globalConfig` afterwards; `InitConfig` populates `Get()` from flags and parses `redis_database` as int; `InitConfig` bind error branches are a table test that registers all flags except one (7 cases, each expects an error naming the missing flag; an empty command gives the first one). Every test calls `viper.Reset()` first and `t.Setenv` for env, and the order must not matter under `-shuffle=on`.
3. `pkg/subscribehandler/main_test.go` (existing file, extended): `Run` returns a wrapped error for QueueCreate failure, TopicCreateWithKind failure and QueueBind failure (the later calls are not made: strict mock); the success and QueueBind cases assert the bound pattern as a literal string (the `customer_deleted` pattern of the customer manager as pinned by `binding_golden_test.go`), not by iterating `topicPatterns`, so that removing an entry makes the new test fail; `Run` success starts the consumer, observed through a channel closed by the `ConsumeMessage` mock; `processEvent` is called synchronously: customer_deleted reaches `EventCustomerDeleted` once with the decoded customer id, an event with an unknown publisher or an unknown type does not call the handler (no EXPECT on the mock); `processEventRun` returns nil and the dispatched goroutine is awaited via a channel in the mock. Tests do not touch prometheus registration.
4. `pkg/directhandler`: `NewDirectHandler` asserts the four injected dependencies are stored in the matching fields and the util handler is set; Create fails after 3 collisions (exactly 3 `DirectCreate` calls, no event published, error returned), Create returns the `DirectGet` error without publishing; Get and GetByHash map `dbhandler.ErrNotFound` to a typed not found error (`cerrors` code `DIRECT_NOT_FOUND`) and pass other errors through unchanged; GetByHash cache hit does not touch the DB and a DB hit populates the cache (only if the existing `Test_GetByHash` does not already assert it); Delete success calls `DirectDeleteByHash` once with the exact hash and publishes `direct_deleted` once, while `DirectGet` failure or `DirectDelete` failure does not call cache invalidation or publish; Regenerate retries after an update error (up to 3 attempts), fails after 3, and does not invalidate the old hash on failure; `EventCustomerDeleted` continues after one Delete error and still deletes the remaining directs, and returns the list error without deleting anything.
5. `pkg/listenhandler`: `NewListenHandler` asserts stored dependencies; `Run` returns the wrapped error on `QueueCreate` failure and on success calls `ConsumeRPC` (goroutine, awaited by a channel); error mapping is fixed by this table, observed through `processRequest` (typed errors only reach their status code through the dispatcher): GET by id and GET by hash return the handler error to the dispatcher (typed error -> its status code, `ErrNotFound` -> 404, other -> 400); list, create and regenerate handler errors -> 500; delete: any handler error -> 400, including a typed not found (characterization test of the current behaviour, with a comment saying the test must be updated if the behaviour changes); malformed list filters, unparsable filter conversion, invalid JSON body on create -> 400; a URI that matches the list route but fails `url.Parse` (`/%zz/v1/directs?page_size=1`, an invalid escape in the path) -> 400 through the dispatcher.
6. `pkg/dbhandler` (sqlmock): only reachable branches: query error, exec error, row scan error, empty result mapped to `ErrNotFound`, and field application errors where the input allows it, for `DirectCreate`, `DirectGet`, `DirectGetByHash`, `DirectGets`, `DirectUpdate`, `DirectDelete`; `NewHandler` asserts it returns a working handler by running one sqlmock query through it. Branches that cannot be reached with the closed input set are excluded and not counted in the estimate.
7. `cmd/direct-control`: `resolveUUID` (empty, invalid, valid) and `printJSON` (marshal error for an unsupported value such as a channel, success output captured); `initCommand` success path only (`cobra.CheckErr` calls `os.Exit` on failure): the root has `direct` with five subcommands plus `migrate`, with the documented flags; `runCreate` returns the validation errors in order customer id, resource type, resource id before any connection; `initCache` against miniredis succeeds and against a closed server returns the wrapped error. Each test resets viper with `viper.Reset()` and `viper.Set`, and sets the config with `*config.Get() = config.Config{...}`, restored by `t.Cleanup`.
8. `cmd/direct-manager`: `runListen` runs the listen handler with a mock sock handler (expects `QueueCreate` and `ConsumeRPC`, awaited by a channel); a separate characterization test pins that a `QueueCreate` error is logged and nil is returned; `runSubscribe` propagates the `Run` error and succeeds otherwise; one test sends exactly one value to `chSigs` and reads `chDone` with a timeout. No other test in the package touches `chSigs` or `chDone`, nothing calls `signalHandler`, `initProm`, `run` or `runService`.
