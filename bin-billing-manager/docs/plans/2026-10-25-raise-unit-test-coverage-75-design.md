## 2. Plan

Only `*_test.go` files are added inside bin-billing-manager (plus this document). No product code, signature, visibility, `go.mod` or `go.sum` change (go-sqlmock is already a dependency).

Estimated gain per group (statements, rough lower bounds): subscribehandler 36 (plus `Run` queue and topic declaration failures, 2); dbhandler about 52 (wrappers and `AccountSetStatus` about 17, exec/scan/begin/commit/parse failures about 35); billinghandler about 14; accounthandler about 14; paddlehandler 3; listenhandler 1; constructors about 9. subscribehandler plus dbhandler already reach about 88, the other groups are the margin.

Order, measuring after each group with the fixed measurement script (kept in the scratch directory and described in the PR body: the command above plus a script that drops `gens/`, `mock_*.go` and `Code generated ... DO NOT EDIT` files and merges duplicate blocks with the max count): (1) subscribehandler, (2) dbhandler, (3) billinghandler and accounthandler, (4) paddlehandler httptest cases, listenhandler short URI, constructors, only while below 76%. The measurement script text (about 40 lines of Python) is committed in the PR body as a fenced block so the baseline and final numbers can be reproduced. Stop rule: if all groups are used and the total is 75% or more but below 76%, raise the PR and record the shortfall; if below 75%, stop and report without lowering the target.

If a test cannot pass without a product change (a product defect), the test is dropped or pinned to the current behavior with a neutral comment, the product code is not edited, and the finding is recorded in the card only.

Rules for every test: table-driven where the cases share a shape, `Test_<function>` naming, gomock controller named `mc` with `defer mc.Finish()`, synthetic values only, no sleep, no external network (loopback httptest only), no wall clock, no package globals written (a read of a package-level metric before and after the call is allowed). Errors are asserted with `errors.Is`/`errors.As` against the injected cause and a message fragment, not only `err != nil`. Expectations are re-read from the code when writing.

Cases:
- subscribehandler: per-function matrix from the coverage profile, written when the tests are written (call.go: the two unmarshal errors; customer.go: unmarshal error and handler error of `processEventCMCustomerDeleted` and `processEventCMCustomerCreated`; email.go and message.go: unmarshal and handler error of one function each; number.go: both for two functions; recording.go and tts.go: both for start and stop). For each: invalid JSON returns an error and the billing/account handler mock is not called (no EXPECT set); a handler error is returned wrapped and `errors.Is` finds the injected cause. `Run`: a failing `QueueCreate` and a failing `TopicCreateWithKind` return the wrapped error and no later sock call is expected.
- billinghandler: `EventCMCallProgressing` returns the wrapped `could not start a billing` when `BillingStart` fails; `EventCMCallHangup`, recording stop and tts stop: the reference lookup (`BillingGetByReferenceTypeAndID` or the one the code uses; re-read when writing) succeeds with a billing and the end time is non-nil, then `BillingEnd` fails at its `BillingConsumeAndRecord` db call; the wrapped end error is returned and `errors.Is` finds the cause (the swallowed lookup-error branch and the nil end time branch are different paths and are not asserted here); recording start and tts start likewise for `BillingStart`. `BillingEnd` for call-extension cost types: a `BillingSetStatusEnd` failure is asserted by the fragment `could not end free billing` plus `errors.Is`; a failed `BillingGet` re-read is returned unwrapped, asserted with `errors.Is == injected error`; a successful free end with both billing times set asserts the `BillingSetStatusEnd` arguments (zero costs plus the end time), the published event payload, and the sample count of the `promBillingDurationSeconds` histogram for the reference type before and after (read through the client_golang `dto.Metric` write, no `testutil` import). `BillingStart` retry path (`could not complete billing on retry`, an existing billing of type SMS whose `BillingEnd` fails) and the flag-end failure (`could not end the billing`) are asserted by fragment and `errors.Is`. `Get`: `dbhandler.ErrNotFound` yields, through `errors.As`, a `*cerrors.VoipbinError` with status NotFound and reason `BILLING_NOT_FOUND` and `errors.Is(err, dbhandler.ErrNotFound)`; any other error is not a `cerrors` type (`errors.As` false) and `errors.Is` finds the cause.
- accounthandler: lookup by customer id succeeds but the inner `IsValidBalance`/`IsValidResourceLimit` fails because `AccountGet` returns an injected error: the result is false, the message fragments are `could not validate the account balance` and `could not validate the account's resource limit`, and `errors.Is` finds the cause (the lookup-failure branch is already covered and is not repeated). `PaddleSubscriptionCreate(planType)` and `PaddleSubscriptionUpdate(newPlanType)` (`paddle.go` 126 and 176) with an unknown plan type return the `unknown plan type` error and no `AccountPaddleTopUpTokens` call is expected. An already-processed Paddle event id in `PaddleSubscriptionRenew` and `PaddleRefund` (`paddle.go` 253 and 307) returns nil and no balance or token write is expected. `Delete` where the post-delete `Get` returns a NotFound `VoipbinError` returns an Internal error that wraps it (assert status Internal and `errors.Is` on the cause). `dbCreate`: `AccountCreate` fails, `AccountGet` succeeds, the returned account equals the `AccountGet` result and `PublishEvent` is called once; a second case where `AccountGet` fails returns an error and `PublishEvent` is not called. The number-valid success branch of `IsValidBalance` (balance at least the cost) returns true.
- dbhandler wrappers, sqlmock (db closed in `defer`, `ExpectationsWereMet` checked): a table of the six wrappers `AccountAddBalance` (+amount, no check), `AccountSubtractBalanceWithCheck` (-amount, check), `AccountSubtractBalance` (-amount, no check) and `AccountAddTokens`, `AccountSubtractTokensWithCheck`, `AccountSubtractTokens` with the same shape. Credit and token rows use distinct SQL regexes (`balance_credit` versus `balance_token`) and different starting balances, so a wrapper wired to the wrong function fails. Each case asserts the exact `UPDATE` arguments (new balance after the signed amount) and the ledger insert amount sign. Insufficient balance: the two `WithCheck` variants return `ErrInsufficientBalance` with a rollback and no update; the two non-check subtract variants succeed with a negative result for the same starting balance, which catches a flipped check flag. `AccountSetStatus` success (sqlite fixture: status and update time read back exactly) and exec failure.
- dbhandler failures, sqlmock: exec failure of `AccountCreate`, `AccountUpdate`, `AccountDelete`, `FailedEventCreate/Update/Delete`, `BillingSetStatus*` returns the wrapped cause (`errors.Is`) and the cache mock is not called; scan and `rows.Err` failures of the list and get functions where not yet covered; `AccountUpdate`/`BillingUpdate`/`FailedEventUpdate` with a slice holding a `chan` value return the prepare-fields error; `AccountList`/`BillingList` with a struct-typed filter value return the apply-filters error; `NewHandler` returns a handler holding the injected db and cache; customer id parse failure of the ledger functions.
- paddlehandler: invalid base URL, transport failure and a body read failure through `httptest` return the wrapped error; a body read failure is produced deterministically by a handler that sets a larger `Content-Length` than it writes and returns (no sleep); listenhandler: a too-short Paddle portal URI returns 400 without calling the account handler.
- constructors: `NewBillingHandler`, `NewAccountHandler`, `NewListenHandler`, `NewFailedEventHandler` return handlers whose unexported fields are identical (`==`) to the injected mocks. They are not counted as mutation-sample tests.
