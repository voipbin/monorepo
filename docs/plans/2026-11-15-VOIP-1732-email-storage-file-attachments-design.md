# VOIP-1732: Storage files as email attachments, and an ownership check for every attachment

## Goal

An email attachment is no longer limited to a call recording. A storage file of type `talk`, `media` or `recording` can be attached (`reference_type` `file`, `reference_id` the storage file id). Types `rag` and the empty type are refused. The same change closes a gap of the existing recording attachment: nothing checked that the recording belongs to the customer who sends the email. Limits: at most 5 attachments and at most 18 MiB of original size in total, refused before the email is created.

No database change (`attachments` is a JSON column, `reference_type` a string in it), so there is no migration.

## Where the check lives

Every sender reaches `bin-email-manager` `emailhandler.Create(customerID, ..., attachments)`: the API (`EmailV1EmailSend` from `bin-api-manager`), the flow action `email_send` (`bin-flow-manager`) and the AI tool `email_send` (`bin-ai-manager`, where the model chooses the id). The ownership check therefore lives in `Create`, with the customer id the caller passes, and is repeated by the engines when they send. `bin-storage-manager` is not changed: its `RecordingGet` takes no customer, but its file list takes `customer_id`, `reference_type`, `reference_id` and `deleted` filters (already used by `bin-api-manager` for the recording play files), and `bin-call-manager` creates the recording files with the customer of the call. `bin-message-manager` already checks MMS media in the same way (`validateMedias`).

## Design

New file `bin-email-manager/pkg/emailhandler/attachment.go`, package level functions that take the request handler (both engines hold one), constants in one place (no setting):

- `attachmentMaxCount = 5`, `attachmentMaxTotalSize = 18 MiB`, `attachmentRecordingListSize = 100`, `attachmentCheckTimeout = 2 s`.
- `inspectAttachment(ctx, reqHandler, customerID, att)` checks one attachment and returns its sanitized file name, content type and original size:
  - `reference_id` nil: InvalidArgument. Unknown type and the empty type: InvalidArgument.
  - `file`: `StorageV1FileGet`. The file must exist, not be deleted (`TMDelete == nil`), belong to the customer (`CustomerID == customerID`) and have a type in {talk, media, recording}. A missing, deleted and foreign file give one and the same NotFound, so the existence of another customer's file is not shown. A wrong type is InvalidArgument.
  - `recording`: `StorageV1FileList` with `customer_id`, `reference_type=recording`, `reference_id`, `deleted=false`, size 100. An empty list is NotFound (also for a recording of another customer). A list that reaches 100 is InvalidArgument (the sum could be cut). The size is the sum of `Filesize` (a negative size is refused), used as the approximation for the limit (the zip of already compressed files can be slightly larger; the 50 MiB download limit per file stays as the last guard).
  - Error mapping: a typed `NotFound` or `requesthandler.ErrNotFound` is NotFound; any other storage error is `Unavailable` (the email-manager listen layer turns an untyped error into 400, which would hide a storage failure as a bad request).
- `validateAttachments(ctx, reqHandler, customerID, atts)` (called by `Create`): count at most 5 (nil and empty pass), no duplicate (type, id), every attachment inspected, total size at most 18 MiB (exactly 18 MiB passes). It runs after the identity gate and before the balance check. Because the default request timeout of the callers is 3 s, so all storage calls of one check share one deadline of `attachmentCheckTimeout` (2 s) and run one after the other (at most 5, a few ms each when storage is healthy). When the deadline passes, the check returns `Unavailable` and no email is created. The deadline bounds this check only: `Create` has no overall deadline (the identity and balance calls before and after keep their own default timeouts, as before), so a caller that already gave up can still get a late email from a slow earlier step; this is the existing behaviour and is not changed here. A deadline that stops a slow storage call counts as a failure of that call in the request circuit breaker.
- `resolveAttachment(ctx, reqHandler, customerID, att)` (called by the engines when sending): runs `inspectAttachment` again (a file deleted after `Create` fails the send and the email stays `initiated`; this is also the check that closes the gap between `Create` and the asynchronous send), then returns the download URI. This step runs in the asynchronous send, which has no deadline, so each storage call keeps its own default timeout (3 s, and 60 s for `StorageV1RecordingGet` as before); `attachmentCheckTimeout` applies to `Create` only. `file`: `StorageV1FileDownloadURIRefresh` every time (the same as `bin-message-manager` does; it updates the file record in storage, which is acceptable for a send). `recording`: `StorageV1RecordingGet` with the existing 60 s timeout, file name `<recording id>.zip`, content type `application/zip`.
- File name: the original name of the file with path parts and control characters removed (`path.Base` after replacing `\`), the file id when nothing is left. Content type from the extension (`mime.TypeByExtension`), `application/octet-stream` when unknown (Mailgun decides by itself from the name). A name that is already used by an earlier attachment of the same email gets a `-<n>` suffix before the extension (`uniqueFilename`), because the providers' rules for equal names are not known.
- The engines keep their interface. Both call `resolveAttachment` and download as before (`download` keeps the 50 MiB limit per file). When Mailgun fails and SendGrid is tried, the attachments are loaded again; this is the existing behaviour and the 18 MiB total bounds it.
- `models/email`: `AttachmentReferenceTypeFile = "file"`.
- OpenAPI `EmailManagerEmailAttachmentReferenceType` gets `file`; the description of `reference_id` names both sources. The description of the enum (now "Type of the action.") is corrected, and the `attachments` description of `paths/emails/main.yaml` names both types. Regenerate `bin-openapi-manager` and `bin-api-manager` generated code (`gens/openapi_server`, `gens/openapi_redoc`). `bin-api-manager` code does not change (it converts the value as is).
- `bin-ai-manager`: the `email_send` tool definition (`enum`, description) and the action catalog description are updated; the sentence "no attachment" in the description of the draft tool (a different tool) is checked so that nothing contradicts (step 3 of the verification). `bin-flow-manager` needs no change (the option holds `[]email.Attachment`; the action is not a builder type).
- Documents: `bin-email-manager` docs (`domain.md`, `architecture.md`, `operations.md`) and `CLAUDE.md`; RST (`email_overview.rst`, `email_struct_attachment.rst`, `email_tutorial.rst` and `quickstart_email.rst` where they name attachments, `storage_overview.rst` (the table of attachment users), `flow_struct_action.rst`, `ai_struct_tool.rst`) and the rebuilt HTML. `bin-email-manager/docs/dependencies.md` is updated too (the reason for the storage calls).

## Decisions and risks

- The 18 MiB value is a fixed product limit, not a setting. With base64 and MIME overhead a full 18 MiB is about 25 MB on the wire, which can pass the 25 MB limit that the Mailgun documentation gives, so a provider can refuse such a send and the other provider is then tried. The value is not changed here.
- The boundary is the customer: `owner_id` of the file is not checked, so a file of the customer can be attached by any sender of the same customer.
- A send that fails after `Create` (deleted file, provider error) stays logged with the status `initiated` as it does today.
- Old stored emails only hold `recording` attachments, so they stay valid. Clients with a strict enum of `reference_type` see a new value `file` in responses.

## Mutation check (scratch copy)

Each mutation must make the listed test fail. Tests compare the full filter map of `StorageV1FileList` (`customer_id`, `reference_type=recording`, `reference_id`, `deleted=false`, size 100) and do not use `gomock.Any()` for it.

| Mutation | Failing test |
| --- | --- |
| remove the `customer_id` filter of the recording list | recording list filter test, foreign recording test |
| remove the `CustomerID` comparison of a file | foreign file test |
| remove the `TMDelete` check | deleted file test |
| allow type `rag` or the empty type | file type table test |
| `>` to `>=` on the 18 MiB total, `>` to `>=` on the count of 5 | boundary tests (exactly 18 MiB passes, 5 passes) |
| `Create` does not call `validateAttachments`, or calls it after the balance check | `Create` refusal test (no balance RPC, no database call) |
| `resolveAttachment` skips the re-check | file deleted after `Create` test, foreign file at send test |
| typed NotFound mapped to Unavailable, or the reverse | error mapping tests, listen handler status test |

The tests run at `Create` level for the ownership cases, so they also fail (not only fail to compile) on the code before the change when the new functions are stubbed out.
