# VOIP-1693 FCM push incoming call with one-time confbridge join address (technical design)

Status: draft rev 3 (a new service bin-push-manager owns device tokens and FCM delivery; devices are keyed by agent; delivered as two PRs). Base: origin/main at the time of writing. Requirements in short: a ring window of 60 seconds, two push kinds (`call_incoming`, `call_cancelled`), SIP registration stays in parallel, the first path that enters the confbridge wins and the other is cancelled, an unanswered call ends with the no-answer result; this document fixes the technical items. Sections 3, 4, 6, 7, 9, 11, 13, 14 are rewritten for push-manager; section 5 rules 1 and 2 and the verify list follow them; C1 to C10 and the call-manager state machine are unchanged unless stated.

## 1. Ticket review (summary)
Verified against code: connect creates the confbridge, a temporary flow and the outgoing groupcall before the caller join is pushed; an extension without a registered contact fails in call-manager (`EXTENSION_NOT_REGISTERED`); legs are RingAll with HangupOthers; the dial timeout is 60 s; the connect confbridge has no join cap (the add-participant feature relies on that); no push code exists. Corrections: (a) nothing on the server hangs up the caller when no leg answers. An unanswered leg never joins the confbridge, so the auto-terminate in `Leaved` never fires, and a leg hangup only updates groupcall state and stops the leg's own activeflow. (b) `RelayReason` has no effect for extension destinations (they are groupcalls).

## 2. Design review (technical view of the product spec)
| Spec statement | Technical finding | Resolution |
|---|---|---|
| Unanswered result equals today's result | Today the caller stays in the confbridge until the caller gives up or the call duration timeout (assumption: a proxy or carrier timer outside this repository may end it earlier; not verifiable here). No server value exists to match. | The ring-window owner (section 5) ends the call with `HangupReasonNoanswer` (existing constant, wire cause `ChannelCauseNoAnswer`, `ConvertHangupReasonToChannelCause`). The caller sees the wire cause. The stored `hangup_reason` is computed by `CalculateHangupReason` after the status is already `terminating` (callhandler/hangup.go `hangingUpWithCause`), so for an incoming call it is stored as `normal` (models/call/call.go incoming table). We accept that stored value and do not add a special update. Applies only to calls that started a push ring session. Calls without a session are unchanged. |
| Caller is in the confbridge ringing before the app enters | Join is pushed after the outgoing call is created and runs asynchronously in the activeflow. | The ticket redemption is refused until the caller's join is confirmed (`caller_joined`). The app retries inside the window (spec rule: pre-join failure allows retry). |
| Ticket bound to device | A SIP INVITE carries no authenticated device identity. | Binding is bookkeeping (one ticket per device, used for cancel and retry attribution). Security rests on: an unguessable 128-bit random value (16 bytes, matches section 8's `crypto/rand` size), 60 s validity (`expires_at`; the Redis key ttl is 150 s per C7), single use, binding to customer, confbridge, extension and caller call. A ticket is a bearer value, bounded by its ttl, a single use and the binding to the session; device binding is bookkeeping. |
| Only one path wins | Join has no cap, and `Join` (confbridgehandler/join.go) can fail at five points after any claim | Two-phase claim: reserve at `Join`, confirm at `Joined` (section 5). |
| Push payload carries caller display | Goes through Google. | Product spec item (recommended: include). The code takes the display value from the call source address only. |

No contradiction that blocks the spec. Open product decisions are in section 12.

## 3. Service split
PR 1 and PR 2 split at the RPC contract of section 6. Merge order: PR 1 first (callee).
- bin-push-manager (new, PR 1): owns the table `push_devices` (service-owned migration `000001_baseline`), the device RPC, the notification RPC and the FCM sender (`pushhandler` with a `Sender` interface; the credential is read from the environment). It has no Redis, no events and no outbound RPC. It subscribes to `customer_deleted` and `agent_deleted` to remove devices.
- bin-common-handler (PR 1): queue and service name constants, `PushV1*` requesthandler methods with mocks and wire-shape tests. The models live in bin-push-manager (repository convention), so every module that imports bin-common-handler gets the `replace` and `require` lines for `monorepo/bin-push-manager` (37 modules).
- bin-api-manager + bin-openapi-manager (PR 1): `POST /service_agents/push_devices`, `DELETE /service_agents/push_devices/{id}`, OpenAPI, RST.
- bin-common-handler (PR 2): `CallV1PushRingStart`, `CallV1PushRingExpire`, `CallV1PushRingClose` requesthandler methods for call-manager's own routes (models stay in call-manager), with mocks and tests.
- bin-call-manager (PR 2): push ring session (Redis state, ticket redemption, lease, expiry), incoming ticket call, hooks. It resolves the agent of an extension (agent-manager `get_by_customer_id_address`, section 3.1), lists the agent's devices and sends notifications through push-manager.
- bin-flow-manager (PR 2): `actionHandleConnect` starts a ring session for a single extension destination and tolerates the not-registered failure when devices exist; `joined.go` fix (C1) is in call-manager.
- bin-registrar-manager: not changed (the tokens and the FCM sender are not stored or sent here).
- bin-direct-manager: not changed. A new direct resource type would put a one-time, 60 s object into a persistent table with regeneration semantics; call-manager Redis already has the claim primitive (`ConfbridgeParticipantClaim` pattern).

### 3.1 Extension to agent (measured, origin/main)
`agent_addresses` (bin-agent-manager) holds the agent's addresses; an address of type `extension` has the extension **id** (UUID) as target. Its unique key is `(customer_id, type, target)`, so one extension belongs to at most one agent; one agent may own several extensions. The lookup exists: `AgentV1AgentGetByCustomerIDAndAddress(ctx, timeout, customerID, address)`; the handler normalizes the target and compares it with an SQL equality (`agenthandler/agent.go`, `dbhandler/agent_address.go`). `groupcallhandler.getAddressOwner` already uses it. api-manager trusts only the canonical (lowercase, hyphenated) target form for ownership (`isCanonicalExtensionTarget`).
The flow connect destination is different: the routing key is the extension **number** in `TargetName` (`groupcallhandler/dial.go`, registrar contacts are listed with the filter `extension = TargetName`). So PR 2 resolves the extension id first: if the destination `Target` is a canonical UUID it is used as is, otherwise `RegistrarV1ExtensionGetByExtension(ctx, TargetName, {customer_id})` gives the extension and its id. Then the agent lookup runs with `{type: extension, target: <id>}`. PR 2 checks that the returned agent belongs to the same customer and is not deleted. Any miss or error at any step means "no agent": `started:false`, which is today's behaviour. The link is 1:1 from extension to agent and 1:N from agent to extension; no policy choice is needed. A device of an agent rings for every extension of that agent, which is the intended agent-level behaviour.

### 3.2 Expansion triggers (no code now)
The notification RPC carries a `kind` string validated against a small code table (`call_incoming`, `call_cancelled` only). A new kind (for example a chat message notification) is added by a table entry (name, TTL, allowed data keys) and a caller; no schema change. Triggers: a second kind with a producer service, or a second platform (`ios`) needing APNs, which needs a new sender and a credential. Neither is built now.

## 4. Data model
`push_devices` (bin-push-manager, `migrations/000001_baseline`, `CREATE TABLE IF NOT EXISTS`, no table options): `id` binary(16), `customer_id` binary(16), `agent_id` binary(16), `platform` varchar(16) (`android`), `token` varbinary(512) (case sensitive without a column character set; the migration check allows only the one character set it knows), `tm_create` datetime(6), `tm_update` datetime(6) (refresh time, used for the expiry). All columns are NOT NULL. Primary key `id`; unique key `idx_push_devices_token (token)`; keys `idx_push_devices_customer_id (customer_id)` (cascade by customer) and `idx_push_devices_agent_id (agent_id)` (list, cascade by agent). A device row is a credential, not a business record: rows are hard deleted (no `tm_delete`), which also lets the unique key hold (a soft delete with a NULL `tm_delete` could not). A token belongs to one agent: registering a token that exists for another agent or customer deletes the old row first (a device handed to another user stops ringing for the previous one). Registration is three idempotent steps without a transaction, arbitrated by the unique key: (1) delete the row of this token if its owner differs, (2) if a row with this token and this owner exists update `tm_update` and return it, (3) otherwise insert; a duplicate-key error on the insert (a concurrent registration) restarts from step 1, at most 3 times, then fails. The cap check after the insert can be exceeded by concurrent registrations of the same agent by a few rows; this is accepted (the cap limits fan-out, it is not a security boundary). Expiry: a device whose `tm_update` is older than 30 days is ignored by list and send (filtered in the handler after the query; the per-agent cap of 10 keeps the page small); the app refreshes on every start. Stale rows are removed on the next registration of the same token, by the invalid-token handling, by the per-agent cap and by the cascade events; there is no cleanup job (trigger for one: table growth reported by an operator). Per-agent cap: 10 devices; registering the 11th deletes the agent's oldest by `tm_update`. Only the FCM error `UNREGISTERED` deletes a device (`INVALID_ARGUMENT` can also be a payload error and does not). The sqlite test schema `scripts/database_scripts_test/` gets the same table by hand.

Ring session (call-manager Redis, ttl 150 s = window + 90 s so the redundant 90 s expiry RPC still finds the keys; no DB). Final shape per 5.1 (C1-C10) supersedes any earlier mention:
- `call:pushring:<session_id>` hash: `customer_id`, `extension_id`, `confbridge_id`, `master_call_id`, `flow_id` (the temporary flow connect created; identifies session calls per C3), `expires_at`, `state` (`ringing`, `push_failed`, `closed` — `push_failed` per C2 is a distinct value: pushes are gone but the SIP gate stays open; only `closed` ends the gate), `lease_owner` (call id) and `lease_until`, `winner` (empty, `sip`, `app:<device_id>`), `caller_joined`, `sip_registered`.
- `call:pushring:cb:<confbridge_id>`, `call:pushring:master:<call_id>` and `call:pushring:call:<call_id>` (per C9, used by the hangup hook of rule 9 to find a lease owner or ticket-call session) -> session id (lookup).
- `call:pushticket:<sha256 of the ticket>` -> `session_id`, `device_id`, `state` (`issued`, `in_use`, `consumed`), `in_use_call_id`, `in_use_until` (per C4, now + 15 s; a call can be hung up before it exists as a call row, so this is the only return-to-`issued` path in that case).

## 5. Behaviour and state transitions
T0 is the start of `PushRingStart` (called by connect). Window = T0 + 60 s (same value as `defaultDialTimeout`). One owner: the call-manager session.

Atomicity rule: every state change of a session (lease, confirm, release, close) is one Redis Lua script on the session hash, so `state`, `lease_owner`, `lease_until` and `winner` are always checked and changed together.

1. connect (single extension destination): after the confbridge and temporary flow exist, flow-manager calls `CallV1PushRingStart(customer, extension, confbridge, master call, source)`. The start RPC has an explicit 5 s timeout. call-manager resolves the agent of the extension (3.1: extension id, then agent), lists the agent's live devices (`PushV1DeviceList`; only the device ids are used) and the SIP contacts (sets `sip_registered`); the contact lookup runs in parallel with the id-to-agent-to-devices chain, and the whole start runs under one 4 s deadline (a context deadline, not a per-call limit), so it always answers inside the 5 s RPC timeout; a deadline expiry means `started:false` and no session is created; it then creates the session and one ticket per device, schedules `CallV1PushRingExpire(session)` as a delayed RPC (existing requesthandler delay) at 60 s and a redundant one at T0 + 90 s (window + 30 s; the keys live until T0 + 150 s per C7, so the redundant call still finds them), and returns `{started, session_id, sip_registered}`. No agent, no devices, or a device list error: `{started:false}` and connect continues exactly as today. Sending is not part of this RPC. T0 is the session start (a few ms after the connect action starts; the spec's connect-start anchor is approximated by this).
2. After the response, call-manager sends `call_incoming` to every device in a goroutine (`PushV1NotificationSend` with `device_id`, so each device gets its own ticket in `join_address`; the FCM attempt inside push-manager is limited to 5 s, the RPC to 8 s). `call_cancelled` is one `PushV1NotificationSend` without `device_id` (all devices of the agent). If every device answers with `sent_count: 0` (an explicit failure; an RPC error or timeout is "unknown" and counts as possibly delivered), the session moves to `push_failed` (C2: tickets deleted, no more pushes, the SIP gate stays open); only if `sip_registered` is also false is the master call hung up with `HangupReasonNoanswer` (documented deviation: the spec's "existing failure result" is the CallsCreate error, which cannot be produced after the response; this deviation from the product spec is listed in section 12). A late `confbridge_join` of flow-manager to a dead master fails harmlessly.
3. flow-manager then runs `CallsCreate` as today. Only when `started` is true, `sip_registered` is false and the error is `EXTENSION_NOT_REGISTERED` does it continue push-only: it skips the "no calls created" error (actionhandle.go lines 555-562) and the `RelayReason` block that reads `resCalls[0]` (lines 575-578), and pushes the caller `confbridge_join`. Any other error calls `CallV1PushRingClose` (best effort) and returns the error as today. If the start RPC timed out, `started` is unknown: flow-manager continues the legacy path; the session, if it exists, is closed by the expiry RPCs.
4. Caller join confirmed in `confbridgehandler.Joined` (master call id matches the session): `caller_joined=1`.
5. App INVITE `sip:direct.<ticket>@sip.voipbin.net`: `startIncomingDomainTypeSIPDirect` first looks up the ticket by `sha256(ticket)` (the Redis key never holds the plaintext). Miss falls through to the existing direct-manager lookup unchanged (unknown and expired values end in the same `NoRouteDestination` hangup, the `DirectV1DirectGetByHash` error branch of `startIncomingDomainTypeSIPDirect`). Hit requires: ticket `issued`, session `ringing`, `now < expires_at`, `caller_joined`, customer and extension match; else hangup. A ticket that is `in_use` refuses a second INVITE (concurrent). The ticket becomes `in_use` with `in_use_call_id`, and the call runs the flow `[confbridge_join(cb)]`. If that call hangs up before it confirmed, the ticket returns to `issued` (hook in the call hangup, same place as rule 9).
6. Lease gate (confbridge `Join`, session confbridges only, found through `call:pushring:cb:<id>`): session calls are the app ticket call and the legs whose `FlowID` equals the session's `flow_id` (C3; the groupcall `MasterCallID` is used only to enumerate the legs of the master at close time and is narrowed by the same flow id, because an add-participant leg inherits the master id but runs its own flow; the `ChainedCallIDs` list can be incomplete after `ChainedCallIDAdd` failures). The caller does not take a lease. Any other call (add-participant legs run their own flow and need a progressing call and confbridge; covered by a test) passes untouched. A session call takes the lease (`lease_owner` = call id, `lease_until` = now + 15 s) only if the session is `ringing`, `now < expires_at` and no lease is held and no winner exists; otherwise the call is hung up before it joins. The lease is released by: any error return of `Join`, an error return of `Joined` (join.go returns success after only requesting the channel, so the real failures are in `Joined`, joined.go: `AddChannelCallID`, `CallV1CallUpdateConfbridgeID`, and the channel being destroyed before Stasis start), the hangup of the lease owner call (rule 9 hook), and `lease_until`. A `Joined` that arrives after its lease expired tries to re-take the lease with the same checks and hangs the channel up if it cannot, so a stale join cannot produce a third participant.
7. Confirm (the successful end of `Joined` of the lease owner): `winner` is set. SIP winner: tickets of all devices deleted, `call_cancelled` to all devices. App winner: `call_cancelled` to the other devices, ticket `consumed`, and the SIP legs are hung up (`HangingUp` on `ChainedCallIDs`, plus the groupcall legs through the groupcall `MasterCallID` match, groupcall finishing through `hangupCommon`). Priority and its limit: for a normal connect the SIP leg answer triggers `HangingupOthers` (groupcall/answer.go) before any join happens, so SIP is a one-shot path: if a leg answered, siblings are already gone. This premise does not hold for early media: an early execution leg joins the confbridge while it is still ringing, before any answer. A connect with `early_media` therefore never starts a session (`connectPushRingStart` returns no session) and keeps the legacy behaviour. The first lease wins. If the lease holder is the app and its join then fails, a SIP leg that was refused during the lease is lost and the caller waits until the window ends. If the lease holder is a SIP leg and fails, the app ticket stays usable. This asymmetry is accepted and listed in section 12 (alternative: add a pre-answer hook to HangupOthers; larger change in the groupcall path).
8. Close (once, idempotent, Lua; the keys stay with `state=closed` until the Redis ttl so the gate refuses late arrivals): triggers are the expiry RPCs, the master call hangup, a failed push (rule 2) and `CallV1PushRingClose`. Strict T0 + 60 s: expiry with no confirmed winner closes immediately even if a lease is held; the lease holder call and the `in_use_call_id` call are hung up, `call_cancelled` goes to all devices, tickets are deleted, and for expiry the master call is hung up with `HangupReasonNoanswer` (existing logic hangs up the chained legs) and the confbridge is terminated if empty. With a confirmed winner the expiry only deletes keys. Without a recorded winner, expiry first reads the confbridge: when it holds two or more channels the call is connected through a SIP leg whose winner was not recorded (a failed cache update, or a join handled by a call-manager that does not know the session), so only the cancel notification is sent and the call is kept. A confbridge that cannot be read keeps the window end behaviour. If both delayed RPCs are lost, the Redis ttl removes the keys without hanging up the master and without the cancel push; this is a known limit (the legacy legs still end at their own dial timeout; a push-only caller then waits as it does in the legacy no-answer case).
9. Hangup hook (call-manager `callhandler.Hangup`): placed at the confirmed hangup point (after `!written`, i.e. the call really ended; not before the early returns for a call that merely moved channel, not for the failover branch, which a session master never takes). Two lookups: master (`call:pushring:master:<id>`) -> close without hanging the master again (the caller already left) and without the noanswer reason; lease owner / `in_use_call_id` (`call:pushring:call:<id>`) -> release lease, ticket back to `issued`. One Redis GET per call hangup is the cost. All handlers are idempotent.
10. Cleanup scope: the empty confbridge and temporary flow that the legacy path already leaves are not new requirements. This ticket guarantees cleanup of what it creates (session keys, tickets, pushes) and terminates the confbridge of a push-only call nobody joined, because `Leaved` terminates only when exactly one channel remains (leaved.go).

### 5.1 Corrections that override rules 1 to 10 where they differ
- C1. Joined failure: every error return of `Joined` first hangs up the join channel (or the call), and only then releases the lease. Joined runs on `ChannelEnteredBridge` (ari_event.go), so the channel is already in the bridge; releasing the lease without ending the channel could allow a third participant. Today one branch breaks this for every caller, not only session calls: the `CallV1CallUpdateConfbridgeID` failure branch (joined.go, between the `AddChannelCallID` success and the `switch cb.Type`) returns the wrapped error without hanging up the channel, unlike the `AddChannelCallID` failure branch just above it, which does call `HangingUp`. This ticket adds a `HangingUp` call to that branch as a required code change (not session-specific; it fixes an existing gap that this feature would otherwise inherit for its join channel). Same rule for a late `Joined` after lease expiry.
- C2. Push failure is not a close: when every device fails, the session gets `push_failed` (tickets deleted, no more pushes). The gate still lets SIP legs through; the expiry owner and the close rules are unchanged. Only when `sip_registered` is false does the failure end the master call (rule 2).
- C3. Session-call identification uses the temporary flow id that connect created (stored in the session at start and compared with the leg's `FlowID`), not the groupcall `MasterCallID`: an add-participant leg is created from a SIP-winner call and inherits that master id (participant.go), but it runs its own flow. The app ticket call is identified by the session key written when the ticket is redeemed. Test: add-participant after a SIP winner is not blocked.
- C4. Ticket state: `issued -> in_use(in_use_until = now + 15 s) -> consumed`. The `in_use` marker is written before a call exists (start.go can hang up a channel without creating a call, so no call hangup hook runs), therefore `in_use` returns to `issued` by time (`in_use_until`) or by the hook of the app call. Every return to `issued` is a Lua script conditioned on `state=in_use` and `winner` empty, so a `consumed` ticket can never return. Ticket and session keys are changed by one script per transition (single Redis client in call-manager).
- C5. Winner app deletes the tickets of all other devices; a ticket redemption also requires `winner` empty. The ticket call flow ends with `hangup` after the join so that a rejected join ends the call (a Join error moves the flow to the next action, as in connect's temporary flow).
- C6. Close also hangs up the SIP legs found through the groupcall `MasterCallID` that run the session's `flow_id` (legs of an add-participant after a SIP winner have another flow and are not touched), in addition to the `ChainedCallIDs` loop of the master hangup, so a leg whose `ChainedCallIDAdd` failed does not keep ringing. Expiry that finds `state != ringing` during a confirm makes the confirming call hang up.
- C7. Redis ttl of session and ticket keys is 150 s (window + 90 s) so the redundant expiry RPC at T0 + 90 s still finds the keys and the Redis ttl is the last cleanup if both RPCs are lost. Fail-closed scope: the session lookup `call:pushring:cb:<id>` is read only for a confbridge that was marked as a push-session confbridge by `PushRingStart` itself (a new `confbridge.Flag` value added with the existing `FlagAdd` route inside the start, before it answers; a `FlagAdd` failure means `started:false`, the session keys are removed and connect continues as today; connect creates the confbridge without flags, so ordinary connects are never marked; a flag in the existing `flags` json of the `confbridge` row, not a blind Redis read on every `Join`), so a Redis outage changes behaviour only for the confbridges this feature created, never for ordinary connect/conference joins. Within that narrowed scope, a Redis error is still treated as a rejection (fail-closed), which trades a cache outage for refused joins on push-session calls only; this is an availability limit scoped to this feature and is listed in section 8 (it only affects the sessions this feature introduces).
- C8. `caller_joined` is set only after `AddChannelCallID` and `CallV1CallUpdateConfbridgeID` both succeeded in `Joined`.
- C9. Data model addition: `call:pushring:call:<call_id>` -> session id (lease owner and ticket call), used by the hangup hook.
- C10. The unknown-hash hangup referred to in rule 5 and section 8 is the `DirectV1DirectGetByHash` error branch of `startIncomingDomainTypeSIPDirect` (no line numbers, they drift).

## 6. API contract (the public part is a contract extension)
Public (api-manager, PR 1), agent surface only (no top-level endpoint). The handlers follow the existing agent-only pattern (`serviceAgentStarCheck` in `servicehandler/serviceagent_contact_star.go`): an identity that is not an agent with a non-nil agent id (access key, direct-scope token) gets `ErrAuthenticationRequired` (401), an agent without `PermissionAll` gets `ErrPermissionDenied`; an agent acts on its own devices only:
- `POST /service_agents/push_devices` body `{platform, token}` registers or refreshes the device for the calling agent (section 4) and returns the device (`WebhookMessage`: `id`, `customer_id`, `agent_id`, `platform`, `tm_create`, `tm_update`; no token). 200 for both a new and a refreshed device. 400 for an unknown platform (`android` only), or an empty or longer than 512 byte token.
- `DELETE /service_agents/push_devices/{id}`: api-manager reads the device (`GET /v1/devices/{id}`), requires that its customer and agent equal the caller's, else 404 (no leak), then deletes it.

Internal RPC, bin-push-manager queue `bin-manager.push-manager.request` (PR 1; PR 2 consumes it through the `PushV1*` methods of bin-common-handler):
- `POST /v1/devices` `{customer_id, agent_id, platform, token}` returns the device. The model has `json:"-"` on the token, so the request is its own type and the client method is `PushV1DeviceCreate(ctx, customerID, agentID, platform, token)`; the sender reads the token from the database only.
- `GET /v1/devices/{id}`; `DELETE /v1/devices/{id}`; `GET /v1/devices?page_size=&page_token=` with the repository's body filters (`customer_id`, `agent_id`) lists the devices of one agent (the cap of 10 means one page; an agent without devices gets an empty list, not 404); the handler drops devices whose `tm_update` is older than 30 days, and the token is never part of any response.
- `POST /v1/notifications` `{customer_id, agent_id, device_id (optional; empty means every live device of the agent), kind, data map[string]string}` returns `{device_count, sent_count}`. `kind` must be `call_incoming` or `call_cancelled` (400 otherwise); `data` must not contain the key `kind` (400; push-manager sets it). A `device_id` that does not belong to the agent gives `device_count: 0`. Delivery is one attempt per device with a 5 s timeout, devices in parallel. `sent_count` counts the devices FCM accepted. When the sender is not configured the answer is a normal `sent_count: 0` (and a metric), not an error, so the caller sees an explicit failure at once. A transient FCM error keeps the device and counts as not sent. Retrying is the caller's decision (PR 2: none; the ring window is short). The `PushV1NotificationSend` RPC timeout is 8 s (above the per-device 5 s); an RPC timeout or error is "unknown" for the caller, never "not sent" (rule 2).
- Go client (bin-common-handler `requesthandler`, models in bin-push-manager): `PushV1DeviceCreate(ctx, customerID, agentID uuid.UUID, platform device.Platform, token string) (*device.Device, error)`; `PushV1DeviceGet(ctx, id) (*device.Device, error)`; `PushV1DeviceDelete(ctx, id) (*device.Device, error)`; `PushV1DeviceList(ctx, customerID, agentID uuid.UUID) ([]device.Device, error)`; `PushV1NotificationSend(ctx, customerID, agentID, deviceID uuid.UUID, kind notification.Kind, data map[string]string) (*notification.SendResult, error)` with `deviceID` equal to `uuid.Nil` meaning all devices and `SendResult{DeviceCount int json:"device_count"; SentCount int json:"sent_count"}`. Request bodies are listenhandler request types and are not exported to handlers.
- Errors follow the repository's listen handler error mapping: unparsable body or invalid field is a typed 400, a missing device 404, anything else 500. api-manager validates `platform` and the token length before the RPC and push-manager validates again.
- Events: push-manager subscribes to `agent_deleted` (payload `id` is the agent id) and `customer_deleted` and imports the agent-manager and customer-manager models for the event constants and payload types (the `replace` lines exist already for every module).
- OpenAPI and server work items (follow the bin-openapi-manager checklist): new path files for `/service_agents/push_devices` and `/service_agents/push_devices/{id}` registered in `openapi.yaml` with the existing Service Agent tag, component schema `PushDevice` (no token), request body schema, responses 200, 400, 401, 403, 404 with the shared error references, DELETE returns the deleted device with 200 as other resources do; `server/service_agents_push_devices.go`, `ServiceAgentPushDevice{Create,Delete}` on the `ServiceHandler` interface with mock regeneration, and a dispatcher for the push queue in the requesthandler `send_request.go`.
- FCM sender timing: a send is limited to 5 s by its context. The OAuth token refresh (about once an hour, shared by all devices) does not take that context and has its own 6 s limit, below the 8 s RPC limit, so a caller that times out is told "unknown", never "failed".
- FCM message (HTTP v1): data only, `android.priority=HIGH`, `android.ttl=60s`; data is the caller's map plus `kind`. `call_incoming` data: `{call_id, caller_display, join_address, expires_at, cancel_key=session_id}`; `call_cancelled`: `{cancel_key}`. The keys are a contract between PR 2 and the mobile app; push-manager does not interpret them. No token, internal address or secret inside.
- Metric: `push_manager_notification_total{kind, result}` with result `sent`, `unregistered`, `failed`, `not_configured` (the signal for later decisions on the device cap and expiry).

## 7. Credentials and configuration
bin-push-manager reads the FCM service account the way bin-storage-manager reads its Google credential: the compose file declares a secret `fcm_sa_json` (`environment: "FCM_SA_JSON"`) mounted at `/run/secrets/fcm_service_account.json`, `komodo/environment.env` sets `FCM_SA_JSON=[[BIN_MANAGER__FCM_SERVICE_ACCOUNT_JSON]]` for the stack, and the service reads the file named by `FCM_SERVICE_ACCOUNT_FILE`. The FCM project id is the `project_id` field of that JSON (no separate variable). The JSON is exchanged for an OAuth2 access token (`firebase.messaging` scope) by `golang.org/x/oauth2/google` and sent to `https://fcm.googleapis.com/v1/projects/<id>/messages:send`; the token source caches and refreshes. The Komodo variable `BIN_MANAGER__FCM_SERVICE_ACCOUNT_JSON` is created by a separate infrastructure change and holds a dedicated service account (or the existing Google one if that account is granted the messaging role; that choice is outside this design). Other variables: `DATABASE_DSN`, `RABBITMQ_ADDRESS`, `PROMETHEUS_ENDPOINT`, `PROMETHEUS_LISTEN_ADDRESS`; no `REDIS_*`. When the file is absent, empty or unparsable the service starts, logs once that FCM is not configured, and every notification is `sent_count: 0` (`not_configured`); a present but malformed JSON is logged the same way without its content. Values are never logged or committed; tests use a fake sender, fake values and an `httptest` server. FCM tokens and join addresses are masked in logs by a local helper that shows at most the first 4 characters (the existing `dmdirect.MaskHash` shows more and is not used for tickets). In call-manager the `ChannelCreated` handler logs a masked copy of the event and of the channel (a `direct.` ticket of 32 lowercase hex characters shows its first 4 characters; direct hashes are not changed). Other call-manager log lines that print a whole channel or event still carry the plaintext ticket (see the known limits in section 12). The FCM and token endpoints are overridable only through the test constructor.

## 8. Threat model
| Threat | Control |
|---|---|
| Guess a ticket | 16 random bytes from crypto/rand, hex, `direct.` prefix (existing direct hashes are 6 bytes, so the new value is longer; whether the SIP ingress accepts this user-part length is an unverified assumption not claimed here and is not part of the unit-test evidence for criterion 4). |
| Replay | single use, state machine, session closed at claim or expiry. |
| Use in another customer / call | ticket bound to session, which holds customer, extension, confbridge, master call; mismatches rejected. |
| Public SIP call to a ticket | miss falls to direct-manager lookup, which fails for a random hash; expired and unknown end in the same hangup (the `DirectV1DirectGetByHash` error branch of `startIncomingDomainTypeSIPDirect`). |
| Leak via FCM or logs | ttl 60 s, one use, masked logs, payload minimal. |
| Token abuse | registration requires an authenticated agent and writes only for that agent and customer; the token is unique across the table and moves to the new owner (a device handed over does not keep ringing the previous agent); per-agent cap of 10; delete is limited to the caller's own devices; the token length is validated. |
| Stored FCM token disclosure | the token has `json:"-"`, never appears in an API or RPC response, log or event; the device row is deleted (not soft deleted) on removal. |
| Push fan-out as an amplifier | 10 devices per agent, one attempt each, 5 s timeout, `call_incoming` only from call-manager; the public API cannot send notifications. |
| Redis outage during a push session | `Join` on a confbridge flagged as a push-session confbridge fails closed (join refused) if the session lookup errors; ordinary (non-session) confbridges never read this flag's Redis key and are unaffected. Known limit: a Redis outage during an active push session can refuse that session's join; it does not degrade any other call. |

## 9. Rolling deploy compatibility and order
Order (callee first), across the two PRs: PR 1 merges first and is deployed before PR 2 starts. Inside PR 1 every changed service has its own pipeline, so the deploys run in parallel and their order cannot be enforced: the new endpoint of api-manager may be live for a short time before the push-manager consumer exists, and then returns a plain 5xx for the new route only; no data is affected and no existing route changes. The FCM variable must exist before the merge (section 12). The `go.mod` edits (about 37 files) change the path of every module, so every service whose pipeline matches is rebuilt and, for the auto-deploy services, redeployed in one wave (a one-time capacity and queue-restart cost of the new wave; the changes in bin-common-handler are additive). The migration of push-manager runs before the service listens. PR 2: call-manager (new Redis keys, new RPC routes, hooks) before flow-manager. A flow-manager that calls an old call-manager gets an unknown-route error; it treats that error (and only that error) as `started:false`. A timeout is `started` unknown (rule 3). An old flow-manager never starts a session. An old call-manager ignores devices. A call-manager that calls a push-manager that is down gets an RPC error, which is "unknown" for the session (rule 2). Rollback of PR 1: revert the PR (code only; the table stays, as the migration rule requires, and is unused). Rollback of PR 2: revert the PR; sessions and tickets expire by the Redis ttl of 150 s and the legacy path is unchanged.

## 14. Impact analysis of the schema change
- a-1 Destructive operations, one by one: DROP (table, column, index, constraint, view, trigger, procedure): none. TRUNCATE, data-changing UPDATE, DELETE, INSERT SELECT: none. Column type narrowing or change, default removal or change, rename, enum value removal: none. NOT NULL, UNIQUE, FK, CHECK added over existing data: not applicable, the table is new and empty (the unique key on `token` and the NOT NULL columns are part of the new table). NOT NULL column without default added to an existing table: none. ClickHouse: not used. `CREATE TABLE IF NOT EXISTS push_devices` only. The baseline down is the no-op `SELECT 1` per the baseline rule. Not `[DESTRUCTIVE]`.
- a-2 Rolling deploy compatibility: no code in main reads or writes `push_devices` (repository grep: no match); only the new service uses it. Old code on the new schema is unaffected; new code on an old schema cannot occur because the migration runs before the service listens (service-owned migration rule). PR 2 has no schema change: the push-session marker on the confbridge is a new value in the existing `call_confbridges.flags` json list (like `no_auto_leave`), sessions and tickets live in Redis.
- a-3 Locks and duration: a new table has no rows and no readers; DDL takes only the metadata lock on a new name. Expected size: at most 10 rows per agent.
- a-4 Rollback: revert the PR (new image without the service); the empty table remains and is harmless. Dropping it would be a separate reviewed `-- DESTRUCTIVE` migration. PR 2 rollback: revert, Redis keys expire.
- a-5 Data loss: not possible (new table). Device rows are credentials and are deleted on purpose (token move, cap, `UNREGISTERED`, cascade events).
- Scratch run: upgrade, downgrade, upgrade on MariaDB 12.3 and MySQL 8.0 through the verify script in `NO_ALEMBIC=1` mode; results go to the PR body.
- Blast radius of the common-handler edit: about 37 modules change `go.mod`; every one of them must still build and pass tests; the pipelines of all matching services run once.

### Known limits (accepted, with the trigger to revisit)

- Ticket in other call-manager logs: the dialplan extension of a ticket call is `direct.<32 hex>` and is printed by about twenty other log lines that dump a whole channel or event (for example channelhandler/db.go, arieventhandler/ari_stasis.go, callhandler/hangup.go), and it is stored in `call_channels.dst_number` like a direct hash. The ticket is one use with a 60 s ttl, and the exposure equals that of a direct hash. Revisit when the access to the log collection widens or the ticket ttl is extended.
- Session call fails after it entered the bridge: when the call of a session joined the confbridge and then fails and hangs up, the auto terminate of the last leave ends a confbridge that only holds the caller. Rare infrastructure error; revisit with a measured signal.
- Start races: a contact that registers after the `sip_registered` decision while every device also answers `sent_count: 0` ends with the caller waiting for the window end. Rare triple condition; revisit with a measured signal.
- Start latency: every single extension connect makes serial RPCs (agent, devices, contacts, notification) of up to 3 to 4 s when push-manager is unavailable. No measurement exists. Revisit when the push-manager availability metric shows start latency.
