# MMS send support (design)

Adds MMS (message with media attachments) to `POST /messages`. Work is split into three pull requests: P1 sending core (this PR, design plus implementation), P2 conversation, flow and AI tool integration, P3 receiving MMS. P4 (square-talk and square-admin screens) is a separate JavaScript track and is out of scope here.

## Part 0. Ticket review and analysis

Every claim of the ticket was assumed wrong and re-checked on `origin/main` (`18297945d`, no newer commit at the time of writing). At the time of writing a search of open and merged pull requests found none that touches MMS.

### Claims that hold (file and line checked)
- `POST /messages` accepts only `source`, `destinations`, `text` (`bin-openapi-manager/openapi/paths/messages/main.yaml`, `bin-api-manager/server/messages.go`). `MessageManagerMessage` has no `medias`; `WebhookMessage` (`bin-message-manager/models/message/webhook.go`) has no medias either, so even stored medias would not be exposed.
- `messagehandler.Send` and both provider `SendMessage` methods take text only. `requestexternal.TelnyxSendMessage` already has a `media_urls` payload field that no caller fills. `MessagebirdSendMessage` posts to the SMS endpoint (`/messages`), not the MMS endpoint (`/mms`).
- `messagehandler.Create` fixes `Type: TypeSMS` and `Medias: []string{}` (`message.go`).
- Provider selection (`send.go`): a map of two handlers is iterated (Go map order is random), the first success stops the loop. `Create` records Messagebird before sending and `dbUpdateTargets` overwrites it with the provider that succeeded. The code comment says "we use the messagebird only" while the code tries both: the real behaviour is nondeterministic.
- Telnyx partial failure: `provider_telnyx.go` returns `nil` and the wrapped first error if any target failed, although other targets were already accepted by Telnyx. The loop then calls Messagebird with all targets. This is an existing duplicate-send path for SMS.
- Billing: `send.go` checks the balance with `ReferenceTypeSMS`; billing-manager charges per target when it receives `message_created` (`billinghandler/event.go`), before any provider call. Five code points branch on the SMS types: `billing.go` lines 62 (retry of an unfinished billing), 82 (immediate end flag, any unknown type returns `UNSUPPORTED_REFERENCE_TYPE`) and 163 (billable units), `accounthandler/balance.go` line 94 (balance check, unknown type returns `UNSUPPORTED_BILLING_TYPE`), and `models/billing/cost_type.go` `GetCostInfo` (maps `CostTypeSMS` to credit only mode and `DefaultCreditPerUnitSMS`; an unknown cost type falls to `default` and returns `CostModeDisabled` with zero rates). `balance.go` and `BillingEnd` both read the rate from `GetCostInfo`. Adding a type to only some of them makes MMS billing fail or, for a missing `GetCostInfo` case, run with a disabled mode and zero rate, so all five must change together and the rate constant is part of P1. A missing `GetCostInfo` case records an ended billing with amount 0 and no error, and it is independent of the `balance.go` pre-check. Two call sites choose the types and must also change: `send.go:59` (balance check) and `billinghandler/event.go:136` (hardcodes `ReferenceTypeSMS` and `CostTypeSMS` and ignores the message type, so without a change an MMS would be charged the SMS rate with no error). `reference_type` and `cost_type` are `varchar(32)` columns, so no schema change is needed. The cost type enum is also generated into `bin-openapi-manager/gens/models/gen.go` and `bin-api-manager/gens/openapi_server/gen.go`. There is no refund path for a message that failed to send (the refund code that exists is for Paddle payments only).
- Inbound messages are billed too: `subscribehandler/message.go` calls `EventMMMessageCreated` for every `message_created` event without looking at `Direction`, and `hookTelnyx` creates inbound messages through the same `Create` that publishes the event. So today an inbound SMS is charged at the SMS rate per target. This matters for P3 (see decision 8 in Part A).
- Callers of `requesthandler.MessageV1MessageSend`: api-manager, flow-manager, ai-manager, conversation-manager (four production callers).
- Conversation: `smshandler.Send` drops medias; conversation `media.Media` has no URL or file id.
- `file.Type` has rag, talk, recording only. Inbound Telnyx media is `[]interface{}` and `hookTelnyx` stores text only.

### Corrections and additions found
1. `message_messages.medias` (json) already exists in the baseline migration, and `Message.Medias []string` already maps it. No schema change is needed.
2. Signed URL lifetime: `bin-storage-manager/CLAUDE.md` says 24 hours, the code says 7 days (`filehandler/main.go`, `downloadURLExpiration`). `StorageV1FileDownloadURIRefresh` already exists and always signs a fresh URL. No new storage RPC is needed. The stale 24 hour sentence is not part of this change.
3. Number capability: `FeatureMMS` exists only on `availablenumber` search results. A purchased `Number` has no feature or capability field, so the sender number cannot be checked for MMS support at send time without a schema change.
4. A failed provider send is never recorded: `Send` logs the error and the targets stay `queued` forever. `StatusFailed` and `StatusDelivered` exist in `target.go` but nothing on the send path writes them, and the Telnyx hook (`hook.go` lines 62 to 65) skips `message.sent` and `message.finalized` events, so there is no delivery receipt update for outbound messages at all. For MMS "no silent loss" is a requirement, so MMS dispatch writes a final status per target (`failed` when no provider accepted it). Accepted targets stay `queued`, the same as SMS, because no delivery receipt handling exists (out of scope). Also, `Create` records Messagebird as the provider before sending; if every attempt fails, that first value stays. For MMS the provider recorded at creation is the first provider attempted (Telnyx) and is replaced by the provider that accepted a target.
   Related: the send goroutine uses the context of the listen handler, which is `context.Background()` (`listenhandler/main.go:155`), so it is not cancelled when the RPC returns. The `targets` slice is only read by the goroutine and the stored copy is a JSON round trip, so there is no data race today. The Telnyx call uses an `http.Client` without timeout, so the MMS dispatch adds a bounded context.
5. `storage file` carries `Filename` and `Filesize` but no MIME type. MIME can only be derived from the file name extension.
6. Messagebird MMS facts (public documentation, re-read): separate endpoint `POST /mms`; US and Canada only; sender must be an MMS enabled dedicated number; at most 50 recipients; `subject` 256, `body` 2000 characters; `mediaUrls`; at most 10 attachments, 1 MB each, URL must be publicly reachable and answer within 5 seconds. Whether our account is activated is unknown and cannot be checked from the repository. One request is all or nothing for its recipient list (the response has no per target failure), so a per target fallback requires one request per target.
7. Modules that depend on `bin-common-handler`: 36 other modules plus the module itself (37 `go.mod` files contain the path), which matches the ticket. Vendor directories are not committed, so this only matters for local `go mod vendor`.
8. `bin-message-manager/docs/domain.md` and `CLAUDE.md` describe a stale provider order and a Target table that does not exist. They are corrected only where this change touches them.

### Verdict
Valid. Nothing is already solved, duplicated or invalidated. The ticket understates two risks that the design must handle: the nondeterministic provider loop (a fallback built on it would duplicate sends) and the missing failure status.

### Analysis conclusions that drive the design
- A new RPC route is safer than adding a field to the existing one (old message-manager would silently send SMS text only). See Part A, decision 3.
- Fallback must be per target and only after a definitive rejection.
- Costs are charged before sending, so a failed MMS is already charged. This is the existing model for SMS and is not changed here (see decision 7 in Part A).

## Part A. Design

### What is built
- P1 (this pull request): `POST /messages` accepts `medias` (storage file ids). Messages with media are sent as MMS: Telnyx first, Messagebird MMS for targets that Telnyx definitively rejected. A new MMS billing type. Media validation and fresh signed URLs at send time. The response and webhook expose `medias` and `type: "mms"`. SMS behaviour and responses are unchanged.
- P2 (later pull request): conversation, flow action and AI tool take media by file id and call the new MMS method.
- P3 (later pull request): receiving MMS (parse provider media, copy into storage, expose on the message).

### Decisions
1. **Scope of P1.** Sending core only: the RPC, message-manager send path with fallback, billing type and balance check, media validation, `POST /messages` with `medias`, OpenAPI, the RST pages. P2 and P3 are not implemented here, but their contract (the new RPC method and the `medias` field) is fixed here so that they only add callers.
2. **API contract.** Request body of `POST /messages`:
   - `source`, `destinations`, `text` as today (`text` stays required; for a media only message it may be an empty string, in which case the provider request omits `text`; whether each provider accepts a media only message cannot be tested here because no test may send).
   - `medias` (new, optional): array of storage file ids (uuid, at most 10 items; the spec has `maxItems: 10` and no `minItems`). Missing or an empty array means SMS and the request takes exactly the old path. Arbitrary URLs are not accepted anywhere (SSRF and expiring signed URLs).
   - Response `MessageManagerMessage`: `type` can now be `mms`; new optional `medias` (the file ids). The field is omitted for SMS (`omitempty`), so an SMS response and an SMS webhook payload stay byte identical to today.
   - Errors (all `INVALID_ARGUMENT`, HTTP 400, unless noted): `MEDIA_TOO_MANY` (more than 10), `MEDIA_NOT_FOUND` (id unknown, deleted, or owned by another customer: one code for all three so existence of other customers' files is not revealed), `MEDIA_FILE_TYPE_INVALID` (an own file that was not uploaded with type `media`), `MEDIA_REQUIRED` (only reachable by an internal caller of the RPC), `MEDIA_DUPLICATE` (the same id twice), `MEDIA_TYPE_UNSUPPORTED`, `MEDIA_TOO_LARGE` (one file or the total over its limit), `TEXT_TOO_LONG` (over 2000 characters), `INVALID_MEDIA_ID` (not a uuid, raised by api-manager). `PAYMENT_REQUIRED` (402, reason `INSUFFICIENT_BALANCE`) when the balance check fails. Today the SMS path returns an untyped error for this case, which the listen handler turns into a 500; the MMS path builds the typed error itself (`cerrors.PaymentRequired`) and the SMS path is left as it is. A storage or signing outage returns the upstream typed error unchanged (its own status), and an exceeded 10 second media deadline returns a typed unavailable error (reason `MEDIA_CHECK_TIMEOUT`, HTTP 503). All of these happen before the message is created, so retrying the request is safe (no message, no charge, nothing sent); the customer documentation says so.
3. **Service-to-service RPC: new route, not a changed signature.**
   | | A. New route `POST /v1/messages/mms` and new method `MessageV1MessageSendMMS` | B. Add `medias` to the body of `POST /v1/messages` and change `MessageV1MessageSend` |
   |---|---|---|
   | Rolling deploy, new caller with old message-manager | route unknown, request fails (404), nothing is sent | old message-manager ignores the unknown JSON field and sends a text only SMS charged as SMS: a silent degrade |
   | Existing callers (api, flow, ai, conversation) | untouched | all four and their tests change in P1 |
   | Mock and generated code | `MockRequestHandler` gains one method | the signature changes in the interface, the mock and every caller |
   | Cost | one more method pair | smaller surface but unsafe |
   A is chosen. The old method stays for SMS, P2 callers switch to the new method only when they carry media.
   The new method uses the long RPC timeout (30 seconds, `requestTimeoutLong`) because the media check calls storage-manager before the message is created (see decision 5); the default of 3 seconds would let the caller time out while message-manager goes on to create, send and charge, and a caller retry would then send twice.
   Deploy order: billing-manager first and fully rolled out (every replica), then message-manager, then api-manager. With a new message-manager and an old billing-manager the balance check fails closed (`UNSUPPORTED_BILLING_TYPE`). The one unsafe window is a mixed billing-manager fleet (or a billing-manager rollback after MMS traffic started): a new replica passes the balance check and an old replica handles `message_created` and charges the SMS rate without an error. So the gate is "all billing-manager replicas run the new image before message-manager is deployed, and billing-manager is not rolled back while MMS is live". An old message-manager answers the unknown route with 404, which api-manager reports as a not-found error: this can only be seen if message-manager is rolled back after api-manager (the order above keeps it away otherwise), and it fails closed. The HTTP edge has a different property: api-manager reads the body with `BindJSON`, which ignores unknown fields, so an old api-manager replica (during the rollout, or after a rollback while MMS is live) drops `medias` and sends a plain SMS, charged as SMS. That cannot be closed in the old code and a global switch is not allowed, so it is handled by order and documentation: the customer documentation and the API reference are published only after every api-manager replica runs the new image, api-manager is not rolled back while MMS is live, and the documentation tells clients to check `type` in the response (`mms` or `sms`).
4. **Data model.** `Message.Medias []string` already exists (column `medias`, json). It stores the storage file ids, never URLs (URLs expire). `Type` gets `mms`. `WebhookMessage` gets `Medias []string` with `json:"medias,omitempty"`. No migration, no change of `Target`. Old code reading rows with type `mms` is safe (the type is a plain string), and new code reading old rows sees an empty `medias`.
5. **Media validation (message-manager, so every future caller is covered).** The file must come from the public upload `POST /storage_files`, which today accepts only `type=rag` (`server/storage_files.go:50`; the file type enum has rag, talk, recording). P1 adds the upload type `media` (one constant in storage-manager, the accepted values in that handler, the upload request enum and the response enum `StorageManagerFileType` that `StorageManagerFile.type` references, and the storage RST page, which also states the media limits and that a file uploaded as another type cannot be used) so a customer has a way to obtain file ids. No other storage change. For each id: `StorageV1FileGet`; reject if the file is not found, deleted (`TMDelete`; storage returns deleted rows), or `CustomerID` differs from the sender customer (`MEDIA_NOT_FOUND`, the typed storage not-found error is converted to this code), or its type is not `media` (`MEDIA_FILE_TYPE_INVALID`; the file is owned by the sender so nothing is revealed). Count at most 10. Size and type limits come from the provider documentation (Telnyx: total attachment size below 1 MB with about 100 KB of headroom, at most 10 items; images 1 MB, audio and documents 600 KB, each carrier dependent; Messagebird: 10 items, 1 MB each) and are constants in one file: at most 10 files, the total at most 900 KiB, and per file at most 900 KiB for `jpg jpeg png gif` images and 600 KiB for `mp3 wav` audio and `pdf`. The type is derived from the file name extension against that allow list; other types are rejected (`MEDIA_TYPE_UNSUPPORTED`). No MIME field is stored. Storage uploads set no content type (`StorageFileCreate` uses a bare writer of the storage client library, which detects the type from the first bytes), so the type served to the provider is the detected one, not the extension; for example an mp3 without a tag header may be served as a generic binary type. The extension check (case insensitive) is therefore a first filter only and the provider is the final judge; if provider rejections for this reason show up in the counter, the trigger is to set the content type at upload time. Telnyx may transcode oversized media on its side. Order inside message-manager: identity verification gate and address normalization (the same code as SMS, reused so MMS cannot bypass the gate), then text length and media validation (parallel per file, at most 10 in flight), then the balance check, then `StorageV1FileDownloadURIRefresh` for every file (parallel), then the message is created and dispatch starts. Media validation and the URL refresh share one 10 second deadline, which keeps the RPC worker (the listen handler has a pool of 10 that also serves reads and inbound hooks) from being held for long when storage is slow; the normal cost is a few milliseconds per file. A rejection at any of these steps has no side effect except that a refresh may update the signed URL stored for a file, which is harmless. The signed URL (7 days) is passed to the provider. The URLs are never stored and never logged. `DownloadURIRefresh` itself does not check the owner or deletion, which is why the owner check above is required before it is called.
6. **Provider selection for MMS (deterministic, per target).** The SMS loop is not reused.
   1. The message is created with provider `telnyx`.
   2. Every target is sent to Telnyx with its own request (at most 10 in flight, 30 second timeout per request through the context; the existing client has none). The request code returns a typed error that carries only the HTTP status and a short reason, never the response body (today the Telnyx error text contains the whole body, and the body can echo the media URLs, which must stay out of logs). An HTTP status from 400 to 499 except 408 is a definitive rejection (the order was refused and nothing was queued). A 408, a 5xx, a timeout or a transport error is ambiguous (the message may exist at the provider).
   3. Only definitively rejected targets are eligible for fallback, and only when the sender and the destination are `+1` numbers (Messagebird MMS is limited to the US and Canada). Ambiguous failures never fall back, because that could send twice (the same rule as the purchase fallback of number-manager).
   4. Eligible targets are sent to Messagebird MMS (`POST /mms`), one request per target, because one Messagebird request is all or nothing for its recipient list (at most 10 in flight, same timeout). The sender number is the same as for Telnyx. The fallback can only succeed when that number is also an MMS enabled number of the Messagebird account (decision 10); otherwise the request is refused and the target fails.
   5. A target that no provider accepted gets status `failed`. A message is never sent as text only when media was requested. `failed` means the provider did not confirm acceptance. For an ambiguous failure (transport error, 5xx, 408) the message may still have been delivered; this is stated in the customer documentation, and the log and counter distinguish the reason (`rejected` or `error`). The scope of "no silent loss" is the provider answering: once a provider accepted a target, a later failure is invisible because delivery receipts are not processed (a separate piece of work), and a pod that stops during dispatch leaves the targets `queued`, the same limit as SMS.
   6. The recorded provider is the one that accepted the targets: `telnyx` if any target was accepted by Telnyx, else `messagebird` if any was accepted there, else it stays `telnyx`. A message split across both providers records `telnyx`; per target provider attribution is not stored (trigger to add it: operations need to know which provider carried which target).
   7. Final target statuses and the provider are written once, after all attempts, with the usual `message_updated` event. A middle write after the Telnyx stage was considered and not taken: it doubles the writes and events, the window only grows with many destinations and slow providers, and a stop during dispatch is the same limit as SMS. Trigger: requests with many destinations become common. Accepted targets stay `queued` like SMS (no delivery receipt handling exists).
7. **Billing.** New `ReferenceTypeMMS`, `CostTypeMMS` (`"mms"`), constant `DefaultCreditPerUnitMMS = 30000` (provisional $0.03, the only place the price is written) and a `GetCostInfo` case (credit only). All five branch points of Part 0 get the new type; `send.go`'s MMS counterpart checks the balance with `ReferenceTypeMMS` and the number of targets and `billinghandler/event.go` picks `ReferenceTypeMMS` and `CostTypeMMS` when `m.Type` is `mms`. Charging stays before sending, per target, and there is no refund for a failed send (the SMS model). Money impact: every target is charged 30000 credit units ($0.03) when the message is created, also when it ends `failed`, and because the sender number cannot be checked beforehand (decision 9) the early failure rate may be high; this is why open decision 1 asks for confirmation. The OpenAPI enums for the billing reference type and cost type get `mms`.
8. **Inbound messages and P3.** Inbound messages are billed today with the same per target event, at the SMS rate. P1 does not change that. Because event.go selects by message type, an inbound message of type `mms` created by P3 would be charged the MMS rate (parity with SMS). Whether inbound MMS should be charged at all was an open decision for P3; it is settled in Part C, decision 12: charged like an inbound SMS, no billing code change.
9. **Sender number capability.** A purchased number has no MMS capability field, so P1 cannot reject a non MMS number up front. The providers reject it, the target becomes `failed`, and the failure is visible in a counter and a log line. Trigger for a real check: failures of this kind show up in the counter; then number-manager stores the capability at purchase (a schema change in its own change).
10. **Messagebird MMS activation premise.** The fallback assumes that the Messagebird account is MMS enabled and owns an MMS capable US or Canada number. This is not verifiable from the repository. If it is not true, the Messagebird request is refused, the target is `failed`, and nothing degrades silently. There is no on/off switch: the behaviour is the same code path either way. Trigger to drop the fallback: the counter shows that Messagebird attempts keep failing.
11. **Observability.** Existing send counters get the label value `mms`; a new counter counts failed MMS targets by provider and reason (`rejected`, `error`, `ineligible`); a histogram observes the duration of the media validation step, because storage latency is what can saturate the RPC worker pool (trigger to act: the step regularly approaches its deadline). Logs carry message id, provider and status code, never URLs or file names.
12. **Cost safety of the change itself.** No test sends a message. The providers are reached only through the `requestexternal` interface (gomock) or through an in process HTTP round tripper that replaces the default transport.

### Impact of P1
- Code: `bin-billing-manager` (models, `billinghandler/event.go`, `billing.go`, `accounthandler/balance.go`, tests), `bin-message-manager` (models, listen handler route and request type, `messagehandler`, `requestexternal`, metrics, tests, mocks of `MessageHandler`, `RequestExternal` and the new `MMSProvider`), `bin-common-handler/pkg/requesthandler` (one new method, `MockRequestHandler` regenerated in `mock_main.go`), `bin-storage-manager` (one new file type constant `media`), `bin-api-manager` (`server/storage_files.go` accepts `media` besides `rag`, `server/messages.go`, a new `servicehandler.MessageSendMMS` so `MockServiceHandler` is regenerated while `MessageSend` and its callers stay; generated server types), `bin-openapi-manager` (spec and generated types: upload type enum `media`, request `medias`, response `medias`, message type enum `mms`, billing reference type and cost type enums `mms`).
- Not changed: flow-manager, ai-manager, conversation-manager (they keep calling the old method until P2), the storage RPCs (existing ones only), number-manager. The other modules that depend on `bin-common-handler` need only a vendor refresh locally; vendor directories are not committed, and a compile check of the dependents is part of the verification.
- Documentation: RST pages `message_overview`, `message_tutorial`, `message_struct_message`, the storage file pages (upload type `media`), billing pages that list reference and cost types; the built HTML; `bin-message-manager/docs` (architecture routing table, domain, operations) and `bin-billing-manager/docs`; `CLAUDE.md` lines of message-manager that state the provider order.

### Alternatives not taken
- Reuse the SMS provider loop with media: the loop order is random and it re-sends all targets after a partial failure.
- Accept media URLs: SSRF and expiring links.
- Fallback on every failure: duplicate sends on ambiguous errors.
- Fail the whole message when one target is rejected: wrong for a multi destination request.
- A global on/off flag for the fallback or for MMS: not allowed by the project rules and not needed.
- Fix the SMS path in the same change: it changes SMS behaviour. Offered as a separate proposal in the open decisions.

### Open decisions (none blocks P1; P1 follows the stated recommendation)
1. Refund when a charged MMS could not be sent (confirmation requested because it is a money matter). Options: (a) none, same as SMS; (b) a refund event after the final status `failed`. Recommendation: (a) for P1 to keep the SMS model and avoid a new billing refund flow; (b) as a follow up if the failure rate is visible in the counter.
2. Inbound MMS charging in P3. Options: (a) keep parity (charged like inbound SMS); (b) not charged. Recommendation: decide in P3 with the real provider cost.
3. The provisional price (30000 credit units). One constant, changed when the contract cost is known.
4. Confirmation that the Messagebird account is MMS enabled (fallback depends on it, see decision 10).
5. SMS path hardening (random provider order, duplicate send after a Telnyx partial failure, no failure status). Recommendation: a separate change after P1.

## Part B. Detailed design

### Wire and Go contracts
- RPC: `POST /v1/messages/mms` on the message-manager queue. Body `request.V1DataMessagesMMSPost{ID, CustomerID, Source, Destinations, Text, Medias []uuid.UUID}`. Response: the created `message.Message` (JSON), as for `/v1/messages`. Errors travel as typed `VoipbinError` responses.
- Client: `requesthandler.MessageV1MessageSendMMS(ctx, id, customerID uuid.UUID, source *address.Address, destinations []address.Address, text string, medias []uuid.UUID) (*mmmessage.Message, error)` with `requestTimeoutLong`. The old `MessageV1MessageSend` is untouched.
- `messagehandler.MessageHandler` gets `SendMMS(ctx, id, customerID, source, destinations, text, medias []uuid.UUID) (*message.Message, error)`.
- api-manager: `servicehandler.MessageSendMMS(ctx, a, source, destinations, text, medias []uuid.UUID)` (new method; `MessageSend` is not changed, so its mock and callers stay). The request type follows the repository convention for ids in request bodies: the spec item is `type: string`, `format: uuid`, `x-go-type: string`, so the generated field is `*[]string` and a malformed id reaches the server code instead of failing in `BindJSON`. `server.PostMessages` parses each item with the uuid parser and rejects a malformed value or `uuid.Nil` with `INVALID_MEDIA_ID`, calls `MessageSendMMS` when the list is not empty, otherwise `MessageSend` as before (an empty array is SMS). The permission rule is the same as `MessageSend`.

### bin-billing-manager
- `models/billing/billing.go`: `ReferenceTypeMMS ReferenceType = "mms"`.
- `models/billing/cost_type.go`: `CostTypeMMS CostType = "mms"`; `DefaultCreditPerUnitMMS int64 = 30000` (comment: provisional $0.03 per message, the single definition); `GetCostInfo` case `CostTypeMMS` returns `CostInfo{CostModeCreditOnly, 0, DefaultCreditPerUnitMMS}`.
- `billinghandler/billing.go`: add `ReferenceTypeMMS` to the three lists that contain `ReferenceTypeSMS` (retry of an unfinished billing, immediate end flag, billable units 1).
- `accounthandler/balance.go`: new case for `ReferenceTypeMMS` using `GetCostInfo(CostTypeMMS)`, credit only, like SMS.
- `billinghandler/event.go`: `EventMMMessageCreated` chooses `(ReferenceTypeMMS, CostTypeMMS)` when `m.Type == mmmessage.TypeMMS`, otherwise the unchanged SMS pair (a small unexported helper, so the choice is tested in one place).
- Tests: `GetCostInfo`, balance (enough, short, boundary), `BillingStart` and `BillingEnd` for the new type including the retry and idempotency branches, the event for an SMS message (must still charge the SMS pair) and an MMS message, and the three `UNSUPPORTED_*` default branches still reject an unknown type.

### bin-message-manager
- `models/message/message.go`: `TypeMMS Type = "mms"`. `models/message/webhook.go`: a `Medias []string` field with the JSON tag `medias,omitempty`, and the conversion copies it.
- `pkg/listenhandler`: regex `/v1/messages/mms$`, a case for POST, `processV1MessagesMMSPost` (unmarshal, call `SendMMS`, marshal, same shape as `processV1MessagesPost`), request type in `models/request/v1_messages.go`.
- `pkg/requestexternal`:
  - `ProviderError{Provider string, StatusCode int}` (error text has the provider and status only) and `IsDefinitiveRejection(err error) bool` (`errors.As`, status 400 to 499 except 408).

## Part C. P3 design: receiving MMS

This part is the P3 row of Part A, designed on `origin/main` after P1 and P2 were merged. P3 touches `bin-message-manager`, `bin-storage-manager`, `bin-common-handler` (one RPC method and the mock), the RST pages and the service docs. No schema change, no change of billing code, no new global switch.

### C0. Ticket review for P3 (claims assumed wrong, then re-checked in code)
- `hookTelnyx` (`bin-message-manager/pkg/messagehandler/hook.go`) reads only the text and the addresses; `Create` fixes `Type: sms` and `Medias: []string{}` (`message.go`). Holds.
- `telnyx.Payload` has no `media` field (a comment only). `telnyx.Message.Media` (`[]interface{}`) is the send response model. Holds.
- `bin-storage-manager` can only register an object that already is in a bucket (`filehandler.Create` takes `bucketName` and `filepath` and moves the object out of the tmp bucket). No RPC takes bytes and `bin-message-manager` has no cloud storage client. Holds, so a new storage RPC is needed.
- The hook is synchronous: `hook-manager` calls `MessageV1Hook` with the default 3 second RPC timeout (`requesthandler/message_hook.go`, `main.go` `requestTimeoutDefault`) and answers the provider with HTTP 500 when that RPC fails or times out. An error returned by `Hook` itself is only logged and answered with 200 (`listenhandler/hooks.go`), so the risk is a slow hook: a hook that works longer than 3 seconds makes hook-manager answer 500 while message-manager still finishes and creates the message, and a provider that retries a failed webhook (documented behaviour of the provider, assumption A6) delivers it again. `hookTelnyx` has no duplicate detection and billing keys on the new message id, so the retry would create a second message and a second charge. This decides the shape of the design (decision 1).
- Inbound messages are billed at `message_created` for every target without looking at the direction, and with P1 the billing event picks the MMS pair when `Type == mms`. So an inbound MMS is charged at the MMS rate, the same way an inbound SMS is charged at the SMS rate. No billing code change; the price constant is changed separately when the contract cost is known.
- Consumers of `message_created` (checked): billing-manager (charge), conversation-manager (`MessageEventReceived`), the webhook path and timeline-manager. Only conversation-manager reads message content. It creates a conversation message with `Medias: []` from the text and starts the flow or agent. It does not subscribe to `message_updated`, so the attachments reach the conversation only if a follow up adds that; see decision 11. Text only behaviour is unchanged.
- P3 adds a new effect to the hook path (downloads and stored files), which is why the ingest is bounded (decision 5 and 6).

### C1. Provider payload (public documentation, read only; no sample of a real inbound MMS exists)
Source: the public Telnyx messaging documentation pages "Receiving webhooks", "Send and receive MMS" and "Receive SMS and MMS Messages" (`developers.telnyx.com`, read 2026-11-06). Confirmed from the documentation: event `message.received`; `data.payload.type` is `"SMS"` or `"MMS"`; `data.payload.media` is an array of objects `{url, content_type, size, sha256}` (empty for SMS); media links expire after 30 days.

Assumptions (not confirmed by any sample or by the account; each is isolated in one place, see C3):
- A1. The media host is a `telnyx.com` host (the documentation shows `media.telnyx.com` only).
- A2. Downloading needs no authentication header (the documentation contradicts itself). No credential is ever sent, so if A2 is false the media is skipped and counted, never leaked.
- A3. The account receives MMS at all.
- A4. `content_type` and `size` are present and typed as documented. The parser tolerates anything else (decision 2).
- A5. The message broker accepts a message of about 2.7 MiB (base64 of a 2 MiB file). The code has no limit (`rabbitmqhandler` sets only the prefetch); the broker default maximum message size is 125 MiB, the deployment value is not visible in the repository.
- A6. The provider retries a webhook that was answered with a non 2xx status (documented, not observed).

If A1 is wrong, every media of a message is skipped after the first release (counter result `host`, and the host name is logged, see decision 5), the text path is unaffected, and the constant is changed in one line. The PR body says so.

Test fixtures use made up values only (`https://media.telnyx.com/example/photo.jpg`, fake numbers and ids, `example.net` for negative host cases).

### C2. Decisions
1. **Flow: create first, ingest media afterwards, off the RPC.** The hook must answer inside the RPC timeout and a download can take much longer, so `hookTelnyx` creates the message immediately (type `mms` when `IsMMS()`, otherwise `sms` as today; `medias` empty; the text is kept), and then starts one goroutine, `ingestInboundMedias`, and returns. The goroutine runs on `context.WithoutCancel(ctx)` with one deadline of 90 seconds that covers the downloads and the storage calls together (the request context ends with the hook answer). It downloads each media, stores it, and writes `medias` once with `message_updated`. Alternative not taken: create the message after the download (a stop or a slow download would lose the text and delay the charge and the webhook). Consequences, stated in the customer documentation: `message_created` of an inbound MMS carries an empty `medias`, the final list comes with `message_updated`, and a media that fails is missing from the list (the text and the record are never lost).
   | Payload | Type | Ingest | Charge at creation |
   |---|---|---|---|
   | `type` SMS, no media | `sms` | none | SMS rate (unchanged) |
   | `type` MMS, media present | `mms` | yes | MMS rate |
   | `type` MMS, empty or undecodable media | `mms` | none | MMS rate |
   | `type` SMS but media present | `mms` | yes | MMS rate |
   The ingest starts only after the message was created and only for events that the hook already processes (`message.sent` and `message.finalized` return before, as today).
2. **Payload parsing is tolerant.** `telnyx.Payload.Media` is a `json.RawMessage`; `MessageEvent.GetMedias()` decodes it into `[]PayloadMedia{URL, ContentType string; Size int64; SHA256 string}` one item at a time. A media field that is missing, `null`, not an array, or an item whose fields have the wrong type never fails the event: the item (or all media) is skipped, counted with result `parse`, and the message is created from the text as before. This keeps the text and charge path free of any dependence on assumption A4. `IsMMS()` is true when `payload.type` equals `MMS` (case insensitive) or the decoded list is not empty. The send response model `telnyx.Message.Media` is not changed. Existing tests that compare a decoded payload with `reflect.DeepEqual` (`payload_test.go`, `message_event_test.go`) get the new field in their expectation.
3. **Message type at creation.** `Create` (fixed `sms`) becomes a thin wrapper of an unexported `create(ctx, id, customerID, source, targets, provider, text, direction, msgType)`; the hook calls `create` with `mms` when `IsMMS()`. `Create` callers and tests stay unchanged.
4. **Storage of bytes: new RPC `POST /v1/files/content`.** The route regex is `/v1/files/content$`; it matches none of `/v1/files$`, `/v1/files\?`, `/v1/files/<uuid>$` and none of those matches it. Signatures:
   - request type `request.V1DataFilesContentPost{CustomerID, OwnerID uuid.UUID; Type file.Type; Name, Detail, Filename, ContentType string; Content []byte}` (the bytes travel as base64 inside the JSON, 2 MiB becomes about 2.7 MiB);
   - `requesthandler.StorageV1FileCreateContent(ctx, customerID, ownerID uuid.UUID, fileType smfile.Type, name, detail, filename, contentType string, content []byte, requestTimeout int) (*smfile.File, error)`;
   - `storagehandler.FileCreateContent(ctx, customerID, ownerID, fileType, name, detail, filename, contentType string, content []byte) (*file.File, error)` and `filehandler.CreateFromContent` with the same arguments.
   `CreateFromContent` rejects empty content or content over `fileContentMaxSize` (2 MiB, one constant) with a typed invalid argument error, writes the bytes to `tmp/<new uuid>` in the tmp bucket with the content type, (the writer's `ChunkSize` is one 256 KiB step above the size cap, so every allowed content goes up in a single request and the writer does not allocate its 16 MiB default buffer), then calls the existing `Create` with `ReferenceTypeNone` and `uuid.Nil` as reference. The quota check, the move to the media bucket, the signed URL, the row, the created event and the counters are reused and cannot diverge from the upload path. If `Create` fails before the move (missing object, quota) the tmp object is deleted (best effort, logged); a failure after the move leaves an orphan in the media bucket, which is the behaviour of the existing upload path too. A crash between the write and `Create` leaves an orphan tmp object; whether the tmp bucket has a lifecycle rule is not visible in the repository, so an orphan is accepted (it needs a process kill in a window of milliseconds). The RPC is internal: the caller names the customer, as for every existing storage RPC. The new handler never logs the request (`m`) or the content; the existing default branch of `processRequest` that logs `m.Data` of an unknown route is changed to log the data length only, because an older image that receives the new route would otherwise log megabytes. The quota error of `ValidateFileInfoByCustomerID` is an untyped error; P3 does not retype it (that would change the upload path status), so the message side counts every storage error as `storage`. The file type is `media` (P1); the limits of inbound files (2 MiB each, `.vcf` allowed) are larger than the outbound limits of `POST /messages` (P1: 900 KiB total, a fixed extension list), so an inbound attachment may not be sendable again as is; the documentation says so.
5. **Download policy (SSRF and abuse).** A `MediaFetcher` interface (`Fetch(ctx, m telnyx.PayloadMedia, index int, budget int64) (*FetchedMedia, FetchResult)` (`budget` is the number of bytes left for the whole message); `FetchedMedia{Content []byte; ContentType, Filename string}`; `FetchResult` is the closed set of counter results) with one production implementation in `bin-message-manager/pkg/messagehandler/media_fetcher.go` (one consumer, so not in `bin-common-handler`), a field `mediaFetcher MediaFetcher` of `messageHandler` set in `NewMessageHandler`, and a generated mock. Hook and ingest tests use the mock only, so no test can reach a network. Rules, each covered by a test of the implementation:
   - URL: scheme `https` only, no user info, port empty or 443, host (lower case, trailing dot removed) equal to or ending with `.` plus an entry of `mediaAllowedHostSuffixes` (`[]string{"telnyx.com"}`, assumption A1). `evil-telnyx.com` and `telnyx.com.example.net` must not match. A URL outside the list is skipped without any network call.
   - Dialled address: a `net.Dialer.Control` rejects the connection when the address actually dialled is not a public unicast address: loopback, private (including IPv6 unique local), link local (including the cloud metadata address), unspecified, multicast, `100.64.0.0/10`, `192.0.0.0/24`, `198.18.0.0/15`, documentation ranges, `0.0.0.0/8`, `240.0.0.0/4`, the IPv6 forms that embed an IPv4 address (`::ffff:0:0/96` mapped, NAT64 `64:ff9b::/96` and `64:ff9b:1::/48`, 6to4 `2002::/16`, Teredo `2001::/32`), and site local `fec0::/10`. The check is an explicit prefix list applied after unmapping, not `IsGlobalUnicast`. Because the check runs on the dialled address, a name that resolves to an internal address and a DNS change between check and connect are both refused. `Proxy` is nil (no environment proxy), TLS verification is the default, `InsecureSkipVerify` is never set.
   - Redirects are never followed (`CheckRedirect` returns `http.ErrUseLastResponse`), so a 3xx is a failure (`status`).
   - Request: `GET`, no authorization header, no cookies, `Accept-Encoding: identity`, `DisableKeepAlives`. A response whose `Content-Encoding` is present and not `identity` is a failure (`status`), so the size limit is on the stored bytes.
   - Status: only 200 is accepted; 401 and 403 count as `auth` (assumption A2); other statuses as `status`.
   - Size: a declared `size` over the per file limit skips the file before any request; a `Content-Length` over the limit skips it after the headers; the body is read through `io.LimitReader(limit+1)` and a body that reaches `limit+1` bytes is rejected (a lying or missing length cannot pass). Limits (constants in one place): 2 MiB per file, 5 MiB per message, 10 media per message. A media that would take the total over 5 MiB is skipped (`size`); media after the tenth are ignored (`overflow`). An empty body is a failure (`status`).
   - Time: 20 seconds per file (connect, headers and body), inside the 90 second deadline of the ingest. Files are fetched one after another (keeps memory at one file and the order of `medias` equal to the payload order). Durations are fields of the fetcher so tests inject milliseconds, and so are the allow list and the dialer control (the production control is a package function, the test server on loopback is reached through a test control, and a separate test proves that the production control refuses that same server).
   - Type: `content_type` (parsed with `mime.ParseMediaType`, lower case, parameters dropped) must be in the allow list that gives the stored extension: `image/jpeg` `.jpg`, `image/png` `.png`, `image/gif` `.gif`, `audio/mpeg` `.mp3`, `audio/wav` `audio/x-wav` `audio/wave` `.wav`, `application/pdf` `.pdf`, `text/vcard` `text/x-vcard` `.vcf`; anything else, including a missing type, is skipped before any request (`type`). The stored file name is generated (`media-<index>.<ext>`); a name or path from the sender is never used. The stored extension and content type come from the sender declared value (the response `Content-Type` is not compared, since providers often answer with a generic type). The bytes are never interpreted by any service and are served only through the storage signed URL, which forces a download (`response-content-disposition=attachment`).
   - Logging: the URL and the file names are never logged (the URL may carry a token). Logs carry message id, index, result and size. The one exception is the host name (no path, no query) on results `host`, `auth` and `network`, so that a wrong assumption A1 or A2 can be fixed from the logs.
   - `sha256` of the payload is not verified (TLS to an allow listed host; not a security control here). Trigger to verify it: reports of corrupted attachments.
6. **Concurrency and memory.** The pod runs at most 2 ingests at the same time (constant `inboundMediaMaxIngest`, a buffered channel that is a field of `messageHandler` so tests have their own, taken without blocking). When it is full the message keeps `medias` empty (the attachment is lost, there is no retry) and the result `busy` is counted once for the message; the hook never waits. Memory: one file is held as the body (at most 2 MiB), the JSON request with its base64 form (about 2.7 MiB, plus the marshalled copy), so one ingest peaks at roughly 3 to 4 times the file size, about 8 MiB, and two ingests about 16 MiB. If the real limits of either service are below what the numbers need, the release waits until the limits are raised (the PR body states this as a condition, it does not ship a limit change inside this PR). The container limits are not known: the manifests in the repository show 20 MB for message-manager and 100 MB for storage-manager, but production runs on containers whose limits are not visible here, so the numbers are deliberately small and the release checks the real limits first (decision 10). Trigger to raise the concurrency or the sizes: `busy` or `size` rising while the real limits leave room. The same limits bound the effect of any single event: it can name only allow listed hosts, must target an existing number, and fills at most 5 MiB of storage per message.
7. **Storing and exposing.** For each accepted download `StorageV1FileCreateContent` is called (owner `uuid.Nil`, type `media`, generated name and filename, the content type, RPC timeout 30 seconds but limited by the remaining ingest deadline). The returned ids are appended in order. When at least one was stored, `ingestInboundMedias` writes `medias` with `MessageUpdate` (field `medias`), reads the message and publishes `message_updated` (new `dbUpdateMedias`, same pattern as `dbUpdateTargets`). When nothing was stored there is no write and no event. A storage call that is cancelled by the deadline can still finish in storage-manager; such a file has no message reference and only uses quota (accepted; it needs the deadline and a slow storage at once). GET and the webhook already expose `medias` (P1).
8. **Failure and crash behaviour.** Every failure of one media is isolated and counted. A storage-manager without the new route (older image) fails each media with result `storage` and the text is kept (the rollout order avoids it). A pod that stops during the ingest leaves the message as type `mms` with fewer or no medias (same limit as the MMS dispatch of P1; the ingest is not awaited at shutdown). Provider retries of the same webhook still create a duplicate message as for SMS today.
9. **Observability.** Counter `message_manager_inbound_media_total{result}` with the closed set `stored`, `parse`, `type`, `host`, `size`, `auth`, `status`, `network`, `timeout`, `storage`, `overflow`, `busy`. The label never carries a URL or name. Trigger to act: `host` or `auth` rising means A1 or A2 is false; `storage` rising means storage-manager or the quota.
10. **Rollout.** Before the release the real memory and CPU limits of the message-manager and storage-manager containers are checked against decision 6 (the PR body asks for it; a download with TLS and base64 coding needs more than the 10m CPU of the repository manifest). Deploy bin-storage-manager first (new route, additive), then bin-message-manager. After the release a real inbound MMS to a number of the operator is received once and the result is read from the counters (`stored`, `host`, `auth`) and from `medias`; the assumptions A1 to A3 are not verified until then, and the PR body and the customer documentation describe the behaviour without promising that every carrier or provider setting delivers media. Rolling storage-manager back later only degrades media storing (`storage`), never the message. No migration. An older message-manager with a newer storage-manager is unchanged.
11. **Not done (proposals only).** (a) Passing inbound attachments to conversation-manager (it needs a follow up that handles `message_updated` or reads the message, and a conversation media model that can carry a file id). Until then an MMS reaches a flow or agent as a text only message, and an MMS without text starts the flow with an empty text. (b) Deleting stored files when a message is deleted. (c) Duplicate suppression of provider retries. (d) A recovery job for interrupted ingests. (e) Verifying `sha256`.
12. **Billing.** Unchanged code; inbound `mms` is charged per target at creation at the MMS rate (provisional constant). A message typed `mms` is charged even when none of its media could be stored, because the charge happens at creation, the same as an inbound SMS.
13. **Logging of the hook.** The webhook body reaches the logs in four places that would carry the media URLs: `hookTelnyx` (`hook_message` field, the raw body in the unmarshal error text), `listenhandler/hooks.go` (the whole request as a field, `m.Data` when the request cannot be decoded), and `listenhandler/main.go` (`data: %s` on an unknown route and on a failed request). They are reduced to the event type and the ids, the body is dropped from the error text, and in `listenhandler/main.go` the logger of `processRequest` is created with the whole request as the field `request` (`m` with its `Data`), which every line of that function carries (`Received request`, the unknown route line, the failed request line). For the hooks URI the field is built from a copy of the request with `Data` cleared (a small helper `loggableRequest`), and the two `data: %s` arguments log the data length instead of the data. The failed request line is not reached for hooks today (`processV1HooksPost` returns no error), so that change is defensive. A test drives `processRequest` itself with a hooks request carrying a media URL, for a succeeding and a failing `Hook`, captures the log output and asserts that no URL appears; a second test covers `hookTelnyx` directly.
