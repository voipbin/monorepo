# VOIP-1559 PR1: PUT /ais/{id} omitted engine_key keeps the stored key, add has_engine_key

## 1. Current behavior
- engine_key is returned in REST responses: bin-ai-manager/models/ai/webhook.go (`EngineKey` copied in `ConvertWebhookMessage`).
- ai_* events are already masked: `publishAIEvent` (pkg/aihandler/publish_event.go) strips the copy.
- PUT replaces the key: `Update` writes `FieldEngineKey` unconditionally (db.go buildUpdateFields). `V1DataAIsIDPut.EngineKey` is `string,omitempty`, so omitted and "" are merged on the wire.
- This change is additive: clients can stop sending the key back, and a flag tells whether a key is held. The key stays in the response here; removing it is a separate, later change.

## 2. Contract
PUT `engine_key`: omitted = keep stored key, "" = delete, value = replace. Same meaning as `engine_base_key` (`decideEndpointWrite`).
POST keeps `engine_key` required. The PUT schema drops it from `required`.

## 3. Server rule (one function, `ai.MergeEngineKey` in models/ai/engine_key.go)
Input: stored AI, new model, `*string`. Output: `*string` (nil = do not write the column).
1. non-nil: write that value (empty clears).
2. nil and service prefix (text before the first dot of engine_model) differs from the stored one and the new model is not platform: write "" (no carry-over to another vendor).
3. otherwise nil (keep; also when the prefix changes to a platform model).
Prefix edge cases: no dot = whole string; case-sensitive; an empty new model is treated as the stored one (keep; defensive, ai-control's Update already rejects an empty model through ValidateEngine). `engine_key: null` reads as omitted (generated `*string`, same as `engine_base_key`). Invariant (tested over `CatalogView()`): no service prefix has both a platform and a non-platform entry. Platform prefixes (anthropic, meta, deepseek, qwen, mistral, local) are disjoint from key prefixes (openai, gemini, grok, openrouter, customendpoint), so a kept key can only follow a platform model to a same-prefix platform model, and any move to another prefix with a non-platform model clears it (openai -> anthropic.x keeps K; anthropic.x -> openrouter.a/b or openai.* clears it).
Platform = exact `CatalogView()` entry with `key_mode == platform` (local models by current registration). Anything else (customendpoint.*, unknown) is non-platform. `ResolveEngine.BlankKey` is not used.
Final key for validation = value written, or the stored key when nil. `ValidateEngine(model, finalKey, changed)` runs on it, so an omitted-key PUT of an `openrouter.*` model passes when a key is stored and fails with ENGINE_KEY_REQUIRED when not.
`buildUpdateFields` receives the `*string` and adds `FieldEngineKey` only when non-nil. The keep path never writes the column, so a concurrent key change cannot be overwritten with the pre-read value. All three branches of `Update` (promptChanged, promptCleared, default via dbUpdate) use the same value.
Cache: `AIGet` reads Redis first; `AIUpdate` refreshes it (ignoring refresh errors), so the merged validation sees the last committed key in practice. A concurrent key delete between the read and the validation (or a failed cache refresh) can let an `openrouter.*` PUT validate against a key that was just deleted; the column is not written, so the result is the already-intended deletion and nothing stale is written (accepted).

Accepted limit: Update's read and write are not one transaction, so two concurrent PUTs (one omitting the key, one replacing it with another vendor's key) can leave the new key under the old prefix. Both values are the customer's own; a conditional write is out of scope. Docs also state that moving to a model with another prefix clears a kept key.

## 4. has_engine_key
`WebhookMessage.HasEngineKey bool json:"has_engine_key"` (no omitempty), true when a key is held.
Event paths: `ai.AI` gets `HasEngineKey bool json:"has_engine_key,omitempty" db:"-"` (a transport hint, never stored). `publishAIEvent` sets it from the real key on the copy before clearing `EngineKey`. `ConvertWebhookMessage` returns `EngineKey != "" || HasEngineKey`. Result: REST (key present), webhook (CreateWebhookEvent converts the copy), event bus consumers all agree. Two consumer paths: (1) websocket: ai-manager's converted webhook payload is forwarded as is by webhook-manager and bin-api-manager subscribehandler/webhookmanager.go (no re-conversion); (2) timeline aggregation: bin-api-manager servicehandler/aggregated_events.go:183 unmarshals the stored event JSON into amai.AI and calls ConvertWebhookMessage again. No plaintext reaches the converted output of masked events. `engine_key` json of ai.AI is unchanged (pipecat-manager keeps reading it by RPC).
`has_engine_key` concerns `engine_key` only (not `engine_base_key`); it is also true for a platform model that still holds a kept key (the key is not used at runtime; only an explicit "" deletes it, and docs say so). It is true for a whitespace-only key too (it reports a stored non-empty value; ValidateEngine's TrimSpace is a request check). Limit: events published before this PR carry neither the key nor the hint, so a replayed old event reads false (events from before the masking carry the plaintext key and read true).

## 6. Impact analysis (no DB schema change)
No migration. Wire compatibility: new ai-manager reading old api-manager: the old one omits "" (omitempty), so no data loss, but key deletion through api-manager is impossible until api-manager is deployed. Serialization point: bin-common-handler requesthandler.AIV1AIUpdate builds `V1DataAIsIDPut` (now `*string`, omitempty drops only nil). An old api-manager marshals the old `string` with omitempty, so an explicit "" from a client becomes omitted (keep) during the transition. Old ai-manager with new api-manager: omission is read as "" and overwrites the key, so the order is fixed: ai-manager first, api-manager second. Rollback is the reverse: api-manager first, then ai-manager (an old ai-manager with a new api-manager overwrites the key on every omitted PUT).
