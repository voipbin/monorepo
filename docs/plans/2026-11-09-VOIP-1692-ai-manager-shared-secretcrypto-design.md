# VOIP-1692 bin-ai-manager uses the shared secretcrypto

Base: origin/main cba1fa69f. Scope: replace the own `SecretCrypto` of `bin-ai-manager/pkg/mcpserverhandler/secret.go` by `bin-common-handler/pkg/secretcrypto`, so the repository has one encryption implementation. No stored layout, env name, or schema changes.

## 1. Review of the claims (checked against the code)

Result: valid. Each claim was checked in the code; the byte equivalence was also run with a throwaway test (both implementations side by side, deleted afterwards).

## 3. Design

- `mcpserverhandler/secret.go` keeps three package functions and loses the `SecretCrypto` type:
  - `NewSecretCrypto(raw string) (*secretcrypto.Crypto, error)`: a list whose entries are all blank becomes `secretcrypto.New("")`, anything else `secretcrypto.New(raw)`. Same approach as `bin-number-manager/pkg/providerhandler/secret.go`. The doc comment states why: a list of only blank entries means no key. The copy is about 10 lines in two services, so it is not promoted to a `secretcrypto` option (that would add verification load on every consumer of `bin-common-handler`). The name stays so the four constructors and the tests change little. No `WithMaxPlaintext`: the old code had no limit.
  - `EncryptSecret(c, plaintext) (ciphertext, nonce []byte, version int, err error)`: `c.Encrypt` then `SplitBlob`.
  - `DecryptSecret(c, ciphertext, nonce, version) (string, error)`: `JoinSplit` then `c.Decrypt`; an `ErrMalformed` from `JoinSplit` is returned as is.
  `DecryptSecret` calls `JoinSplit` before `Decrypt`, so a malformed row read with no key configured returns `ErrMalformed` instead of `ErrKeyNotConfigured`; no caller compares the error type (checked). Comments that name the old type or the old parser behavior are updated: `cmd/ai-manager/main.go:155-156` (the fixed log text stays as a defensive choice, the reason is rewritten), `mcptoolhandler/client.go:65`, `mcpserverhandler/main.go`, `mcptoolhandler/main.go`, `mcpoauthhandler/main.go`.
  The two column layout is shared by `mcpserverhandler`, `mcptoolhandler`, `mcpoauthhandler`; the last two already import `mcpserverhandler`, so the helper lives there (no new package, no change to `bin-common-handler`).
- The engine base key keeps its own file: `aihandler/engine_base_key.go` holds `*secretcrypto.Crypto`; `sealEngineBaseKey` is `c.Encrypt` + `PackVersioned`, `openEngineBaseKey` is `UnpackVersioned` + `c.Decrypt`. The local packed-length constants and the manual byte handling are removed (orphaned by this change). Error values `errEngineBaseKey*` and the log text stay; `ErrMalformed` from `PackVersioned` maps to `errEngineBaseKeyBadVersion`, an unpack error to `errEngineBaseKeyBadCiphertext`, any `Decrypt` error to the existing "could not decrypt ... (version N)" text with the version taken from `UnpackVersioned`.
- Types: `crypto *secretcrypto.Crypto` in `mcpServerHandler`, `mcpToolHandler`, `mcpOAuthHandler`, `aiHandler` and `NewAIHandler`. Constructor signatures with a key string are unchanged, so `cmd/ai-manager` and all mocks are unchanged except the `engineBaseKeyCrypto` type.
- Call sites: `h.crypto.Encrypt(x)` becomes `mcpserverhandler.EncryptSecret(h.crypto, x)` (or `EncryptSecret` inside the package), `h.crypto.Decrypt(ct, n, v)` becomes `DecryptSecret(h.crypto, ct, n, v)`: `handler.go` (2), `access_token.go` (4), `complete.go` (2), `client.go` (2), `carrier.go` (1).
- The old `secret.go` type, `secret_test.go`, `secret_coverage_test.go` are deleted after the replacement tests exist; the doc comment of `models/mcpserver/main.go:92` and `bin-ai-manager/docs/domain.md` wording are updated; the shared library CLAUDE.md package table is unchanged (still true).

## 4. Stored rows and rolling deploy

- Layout is unchanged: `ai_mcp_servers` keeps ciphertext and nonce in two columns and `key_version`; `ai_ais.engine_base_key_enc` keeps `version(2B BE)||nonce||ct`. The shared adapters map them without a byte change, so no re-encryption and no migration is needed. Basis: Seal output is identical (section 1), proven by the frozen vectors below, and the adapters only concatenate or slice.
- Rolling: a new instance reads rows written by an old one and the reverse, in both layouts, with both versions in the list (vectors below). No schema change, no env change. A new value never exceeds what the old code reads (nonce 12, version <= 65535 for the engine key).
- Deploy order risk: none found, because old and new instances read each other's values. The one operational change is that the list `","` stays accepted, a malformed list still stops the start in both.

### Order (test first)

The type switch cannot be split: once `secret.go` loses `SecretCrypto`, every test file that still builds or calls it fails to compile in five packages (`mcpserverhandler`, `mcptoolhandler`, `mcpoauthhandler`, `aihandler`, `aicallhandler`). So the plan has one atomic switch and puts the real RED before it, on the current code, using only the old API:

1. Vectors (characterization, GREEN on the old code): freeze the vectors (below) in a test that decrypts them with the old API in `mcpserverhandler` and `aihandler`. Run `go test` of both packages.
2. Behavior tests that fail on the old code (a genuine RED on the current code): (i) a malformed key list returns an error that does not contain a sentinel put into the input, tested at the three constructors (old code quotes the entry); (ii) `buildAuthHeader` (bearer and api_key) and `GetValidAccessToken` (access token and refresh token paths) with both secret columns empty return an error (old code panics, tested with a recover that fails the test; the carrier closure returns before decrypting on an empty ciphertext, so it is not part of this); (iii) `openEngineBaseKey` on a stored version 0 returns `errEngineBaseKeyBadCiphertext` (old returns the decrypt text). Run `go test` of the four packages (`aihandler`, `mcpserverhandler`, `mcptoolhandler`, `mcpoauthhandler`): these fail, everything else passes.
3. Atomic switch: `secret.go`, `engine_base_key.go`, call sites, field types, and in the same step the mechanical change of all test files and helpers and the deletion of `secret_test.go`/`secret_coverage_test.go`; the vector test is ported to `DecryptSecret`/`sealEngineBaseKey`/`openEngineBaseKey` with the same constants and gets the new-to-old direction; add the adapter tests (verify items 2 and 3). Only `go build ./...` is required to pass while editing; then `go test ./...` of `bin-ai-manager` must be GREEN, including the step 2 tests. ### Fixed vectors

- Deterministic, so anyone can recompute them: standard library `gcm.Seal(nil, nonce, plaintext, nil)` with a fixed nonce (`00 01 02 ... 0b`), key version 1 = 32 bytes of `0x01`, key version 2 = 32 bytes of `0x02`, plaintext `fake-secret-1` (version 1) and `fake-secret-2` (version 2). The inputs are written in a comment of the test; the old `SecretCrypto.Encrypt` only differs by drawing the nonce at random, so the vectors are the old output format with a fixed nonce. Nothing real; the generator is not committed.
- Vectors: two column layout (ciphertext, nonce) for version 1 and 2; the engine packed value (`version||nonce||ct`, 2 byte big endian prefix) for version 1 and 2; the key list `1:<k1>,2:<k2>` (current version 2).
- Directions: old to new (the constants decrypt through the new code) and new to old (a value from `EncryptSecret` / `sealEngineBaseKey` is opened by a test-local copy of the old logic: `gcm.Open(nil, nonce, ct, nil)` for the columns, manual split of prefix, nonce and ct for the engine value). This test-local function is the only copy of the old logic that stays.
- Relation to `bin-common-handler/pkg/secretcrypto/compat_test.go` (`Test_compatAIManagerMCPLayout`, `Test_compatEngineBaseKeyLayout`): the library test freezes the layouts and the adapter functions; this PR freezes what ai-manager adds on top (`EncryptSecret`, `DecryptSecret`, the engine seal/open mapping, the blank-list rule), so the overlap is the constants' idea, not the code under test.
