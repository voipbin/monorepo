# Production DB migration apply via a one-shot Komodo runner (VOIP-1596)

Status: DRAFT (design only; no implementation, no Komodo change, no production write in this card).
Decision input (CEO, 2026-10-14): automate the production apply with a one-shot runner inside Komodo, not with CI reaching the database. Phase 1: a human approves in Komodo and the runner applies. Phase 2, after it is stable: automatic. Destructive migrations are excluded from automatic apply.

## 2. Goal and non-goals

Goal: after a migration PR is merged, the schema can be applied to production without a human opening a VPN session, with a backup, a single-writer guarantee, loud failure and a machine-checkable result.

Non-goals: ClickHouse migrations of timeline-manager and rag-manager (they self-migrate at service start); downgrade of any kind (human only, 8); destructive migrations (refused by the runner, 4.7); any Komodo or production change in this card; a global on/off flag (the phase switch is a CI workflow edit, 4.2).

## 3. Options considered (runner shape)

| option | where it runs | verdict |
| --- | --- | --- |
| Komodo Action (TypeScript) | inside Komodo Core | rejected: Core is on `komodo_default`, no route to `production`/`db`, no docker; the script lives in Komodo state, not git (0 Resource Syncs) |
| Komodo Procedure only | n/a | cannot run code; it is the approval and permission unit (4.2) |
| Stock python image plus a git checkout through a Komodo Repo | periphery on the production host | rejected: `pip install` at apply time, a git token in Komodo, a moving branch as revision |
| One-shot compose service of a dedicated Stack (`RunStackService` = `docker compose run --rm`) with an image built by CircleCI, wrapped by Procedures (chosen) | periphery on the production host, network `production` | immutable image per commit, same pattern as 31 services, orchestration in git, secrets from Komodo Variables, result in an Update log |
| Run alembic from a laptop | VPN | today's manual path; kept as fallback (8) |

## 4. Design

### 4.1 Components

- Image `voipbin/bin-dbscheme-manager:<git sha>`: `python:3.11-slim` (as `migration-lint`), pinned `alembic`, `sqlalchemy<2.0`, `pymysql` (requirements with hashes, installed with `--require-hashes`), Debian `mariadb-client` (same source as bin-schedule-manager), both alembic trees, `runner.py`. Built by the existing `docker-build` command on `main` only from a new `bin-dbscheme-manager/Dockerfile`. `migration-lint` is moved to the same pinned versions so CI and runner classify identically.
- Komodo Stack `bin-dbscheme-manager`, `file_contents` from `bin-dbscheme-manager/komodo/docker-compose.yml`, one service `migrate`: fixed entrypoint `python /app/runner.py`; env `DBSCHEME_DB_HOST=db`, `DBSCHEME_DB_PORT=3306`, `DBSCHEME_DB_USER=dbscheme_migrator`, `DBSCHEME_DB_PASSWORD=[[DBSCHEME__MIGRATOR_PASSWORD]]`, `DBSCHEME_IMAGE_TAG=__IMAGE_TAG__`; bind mount `<backup-root>/dbscheme:/backups`; network `production` external; `restart: "no"`; no ports; hardening `read_only: true` (plus a tmpfs for `/tmp`), `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, non-root `user` that owns `/backups`. The stack is never deployed (`up`); each run is `docker compose run --rm` and leaves no container.
- Two Komodo Procedures, created from git (`bin-dbscheme-manager/komodo/*.json`) by an idempotent bootstrap in the CI stage script, each with a single stage and a single `RunStackService` execution (executions inside a stage run in parallel; two stages would leave a window in which the stack can change between them): `dbscheme-check` (command `check`) and `dbscheme-apply` (command `apply`, which repeats every `check` step and the classification itself before the first statement). Both use `pull: true`, `no_tty`, `no_deps`. Splitting them lets Execute be granted separately: QA and CI may run `check`; `apply` is held by humans (phase 1) and, in phase 2, by the CI identity.
- Runner wiring: the image bakes the alembic trees and `alembic.ini` (placeholder URL). `runner.py` reads `DBSCHEME_DB_PASSWORD`, removes it from `os.environ` before alembic loads any revision module (alembic imports every module of the chain, so module-level code of a revision would otherwise see the secret), builds the URL in memory (`mysql+pymysql://`, `%` escaped for configparser), and injects it with `config.set_main_option`. Session settings (`lock_wait_timeout`, `innodb_lock_wait_timeout`, fixed `sql_mode`) are passed as `init_command` URL query parameters. The runtime hook (4.7) is a class-level `event.listen(Engine, ...)` listener, which needs no change to the two `env.py` files (they create their own engine); this is safe because every query of the runner itself (grants, locks, processlist, `KILL QUERY`) uses raw `pymysql` connections and so SQLAlchemy only ever carries migration traffic. The runner applies the pending revisions one at a time (`command.upgrade(cfg, <rev>)` per revision, which re-runs `env.py` and opens a new connection each time), and a `connect` listener records the latest server thread id for the watcher. SQLAlchemy 1.4 hides the password in `str(url)`; the URL handed to `set_main_option` is rendered with `render_as_string(hide_password=False)` and `%` doubled. `env.py` calls `fileConfig()` with `disable_existing_loggers` on, which disables the runner's named loggers after every `command.upgrade` (measured), so the runner re-enables its loggers (`logger.disabled = False`) after each revision step. Neither tracebacks nor exception strings are written to stderr (an SQLAlchemy exception message contains `[SQL: ...]`, and the Komodo Update keeps stderr): only the exception class and the revision id are logged. `PYTHONDONTWRITEBYTECODE=1` and a `.dockerignore` keep `__pycache__` out; `umask 077` makes backups 0600 in a 0700 directory; the compose service sets `init: true` and `stop_grace_period: 6m` (the default 10 s is shorter than the 5 minute kill confirmation of 4.5) and the runner handles SIGTERM like a timeout, which PR 1b tests with a real `docker stop`. The base image is pinned by tag and digest (the floating `python:3.11-slim` already moved from bookworm to trixie, which changes the `mariadb-client` major version). Alembic's stdout is redirected to stderr so a `print` in a revision cannot pollute the result line.
- CI, `bin-dbscheme-manager` workflow: `migration-lint` (all branches, unchanged plus the classifier step) then on `main` `bin-dbscheme-manager-build` then `bin-dbscheme-manager-stage`. The stage job (`serial-group`, plus the stale-commit guard of `komodo-api-deploy.sh`: it refuses to pin a sha that is not a descendant of the sha currently pinned) renders the tag, updates the stack (`UpdateStack`), upserts the Procedures, runs `RunProcedure dbscheme-check`, polls `GetUpdate` (a new `komodo-api-run.sh`, bats-tested, modeled on `komodo-api-deploy.sh`) and judges the result line (4.3). Komodo rejects `UpdateStack` while a run on the stack is busy (its message is "stack busy"; the job decides on state, not on the message text); the job then waits (poll `ListUpdates`, up to 45 minutes) and fails if the run is still going; a later merge pins again anyway. Like `komodo-api-deploy.sh`, it prints only the result line and the Update id to the CI log, never the full Komodo log or error body (an error body can contain an interpolated secret). It replaces `migration-applied-checkpoint`.

### 4.2 Trigger, approval and what the approval means

Phase 1: after a merge the stage job pins the stack to the merge commit and posts the `check` result (pending revisions and class). The maintainer (CEO) runs Procedure `dbscheme-apply` in the Komodo UI; QA runs `dbscheme-check` and verifies the evidence but does not run `apply` in phase 1 (the root CLAUDE.md requires human confirmation for DB migrations). Phase 2 changes who triggers it, so the PR that introduces phase 2 also amends the "never run alembic upgrade" wording in the root `CLAUDE.md` and `bin-dbscheme-manager/CLAUDE.md`, which currently forbid agents from applying to production. The Update records operator, time and log.

Approval semantics, stated exactly: the click authorizes "apply every pending additive revision of the image pinned when `dbscheme-apply` starts" (one stage, one execution, so nothing can change between check and apply inside the run). The runner shows the range it applied (`*_from`, `*_to`) in the result line. A merge that lands between reading the `check` and clicking can add more revisions to that range; all of them were merged after QA verification (and maintainer confirmation for migration PRs), and only additive ones are applied, so the accepted residual is "a later additive revision is applied earlier than the clicker looked". Komodo's busy state stops a re-pin during a run, the stage job's stale guard stops an older sha from replacing a newer pin, and the runner's `db_ahead` check stops an image older than the DB.

What the approval does not control: the CI identity has broad Komodo rights today (F4) and a stack write is the right to choose what runs with the migrator secret (F6). In phase 1 the click therefore protects against mistakes (wrong time, unreviewed range, an unattended apply), not against a hostile CI. This is stated as risk R2/R3 in section 7 and is the reason for prerequisite P1 below.

Phase 2: a CI job `bin-dbscheme-manager-apply` (main only, `serial-group`, after `stage`) calls `RunProcedure dbscheme-apply` in place of the human. The runner does not change between phases. Entry criteria (signals, not a date): at least 5 phase 1 applies of non-empty ranges with matching result lines; no `dirty`, `verify_mismatch` or `statement_not_allowed` event and no post-apply finding by QA within 7 days of each apply; zero cases where the printed class is `additive` while QA judged the PR destructive (cases where the class is `needs_human` and QA judged it harmless are counted separately as a classifier improvement signal, not as a failure); the classifier mutation and fuzz tests of PR 1a pass in CI (they, not the 5 applies, are the evidence against false negatives, because the applies are additive by construction), and at least one `needs_human` block has been observed in production or in the scratch run; a Komodo Alerter exists; the CEO signs off; prerequisite P1 is decided. It is a workflow edit in a PR, not a runtime flag.

Prerequisite P1 (recommended before phase 2, owner CEO): replace the broad CI identity for this workflow with a non-admin Komodo service user. Source shows what it needs: `UpdateStack` needs Write on the stack, creating or editing a Procedure needs Execute on every resource it references (`resource/procedure.rs`), `GetUpdate` needs Read on the target (`api/read/update.rs`). So a realistic P1 grants Write on stack `bin-dbscheme-manager` and the two Procedures and Read for updates; Write on the stack is the right to choose what runs under the migrator secret. P1 therefore shrinks the blast radius from all of Komodo to the migrator secret and these two Procedures, but CI still decides what runs there. Without P1, phase 2 removes the last human step while CI keeps broad rights.

### 4.3 Runner contract (`runner.py`, modes `check` and `apply`; there is no downgrade mode)

Both modes end with exactly one last stdout line; everything else (alembic logging, migration `print`) goes to stderr:

```
DBSCHEME_RESULT v=1 mode=<check|apply> status=<S> reason=<R> image=<tag> bm_from=<rev|none|unknown> bm_to=<rev|none|unknown> bm_head=<rev|unknown> ast_from=<...> ast_to=<...> ast_head=<...> pending=<n|unknown> applied=<n> class=<additive|needs_human|na|unknown> blocked=<id,id|none|unknown> backup=<bm:<name>,ast:<name>|none|failed>
```

Grammar: `key=value` pairs separated by single spaces, values match `[A-Za-z0-9_.,:-]+`. `*_from` is the revision before the run, `*_to` the revision after it (in `check`, `*_to` equals the current revision); `none` means an empty database, `unknown` means the value could not be determined because the run stopped early (then `*_head` comes from the image). `pending` is the count before the run, `applied` the count applied by it (0 in `check`), so "applied" and "nothing to do" differ. `blocked` lists the revisions that make the range `needs_human` (not the whole pending list). Any key may be `unknown` when the run stopped before it could be computed; an error before classification prints `pending=unknown applied=0 class=unknown blocked=unknown`. `class`, `pending`, `blocked` merge both streams: one `needs_human` revision in either stream blocks both (intentional: the order across the two databases is not guaranteed independent). `check` is short-circuit in the order of 4.6, so exactly one reason is reported, the first failing step; within the classification step the reason reported for a mixed range is the first by the priority `data_dependent`, `not_renderable`, `unparsable`, `destructive` over the whole range, and `blocked=` lists every blocking revision; `apply` runs the same steps in the same order, with `GET_LOCK` in place of `IS_FREE_LOCK`. `class` is `na` when nothing is pending, `additive` for `pending` in `check`, after a successful apply of a non-empty range, and on any failure after the classification passed; `unknown` on a failure before it. On `multiple_heads` the head fields are replaced by `heads=<id,id>`. Closed status and reason sets:

| status | reasons | exit |
| --- | --- | --- |
| `ok` | `none` | 0 |
| `pending` (check only) | `none` | 0 |
| `needs_human` | `data_dependent` (source gate), `not_renderable`, `unparsable`, `destructive` (checked in this order) | 3 |
| `dirty` | `previous_run_incomplete`, `ddl_running` | 4 |
| `busy` | `locked` | 5 |
| `error` | `secret_empty`, `db_unreachable`, `login_as_root`, `grants_mismatch`, `schema_mismatch`, `db_ahead`, `multiple_heads`, `schema_objects_present`, `backup_dir`, `backup_failed`, `marker_write_failed`, `marker_delete_failed`, `statement_not_allowed`, `apply_failed`, `verify_mismatch`, `lock_lost`, `timeout`, `tool_missing`, `internal_error` | 1 |

Mapping of the remaining paths: disk space too low or directory not writable is `backup_dir`; session settings or `alembic_version` unreadable or empty is `schema_mismatch`, as is a connected schema that differs from the expected one; an unhandled exception is `internal_error`. Every exit path runs inside `try/finally` so that exactly one line is printed.

Judging rule (runner scripts, `komodo-api-run.sh`, QA): read only the stdout of the `Compose Run` log of the stack's `RunStackService` Update (the pull log and stderr are separate). Success requires exactly one `DBSCHEME_RESULT` line there, and for `apply` `status=ok`; for `check` `status` is `ok` or `pending`. `needs_human` is not a success: the Komodo Update fails with exit 3 and CI turns the stage job red with the message "ACTION REQUIRED, human path (section 8)", which is intended because a destructive revision has been merged. `dirty`, `busy`, `error` are plain failures. No result line means failure; this covers failures before the runner exists: a missing Komodo Variable (Core interpolation error), "Resource is busy", an image pull failure, an OOM kill (exit 137).

Linking a Procedure run to the stack Update that holds the stdout: the Procedure Update only contains stage summaries and no child Update id (the id appears only in a failure message). The rule is: target stack `bin-dbscheme-manager`, operation `RunStackService`, `start_ts` at or after the Procedure start, the newest one; the line's `mode` and `image` must match the expected mode and the tag the stage job pinned. QA applies the same rule and additionally checks that the `image` commit contains the migration (`git merge-base --is-ancestor <merge commit> <image>`), so an old result cannot pass for a new revision.

The line never contains the DSN, password, SQL text or row data.

### 4.4 Credentials

- One DB account `dbscheme_migrator@'<production-network-pattern>'` (created by a human, SQL in section 10), generated 32 character alphanumeric password, stored only as Komodo Variable `DBSCHEME__MIGRATOR_PASSWORD` (`is_secret`). Host, port and schema names are plain compose values; no DSN string is stored, so there is no URL quoting issue and no confusion with the Go DSN format of the existing variables (the format mismatch cost VOIP-1246 a review round). `runner.py` builds the SQLAlchemy URL in memory with `URL.create`.
- Grants (measured on a scratch MariaDB 12.3.3): schema level `SELECT, CREATE, ALTER, INDEX, SHOW VIEW` on `bin_manager.*` and `asterisk.*`; table level `INSERT, UPDATE` only on each schema's `alembic_version` (there is no downgrade mode, so no `DELETE`; PR 1b confirms on the scratch server that an upgrade on an empty database and on a populated one needs nothing more). `SELECT` and `SHOW VIEW` are enough for `mariadb-dump --single-transaction --skip-triggers`. With these grants the database refuses `DROP TABLE`, `TRUNCATE`, data `DELETE`/`INSERT`/`UPDATE`, `SUPER`, `GRANT`, `FILE`, anything on `mysql.*`. It does not refuse `ALTER TABLE ... DROP COLUMN`, `MODIFY`, `CHANGE`, `DROP INDEX` (ALTER covers them): column-level destruction is stopped only by the classifier (4.7), its runtime hook and review. That is residual R1 and the doc does not claim more.
- No FK is created by the runner (a `REFERENCES` clause is `needs_human`), so `REFERENCES` is not granted.
- Two databases, one account, schema-scoped grants, two sequential alembic streams. A second account would live in the same runner and add no isolation. Each stream asserts that the connected schema equals the expected one before any statement.
- The host pattern covers the whole `production` docker network (every service container and the host gateway). It limits origin to that network, not to the runner.
- Rotation: new password on the DB account (human), then `UpdateVariableValue`; no service restarts because only the one-shot runner reads it. Rotate on staff change, suspected exposure, yearly. Revoke: `DROP USER` and delete the Variable.
- Masking: Komodo replaces secret Variable values in Update logs. The runner additionally prints no URL, no password, no SQL bodies. `check` fails (`login_as_root`) if `CURRENT_USER()` is `root`, which catches a wrong variable wiring. The Variable must be created with `is_secret` (H2): Komodo prints the values of ordinary Variables in the interpolation log and only the names of secret ones.

### 4.5 Backup, concurrency, failure and partial state

- Order invariant of an `apply` run: the environment steps of 4.6, in exactly the order listed there, first, then acquire the advisory lock, then read the marker (so a wrongly mounted empty directory is detected before the marker is trusted), then classification, backup, write the marker, run the migrations one revision at a time, verify, delete the marker, release the lock last. With `pending=0` nothing is backed up and no marker is written. Only the lock holder creates or deletes the marker, so "marker plus lock held" cannot be confused with "marker plus lock free". The lock connection needs no keepalive (`wait_timeout` is 28800).
- Single writer, two layers. (1) Komodo rejects a second run on the same stack ("Resource is busy"); that state is Core memory only. (2) The runner takes `GET_LOCK('dbscheme_apply', 0)` on a dedicated DB connection held for the whole run (no privilege needed); failing to get it returns `busy locked`. `check` uses `IS_FREE_LOCK` and never takes the lock, so it cannot make a concurrent `apply` fail. A human running alembic by hand can take the same lock (8) but is not forced to.
- Marker: before the first statement `apply` writes `/backups/APPLY_IN_PROGRESS` (range and image), `fsync`s it and the directory; failing to do so aborts before any DDL (`marker_write_failed`, fail closed). Marker with the lock free means an aborted run: `dirty previous_run_incomplete`, or `dirty ddl_running` if the processlist still shows a running statement of the migrator account (a DDL keeps running on the server when its client disappears; measured on MariaDB 12.3: a 30 second `ALTER ... ALGORITHM=COPY` continued after the client socket was cut). Between revisions and before deleting the marker the runner checks `IS_USED_LOCK('dbscheme_apply')` equals its own lock connection id; otherwise it keeps the marker and reports `lock_lost`; a failed delete is `marker_delete_failed`. No automatic retry, no automatic downgrade.
- Automatic marker clean-up has one narrow case, so that a metadata-lock timeout on the first DDL needs no manual SSH: all of these hold at once: the failing statement was answered with server error 1205 or 1213, the connection is alive, the processlist shows no statement of the account, the count of successfully executed non-bookkeeping statements over both streams (counted in `after_cursor_execute`, which fires only on success) is 0, and every stream's revision equals the marker's `from`. Then the runner deletes the marker and reports `apply_failed`. In every other case, including a lost connection or a timeout (server-side outcome unknown), the marker stays for a human.
- Timeout and every failure path: the connection id of the migration connection is recorded without SQL, from the `connect` event (`dbapi_conn.thread_id()`). A 30 minute limit, SIGTERM or any exception makes a watcher connection (raw `pymysql`) run `KILL QUERY <thread_id>` (the same account may kill its own threads, measured) and confirm in the processlist (excluding the watcher, the lock connection and `Sleep` rows) that the statement ended, waiting at most 5 minutes; then it prints the result line and releases the lock last. If the statement cannot be confirmed ended the result is `dirty ddl_running`. Closing the client connection alone is not enough (above).
- Mount check: the directory `<backup-root>/dbscheme` is created by a human with a sentinel file `.dbscheme-ok` (H3). The compose bind mount uses the long syntax with `create_host_path: false` so Docker does not silently create an empty root directory on a mistyped path, and `check` fails (`backup_dir`) if the sentinel is missing.
- Backup: `apply` does it itself, only when `pending > 0`, so a different trigger cannot skip it. `mariadb-dump --single-transaction --skip-triggers <schema>` per schema, without `--databases` (the dump then contains no `CREATE DATABASE` or `USE`, like the nightly dump). `SELECT` and `SHOW VIEW` suffice; `--routines` and `--events` are not used because the schemas have none, which `check` asserts (`schema_objects_present`). The password goes through a 0600 defaults file in the tmpfs `/tmp` (never argv). The pipeline `mariadb-dump | gzip` checks both exit codes (`pipefail`). Files: `/backups/<UTC>-<image>-<schema>.sql.gz`, then `gzip -t`, size greater than 0 and the dump trailer present; any failure stops before the first DDL (`backup_failed`). A set is the pair of both schemas from one run; keep the newest 10 sets (the nightly keeps 7 files; these are rarer change-time recovery points). The prune glob matches only `*.sql.gz`, never the marker or sentinel. The two schemas are dumped one after the other, so they are not a single snapshot; this is acceptable because the two streams do not reference each other and the apply has not started. A restore rehearsal is a PR 1b condition; the procedure is in section 8.
- Lock waits: the session sets `lock_wait_timeout=15` and `innodb_lock_wait_timeout=15` (the second lowers the default 50). A DDL blocked by a long transaction fails within 15 s instead of queueing every other query behind it for 24 h; the cost is that queries on that table can wait up to 15 s while the DDL waits. The nightly dump holds shared metadata locks around 02:00; applying outside roughly 01:50 to 02:15 avoids a pointless failure, and a failure there is safe. Fixed `sql_mode` in the session (4.7).
- Failure: on a failing revision the runner stops the stream, does not start the second stream, prints the revision id and the exception class (no SQL), exits non-zero. Order: `bin_manager`, then `asterisk`.

### 4.6 Silent-failure guard and the check mode (lesson of VOIP-1246: find environment errors first)

After apply, `alembic current` must equal `alembic heads` for each stream, read on a fresh connection, otherwise `error verify_mismatch` and the marker stays. The result line is the single success signal (4.3).

`check` changes nothing in the database or in `/backups` (it never creates `alembic_version`, tested on SQLite; apart from a temporary empty file `.probe-<pid>` that is created and removed in `/backups` (any leftover `.probe-*` is deleted at the start of the next `apply`) and never counted by the prune, its `--no-data` dump goes to `/dev/null`) and is harmless in production at any time (its only lock is the short metadata lock of the schema-only dump, bounded by the 15 second `lock_wait_timeout`). It is short-circuit, in this order, each step with its own `reason`: password present and non-empty; connect with the real driver (`pymysql` through the same URL path as `apply`) to `db:3306`; `CURRENT_USER()` is not root; connected schema equals the expected one; `SHOW GRANTS` equals the expected set exactly (the privilege lists are parsed into sets per schema and table before comparing, because MariaDB prints them in its own order and with backticks; the `GRANT USAGE ... IDENTIFIED BY PASSWORD '<hash>'` line is dropped before comparing and no diff is printed); session settings applied; backup directory sentinel present and writable; free space at least the sum of the current database sizes; `mariadb-dump --version` runs and a `--single-transaction --no-data` dump of both schemas succeeds (when a marker exists or the lock is held, the dump is skipped and the result is `busy` or `dirty`, so a concurrent apply is never reported as `backup_failed`) (without `--single-transaction` the dump fails on `LOCK TABLES` with these grants, measured) (a `backup_failed` is found before an approval, not after); routine, trigger, event and view counts are zero; `alembic_version` readable in both schemas; current revisions exist in the baked chain (else `db_ahead`: the image is older than the DB); exactly one head per stream; then, after the sentinel and environment steps above, the concurrency state: read the marker, then `IS_FREE_LOCK`, then read the marker again (a change between the reads, or a held lock, is `busy`; a stable marker with a free lock is `dirty`, and a running statement of the account makes it `ddl_running`); then the full classification of the pending range (4.7), so the classifier path is exercised by the environment test too. `apply` runs the same sequence and differs only in that it takes the lock (`GET_LOCK`) at the concurrency step instead of `IS_FREE_LOCK`. `check` has a 10 minute limit; `apply` 30.

`apply` runs the same sequence itself before the first statement, so it never trusts an earlier `check`.

Evidence for QA and for rule 17(d) of the backend rules: QA reads the Updates with the read API (`ListUpdates` on the stack, then `GetUpdate`; the linking rule is in 4.3; this needs Read on the stack, which CI and QA identities must have). `mode=` tells check and apply Updates apart. `bm_to` and `ast_to` are the schema revisions after the run; QA verifies that they are at or after the migration's revision in the alembic chain (`alembic history` on the repo) and that the `image` commit contains the merge. A human-applied range gets the same evidence from a `dbscheme-check` run afterwards.

### 4.7 Which migrations are applied automatically (QA rule 19 and rule 17 link)

Three layers, all fail closed (unknown is `needs_human`). The runtime replay check (layer 3) is what actually stops a wrong statement; the source gate and the render classification exist so that a revision is refused before the first statement of the range runs, which keeps partial applies rare. They apply to every pending revision (the pending range only, not the already applied part of the chain) and are evaluated on the baked files. Order and reason, one table: source gate rules (`get_bind`, `get_context`, `inspect`, `batch_alter_table`, raw DBAPI, forbidden names, module-level calls) give `data_dependent`; tuple `down_revision`, `depends_on`, a multi-statement `op.execute` and a bind-style `:name` give `unparsable`; an offline render failure gives `not_renderable`; the statement parser gives `unparsable` for anything outside the grammar and `destructive` for a recognised destructive statement. The reported reason for a mixed range follows the priority of 4.3.

1. Source gate (AST allow-list). Module level: only the template's imports (`alembic.op`, `sqlalchemy`, `sqlalchemy.dialects.mysql`, `sqlalchemy.dialects.postgresql` for `ENUM` only (the asterisk template uses it), `__future__`, `typing`), the docstring, assignments of constants (strings, numbers, tuples and lists of constants) and `def`. Alembic imports every module of the chain and runs module-level code, so anything else at module level (a call, `op.execute(...)`, `os`) is `needs_human`; this was reproduced (a module-level `op.execute("DROP TABLE ...")` showed up in the `--sql` render). In `upgrade()` and the module-level functions it can reach: calls of `op.execute`, `op.add_column`, `op.create_table`, `op.create_index` with constant arguments (constants may be held in module-level constants and local variables, star-args of constants allowed), `sa.<Type>`, `sa.Column`, `sa.text`, `mysql.<Type>`, `ENUM`. Anything else, including `get_bind`, `op.get_context`, `op.batch_alter_table`, `inspect`, `Inspector`, `os.environ`/`getenv`, `getattr`, `__import__`, `eval`, `exec`, `op.impl`, aliases of these, a Session, or `.execute` on an object other than `op`, is `needs_human data_dependent`. The gate is default-deny from the first line of code; there is no deny-list variant. The replay check (layer 3) sees only statements that go through SQLAlchemy `before_cursor_execute`, so a statement sent through a raw DBAPI cursor is invisible to it (reproduced: `getattr(op, "get" + "_bind")` inside a `try`/`except` that swallows the offline failure rendered only an additive `ADD COLUMN`, and online dropped a column). The source gate is therefore the only control on that path, and it rejects every call target outside the enumerated names, any call whose target is itself a call or a subscript, `try`, `with`, `getattr`, `setattr`, `eval`, `exec`, `compile`, `__import__`, `vars`, `globals`, `locals`, `op.impl`, and any attribute access beyond the enumerated list. Names are resolved strictly: `op`, `sa`, `mysql` and `ENUM` must come from the template imports and must not be rebound by a `def`, assignment or import anywhere in the module (a same-named `def ENUM(...)` hiding `op.get_bind()` is rejected); every module-level `def` body is checked by the same rules whether or not it is reachable; a `Name` resolves only to a constant the gate tracks (`__file__`, `__builtins__`, `__debug__` are rejected); the source is parsed with `ast.parse(<bytes>)` so gate and runtime decode alike; fixtures: `def ENUM`, `op = 1`, `if __debug__:`, `upgrade` calling `downgrade()`. The AST walk covers default arguments and annotations of module-level functions (they run at import), `down_revision` must be a `str` or `None`, `depends_on` must be `None`, and type arguments are numbers and quoted strings only. This bypass revision is a negative fixture of PR 1a and is covered by the per-rule mutation check. `downgrade()` is out of scope (65 of 131 asterisk revisions use `op.get_context()`; 51 only in `downgrade()`, 14 in `upgrade()` as well). Reason: offline mode returns `None` from `conn.execute(...)`, so a migration that branches on query results renders as a different statement list than it executes (the reviewer built `try: conn.execute(SELECT 1).scalar()` with `DROP TABLE` and `ADD COLUMN` branches and got the additive branch offline).
   Further gate rules: import forms are exactly `from alembic import op`, `import sqlalchemy as sa`, `from sqlalchemy.dialects import mysql` (and `from sqlalchemy.dialects.postgresql import ENUM`); the allowed `sa.`/`mysql.` attribute names are an enumerated list of column types plus `Column`, `text`; node kinds inside `upgrade()` are assignments, expression statements, `for` and `if` over constants, and constant f-strings, `+` and `%` on constants (the corpus has f-string and `for` revisions, e.g. `08d686855c69`; the render is the truth for what they emit); `class`, `lambda`, nested `def`, decorators and comprehensions over non-constants are `needs_human`. After constant folding each `op.execute` argument must be exactly one non-empty statement (split on top-level `;`); two or more are `needs_human` (reproduced: a two-statement string renders as two statements but fails online with error 1064 because pymysql sends it as one). A constant string containing a bind-style `:name` is `needs_human` (offline render turns it into `NULL`, online raises). A revision with a tuple `down_revision` (merge) or a `depends_on` is `needs_human` (reported as `unparsable`, as are a multi-statement `op.execute` and a bind-style `:name`) (none exists in the corpus today; the `<down>:<rev>` render and the single-row bookkeeping assume a linear chain). A module-level `X = sa.Enum(...)` call is `needs_human` and is counted under its own reason in the corpus statistics.
2. Offline render per revision. For each pending revision `<down>:<rev>` runs `alembic upgrade <down>:<rev> --sql`, so statements and revision ids are attributed to one revision (`blocked=` is exact). A render failure is `not_renderable`. The rendered statements are classified by the parser below. The rendered bookkeeping statement must appear exactly once per revision and with exactly that revision's pair, so a bookkeeping-looking statement in a revision body (two occurrences, or a wrong pair) is rejected. Offline render and online execution use the same SQLAlchemy dialect: the baked `alembic.ini`, the offline render and the online URL are all `mariadb+pymysql://` (measured: the `mysql` dialect renders a column named `position` unquoted offline while the online connection to MariaDB quotes it with backticks, which made revision `fbb7766f17bc` fail the replay check), and `migration-lint` renders with the same dialect. Both the render list and the hook use one function `normalize()`, built on the same quote-aware tokenizer as the parser: strip only `-- ` line comments (never inside quotes or backticks; `#` is not stripped, the corpus needs neither), and reject, before comparing, any online statement that contains `/*` outside quotes (so an executable comment present online but not in the render cannot hide in the comparison; a negative test covers it); then remove backticks around simple identifiers (`[A-Za-z0-9_]+`), remove spaces next to parentheses and commas, turn `%%` back into `%` on the online side only (online statements arrive pyformat-escaped: the rendered `'50%'` arrives as `'50%%'` and a rendered `'50%%'` as `'50%%%%'`, measured; applying it to both sides would reject a rendered `%%`), drop trailing `;` characters, replace every tab by four spaces on both sides, inside quotes too (alembic's offline renderer does `replace("\t", "    ")` on the whole statement, so a tab inside `COMMENT 'a<TAB>b'` is four spaces offline and a tab online), then collapse whitespace outside quotes only; a quoted-tab fixture is a positive test of PR 1a. A test pins, over the whole corpus of both streams (render versus a captured online run on a scratch MariaDB 12.3, an acceptance condition of PR 1a), that rendered and captured statements are equal after `normalize()`, including `;;` endings, `--` comments inside `CREATE TABLE` (the six newest corpus `CREATE TABLE` revisions have them) and `%`.
3. Runtime replay check. The runner keeps the normalized rendered statement list of the current step. The hook (`before_cursor_execute`, a class-level listener on `Engine`, see 4.1) requires every executed statement to equal, whitespace-normalized, the next statement of the rendered list, or to be one of the read-only statements alembic itself issues on every run, anchored to the shapes alembic 1.19 and SQLAlchemy 1.4 emit with bound parameters (`SELECT COUNT(*) FROM information_schema.tables WHERE table_schema = %(table_schema)s AND table_name = %(table_name)s`, with `table_schema` equal to the expected schema and `table_name` equal to `alembic_version`, and `SELECT alembic_version.version_num FROM alembic_version`). Any other statement raises before execution (`statement_not_allowed`). Replay against the classified render closes the gap between render and execution, and also makes forged bookkeeping statements impossible, without a second parser. Earlier statements of the same revision may already have run when it rejects; marker and backup cover that. The empty-database `CREATE TABLE alembic_version (version_num VARCHAR(32) NOT NULL, CONSTRAINT alembic_version_pkc PRIMARY KEY (version_num))` is the one statement alembic creates by itself; it is allowed by an anchored regex that is applied after `normalize()` (online it is printed with spaces inside the parentheses) and only on an empty database, which exists in tests only (production has the table), so the rule that no body statement may target `alembic_version` stays intact.

Statement parser specification:
- Session `sql_mode` is fixed by the runner to `STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION` (no `ANSI_QUOTES`, no `NO_BACKSLASH_ESCAPES`), so parser and server agree on quoting; the session charset is fixed to `utf8mb4` in the URL as well. A backslash inside a string literal is `needs_human`.
- The only characters allowed outside quotes and backticks (comments included, so a `--` comment with a non-ASCII character is `needs_human` too; the draft corpus only has such a comment in a revision that the grammar rejects anyway) are printable ASCII, tab, line feed, carriage return and space; anything else (NBSP, full-width space, NUL, `\x01` to `\x08`, `\x0b` to `\x1f`, `\x7f`) is `needs_human` because Python and the server disagree on what whitespace is. Tokenize with awareness of single and double quotes (including doubled `''`), backticks (including doubled) and `--` comments (a comment starts with `--` followed by whitespace or a control character, or `#`). Any `/*` outside quotes is `needs_human unparsable`: MariaDB executes `/*M! ... */` and `/*!50000 ... */` bodies (measured: `... add column c int /*M! , drop column b */` dropped column `b`). Split on top-level `;`, ignore empty statements (the corpus has `;;` from `op.execute("...;")`), split `ALTER TABLE` clauses on top-level commas. Keywords are case-insensitive (the corpus has lowercase SQL), identifiers may be backticked, matching is on tokens, not substrings (`COMMENT 'users like this'` is fine).
- Index column lists are comma-separated `ident` or `ident(n)` (a prefix length, which alembic emits), with balanced parentheses; `USING HASH|BTREE` is not allowed. `CREATE TABLE` column attributes use the same `DEFAULT <value>` list as `ALTER`. Names: a table name matches `[A-Za-z0-9_]+`, or is qualified with the current stream's own schema only. Any other schema qualifier (`mysql.`, another database) is `needs_human`, and `alembic_version` is never a target of a body statement (compared on tokens, not on strings, after case folding, backtick removal and schema-qualifier removal, because the server accepts `bm . ALEMBIC_VERSION` with spaces or comments around the dot; the same token-level check applies to the schema qualifier; `bm . ALEMBIC_VERSION` and `` `mysql`.`user` `` are negative fixtures).
- A statement is one of: `CREATE TABLE [IF NOT EXISTS] <name> (<definitions>) [table options]`; `CREATE INDEX <name> ON <table> (<cols>)` with no other option; `ALTER TABLE <name> <clauses>`; the bookkeeping statements, which are matched against the exact expected pair of the step: `UPDATE alembic_version SET version_num='<to>' WHERE alembic_version.version_num = '<from>'` and, on an empty database, `INSERT INTO alembic_version (version_num) VALUES ('<to>')`; ids match `[0-9A-Za-z_]+` (some real revision ids are not hex).
- `CREATE TABLE` (a new table has no rows): column definitions may be `NOT NULL` without `DEFAULT`, `AUTO_INCREMENT`; `PRIMARY KEY`, `KEY|INDEX`, `UNIQUE KEY|INDEX`, `CONSTRAINT <n> UNIQUE (...)`, `CONSTRAINT <n> PRIMARY KEY (...)` are allowed. After the closing parenthesis only `ENGINE=InnoDB`, `ROW_FORMAT=DYNAMIC|COMPACT`, `[DEFAULT] CHARSET`, `CHARACTER SET`, `COLLATE`, `COMMENT` are allowed (other engines such as CONNECT, FEDERATED, BLACKHOLE are rejected). Column types in `CREATE TABLE` use the same enumerated list. `FOREIGN KEY`, `REFERENCES`, `CHECK`, `GENERATED`, `SELECT`, `WITH`, `PARTITION`, `AS`, `LIKE`, `OR REPLACE`, `TEMPORARY`, `ALGORITHM`, `LOCK` anywhere (as tokens) are rejected, which also closes `CREATE TABLE t (a int) SELECT ...` without `AS`.
- Every `ALTER TABLE` clause (on existing rows, so stricter) must match exactly one of: `ADD [COLUMN] [IF NOT EXISTS] <name> <type> <attrs>`, or `ADD INDEX|KEY <name> (<cols>)`. `<type>` is one of an enumerated list (`tinyint`, `smallint`, `int`, `bigint`, `decimal`, `mediumint`, `integer`, `bool`, `numeric`, `dec`, `real`, `year`, `float`, `double`, `varchar`, `char`, the `text` and `blob` families, `binary`, `varbinary`, `datetime`, `timestamp`, `date`, `time`, `json`, `enum`, `set`, `bit`, `boolean`) with optional arguments (`varchar(255)`, `decimal(p,s)`, `enum('a','b')`). `<attrs>` is any order of at most one each of `UNSIGNED`, `CHARACTER SET x`, `COLLATE y`, `NULL` or `NOT NULL` (both together are rejected: the server takes the last one, so `int NULL NOT NULL` adds a NOT NULL column without a default; the `NULL` of `DEFAULT NULL` is not counted here), `COMMENT '<text>'`, `DEFAULT <value>`, `AFTER <col>` (it changes column order, which is not data loss but matters to `SELECT *` and column-less `INSERT`; `FIRST` is not allowed) (alembic emits `NOT NULL COMMENT '..' DEFAULT 'x'`, measured), and a `NOT NULL` column needs a `DEFAULT` other than `NULL`. A repeated attribute (`DEFAULT 1 DEFAULT 2`) is rejected. An `ADD COLUMN` name that is a clause keyword (`UNIQUE`, `PRIMARY`, `FULLTEXT`, `SPATIAL`, `FOREIGN`, `CONSTRAINT`, `CHECK`, `PERIOD`, `INDEX`, `KEY`, `PARTITION`, `SYSTEM`) is rejected unless backticked, so `ADD UNIQUE bool (b)` is never read as a column named `UNIQUE`; fixtures: `int NULL NOT NULL`, `NOT NULL NULL`, `DEFAULT 1 DEFAULT 2`, `ADD UNIQUE bool (b)`, `ADD FULLTEXT text (c)`, `ADD CONSTRAINT year UNIQUE (a)`. Every other token is rejected, in particular `SERIAL`, a bare `KEY`, `UNIQUE`, `PRIMARY KEY`, `AUTO_INCREMENT`, `INVISIBLE`, `ON UPDATE`, `COMPRESSED`, `WITH SYSTEM VERSIONING`, `GENERATED`, `REFERENCES`, `CHECK` (measured: `ADD COLUMN s serial` creates a NOT NULL AUTO_INCREMENT UNIQUE column and `ADD COLUMN k int key` a primary key, both on a table with rows). `<value>` is one of `NULL`, a number, a quoted string, `true`, `false`, `0x[0-9A-Fa-f]+`, `CURRENT_TIMESTAMP[(n)]`, `now()`, or the parenthesized expressions `(JSON_OBJECT())`, `(JSON_ARRAY())`, `(UNHEX('<hex>'))` (the repository's standard zero UUID default is `0x00...`; without this list 8 additive revisions of the corpus were blocked by grammar alone). One non-matching clause makes the whole statement `needs_human`. `ADD COLUMN IF NOT EXISTS` silently skips a column that exists with a different definition; that is not destructive, and the drift it hides is outside `verify_mismatch`.
- Not in the allow-list, therefore `needs_human`: any `DROP`, `TRUNCATE`, `DELETE`, `UPDATE` or `INSERT` on data tables (seed `INSERT ... VALUES` included, deliberately conservative), `RENAME`, enum or type changes, `ALTER IGNORE`.
- Authoring note (goes into `docs/migrations.md` and the template): write server defaults as `sa.text('0')` or `server_default='x'`; SQLAlchemy forms such as `sa.UniqueConstraint` on an existing table, or `batch_alter_table`, are `needs_human` by design and are fine when a human applies them.
- Tests (PR 1a): the synthetic bypasses become negative fixtures (`ADD COLUMN a int, DROP COLUMN b`; `, MODIFY`; `, CHANGE`; `, RENAME COLUMN`; `, ENGINE=MyISAM`; `ADD COLUMN a INT NOT NULL, ADD COLUMN b INT DEFAULT 0`; `NOT NULL COMMENT 'default'`; `ADD COLUMN a int; DROP TABLE x`; `CREATE TABLE t AS SELECT`; `CREATE TABLE t (a int) SELECT 1`; `ADD FULLTEXT INDEX`; `ADD COLUMN s serial`; `ADD COLUMN k int key`; a two-statement `op.execute` string; `ADD COLUMN a int DEFAULT '50%'` and a `--` comment inside `CREATE TABLE` as normalization positives; `/*M! , drop column b */`; `/*!50000 , drop column a */`; a trailing `-- c` or `# c` comment on an `op.execute` string that swallows the offline `;` and merges two statements (rejected); `ALTER TABLE mysql.user ...`; `CREATE TABLE other_db.x`; a forged `UPDATE alembic_version` in a revision body), the real multi-`ADD` statement (`adb8daac2bb0`) and the zero-UUID default as positive fixtures, a mutation check per rule (reverting a rule must fail its test), a run over the whole corpus through all three layers whose output replaces the indicative shares below in `docs/migrations.md`, and a fuzz test that executes every statement classified additive on a scratch MariaDB 12.3 and asserts the schema diff only adds. Known corpus note: `a1b2c3d4e5f6_contact_create_tables` has a `FULLTEXT` definition inside `CREATE TABLE`, which the `CREATE TABLE` allow-list rejects, so it counts as `needs_human` in the head-of-line statistics (PR 1a records the reason). Indicative render-level shares measured with draft classifiers (they differ by a few revisions because the draft grammars differed, which is why the doc requires PR 1a to publish the authoritative numbers): bin_manager about 125 to 127 of 281 additive (44 to 45%), 21 `not_renderable`; asterisk about 95 to 102 of 131 additive at render level; the source gate then removes the asterisk revisions that import the postgresql `ENUM` unless that import is allowed as above. No destructive revision leaked as additive in the real corpus.

Policy: the runner applies nothing when any revision in the pending range is `needs_human`; it reports `blocked=`. The same layers run in `migration-lint` for the revisions a PR adds (`git fetch origin main` then `git diff --diff-filter=A origin/main...HEAD -- 'bin-dbscheme-manager/*/versions'`; the lint has no database, and a missing ref fails the job closed) and print the class in the CI output; QA compares it with the `[DESTRUCTIVE]` mark in the PR body (the lint job has no access to the PR body, so it does not fail on the mark). Authors who want a revision to be auto-eligible write it offline-renderable per the authoring note; the migration template and `docs/migrations.md` say so. QA rule 19 reads `class`, `status` and `blocked` from the line of the merge-time `check`; after a human applied a range by the manual path, `dbscheme-check` reports `class=na` because nothing is pending, so for that case QA relies on the merge-time `check` line and the PR mark, which it compares as before.

Head-of-line blocking is accepted and stated: once a `needs_human` revision is pending, later additive revisions wait behind it (alembic is a linear chain), and for an auto-deployed service the code PR waits too (4.8). It happens now: among the last 40 bin_manager revisions about 15 to 16 are additive-only, 18 to 19 `needs_human`, 6 `not_renderable`, and the two newest are data `UPDATE` revisions. The release path is the human path (8); afterwards `dbscheme-check` records the evidence.

Ordering stays a human concern: destructive follow-ups such as `queue_queues_drop_execute` (header of `9cc9fded2d17`: drop only after the code deploy) are never auto-applied, so they cannot run early.

### 4.8 Interaction with auto-deploy

Services with `<svc>-test-auto` deploy on merge (VOIP-1592). A code PR that reads a new column must not merge before the schema is applied. Flow with the runner: merge the dbscheme PR, wait for the stage `check` result, click (phase 1) or wait (phase 2), read the apply result line (`bm_to` or `ast_to` at or after the revision, 4.6), then merge the code PR. What the runner enforces is classification (what may be applied unattended); it does not enforce the merge order of a code PR relative to its schema. No CI enforcement of that order is added (same stance as the VOIP-1592 design D8); the QA check is the result line. A later card could add a check on the code PR that reads the corresponding `bm_to`.

## 5. Rollback and manual fallback

Switch off: stop clicking `dbscheme-apply` (phase 1) or remove the CI apply job (phase 2); delete the Stack, Procedures, Variable and DB account if retired. The manual path in `operations.md` is unchanged and needs nothing from the runner, because all state is the `alembic_version` table. While a human works manually nobody runs the Procedure (the human may also hold `GET_LOCK('dbscheme_apply')`). Emergency downgrade is human only and has no runner mode.

| situation | detected by | result |
| --- | --- | --- |
| Variable missing in Komodo | Core interpolation | Update fails, no result line, treated as failure |

| DB unreachable or wrong network | check | `error db_unreachable` |
| wrong account (root) or wrong grants | check | `login_as_root`, `grants_mismatch` |
| DB ahead of the pinned image | check | `error db_ahead` |
| destructive, data dependent or unrenderable pending revision | check, apply | `needs_human`, nothing applied |
| backup directory missing or backup fails | check, apply | `backup_dir`, `backup_failed`, before any DDL |
| marker cannot be written | apply | `marker_write_failed`, before any DDL |
| revision fails mid-way | apply | `error apply_failed`, marker stays (except the narrow automatic clean-up of 4.5), stream stops, second stream skipped |
| bind mount source missing (`create_host_path: false`) | compose | container does not start, no result line, treated as failure |
| statement outside the allow-list at run time | hook | `statement_not_allowed`, marker stays |
| container or Core killed mid-apply | marker plus lock | next run `dirty` (`ddl_running` if a statement is still running), or `busy` while still running |
| timeout or exception | watcher `KILL QUERY` | statement ended, then the result line, marker stays |
| apply ended but current is not head | apply | `verify_mismatch`, marker stays |
| executable comment or unparsable SQL | classifier | `needs_human unparsable`, nothing applied |
| executed statement differs from the rendered one | replay hook | `error statement_not_allowed`, marker stays |
| lock connection lost or marker delete fails | runner | `lock_lost`, `marker_delete_failed`, marker stays |
| unexpected exception | `try/finally` | `internal_error`, one line still printed |
| schema, head, object or tool problem found by the environment steps | check, apply | `schema_mismatch`, `multiple_heads`, `schema_objects_present`, `tool_missing`, before any DDL |
| 30 minute limit exceeded | watcher | `error timeout` after `KILL QUERY` is confirmed, or `dirty ddl_running` when it is not |
| metadata lock on a hot table before any statement ran | session timeout, hook count | fails within 15 s, runner clears its own marker, `apply_failed` |

### 보안 검토 요약 (대표님 검토용)

- 러너가 갖는 DDL 권한: 신규 전용 계정 `dbscheme_migrator`(생성은 사람이 수행). 현재 Go 서비스의 DSN 이 모두 root 라 러너가 새로운 종류의 권한을 만들지 않고 root 보다 좁습니다. 권한은 CREATE, ALTER, INDEX, SELECT, SHOW VIEW 와 alembic_version 한정 INSERT/UPDATE 입니다. DB 가 막는 것은 DROP TABLE, TRUNCATE, RENAME TO, CREATE OR REPLACE, 데이터 DELETE/INSERT/UPDATE, SUPER, GRANT 입니다. ALTER 권한으로는 컬럼 삭제, MODIFY, DISCARD TABLESPACE(테이블 전체 사용 불능), 장시간 테이블 잠금이 가능하므로 이 부분은 분류기, 실행 시점 재생 검사, 리뷰로만 막습니다(잔여 위험). 비밀번호가 유출되면 두 DB(asterisk 의 SIP 자격증명 포함)를 읽고, ALTER 로 서비스를 멈추게 하고, alembic_version 을 조작할 수 있으므로 실질 방어선은 비밀 보호와 순환입니다. 호스트 패턴은 production 네트워크 전체이므로 출처 격리 효과는 제한적입니다.
- Komodo 키 탈취 시 영향: 현재도 CI 신원이 넓은 Komodo 권한을 갖고 있고 CI context 가 브랜치로 제한되어 있지 않은 기존 위험이 있습니다(구체 내용은 공개 문서에 싣지 않고 비공개 카드 코멘트에 기록). 키가 탈취되면 러너 도입과 무관하게 운영 전체에 도달합니다. 러너는 이 영향을 키우지 않지만 줄이지도 않습니다. 권고(이 카드 범위 밖)와 선행 조건 P1 결정은 비공개 카드 코멘트를 보십시오. P1 은 스택 Write, 두 Procedure Write(git 에서 upsert)와 Execute, Update Read 만 가진 CI 전용 비 admin Komodo 계정이며, 피해 범위를 줄이지만 스택 Write 로 CI 가 실행 내용을 정하는 점은 남습니다.
- 1단계의 "사람 승인"은 절차적 통제입니다. CI 키가 넓은 권한을 갖는 동안은 CI 가 Procedure 나 스택을 직접 실행할 수 있어 악의적 CI 를 막지 못하고, 실수(잘못된 시점, 검토 안 된 범위)를 막습니다. 2단계 전환 전에 P1 을 결정해야 합니다.
- CI 에서 오는 트리거 변조: 적용 job 은 main 전용이고 compose 와 Procedure 정의는 git 리뷰를 거치지만, 브랜치 파이프라인이 Komodo 자격증명에 접근할 수 있는 기존 위험은 그대로입니다.
- 로그 노출: Komodo 가 secret Variable 값을 마스킹하고(반드시 is_secret 으로 등록) 러너는 URL, 비밀번호, SQL 본문을 출력하지 않습니다. periphery 컨테이너 안의 compose.yaml(0600 root)과 docker inspect 에는 기존 스택과 동일하게 값이 남습니다.
- 이 요약은 주요 위험만 다룹니다. 전체 위협(T1~T14)은 영문 7절 표를 보십시오. 그중 스택 Execute 권한이 곧 임의 entrypoint 실행 권한이라는 점(T5), 이미지 공급망(T8), 분류기 오탐(T11), 다른 계정이 advisory lock 을 선점해 적용을 막는 경우(T13, 가용성만 영향), Komodo Alerter 부재로 실패 알림이 없는 점(T14, 2단계 전 H4)은 표에만 있습니다.
- 승인자 식별: Komodo 사람 로그인이 하나(admin)라 Update 기록에 개인이 구분되지 않습니다(R8). 병합된 리비전 모듈은 러너 프로세스 안에서 실행되므로 비밀번호는 환경변수에서 제거해 메모리에만 두지만, 병합된 코드가 프로세스 메모리를 읽는 위험은 병합 코드 신뢰 범위와 같습니다(R9).
- 키 순환: DB 계정 비밀번호 변경 후 Komodo Variable 갱신, 서비스 재시작 불필요. 사고 시 계정 DROP 과 Variable 삭제로 즉시 폐기.
- 백업: 적용 전 자동 덤프(bin_manager 와 asterisk 모두). 기존 야간 백업은 bin_manager 만이며 asterisk 는 대상이 아니고 오프호스트 사본이 없습니다(기존 공백, 보고만).
- 파괴적 변경: 러너가 거부하고(사람 경로 유지) 긴급 downgrade 모드는 없습니다. 파괴적 리비전이 대기 중이면 뒤의 비파괴 리비전도 함께 대기합니다(선형 체인).
- 사람 조치가 필요한 선행 항목: DB 계정 생성, Komodo Variable 등록, 백업 디렉터리와 sentinel 준비, (2단계 전) Komodo Alerter 생성과 P1 결정.

## 8. Manual and emergency path (human only, unchanged)

`operations.md` stays authoritative for downgrade, repair after `dirty`, restore, and any `needs_human` range. Mandatory checklist for a human working by hand (the lock is not forced on a manual alembic run, so the checklist is the control): (1) run `SELECT GET_LOCK('dbscheme_apply', 0)` on the session and keep it for the whole session, so the Procedure returns `busy`; (2) tell QA in the card; (3) after finishing run `dbscheme-check` and attach its result line.

Repair after `dirty`: look at the marker (range and image), the schema, and `SHOW PROCESSLIST` for a still running statement (`ddl_running`); a human repairs or stamps, deletes `APPLY_IN_PROGRESS`, then runs `dbscheme-check`.

Restore from a runner dump is a last resort for damage, not the answer to a failed additive migration (forward fix or a human downgrade comes first). The dump contains `DROP TABLE IF EXISTS` for the tables it knows only, so a table created by the failed migration survives and `alembic_version` goes back, which makes a re-apply fail on `CREATE TABLE`; data written after the dump is lost. Rehearse it (PR 1b) in a scratch server, never against the production server. Production restore: stop the writers, `DROP DATABASE` the schema, create it, `gunzip -c <file> | mariadb <schema>`, human only.

## 10. Appendix: account SQL for the human (not executed by this card)

```
CREATE USER 'dbscheme_migrator'@'<production-network-pattern>' IDENTIFIED BY '<generated>';
GRANT SELECT, CREATE, ALTER, INDEX, SHOW VIEW ON `bin\_manager`.* TO 'dbscheme_migrator'@'<production-network-pattern>';
GRANT SELECT, CREATE, ALTER, INDEX, SHOW VIEW ON asterisk.* TO 'dbscheme_migrator'@'<production-network-pattern>';
GRANT INSERT, UPDATE ON bin_manager.alembic_version TO 'dbscheme_migrator'@'<production-network-pattern>';
GRANT INSERT, UPDATE ON asterisk.alembic_version TO 'dbscheme_migrator'@'<production-network-pattern>';
```

In MariaDB `_` is a pattern character in a schema-level grant, so the schema names are written escaped (`bin\_manager`) in the real statements and in the expected `SHOW GRANTS` set, otherwise `binXmanager` would match too. Both `alembic_version` tables exist in production, so the table-level grants succeed there. The exact privilege set is re-confirmed on a scratch MariaDB 12.3 in PR 1b; `check` rejects any difference.
