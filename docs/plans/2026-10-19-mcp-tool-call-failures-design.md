# VOIP-1632: MCP tool call failures in the Test Agent chat

## 1. Ticket review

Verdict: valid. Three separate VoIPBin defects, none of them caused by the external server (DeepWiki). Evidence is from production docker logs (read only, 10 hours) and a local replay of the same public requests.

All three attempts used an AI with the DeepWiki server (`https://mcp.deepwiki.com/mcp`, no auth) and the tools `read_wiki_structure`, `read_wiki_contents`, `ask_wiki_question`. All three reach the same code path as real customer chat (conversation), ai_task and call AIcalls: pipecat tool call -> pipecat-manager `RunnerToolHandle` -> RPC `AIV1AIcallToolExecute` -> ai-manager `ToolHandle` -> `toolHandleMcpCall` -> `mcptoolhandler.CallTool`. Only the session start differs (Test Agent chat is `ReferenceTypeNone`, `SendReferenceTypeOthers`).

| Attempt | Observation | Root cause |
|---|---|---|
| 1 error | ai-manager: `MessageCreate ... Error 1406 Data too long for column 'content'` | `toolHandleMcpCall` stores the whole MCP text (241 KB here) in `ai_messages.content`, a `text` column (64 KiB, `bin-ai-manager/migrations/000001_baseline.up.sql:190`). The production log proves only that the content exceeded 64 KiB; the 241 KB figure comes from the local replay of the same request. |
| 2 success after the answer | script-runner `HTTP 400 ... context deadline exceeded` exactly 3.0 s after the call; ai-manager saved the result 8.6 s after the call, 5 s after the answer | `AIV1AIcallToolExecute` uses `requestTimeoutDefault` (3 s, `bin-common-handler/pkg/requesthandler/ai_aicalls.go:270`, `main.go:152`) while ai-manager bounds an MCP call (the same aicall's first tool call took 0.5 s and succeeded, so only the slow call hit the limit; the 8.6 s ai-manager time covers the MCP call and the DB write) at `mcp_tool_call_timeout_seconds` (10 s) and the pipecat HTTP call at 10 s (`scripts/pipecat/tools.py:165`). pipecat gets the error, the LLM answers from it, ai-manager keeps running and stores the real result afterwards. Not refuted: all three attempts really called `mcp_` tools and got an error or a late result. No open or merged PR covers this (`gh pr list --state all`, `git log` on the four paths). Out of scope (one line for the report): the voice-call MCP exposure doc versus `runner.go` mismatch.

## 2. Design

Three small changes in one PR. No flag, no schema change, no new config.

1. Tool RPC timeout. New const `requestTimeoutToolExecute = 15000` in `requesthandler/main.go`, used only by `AIV1AIcallToolExecute` (its only Go caller is `bin-pipecat-manager` `runner.go:517`). It must be larger than the ai-manager bound (10 s default plus the 250 ms session close plus DB writes). The two Python callers of the same endpoint move from 10 s to 20 s: `tools.py:165` (`ClientTimeout(total=20)`, and the log text) and the shared session in `team_flow.py:258` (team pipelines call the same endpoint). Order: MCP 10 s < RPC 15 s < pipecat HTTP 20 s. The 10 s is applied twice (`tool.go:178` wraps `toolHandleMcpCall`, `CallTool` wraps its own call); the tool-call row write before it and the result row write after it are outside that bound and live on the 5 s margin. `sendRequest` records an RPC timeout as a circuit breaker failure for the ai queue, so the longer limit also lowers how often a slow MCP call feeds the breaker. pipecat itself adds no earlier cut: the runner pins `pipecat-ai>=1.12,<1.13`, where `LLMService.function_call_timeout_secs` defaults to `None` (checked in the 1.12.0 wheel, `llm_service.py:316`) and the repo never sets it nor passes `timeout_secs` to `register_function`. A test pins that (see section 4). If an operator raises `MCP_TOOL_CALL_TIMEOUT_SECONDS` above 10 the 5 s margin for the message writes shrinks and at 15 or more the order breaks; this is stated in the const comment and in the `bin-ai-manager/docs/operations.md` row, with no config validation added (no flag or new rule without instruction).
   Why all tools and not only `mcp_` names: the 3 s limit is wrong for any tool whose handler legitimately does an RPC chain, a name prefix check would copy the `mcp_` namespace rule into `bin-common-handler`, and the cost is only a longer wait on a failing built-in tool. Worst case silence in a voice call during a hung tool is 15 s instead of 3 s; there is no global flag (hard rule 7).
2. Honest oversize error. In `mcptoolhandler/session.go` add `ErrResponseTooLarge` (package level, wrapped with `%w`; `errors.Is` survives `readSSEResponse`'s `could not read event stream: %w`, the JSON path's `could not read response body: %w` and `doJSONRPCRequest`'s `%w` wrapping, which never stringifies). Only `request()` changes: its `io.LimitReader` becomes a small reader that returns the error once more than `McpHTTPResponseSizeCapBytes` bytes were read (it needs to see one byte past the cap, so exactly the cap is accepted). Contract: the reader hands at most `cap` bytes to the caller and returns the error on the next call; the cap+1 th byte is never returned as data (otherwise `bufio` would accept an SSE line ending at byte cap+1). `notify()` (body discarded) and `statusError` (reads 4096 bytes) keep `LimitReader`. A matching SSE event completed before the cap is returned early as before; a bare JSON body over the cap now fails with the new error instead of `could not parse JSON-RPC response`. `initialize` and `ListTools` also pass through `request()`, so their over-cap message changes the same way (intended). `toolHandleMcpCall` maps `errors.Is(err, mcptoolhandler.ErrResponseTooLarge)` to the LLM-facing message `MCP tool result is too large`; the log line keeps `capErrText(err.Error(), 200)` and the outcome counter stays `failed` (no new label). The cap stays 1 MiB (the memory bound for the 40M container).
3. Bounded success text. In `toolHandleMcpCall` the success `msg` is cut to at most 32 KiB on a rune boundary, then shortened by a binary search over `utf8.DecodeRuneInString` step positions (invalid bytes count as one step each; not `truncateUTF8`, which can step back on invalid input) (the marshalled length is monotonic in the prefix length, so about 15 marshals instead of tens of thousands for 32 KiB of `<`) until `len(json.Marshal(messageContent))` of the whole result, measured with the real marshaller, is at most 60000 bytes; a marker with a fixed text (`\n[truncated]`, no number, so its length is constant) is appended only when the text was actually cut, and is part of the text that is measured; a result that fits is returned unchanged without marker. The `tool_call_id` column is `varchar(255)`, so the fixed part of the content is about 1.5 KB at most and the search always finds a prefix (tested with a 255 character id). Measuring the real marshalled struct covers HTML escaping (`<`, `>`, `&` become 6 bytes), control characters (6 bytes), U+2028 and U+2029 (6 bytes), invalid UTF-8 (6 bytes per bad byte) and an LLM chosen long `tool_call_id`, with no assumption about them. Korean text is not escaped, so utf8mb4 byte counts equal the marshalled counts. The error branch keeps `capErrText(msg, 200)`.

Alternatives rejected: raising the 1 MiB cap (memory), `mediumtext` (schema change, and the LLM context would still be flooded), a per tool timeout table (more code than one const), streaming truncation of the SSE data line (over engineering), a config validation for the MCP timeout (not requested).

## 3. Impact and compatibility

- No DB schema change and no migration. Rolling deploy: any mix of old and new ai-manager, pipecat-manager and script-runner works; only timeouts and message text change. Until `bin-common-handler` is rebuilt into pipecat-manager the RPC keeps the 3 s limit (no regression, no gain). `bin-common-handler` is a shared library, so the full verification runs in every module that imports `requesthandler` (build of each `bin-*` is left to CI plus a local `go build ./...` of the three touched modules).
- Residual, not fixed here: when `MessageCreate` for a tool result fails for an infrastructure reason, the tool-call row stays unpaired and the next turn of the same aicall replays that history to the LLM (same family as VOIP-1460, whose unknown tool fix records a failure row). The oversize cause of that failure is removed by change 3. A late result row can also reappear when `MCP_TOOL_CALL_TIMEOUT_SECONDS` is 15 or more. Suggestion only.
- No user facing API field changes, so no RST change (`docsdev` has no MCP result size description; checked by grep). Docs to update: `bin-ai-manager/docs/operations.md` (timeout row: the 15 s dependency, and the 1 MiB / 32 KiB behaviour visible to the LLM), `bin-pipecat-manager/docs/domain.md` (tool execution path timeouts).

## 4. Verification plan

Tests are written after the design review closes. Reproduction first on an unmodified scratch copy, failure output saved to the card. Existing test to change: `mcptoolhandler/client_test.go:157-160` (the `methodRawBody` case, body over the size cap; the other `could not parse JSON-RPC response` cases at `:130` and `:255` are not cap cases and stay) currently pins `could not parse JSON-RPC response` and must expect `ErrResponseTooLarge`; it does not count as a regression test.

- New tests go into the existing `mcptoolhandler/client_test.go` (there is no `session_test.go`). SSE and bare JSON bodies over the cap return `ErrResponseTooLarge` (today: stream ended or parse error); exactly the cap bytes is accepted and cap plus one byte is refused, each checked for both SSE and bare JSON; a matching SSE event completed before the cap with more bytes after it still succeeds; `notify()` with an over-cap ack still succeeds; a non-2xx body is unchanged; `errors.Is` holds through `CallTool`.
- `mcp_tool_test`: a 100 KB result succeeds with the marker and `len(json.Marshal(content))` at most 60000; the boundary around 60000 bytes of the marshalled content (exactly fits, one byte over); results made of `<`, of `\x01`, of U+2028 and of invalid UTF-8 bytes also fit; Korean text is cut on a rune boundary; a 100 byte result is unchanged; a very long `tool_call_id` still fits; `ErrResponseTooLarge` yields the specific failed message and the `failed` counter.
- `requesthandler`: capture the ctx handed to `RequestPublish` and assert its deadline is between 14 s and 15 s ahead for `AIV1AIcallToolExecute` and about 3 s for another RPC. Fails before the change (3 s).
- pipecat Python (aiohttp is a mock module in `conftest.py`, so only call arguments are asserted, not real aiohttp behaviour): `tool_execute` passes `ClientTimeout(total=20)`; `team_flow._get_http_session` builds `ClientTimeout(total=20)`; `register_function` is called without `timeout_secs` and `function_call_timeout_secs` is not set in `run.py` (a pin test of the pipecat default assumption; it passes before the change and is not a regression test).
- Local replay through the real `mcptoolhandler` against the public DeepWiki server (read only, no cost) for `voipbin/voipbin` and `facebook/react`.
- Reproduction before the fix: the new `ErrResponseTooLarge` symbol does not exist in the unmodified code, so the RED run on the scratch copy asserts the error text (today `event stream ended` / `could not parse JSON-RPC response`) or uses a stub symbol; the requesthandler deadline test and the Python argument tests fail on the unmodified code as they are.
- Out of scope, one line for the report: other built-in tools share the same 64 KiB risk at `toolCreateResultMessage` (`tool.go:257`); `bin-pipecat-manager/docs/domain.md` currently has no timeout text for the tool execution path, so that note is an addition.
- Full verification workflow in `bin-common-handler`, `bin-ai-manager`, `bin-pipecat-manager`; Python tests in `bin-pipecat-manager/scripts/pipecat`.
