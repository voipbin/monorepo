# main auto-deploy phase 2 design (VOIP-1592, monorepo)

Extends `docs/plans/2026-10-13-main-auto-deploy-design.md` (VOIP-1586, pilot). Read that document for the structure, the guard and the checker; this one covers only what changes when the remaining services are converted. Where it differs from the pilot document's condition "convert the rest after the pilot is observed" (D4 and Phase 2 there), this document supersedes it, see section 5.

## 1. Facts (measured on origin/main, 2026-10-14)

- F1. `config_work.yml` has 31 services with a `<svc>-deploy` job that are still approval-gated: 28 follow the identical job shape `build-approval -> <svc>-test -> <svc>-build -> <svc>-deploy` (compared by parsing the YAML and masking the service name), and 3 are on the approval-keep list (`bin-timeline-manager`, `bin-rag-manager`, `voip-kamailio-proxy`). In all 28, `jobs:` holds one `<svc>-deploy` that calls `komodo-api-deploy.sh` exactly once with the service name as first argument.
- F2. One of the 28, `bin-api-manager`, is armed by two parameters (`when: or: [run-bin-api-manager, run-bin-openapi-manager]`), because the gateway embeds the generated OpenAPI code. Among the 28 it is the only workflow using `or` (the three kept `voip-*` workflows use a one-element `or`, which D3 also accepts). Its deploy call has a third argument (`environment.env`), as do three others (`bin-pipecat-manager`, `bin-transcribe-manager`, `bin-tts-manager`); the insertion is the same for both shapes.
- F3. The checker requires the guard value to equal the service name exactly (`guards == [svc]`) and its error text names the service. It never reads `when:`.
- F4. `bin-trigger-sender`, `voip-asterisk-proxy`, `voip-rtpengine-proxy`, `bin-common-handler`, `bin-openapi-manager`, `bin-dbscheme-manager` have no deploy job. They are not conversion targets and stay unchanged.
- F5. Pilot services have had no merge since conversion, so no real automatic deploy on `main` has been observed yet.
- F6. The `bin-call-manager` workflow block carries a comment block (inside the block, after the `<<: [*context_production, *deploy_filters]` line of the `- bin-call-manager-deploy:` entry; it is the only such comment in the file, found by grep) saying one `build-approval` puts a change into production. It becomes false after conversion, so it is rewritten as part of the block edit. The header comment of `config_work.yml` ("Approval-kept mode (most services today)") also becomes stale and is updated in this PR as the one allowed change outside the blocks. Other occurrences of that host name elsewhere in the file are out of scope here.
- F7. Compose files of the 28 use the commit-SHA image tag only (`__IMAGE_TAG__`), never `:latest`, so a build that finishes late cannot move a floating tag.

## 2. Scope

Convert the 28 services of F1 to the pilot shape: `build-approval` and `<svc>-test` ignore main, `<svc>-test-auto` only main, `build` requires both, `deploy` only main with `serial-group` and the guard. The 3 approval-keep services with a deploy job stay untouched, as do the 6 deploy-less workflows of F4. The allowlist grows from 3 to 31 entries.

## 3. Design

- D1. One-shot script (text edit, not a YAML re-dump, to keep anchors and comments). It changes exactly two things per service: the workflow block (filters, test-auto, build requires, deploy serial-group) and the `<svc>-deploy` job definition, where it inserts one new line `DEPLOY_REQUIRE_LATEST_FOR_PATHS="<paths>" \` as the first line under `command: |`, directly before the existing `CC_KOMODO_POLL_ATTEMPTS=... \` line, exactly where the pilot put it (existing lines are not edited; both argument shapes of F1 and F2 are handled). It also rewrites the comment block of F6 inside the `bin-call-manager` workflow block. Every other byte is unchanged. The script is not committed; its result is verified by the block-wise diff in section 6.
- D2. Guard paths: the service directory. `bin-api-manager` uses `bin-api-manager bin-openapi-manager`, so a newer OpenAPI-only commit marks an older gateway deploy superseded, matching the arming rule of F2. The guard accepts a space-separated list.
- D3. The checker derives the expected guard path set from the workflow itself: the service directory, plus the directory `bin-X` for each extra `run-bin-X` parameter in the workflow's `when`. For `bin-api-manager` that gives `bin-api-manager bin-openapi-manager`; for every other service exactly the service directory. This ties the guard to what arms the workflow, so a later change to either side fails the check instead of drifting. The mapping is read from `workflows.check-changes.jobs[].path-filtering/filter.mapping` of `config.yml`. A PR that edits only `config.yml` does not run the shell tests (its path is not in the shell-tests mapping), so such a drift is reported at the next run triggered by a `config_work.yml`, script, test or allowlist change; this is accepted and `config.yml` is not touched by this PR. The error text is generalized to print the expected set. The checker takes a third optional argument, the path of `.circleci/config.yml` (default: next to the config file), reads its `path-filtering` `mapping` string (one `<pattern> <parameter> true` per line) and resolves directories against the repository root passed as a fourth optional argument (default: the parent of `.circleci`); fixtures pass tampered copies. Only the shapes `when: or: [<< pipeline.parameters.run-bin-X >>, ...]` (one or more elements) and the single `when: << pipeline.parameters.run-bin-X >>` form are accepted; any other form (`and`, `not`, `equal`, a literal) fails the check. The workflow's own `run-<svc>` must be present; every other parameter in `when` must be of the form `run-bin-X` whose directory `bin-X` exists and whose mapping contains the single line `bin-X/.* run-bin-X true` (the pattern and the parameter on the same line), otherwise the check fails (message: `<svc>: when references <param> that is not a mapped service directory`). The mapping lines use runs of spaces for column alignment, so the pair check splits on whitespace runs. The `when` derivation applies only to allowlist services; the keep-service check does not read `when`. Negative fixtures: guard missing the extra path; extra path on a service whose `when` has none; `when.or` with a parameter that has no mapped directory; `when` without the service's own parameter; an unsupported `when` form.
- D4. The allowlist file gains the 28 names. The checker already fails if an allowlist service lacks the shape or a shaped workflow is missing from the list, so list and config cannot drift.
- D5. `DENY` in the checker (timeline, rag, trigger-sender, asterisk-proxy, rtpengine-proxy, kamailio-proxy) is unchanged and still rejects those names if added to the allowlist (applied at the allowlist stage, independent of D3). This is a different set from the six deploy-less workflows of F4.
- D6. One PR (one repository, one logical change) touching only `.circleci/` and `docs/`. The path mapping flips only `run-shell-tests` and `run-lint-config-check` for these paths and no service workflow, so merging it deploys nothing.
- D7. First real automatic deploys happen on the next merge of each service. The post-merge check reads the pipeline of the merge commit: test-auto, build and deploy success, or deploy failed with a newer commit on the guard paths (superseded, then the newer commit is followed).
- D9. Existing checker tests. Two changes to `check-auto-deploy-config.bats`.
  - Harness (affects every test that calls `run_checker`, including the `bin-agent-manager` ones): `setup` currently copies only `config_work.yml` and the allowlist into the temp directory and `run_checker` passes two arguments. After conversion the real allowlist contains `bin-api-manager`, whose derivation (D3) needs `config.yml` and a `bin-openapi-manager/` directory, so without a change the checker fails closed with `cannot check` in the positive test and in every negative test. `setup` therefore also copies `config.yml` into the temp `.circleci/`, creates empty service directories under a temp repo root for each mapping line whose parameter is `run-bin-*` (other lines are skipped); the default for the config path and for the repo root are both resolved from the checker's own location (`.circleci/config.yml` and its parent), and the guard value is compared as an ordered space-separated string equal to the derived set in the order service directory first, then extra directories in `when` order, and `run_checker` passes the third and fourth arguments. The one test that runs the checker with default paths against the real repository is unchanged.
  - Keep-service examples: the file uses `bin-call-manager` as its approval-kept example on 20 lines (215, 216, 218, 228, 234, 236, 240, 242, 246, 247, 248, 250, 294, 296, 313, 315, 319, 321, 331, 333): renamed-deploy, ungated build, test with a branch filter, widened deploy filter, adding it to the allowlist (294), a stray `-test-auto` (313), and block-text mutations (319). After conversion these premises no longer hold, except line 228, which builds a stray `bin-call-manager-deploy` key inside the agent workflow and passes unchanged. The others move to `bin-timeline-manager`, whose workflow has the same four-job shape and whose block text matches under a plain name substitution except the F6 comment of `bin-call-manager`, which is rewritten by D1 and then matches. `bin-timeline-manager` is in the checker's `DENY` list, whose error is added (the checker keeps collecting errors) together with the rule under test; the tests assert a substring, so they would still pass, but for a clean assertion the allowlist cases (294) use a fixture that copies the `bin-timeline-manager` block under a synthetic name outside `DENY`. Case 313 needs no synthetic name because the service is not in the allowlist. Each moved test must keep its rule coverage: it is accepted only if reverting the corresponding checker rule makes it fail (mutation check). `voip-kamailio-proxy-komodo.bats` reads only the kamailio workflow and is unaffected; the other bats files do not read `config_work.yml`.
- D8. Schema-dependent changes. The merge-time rule that a service PR is held while a schema migration is unapplied is a process rule, not a CI check. Its mode switch is keyed off the workflow shape (presence of `<svc>-test-auto`), not a service list, so it applies to the 28 converted services as soon as the shape is on `main`; no instruction file needs a list update. This PR adds no CI enforcement for it.

## 4. Known behaviors the design does not remove

- A merge is a deploy for all 31 converted services; the controls are pre-merge review, the test-auto gate and the guard, not repository settings.
- One PR that changes several services deploys them in parallel. A contract addition must merge callee first. A fleet-wide change (toolchain upgrade, repository-wide cleanup) redeploys many services at once, including call-path ones that restart together; such a change is merged in service groups with the call-path group last, one group per merge.
- Rollback is a revert PR; there is no automatic rollback.
- Changes to shared modules (`bin-common-handler` and the model packages of sibling services referenced through `replace`) do not deploy a dependent service by themselves; they ride that service's next deploy, as today.
- Old `on_hold` approval gates: an approval left on hold in a pipeline created before the merge still runs the old, unguarded job definitions for its old SHA. Right after the merge, on-hold workflows of the 28 converted services are cancelled (cancelling an on-hold workflow deploys nothing), and nobody reruns or approves a pre-merge pipeline of them.

## 5. Accepted risk and alternatives considered

The pilot document required observing the pilot before converting the rest. That is not satisfied (F5). The owner decided on 2026-10-14 to convert all remaining services at once, including call-path services (`bin-call-manager`, `bin-conference-manager`, `bin-registrar-manager`, `bin-route-manager`, `bin-transfer-manager`, `bin-pipecat-manager`, `bin-tts-manager`, `bin-transcribe-manager`, `bin-api-manager`).

| option | cost | what it keeps |
| --- | --- | --- |
| all 28 at once (chosen) | one PR | no wait for a pilot merge; call-path services convert before any real main run exists |
| non-call-path first, call-path after the first observed pilot merge | two PRs, waiting time | one real main run before call-path services convert |

Mitigations of the chosen option: guard, checker, allowlist (removing a name restores approval for later pipelines; it does not stop a pipeline already running), post-merge verification of every service's first merge, and rollback by the revert PR of section 4.

Pre-check of pending commits (read-only). A service whose newest successful deploy is older than its newest path commit carries pending commits that ship with its next merge; today an unapproved `build-approval` shows them, after conversion nothing does. The pre-check is therefore a merge-time step, not a fact frozen in this document, because the numbers move with every merge. Method, run right before the PR is declared ready and again right before merge: for each of the 28 services, list main pipelines through the CircleCI API (`GET /project/<slug>/pipeline?branch=main`, then `/pipeline/<id>/workflow` and `/workflow/<id>/job`), follow `next_page_token` until the service is found, then take the checkout SHA of the newest pipeline (by creation time; if deploys were approved out of order, the SHA that is a descendant of the others, checked with `git merge-base --is-ancestor`) whose workflow named like the service has a successful `<svc>-deploy` job, and run `git log --format='%h %s' <sha>..origin/main -- <guard paths>` with the guard paths of D2 (the service directory; for `bin-api-manager` also `bin-openapi-manager`). The result is a table (service, last deploy SHA, pending commit list, number of old `on_hold` workflows) attached to the PR description and to the review card.

State on 2026-10-14 for the five services whose pending ranges are old enough to include more than the two latest cleanup commits (git log reproduced by reviewers; most commits are non-functional, the behavior-relevant ones are named): hook, last deploy `81588cf6a`: `1e333b264` (identifier typo fix), `ec3d0790e` (convention cleanup), `1d71c0dd8` (go.sum and indirect dependency fix), `e15975e58` (Go toolchain upgrade), `41e5316ba` (sentinel-manager CI/CD reintegration). outdial, `c8fa2a202`: `ec3d0790e`, `1d71c0dd8`, `e15975e58`, `41e5316ba`, `0c7964860` (removal of fanout dual publish; in outdial it changes only an architecture document, in tag and transfer it changes handler code), `a9c81fa0b` (explicit event subscription id enforcement, test file). tag and transfer, `c2934eff3`: `1e333b264`, `ec3d0790e`, `1d71c0dd8`, `e15975e58`, `41e5316ba`, `0c7964860`. schedule, `e15975e58`: `ec3d0790e`, `1d71c0dd8` (an indirect dependency bump `go.yaml.in/yaml/v2` v2.4.3 to v2.4.4 with its go.sum fix, no feature change). For the other services the same command is run at merge time and is mandatory for every call-path service (their recent commits, for example in `bin-call-manager`, include behavior changes that may or may not already be deployed); the pending commits seen so far for the remaining ones are the typo fix and the cleanup commit above, which touch Go source (formatting, renames, test messages) and are not documentation-only, so each service's diff is read before the PR is declared ready.

Handling of services with pending behavior changes: the owner chooses before merge to flush them (one manual approval of the current `main` pipeline per service, after reading the pending range) or to accept that they ride along with the next merge. Old `on_hold` workflows of the 28 services are cancelled right after the merge, as in section 4. The pre-check does not read migrations: schema-dependent pending commits are checked by listing `bin-dbscheme-manager` and per-service migration changes in the same range.

## 6. Verification plan

0. Pre-check of pending commits re-run immediately before merge; result recorded in the PR description.
1. `bats .circleci/tests/*.bats` passes locally, including the migrated tests of D9 (with the mutation check) and new checker fixtures for D3.
2. Static diff against `origin/main`: for the 28 services only the workflow block, the one deploy command line and the F6 comment differ; the 3 keep workflows, the 6 deploy-less workflows and all other job definitions are byte-identical, and every converted deploy job shows +1 line and 0 deleted lines. Compared by splitting both files at two-space-indented keys under `workflows:` and `jobs:` (a `# bin-X` comment above a job belongs to that job), diffing each block, and also diffing the remaining text outside all blocks (header, anchors, `parameters:`, section banners) for byte equality, except the header comment update. Comment lines directly above a key belong to that key's block, except runs of `####` banner lines and the comment lines immediately between two banner lines, which belong to no block and are compared as outside text.
3. PR branch pipeline: no config error, shell-tests and lint-config-check success, no deploy job created on a branch.
4. A temporary commit inside one converted call-path service directory (comment line) creates its workflow on the branch: `build-approval` on hold, no `test-auto`, no `deploy`; then it is reverted and absent from the final diff. No approval is clicked on any branch pipeline.
5. After merge: on-hold workflows of the 28 services cancelled; the next merge of each service shows test-auto, build, deploy without a click.
