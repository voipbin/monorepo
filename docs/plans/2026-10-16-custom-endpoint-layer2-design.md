# Customer-specified OpenAI-compatible endpoint, Layer 2 detailed design (VOIP-1599)

Status: implemented in the same pull request (the schema change is merged separately). Layer 1 (operator-registered local models) is merged. This document is the design that `docs/plans/2026-10-15-self-hosted-llm-design.md` section 4 requires before any Layer 2 code or schema. Section 4 of that document stays authoritative for the gates and invariants; this document only fixes what section 4 left open (write path, validator placement, request DTO, key update semantics, schema columns, exact files, rollout order) and records the values that the proof of concept refined. 

Scope: bin-ai-manager, bin-pipecat-manager (Go service and Python runner), bin-api-manager, bin-openapi-manager, bin-common-handler (`requesthandler`), docs. Out of scope: front-end, billing, private address allowlists, global on/off flags.

## 1. Issue analysis (verified on main)

### 1.1 Current state

- Layer 2 is not implemented. `ResolveEngine` (`bin-ai-manager/models/ai/resolve.go`) knows no `customendpoint.` prefix, `ai.AI` (`models/ai/main.go`) has no base URL, and `ai_ais` has no such column (`migrations/000001_baseline.up.sql`).
- Write chain today: api-manager `server/ais.go` (`PostAis`, `PutAisId`) -> `servicehandler/ai.go` `AICreate` and `AIUpdate` -> `requesthandler` `AIV1AICreate` and `AIV1AIUpdate` (positional arguments) -> ai-manager `listenhandler/v1_ais.go` -> `aihandler/chatbot.go` `Create` and `Update` -> `aihandler/db.go` `dbCreate`, `dbUpdate`, `buildUpdateFields` -> `dbhandler/ai.go` `AICreate`, `AIUpdate` (map based, refreshes the Redis cache). `PUT` is a whole replacement: every omitted string field arrives as an empty string. Other writers of `ai_ais` (`UpdateMcpServerIDs` right after create and update, `DirectHashRegenerate`, `AIActivateInsight`, the raw `UPDATE` in `AIAcceptProposal`, `AIDelete`) name their columns and do not touch the new ones, except `AIDelete` (below). The ai-manager `Update` reads the stored row first (`preUpdateAI`) through `AIGet`, which is cache first; cache refresh errors after a write are ignored (`dbhandler/ai.go`), so the snapshot can be stale.
- Read chain: `AIGet` serves from the Redis cache (the whole `ai.AI` is stored as JSON, so every JSON tagged field is cached). pipecat-manager reads the AI through `AIV1AIGet` in `resolveAIFromAIcall` (used by `startReferenceTypeAIcall` and, after the session exists, by the tool resolution in `runner.go` `runnerStartScript`) and in `resolveTeamForPython` (defined in `run.go`, called from `runnerStartScript`). `runGetLLMKey` is called only from `startReferenceTypeCall` (reference type call), where it has no live AI, so a custom endpoint session there fails closed. ai-manager starts a pipecatcall once per call for voice (`aicallhandler/start.go:279`, the session lives as long as the call) and once per turn for conversation, contact case, send and listen paths (`start.go:409`, `start.go:620`, `send.go:138`, `listen.go`), which terminate it with a delay; task aicalls (`start.go:1250`) start one per task and end with the aicall. A lookup in the start path is therefore paid once per call for voice and once per turn elsewhere. The URL and key read from the live AI at the start of a session are used until it ends. The session model type is the aicall snapshot, while the URL and key are read from the live AI when the session starts; an AI that was switched to another model or deleted in between is still returned by `AIGet` (`aiGetFromDB` does not filter `tm_delete`). Other callers of `AIV1AIGet`: api-manager `aiGet` (about ten call sites: `servicehandler/ai.go`, `aiprompthistory.go`, `aipromptproposal.go`, `aicall.go`, `serviceagent_aicall.go`; none needs the key) and call-manager `start_incoming_domain_type_sip.go`. Every one of them receives the decrypted key over the internal RPC once `AIGet` returns plaintext.
- Runtime chain: `llmresolve.go` `resolveSessionLLM` -> `SessionCreate` -> `runnerStartScript` -> `PythonRunner.Start` (HTTP POST to the runner on localhost) -> `main.py` `PipelineRequest` -> `run.py` `create_llm_service`. Team members take `resolveTeamForPython` -> `resolvedAIData` -> `ResolvedAI` -> `create_llm_service` (`run.py` team path).
- `Session.LLMKey` is `json:"-"` (`models/pipecatcall/session.go`); the runner request is a separate struct in `pythonrunner.go`. Sessions are logged with `WithField("session", se)` (`runner.go`), so a field without `json:"-"` would reach a JSON log and a plain `string` field reaches a text log. `checkLiveEngineVendor` returns nil when the runner key is empty, so outcomes with a blank key skip it.
- AI ids referenced by other resources are not checked for ownership; this predates the change and is outside it (R13).
- `AIDelete` (`dbhandler/ai.go`) is a soft delete that changes only `tm_delete`, `tm_update` and `is_insight_active`, so a stored key would survive the delete. ai-manager has no subscription to the customer deleted event (`subscribehandler`), so rows of a deleted customer are not soft deleted either.
- `pipelineerror.go` classifies a customer server's HTTP errors (404 for a missing `/v1` segment, unknown model, 5xx) as unknown, and `shouldNotifyPipelineError` notifies unknown only without STT, so these misconfigurations are silent in voice sessions. Only 401 and 403 (authentication), 429, timeouts and fatal errors notify. `Connection error.` is likewise unknown today.
- pipecat `OpenAILLMService` creates one `AsyncOpenAI` client per service object through `create_client`, never closes it (only streams are closed, `base_llm.py` around 497 to 503; its stock client allows up to 1000 connections, keeps 100 idle ones without expiry and reads for up to 600 seconds), and the service object lives for one pipecatcall (the whole call for voice, one turn for the other paths). The runner has no limit on concurrent sessions.
- Team sessions: the top level `llm_type` of a team session is the start member's model on the flow start path (`resolveAI`) and the current member's model on the send path (`aicallhandler/send.go` `resolveTeamMemberForSend`); either can be a `customendpoint.` model, and the top level then receives a blank key.
- The existing outbound guard for MCP servers (`mcpserverhandler/ssrf.go`: literal IP classifiers in `ValidateURL`, dial-time `Control` hook, `RefuseRedirects`, 1 MiB response cap) is Go only, checks literal IPs at validation time, and does not apply to the Python runner; it is not reused (earlier design, section 4.1).
- `ai-control` prints whole `ai.AI` values as JSON (`printJSON`), so a new JSON tagged ciphertext field would be printed to the operator terminal; the plaintext is never set there (`ai-control` has no key set).
- Secrets today: `ai_ais.engine_key` is plaintext, returned by `WebhookMessage` (`webhook.go`), stripped in `publishAIEvent`. The MCP secret mechanism is `mcpserverhandler.SecretCrypto` (AES-256-GCM, key set from `MCP_SECRET_ENCRYPTION_KEYS`, `<version>:<base64 32 bytes>` list, `Encrypt` returns ciphertext, nonce, version). It has no dependency on `aihandler`, so `aihandler` can import it.
- `pipelineerror.go` classifies `Error during completion: Connection error.` (pipecat 1.12.0 `OpenAILLMService`, `services/openai/base_llm.py`) as unknown, and unknown is not notified in sessions with STT.

### 1.2 Facts that differ from the assumptions in the earlier design

1. Schema ownership changed. `ai_ais` is owned by bin-ai-manager and migrated at startup from `bin-ai-manager/migrations` (golang-migrate). The `bin-manager` Alembic stream is frozen. Section 4.3 of the earlier document assumed that the production schema is applied separately and by hand; that does not apply to this table any more. The schema change is two migration files in `bin-ai-manager/migrations` (section 5). The schema change still ships as its own earlier change, which keeps the blast radius of the code change small and means every consumer of `GetDBFields(ai.AI{})` meets the columns before the struct gains the fields.
2. `requirements.txt` of the runner does not pin `httpx`, `httpcore` or `openai` (only `uv.lock` does, and the Dockerfile installs from `requirements.txt`). The proof of concept depends on private attributes (`httpx.AsyncHTTPTransport._pool`, the pool's ssl context, `httpcore._backends.auto.AutoBackend`), so the image must pin the versions the proof of concept passed on (httpx 0.28.1, httpcore 1.0.9, openai 2.15.0, pipecat-ai 1.12.0) and the client builder must verify the swap at runtime.
3. New finding, measured with openai 2.15.0: `AsyncOpenAI` falls back to `OPENAI_ORG_ID` and `OPENAI_PROJECT_ID` when `organization` and `project` are `None`, and then sends `OpenAI-Organization` and `OpenAI-Project` headers. With `default_headers={"OpenAI-Organization": Omit(), "OpenAI-Project": Omit()}` the headers are not sent. An empty `api_key=""` sends no `Authorization` header and does not fall back to `OPENAI_API_KEY`. The proof of concept did not cover this; the runner for a customer host must not rely on the operator never setting these variables.
4. The runner tests are not run in CI (the CI test job for pipecat-manager is Go only) and `scripts/pipecat/conftest.py` replaces `pipecat` with mocks, so a subclass of the real `OpenAILLMService` cannot be tested there. Pure network code therefore goes into a module that does not import pipecat, and real-library tests go to `scripts/pipecat_realtest` (run with `--noconftest`).
5. `requesthandler` default RPC timeout is 3 seconds, for the pipecatcall start call as well (`PipecatV1PipecatcallStart`), whose voice path waits synchronously for the media start. Create also creates the direct hash (another RPC), writes and reads the row; update reads and writes (api-manager has already made its own reads before the hop). The lookup inside create and update therefore gets a 1 second deadline and runs before the direct hash is created.
6. `ai-control` `update` replaces most fields (the type is preserved) and has no base URL option; `customendpoint.` AIs are not managed by `ai-control`. Updating an existing `customendpoint.` AI with `ai-control` fails closed with `ENGINE_BASE_URL_REQUIRED`.
7. Existing mismatch, not touched here: `WebhookMessage` returns `EngineKey` although the OpenAPI text says `engine_key` is write-only. The new key is never returned.
8. Compatibility of the new columns: reads use `GetDBFields(ai.AI{})` (`dbhandler/ai.go` `aiGetFromDB`, `AIList`) and the raw SQL on `ai_ais` (`dbhandler/aipromptproposal.go`) names its columns, so old code ignores added columns and old inserts rely on the column defaults.

9. Measured with httpx 0.28.1 and openai 2.15.0: an error raised while a stream is being read (`httpx.ReadError`, `RemoteProtocolError`) is not wrapped by the SDK and reaches pipecat as `Error during completion: ` (`ReadError` has an empty message, `RemoteProtocolError` a non-empty one; neither contains "connection error"), which the classifier maps to unknown; only a failure before the response headers is reported as `Connection error.`. Also measured: a 1 MiB gzip response expands to about 2 GB of resident memory within 2 to 5 seconds (depending on the host) when read line by line; an endless `103 Early Hints` response keeps the client busy without any timeout firing; `getaddrinfo` resolves `127.1`, `0x7f.1`, `0177.0.0.1` to loopback, and the same names with a trailing dot fail.
10. The OpenAPI `required` list still contains `engine_key`, so customers always send the field and may put the endpoint key there.

### 1.3 Failure modes the design closes

| # | Failure mode | Closed by |
|---|---|---|
| R1 | Hostname resolves to a public address at create time and a private one at connect (rebinding), or to a mix | connect-time validation in the runner (3.8) |
| R2 | Legacy `engine_key` reaches a customer-chosen host after a model switch | BlankKey for the new outcome, key from the dedicated column only (3.6, 3.7) |
| R3 | Operator environment credentials reach the customer host (`OPENAI_API_KEY`, org and project ids, proxy variables, `SSL_CERT_FILE`) | explicit empty key, `Omit()` headers, `trust_env=False` (3.8) |
| R4 | Redirect to a private target or a downgrade | `follow_redirects=False` |
| R5 | Key or URL in logs, error bodies, events, webhooks, cache | 3.9 |
| R6 | Connection failure invisible to the customer | `connection` category (3.10) |
| R7 | Stored row or `ai-control` bypasses the API check | validator repeated before session start (3.7) |
| R8 | Dependency drift breaks the private-attribute swap silently | pins plus runtime self-check (3.8) |
| R9 | `PUT` replaces or drops the key by accident | explicit three-state key semantics (3.2) |
| R10 | Stored key paired with a different URL by concurrent updates | URL and key written in one statement or not at all (3.4) |
| R11 | Error messages, or search-list expansion of single label names, reveal internal names to the customer (a timing difference between a private answer and NXDOMAIN remains and is accepted) | one fixed rejection message, dotted names only, absolute-name lookup (3.3) |
| R12 | A hostile server exhausts the shared single-process runner: body flood (40 MB of unterminated SSE data took 4 to 5 s and 135 to 140 MB RSS), compression bomb, endless 1xx responses, slow drip | wire guard (wire byte cap with small reads) and transport guard (identity encoding, total deadline) in 3.8; bounded per response, the remainder is accepted in R17 |
| R13 | Ownership of AI ids referenced by other resources is not verified today, and a referenced AI would bring its endpoint settings with it (the exposure `engine_key` already has) | outside this change; tracked separately |
| R14 | Ciphertext outlives its AI, or a decrypt failure is silent | cleared on delete, error log on decrypt failure (3.6) |
| R15 | A mid-stream failure never reaches the customer (item 9 above) | stream errors become `APIConnectionError` (3.8) |
| R16 | Certificate verification switched off by a code or config change | verification is not a parameter of the production builder, and a test fails if it is relaxed (3.8) |
| R17 | Accepted: the decrypted key travels over the internal RPC to every caller of the AI get, the runner can reach arbitrary public ports, and outbound requests to third parties can be caused by customer settings | same internal trust level as `engine_key` (earlier design, section 4.1); certificate and SNI checks make a customer chosen name that points at the platform itself unusable against internal services; rate limiting and abuse handling are tracked separately |
| R18 | The platform-wide runner is exhausted by sessions rather than by one response: a client that is never closed (per call for voice, per turn elsewhere), the stock pipecat client allows up to 1000 connections, keeps 100 idle ones without expiry and waits up to 600 seconds for a read (`base_llm.py` `create_client`, openai `DEFAULT_TIMEOUT`), no concurrency limit | idempotent release of client and slot, small pool, per customer and total limit counted in the runner by customer id (3.7, 3.8) |
| R19 | Rows and ciphertext of customers that were deleted remain, because ai-manager does not handle the customer deleted event | outside this change; the ciphertext is unreadable once the key set is retired |
| R20 | Customer HTTP errors (404, unknown model, 5xx) are silent in voice sessions because unknown does not notify with STT | accepted for this change; only the connection category is added (3.10), section 9 lists broader notices |
| R21 | The new `connection` category also fires for platform managed models | accepted: it follows the earlier design (section 4.1), the text is generic and, as for other categories, shown once per session |
| R22 | A running call keeps the key and URL read at its start: a deleted or replaced key (for example after a leak) and a changed URL apply from the next call or turn, up to the length of a voice call | accepted; documented in the API description and the RST; no mid-call re-read |
| R23 | A client that does not know the new fields sends `PUT` for a `customendpoint.` AI with an empty URL and gets `ENGINE_BASE_URL_REQUIRED` | accepted; fail closed, the old client cannot damage the stored settings |
| R24 | A customer's DNS server answers slowly or not at all: `asyncio.wait_for` around `loop.getaddrinfo` cancels the wait but not the worker thread, so the threads of the default executor (`min(32, cpu + 4)`) stay occupied and unrelated lookups of other sessions in the same runner wait (measured in the proof of concept environment: 26 lookups of a 15 second name with a 5 second timeout released the waiters at 5 s, and an unrelated `localhost` lookup then took 10 s) | dedicated executor, non-blocking semaphore and per customer lookup limit given back when the thread ends (3.8); four customers can still take every worker (accepted in R17) |

## 2. Decisions

| # | Decision |
|---|---|
| D1 | API fields: `engine_base_url` (string) and `engine_base_key` (write-only string). Model prefix `customendpoint.` followed by a model id with the rule of `local.` ids. |
| D2 | Key update: omitted keeps, empty string deletes, value replaces; a changed base URL discards the stored key unless the same call sends a non-empty key (3.2). |
| D3 | One new encryption key set `ENGINE_BASE_KEY_ENCRYPTION_KEYS` for ai-manager only, same format as `MCP_SECRET_ENCRYPTION_KEYS`, using `mcpserverhandler.SecretCrypto` unchanged. The name is open (section 9). |
| D4 | The key is stored as one packed `varbinary` value (`version(2) | nonce(12) | ciphertext+tag`). Decryption happens only in the `GET /v1/ais/<id>` response. |
| D5 | The connection failure category is `connection` with a fixed notice text (3.10); it applies to every OpenAI compatible provider, and its text is generic. |
| D6 | Go and Python block tables are identical and tested against one shared fixture file (3.5, appendix A). |
| D7 | Base URL rules: https only; no userinfo, query or fragment; ASCII only; at most 512 bytes; any port from 1 to 65535 (no port policy is added; see section 9). |
| D8 | `ai-control` does not manage the new fields. |
| D9 | No catalog entry and no `has_engine_base_key` read indicator in this change (section 9). |

## 3. Design

### 3.1 Names and shapes

- `ai.AI` gets `EngineBaseURL string` (`json:"engine_base_url,omitempty" db:"engine_base_url"`), `EngineBaseKeyEnc []byte` (`json:"engine_base_key_enc,omitempty" db:"engine_base_key_enc"`, ciphertext, cached with the row) and `EngineBaseKey RedactedString` (`json:"engine_base_key,omitempty" db:"-"`, plaintext, filled only by the get-by-id response; `RedactedString` is a string type in `models/ai` whose `String()`, `GoString()` and `Format` print `<redacted>`; its JSON form is the plain string because the key must cross the RPC, so the protection covers `fmt` verbs and text formatting only, and no code logs a whole `ai.AI` today; the JSON log case is covered by the hook test of 3.9 on the real paths and stays listed in R17). New `ai.Field` values `FieldEngineBaseURL`, `FieldEngineBaseKeyEnc`.
- `WebhookMessage` gets `EngineBaseURL` only (whitelist copy in `ConvertWebhookMessage`). The key, the ciphertext and the plaintext are never in it.
- Request DTOs (`listenhandler/models/request/ais.go`, both `V1DataAIsPost` and `V1DataAIsIDPut`): `EngineBaseURL string` (`engine_base_url,omitempty`) and `EngineBaseKey *string` (`engine_base_key,omitempty`). The pointer keeps omitted and empty apart end to end, like `McpServerIDs`; `omitempty` omits only a nil pointer, so a pointer to `""` is marshaled.
- OpenAPI request bodies of `POST /ais` and `PUT /ais/{id}`: `engine_base_url` and `engine_base_key`, both optional (not in `required`, which still lists `engine_key`); generated api-manager types are `EngineBaseUrl *string` and `EngineBaseKey *string`. Response schema `AIManagerAI` gets `engine_base_url`; the key is documented as write-only and is absent from the response schema. No `service_agents` counterpart exists or is added (AI configuration is admin and manager only). The URL is not a secret and travels in `WebhookMessage`, events and list responses; the docs tell customers not to put credentials in the URL path. A non-empty legacy `engine_key` sent with a `customendpoint.` model is stored as sent and never forwarded (the docs point to `engine_base_key`).

### 3.2 Key update semantics

Let `model'`, `url'`, `key'` be the request values, `model`, `url`, `enc` the stored ones. `custom(m)` means `m` has the prefix `customendpoint.`.

| Request | Result |
|---|---|
| `custom(model')`, `url' == url`, `key'` omitted | keep `enc`; neither `engine_base_url` nor `engine_base_key_enc` is written |
| `custom(model')`, `url' == url`, `key' == ""` | `enc = NULL`; `engine_base_url` is not written |
| `custom(model')`, `url' == url`, `key'` = value | `url = url'`, `enc = seal(key')` |
| `custom(model')`, `url' != url` (or `model` was not custom), `key'` omitted or `""` | `url = url'`, `enc = NULL` |
| `custom(model')`, `url' != url` (or `model` was not custom), `key'` = value | `url = url'`, `enc = seal(key')` |
| `!custom(model')` | `url'` must be empty (else 400), non-empty `key'` rejected (400), result `url = ''`, `enc = NULL` (this clears them when switching away) |

"Changed" is byte inequality of the stored string and the request string; a change in letter case counts as a change, which discards the key (safe direction). A key is 1 to 512 bytes of printable ASCII (0x21 to 0x7E), which also rules out header injection. On create the same table applies with `url`, `enc` empty. A value `key'` needs a configured key set; without one the call fails with a server error and a log line without secrets (3.6). The URL and the ciphertext are always written by one `UPDATE` statement or not at all, so a key is never stored next to a URL other than the one in the request (R10): the unchanged-and-kept case writes neither column, so a stale snapshot cannot revert them. The snapshot can be stale (1.1); the accepted effect is that a key deletion or URL change may be decided against slightly old data, never that a key is paired with an unrelated URL.

### 3.3 Base URL validation

Pure rules (`models/ai`, new `endpoint.go`), applied to the raw string with no trimming: 1 to 512 bytes, all bytes 0x21 to 0x7E; `url.Parse` succeeds; scheme `https`; no userinfo, no query (no `?` anywhere), no fragment (no `#`), not opaque; non-empty host; port, when present, from 1 to 65535; a host name consists of labels of `[A-Za-z0-9-]` that are not empty and do not start or end with `-`, separated by dots (so the name Go checks is the name the runner resolves; Go's `url.Parse` would otherwise decode escapes and accept characters that `httpx` leaves alone), contains at least one dot and does not end with a dot (single label names are resolved through resolver search lists and answer with internal timing; a trailing dot is not usable in SNI). An IP literal host is checked against the block table immediately.

Network rule `ValidateEngineBaseURL(ctx, raw)` (the resolver is a package level function variable; a non-test file `endpoint_testhook.go` exports a setter whose comment forbids production use, so tests of other packages can replace it; at most 4 validation lookups run at once in one ai-manager process, taken without blocking, and a request over that limit fails with the same `ENGINE_BASE_URL_REJECTED`, which bounds what a slow DNS server of one customer can take from the 10 RPC workers (R24 for ai-manager); the per customer share is bounded by the api-manager rate limit): runs the pure rules, then for a host name resolves with `net.Resolver.LookupNetIP` under a 1 second deadline (inside the 3 second RPC budget, 1.2 item 5), looking up the absolute name (the name plus a trailing dot; an IP literal is parsed first and never looked up) so that resolver search lists and legacy IPv4 spellings such as `127.1` cannot be expanded by the resolver, requires at least one answer and requires that no answer is in the block table (zone ids stripped). Failure types: `ErrInvalidEngineBaseURL` (pure rule; the typed 400 `INVALID_ENGINE_BASE_URL` states the rules) and `ErrEngineBaseURLRejected` (resolve failure, no answer or a blocked answer; one fixed typed 400 `ENGINE_BASE_URL_REJECTED`: "The host could not be resolved to a public address."). One message for both causes avoids an oracle for internal names (R11). Neither message echoes the URL (it may carry credentials the customer pasted).

Pure checks tying the model to the URL (`ValidateEngineEndpoint(model, baseURL)`): a `customendpoint.` model needs a URL (`ENGINE_BASE_URL_REQUIRED`); any other model with a URL is `ENGINE_BASE_URL_NOT_ALLOWED`. Key rules give `INVALID_ENGINE_BASE_KEY` and `ENGINE_BASE_KEY_NOT_ALLOWED`. `ResolveEngine` gets `OutcomeCustomEndpoint` (appended last, iota values stable): exact case-sensitive prefix `customendpoint.`, id matching `^[A-Za-z0-9][A-Za-z0-9._:/-]*$`, whole value at most 255 bytes, returns `Resolved{RunnerType: string(m), BlankKey: true}` and no `Entry` (not in the catalog; `GET /ai_models` is unchanged). A malformed id is rejected like a malformed custom OpenRouter id, without echoing the input (`engineValidationError` and `ai-control` `engineCheckError` get the prefix case).

### 3.4 Validator placement and order (ai-manager `aihandler`)

Create: `ValidateEngine` (model) -> `ValidateEngineEndpoint` -> key rules -> if custom, `ValidateEngineBaseURL` (network) -> seal the key -> `dbCreate` (the direct hash is created inside `dbCreate`, after all validation, so a rejection leaves nothing behind).
Update (after reading `preUpdateAI`): same checks; the network check runs when the model is custom and (the URL changed or the stored model was not custom). An unrelated edit of an AI whose stored URL is unchanged does not hit DNS. The key decision of 3.2 is computed once in `Update` from the `preUpdateAI` result and passed as a small value (url, sealed key, which columns to write) through `dbUpdate` to `buildUpdateFields`, which is the single place that adds the two columns; all three `Update` branches go through it. Stored rows and `ai-control` can bypass these checks, hence 3.7.

### 3.5 Block table parity

The table is in appendix A (the proof of concept table). Go (`models/ai/endpoint_block.go`, `net/netip`) and Python (`custom_endpoint_net.py`, `ipaddress`) implement the same steps: parse (fail closed on anything unparseable), drop a zone, an IPv4-mapped address is checked on the embedded IPv4, `64:ff9b::/96` on the embedded IPv4, `2002::/16` on the embedded IPv4, otherwise the v4 or v6 table. Section 4.1 of the earlier design lists "IPv4-mapped IPv6" as blocked; the proof of concept checks the embedded IPv4 (private, loopback and metadata addresses stay blocked, a mapped public address is allowed) and that behavior is kept.
One fixture, `bin-ai-manager/models/ai/testdata/endpoint_blocklist.json`, holds the CIDR lists (`v4`, `v6`, `nat64`) and a corpus of `{addr, blocked}` cases. The Go test asserts the code tables equal the file and every case; the Python test (path from the repository root) asserts the same. Editing one table without the file fails a test; editing the file fails the other language's test.

### 3.6 Key storage (ai-manager)

- Config `engine_base_key_encryption_keys` (env `ENGINE_BASE_KEY_ENCRYPTION_KEYS`) in `internal/config`, same `<version>:<base64 32 bytes>[,...]` format; the highest version encrypts, every listed version decrypts. A malformed value stops the start (like the MCP key); an empty value starts with a warning, and storing a key then fails. A separate key set means MCP key rotation never touches AI keys.
- `aihandler.NewAIHandler(..., crypto *mcpserverhandler.SecretCrypto)`; the `AIHandler` interface gets one method that fills the plaintext of a copy (`FillEngineBaseKey(ai) *ai.AI`), which `listenhandler` `processV1AIsIDGet` calls (no crypto in the listenhandler constructor); `sealEngineBaseKey` returns an error when the crypto is nil; `cmd/ai-manager` builds it with `NewSecretCrypto(cfg.EngineBaseKeyEncryptionKeys)` (a second instance next to the MCP one); `ai-control` passes `nil` (it never stores a key and never decrypts) and clears `EngineBaseKeyEnc` on the value it prints (`printJSON`), so the terminal never shows a ciphertext.
- Packed value: 2 bytes big endian key version, 12 bytes nonce, ciphertext with the 16 byte GCM tag. `sealEngineBaseKey` rejects a version above 65535; `openEngineBaseKey` rejects a value shorter than 30 bytes. Code in `pkg/aihandler/engine_base_key.go`.
- Decryption: only `listenhandler` `processV1AIsIDGet`, on a copy, right before marshal. List, create, update and delete responses carry no plaintext. A decrypt failure (for example a retired key version) is logged at error level without secrets and never fails the get: the plaintext stays empty and the ciphertext stays set, so customer paths (`aiGet` in api-manager for permission checks, update, delete) keep working, and pipecat-manager treats "ciphertext present, plaintext empty" as a hard failure (3.7).
- `AIDelete` also sets `engine_base_key_enc` to `NULL` (the URL is kept). `SecretCrypto` seals without associated data and its error texts say "mcp"; it is reused unchanged as required, so a ciphertext is not bound to the AI id or the URL (the URL and key are always rewritten together, 3.2); whoever can write the table could copy a ciphertext between rows, as with MCP secrets (accepted). During a key set rotation the replicas of ai-manager briefly differ in the highest version; a get then fails to decrypt on a replica that lacks the new version and pipecat-manager fails closed for that call, so the new version is added to every replica first and operators rotate in a quiet window; retired versions stay listed until no row uses them. Operator docs state how to generate the key set, that losing it makes stored endpoint keys unusable (fail closed, customers send the key again), and that the separate operator install repository must carry the same variable.
- `publishAIEvent` clears `EngineKey`, `EngineBaseKey` and `EngineBaseKeyEnc` on its copy. The cache holds the ciphertext only: the plaintext is never set on an object that is cached, and `db:"-"` keeps it out of every query.

### 3.8 Runner (Python)

- `custom_endpoint_net.py` (no pipecat import): `is_blocked`, `ValidatingBackend`, `ValidatingTransport`, `build_http_client`. `custom_endpoint.py`: `CustomEndpointLLMService(OpenAILLMService)` whose `create_client` builds `AsyncOpenAI` with that client; it is imported lazily inside the `customendpoint` branch of `create_llm_service`. The proof of concept is reference only and is not copied.
- Client settings: `follow_redirects=False`, `trust_env=False`, `http2=False`, `httpx.Timeout(connect=5, read=30, write=10, pool=5)`, pool `max_connections=10`, `keepalive_expiry=30`, `retries=0`, SDK `max_retries=0`, resolve timeout 5 seconds. One connect deadline of 5 seconds is shared by all addresses of an answer (the proof of concept gave each address its own 5 seconds). `connect_unix_socket` is refused. Name lookups use the absolute name (trailing dot) like the Go validator, with an IP literal parsed first and never looked up; the certificate and SNI host stay the original name.
- Name resolution (R24): the runner resolves on a dedicated `ThreadPoolExecutor` of 8 workers guarded by a `threading.Semaphore(8)` taken without blocking, plus a per customer counter of lookups in flight (at most 2). Both are given back by a done callback on the `concurrent.futures.Future` that `executor.submit` returns (`take()`, then `cf = EX.submit(...)` and `cf.add_done_callback(give)` inside a `try/except BaseException` that calls `give` itself and re-raises when `submit` fails, then `asyncio.wrap_future(cf)`), which runs when the thread ends for a running lookup and at once when a lookup that no thread has started yet is cancelled (a `finally` inside the worker function would never run in that case and the slot would leak); it is not given back when the awaiting coroutine times out, which would free a slot while the thread is still busy. The callback takes one lock because the thread and the event loop both touch the counters; a customer entry at zero is deleted. A lookup that cannot take either fails closed as a connection failure instead of queueing. There is no answer cache (a successful answer is never reused, so no stale answer and no rebinding window) and no single flight or negative cache (the semaphore and the per customer limit bound the cost without them). Residual: four customers with two slow names each can still hold all eight workers; this is accepted in R17. Limits are per instance (the runner runs as more than one instance, each with its own counters, reset on restart).
- Client lifecycle (R18): the slot is taken before the service is constructed and given back if the constructor fails. Every `CustomEndpointLLMService` has an idempotent `release()`: it sets one flag, gives the slot back synchronously first, then closes the `AsyncOpenAI` client (and so the pool) with the close shielded from cancellation and its errors swallowed. `cleanup()` is `try: await super().cleanup() finally: self.release()`. pipecat calls `cleanup()` more than once (at the end of the pipeline, then `execute_single_ai_pipeline` in its `finally`, and `RoutingLLMService` once per member), and the cleanup chain in those `finally` blocks is a sequence of awaits in which an earlier failure or a cancellation skips the later steps, so the safety net does not depend on it: `create_llm_service` records each custom service under its `pipeline_id`, and the outermost `finally` of `execute_single_ai_pipeline` and `execute_team_pipeline`, and the `/run` failure path (`except BaseException`, covering a failed initialization with a built LLM service whose STT or TTS sibling failed, or earlier team members whose later member failed), call `release_pipeline(id)`, which releases every recorded service of that pipeline and forgets the entry. The duplicate check is made once per request at the start of `/run`, before any slot is taken: a request that carries a custom endpoint and whose `pipeline_id` is already registered is refused, and a refused request registers nothing and releases nothing (the failure path calls `release_pipeline` only when this request registered the id), so the pipeline that is running keeps its slots; several custom members of one team share the id legitimately. Slots are counted per member service: per customer limit 16 and total limit 64 per runner instance, and the per customer limit is also the most custom members one team session can hold. Over a limit, `create_llm_service` raises the fixed `ValueError("custom endpoint is not available")`. The numbers (16, 64 and the lookup numbers above) are provisional and are confirmed or changed by a measurement of one session's memory and descriptors attached to the pull request, which also records the lookup failure rate when one customer starts 16 sessions at once (the per customer lookup limit fails closed without queueing); they are constants, not flags.
- Wire guard (R12, R15), in two places. (1) `ValidatingBackend` wraps the network stream it returns (and the result of `start_tls`): every `read` asks for at most 4096 bytes, yields to the event loop after each read (`await asyncio.sleep(0)`), counts all bytes received for the current request (status line, interim 1xx responses, headers, chunk framing and body) and fails the read above 4 MiB; the counter is reset when the wrapper's `write` is called (the start of a request on a pooled connection; a server cannot cause a client write), and the wrapper delegates `get_extra_info`, `is_readable` and the TLS accessors that httpcore uses; this bounds the loop time a single response can take, whatever its framing (measured: 1 byte chunks, chunk extensions and 1xx floods starved the loop for seconds with only a decoded byte cap). (2) `ValidatingTransport.handle_async_request` sets `Accept-Encoding: identity`, refuses a response whose `Content-Encoding` is anything else (httpx would decompress it), and applies a total deadline of 120 seconds to the header phase (an endless 1xx sequence) and to the whole body (a slow drip). The numbers are working assumptions: completions for a voice agent are small. The guard bounds the cost of one response (measured: a 1 byte chunk flood of 4 MiB costs about 4 seconds of loop time in small slices, with loop delays of 0.3 to 18 ms); a customer repeating it up to the session limits still adds jitter to the other sessions of the instance, which stays accepted in R17. A violation, and any `httpx.TransportError` other than a timeout raised while the body is read, is re-raised as `openai.APIConnectionError` so that pipecat reports `Error during completion: Connection error.` and the classifier of 3.10 sees it; a read timeout is left alone (pipecat maps it to the timeout category).
- TLS: certificate verification and host name checking stay on. The builder takes a different SSL context only through a class attribute test hook that production code never sets; a test asserts that without the hook the context has `verify_mode == CERT_REQUIRED` and `check_hostname` true. `api_key` is the stored key or `""`, never `None`; `default_headers` carries `Omit()` for `OpenAI-Organization` and `OpenAI-Project`; `base_url` is explicit.
- Self-check: after building the client the code verifies that the client's transport is the validating one, that no mounts or proxies exist and that the pool's network backend is the validating one, and fails closed otherwise (R8). `requirements.txt` and `pyproject.toml` pin httpx 0.28.1, httpcore 1.0.9, h11 0.16.0, anyio 4.12.1 and openai 2.15.0 (the versions in `uv.lock`); `uv.lock` is regenerated and must show no other change.
- `run.py`: the arguments `customer_id`, `llm_base_url`, `llm_base_key` flow from `PipelineRequest` in `main.py` through `init_pipeline`, `init_single_ai_pipeline` and `init_team_pipeline` into `create_llm_service(..., **options)` at its two call sites; the `customendpoint` branch of `create_llm_service` requires a `customer_id` that parses as a UUID (a missing or malformed one raises the fixed `ValueError`, so the per customer limit cannot be bypassed); the legacy `key` is ignored; a missing URL or any failure while building raises `ValueError("custom endpoint is not available")` with `from None`. `_member_llm_type` never honors a `customendpoint` service name from customer data (same invariant as `platform_openrouter`); the team path at `run.py` passes the member's base URL and key. `run.py` log lines that print the exception of a custom endpoint session (`[INIT] Pipeline initialization failed`, `[RUN] Pipeline error`, also in the team path) print a fixed text instead. `main.py`: both error paths of `/run` (`ValueError` to 400 and any other exception to 500, which put `str(e)` into the response) return a fixed detail for a custom endpoint request, and the pipeline execution failure log keeps no raw error text for it; `PipelineRequest` and `ResolvedAI` get `llm_base_url`, `llm_base_key`; `run_request` logs `customendpoint.<redacted>` instead of `llm_type`; a `RequestValidationError` handler returns a fixed body (FastAPI's default 422 body repeats the request, key included, and `pythonrunner.go` puts non-200 bodies into its error text).
- The runner checks the scheme (`https`) and the absence of userinfo before it builds the client, because it takes requests that did not pass the Go validator (it listens on the network namespace of its pipecat-manager instance); it enforces no port policy. The block table and the connect-time validation apply to every request.

## 6. Impact analysis (schema)

- Destructive operations (upgrade): none. `ADD COLUMN` only. DROP (table, column, index, constraint, view, trigger), TRUNCATE, `UPDATE`/`DELETE`/`INSERT SELECT`, type narrowing or change, default removal or change, rename, new NOT NULL/UNIQUE/FK/CHECK on existing data, enum value removal: all absent. `engine_base_url` is NOT NULL with a default, so existing rows get `''`. The downgrade drops the columns and loses their data (marked `DOWN-LOSSY`), used only for rollback.
- Old code on the new schema: `aiGetFromDB` and `AIList` select `GetDBFields(ai.AI{})` (explicit columns, `dbhandler/ai.go` lines 63 and 171), `AIActivateInsight` and `aipromptproposal.go` use explicit column lists; inserts name their columns and the new columns have defaults. Works.
- New code on the old schema: cannot happen for the service itself (the migration runs before the service listens); the other services only read the AI over RPC. Not applicable.
- Lock and duration: `ALGORITHM=INPLACE, LOCK=NONE` keeps reads and writes allowed on both engines (a rebuild on MySQL 8.0 is possible and acceptable); the table holds one row per AI configuration. The row count is not measured (no production access). Source of the claim: the migration pair ran up, down, up with the statements of section 5 on both MariaDB 12.3 and MySQL 8.0 against the baseline `ai_ais` table (which has a stored generated column and a unique index); on MySQL 8.0 an explicit `INPLACE` may rebuild the table, and `INSTANT` combined with `LOCK=NONE` is rejected there (error 1221), which is why the required `INPLACE, LOCK=NONE` form is kept. The PR repeats the run and records timings.
- Rollback: revert the code and keep the columns (compatible); the downgrade is available but lossy.
- Data loss: none on upgrade.
- No earlier migration of this service is unapplied: `bin-ai-manager/migrations` holds only `000001_baseline`, and the new files are `000002` and `000003`.

Rollout order: (0) read-only check before enabling that no `ai_ais.engine_model` starts with `customendpoint.` (validation rejected the prefix until now, so none is expected); (1) create the Komodo variable `BIN_MANAGER__AI_MANAGER_ENGINE_BASE_KEY_ENCRYPTION_KEYS` before the code change merges (a missing variable stops the container; same gate as Layer 1); (2) merge and deploy the schema change; (3) merge the code change. All services deploy automatically on merge, so the order inside the code change cannot be forced. A window in which ai-manager is new and pipecat-manager is old is fail-closed (the old pipecat-manager rejects `customendpoint.` as an unavailable model), and a new api-manager with an old ai-manager only drops the unknown fields. The runner pins ship in the pipecat-manager image together with the Go code. Known effects of mixed versions: while two ai-manager versions run, an older instance that writes an AI refreshes the shared cache entry from its older struct, so the entry lacks the new fields until the next write or expiry; a session start then fails closed (empty URL) and an update decided on that entry may drop a stored key. Both are safe-direction effects limited to AIs written during the window. After a rollback of the code, an older ai-manager does not clear the URL and ciphertext when a model is switched away and `AIDelete` does not clear the ciphertext; the stored pair stays consistent, and the next current version treats a switch away as a clearing change (3.2). A key deleted or a URL changed is persisted in the database at once; if the following cache refresh fails (errors are ignored by the existing convention), the old value can be served from the cache until it expires (24 hours); this is accepted and not specific to the new fields.

## 9. Open points (not decided here)

- Not closed here and tracked separately: R13, R17 (rate limiting and abuse handling), R19, R20.
- The provisional runner limits (3.8: 16 custom services per customer, 64 per instance) are a product-visible ceiling on concurrent calls that use customer endpoints (a team call uses one slot per custom member, so a team of five custom members allows three concurrent calls per instance); they are confirmed after the measurement.
- Port policy: any port from 1 to 65535 is allowed because nothing in the requirements restricts it; a restriction would be a new policy.
- Naming of the new key setting (`ENGINE_BASE_KEY_ENCRYPTION_KEYS`) is open (section 4.1 of the earlier design lists it as open).
- A read indicator that a key is stored (like `has_secret` of MCP servers) is not part of the requirements; without it a client cannot show whether a key is set. Proposed as a follow-up.
- Catalog entry for discovery of the `customendpoint.` prefix in `GET /ai_models`: not added; the prefix is documented in OpenAPI and RST.
- Outside this change and only reported: `WebhookMessage` returning the legacy `engine_key` (section 1.2, item 7); the legacy plaintext `Session.LLMKey` reaching text logs; ownership checks for AI ids referenced by other resources (R13), tracked separately; the authentication notice text, which mentions a custom engine key and is shown for a 401 of a customer server as well (kept).
- The runner tests are not part of CI; real-library tests are run by hand and their output is attached to the pull request. A pytest step for the pure runner modules (block table, transport) would be a separate CI change.
