# Provider independent SMS segments, automatic MMS promotion and flat MMS billing (design)

The platform computes the SMS segment count itself, from the text and the international standard (3GPP TS 23.038 and TS 23.040), whatever the provider counts. A text that needs more than one segment (161 or more GSM-7 septets, 71 or more UCS-2 units) is promoted to a text only MMS (LMS) and charged the flat MMS rate; a text of one segment is an SMS at the SMS rate. The change also fixes two defects of the outbound path: the delivery status of Telnyx messages is never updated, and the provider order is random.

Services: `bin-message-manager` (core), `bin-openapi-manager` and the RST docs in `bin-api-manager/docsdev`; `bin-billing-manager` gets a test only (Part A decision 4). One pull request. `bin-api-manager` needs no code change (see Part 0, item 2).

## Part A. Design

### 1. Segment calculator

A new package `bin-message-manager/pkg/segmenthandler` (one consumer, so it stays in the service, not in `bin-common-handler`). Pure function `Count(text string) Result{Encoding, Units, Segments, Chars}`.

- Alphabet: the GSM 7 bit default alphabet and its extension table of TS 23.038 section 6.2.1. A character in the base table costs 1 septet; the extension characters (`|^€{}[]~\` and form feed) cost 2 septets (escape plus character).
- If every character is in the base or extension table the encoding is GSM-7, otherwise the whole text is UCS-2 and the unit is a UTF-16 code unit (a character outside the BMP costs 2 units). One character outside the alphabet switches the whole text.
- Single message: at most 160 septets or 70 UCS-2 units (TS 23.038 4 and 6.1.2.1.1). Concatenated message: 153 septets or 67 units per segment (TS 23.040 9.2.3.24.1, 8 bit reference: 140 - 6 octets of header, 7 bit alignment gives 153). The 16 bit reference variant gives 152 and 66 and is not used.
- An escape pair and a surrogate pair are never split between two segments, so segments are packed greedily, not by integer division. Empty text counts as 1 segment.
- No smart encoding: the text is never transliterated and is sent as the customer wrote it. Telnyx has smart encoding on by default (`encoding=auto`) and Bird has it off, so a provider may report fewer segments than we do for a text with typographic quotes. Our count is the charge; the provider count is kept for comparison (decision 3).
- Input: Go `range` over the string. An invalid UTF-8 byte is read as U+FFFD (not in the alphabet, so UCS-2, 1 unit); Go's JSON decoder does not reject invalid UTF-8 but replaces it with U+FFFD, so the text is counted, charged and delivered with the replacement character; no new error is added. Known limit: a combined emoji sequence (zero width joiner) is several code points and may be split between two segments, as a handset would.
- Tests: boundary table (160/161 GSM-7, 70/71 UCS-2, 153 x n, 67 x n, extension character on a boundary, surrogate pair on a boundary, mixed text, text made only of extension characters or emoji, a U+FFFD from invalid input). The expected values come from the 3GPP text, not from the implementation.

### 2. Promotion in `Send`

`Send` computes `Count(text)` after the identity gate. Constants in `pkg/messagehandler`:

- `smsPromoteSegments = 1` (plan C, maintainer decision): a text that needs more than 1 segment is promoted. For a single message the standard limit is 160 septets or 70 UCS-2 units, so a text of 161 or more septets (an extension character counts 2) or 71 or more UTF-16 units (an emoji counts 2) is promoted. At the limit of one segment the greedy packing of decision 1 does not matter: the text fits one segment exactly when septets <= 160 or units <= 70. Alternatives 2, 3 and 5 were considered in the research and discarded by the maintainer for the sake of a simple and consistent price.
- `smsMaxSegments = 10`: a text without media that needs more than 10 segments is rejected with `TEXT_TOO_LONG` (InvalidArgument). 10 is the documented Telnyx limit. The Messagebird endpoint used by this service (`rest.messagebird.com/messages`) has no limit that the research could verify (the old Channels API pages recommend 9 parts, the newer Bird API allows 12, and neither is this endpoint), so 10 is the only documented bound of the chain and is used as the conservative limit. The 2000 character limit (`mmsTextMaxLength`, counted with `utf8.RuneCountInString`, `media.go:28,55`) stays for an MMS with attached media; for a text without media the 10 segment rule always applies first (2000 characters is already more than 10 segments). The vendor pages differ on the Telnyx limit (10 segments or 1600 characters, research report section 2). Today such a long text is accepted and fails at the providers.

Not promoted: type `sms`, `parts` = 1. Promoted: type `mms`, no media, `parts` = the computed segment count (2 to 10). The internal `create()` already takes the message type. An MMS with attached media (`SendMMS`) is unchanged except that its targets get `parts` = 1. The promotion decision never looks at the destination country or the provider. The only destination rule is the existing +1 rule of the dispatch (decision 6), which decides how a promoted message is sent, not whether it is promoted.

Order inside `Send` (the `message_created` event is published inside `dbCreate`, before the provider call, so type and parts must be final before `create`): identity gate; validation of `source` (required, a nil source would be dereferenced by the +1 rule) and of the destinations (the checks that `SendMMS` already makes: SOURCE_REQUIRED, DESTINATION_REQUIRED); `Count`; `TEXT_TOO_LONG`; build targets with `parts`; balance check with the type decided here (`ReferenceTypeSMS` or `ReferenceTypeMMS`); `create(type, parts)`; asynchronous dispatch. A test asserts that the message passed to `MessageCreate` already has the type and the `parts`, and that the balance check type equals it. The +1 rule is the existing prefix test (`HasPrefix "+1"`, no length check); it also matches the Caribbean +1 countries and any input beginning with +1. This is a known limit of the existing rule and is kept.


### 3. Data model (no column change)

`target.Target` is stored in the JSON column `message_messages.targets`, so new keys need no change of the table definition and are compatible in both directions during a rolling deploy (old code ignores unknown keys, new code reads missing keys as zero).

- `Parts int` (existing): the platform segment count of the text (what the standard says), for an `sms` and for a promoted message; 1 for an MMS with attached media. The meaning changes from "what the provider said" to "what the platform computed". It is written once at creation and never changed afterwards. It is shown in the API and is not used for billing. It is not `omitempty`.
- `ProviderParts int` (new, `json:"provider_parts,omitempty"`): what the provider reported, for comparison only.
- `ProviderReferenceID string` (new, `json:"provider_reference_id,omitempty"`): the provider message id of this target. Telnyx has one id per target; Messagebird has one id for all recipients, copied to each target. The message level column `provider_reference_id` stays unused: it holds one value, which cannot represent several Telnyx targets, and a second lookup path would only cover the single target case.

The two new keys are internal. `WebhookMessage.Targets` becomes `[]WebhookTarget` (destination, status, parts, tm_update; the same JSON as today) so provider ids are not exposed through the API or the customer webhooks. The internal event bus is different: `PublishWebhookEvent` marshals the full internal `Message` (Part 0, item 10), and timeline-manager stores and serves it. One helper builds the published copy and every `PublishWebhookEvent` call site uses it (`dbCreate`, `dbUpdateTargets`, `dbUpdateMedias`, `dbDelete`): the copy has its own `Targets` slice (deep copy, so the stored and returned message keep the ids) with `ProviderReferenceID` and `ProviderParts` cleared (`omitempty` removes the keys). The RPC response to the internal callers still carries the full `Message`; api-manager converts it with `ConvertWebhookMessage`. Consumers that unmarshal the event into `message.Message` (billing, conversation-manager) keep working. New code does not log provider ids or text (the older send code logs `text` and `targets` at debug level; the new code paths remove those fields from their log entries); the receipt match relies on the id being hard to guess.

A mismatch of `Parts` and `ProviderParts` is counted only for a target that went through the SMS chain (provider answer for an `sms` or for a promoted message sent as SMS segments), once per target when the provider count is first stored. It increments `message_manager_segment_mismatch_total{provider}` and logs the two counts (no text, no number). Targets accepted at the MMS stage are not compared.

Inbound messages: `Parts` is also computed by the platform (SMS) and the provider count goes to `ProviderParts`. Billing keeps charging one unit for an inbound message (Part 0, item 4).

### 4. Billing (plan C: no billing-manager code change)

With the limit at one segment, an outbound `sms` is always a single segment (an inbound `sms` can have more segments and is charged one unit as today) and a longer text is a promoted MMS at a flat rate, so there is no segment multiplication anywhere. `bin-billing-manager` is not changed.

- Balance check (`Send`): SMS: `ReferenceTypeSMS` with `count = len(targets)` (as today); promoted: `ReferenceTypeMMS` with `count = len(targets)`. `IsValidBalance` already multiplies the rate by `count`.
- Charge: `EventMMMessageCreated` (`billinghandler/event.go`) selects the rate from the message type through `messageBillingTypes`, so a created event of type `mms` is charged at the MMS rate once per target and an `sms` at the SMS rate, exactly as for an attached MMS. `billableUnits = 1` stays. The balance check and the charge use the same message type, which is decided once in `Send` from one `Count` result.
- `Target.Parts` is informational (platform segment count, decision 3). Billing does not read it, so a wrong or zero `parts` cannot change a charge.
- Idempotency: unchanged (per target reference id `NewV5(message id, "target-i")`, a redelivered event is skipped by the existing "billing already ended" check).
- The price is fixed when the message is created and never changes when a provider later falls back (decision 6, Q2 and Q3): a promoted message is charged 0.03 per recipient whether it is finally sent as an MMS or as SMS segments.
- Deploy and rollback have no ordering constraint between the services (no contract change). Old billing-manager already charges type `mms` at the MMS rate.
- A billing-manager test is added for the promoted shape (type `mms`, no media) to prove the above; no production billing code changes.


### 5. Receipt handling (defect A)

- `hookTelnyx` processes `message.received` as inbound (unchanged), `message.sent` and `message.finalized` as receipts for outbound messages, and ignores every other event type with a debug log.
- A receipt is matched by the Telnyx message id (`payload.id`) against `Target.ProviderReferenceID`. The id must parse as a UUID, otherwise the receipt is ignored with a debug log before any query (it can never match, so a redelivery is pointless and the answer is 200). New `dbhandler.MessageListByProviderReference(ref, since)` (with `MessageUpdateTargetsIf` and a database read that bypasses the cache, `messageGetFromDB` exported under a new name; the dbhandler mock is regenerated): `direction = 'outbound' AND tm_create >= since AND targets LIKE '%<id>%'`, and the exact id is compared in Go. There is no `provider_name` condition because the stored provider of a mixed message is the one that accepted the most targets. `since` is 7 days. The query scans the rows of the window, not the history.
- No index is added. The columns `tm_create` and `direction` have no index, so the `LIKE` query reads the whole table and filters; at the measured size (Part B) this is negligible;  Choosing this over the existing `provider_reference_id` column gains correct matching of multi target Telnyx messages at the cost of that scan. The trigger for an index on `tm_create` (or a dedicated id table) is a lookup p95 above 200 ms or more than 100000 rows in the table, measured, not assumed.
- Status mapping (Telnyx `to[].status`): `sent` -> `sent`; `delivered` -> `delivered`; `delivery_failed`, `sending_failed` -> `failed`; `delivery_unconfirmed` -> `dlr_timeout`; others keep the current status. Order: `queued` < `sent` < final (`delivered`, `failed`, `dlr_timeout`, `gw_timeout`). A receipt only moves a target to a higher rank; a final state is never replaced, so repeated, late or reordered receipts are harmless. `ProviderParts` is set from `payload.parts`; the platform `Parts` is never touched.
- One helper changes targets for both the receipts and the dispatcher: `updateTargets(ctx, id, fn)` (the provider name is set by an optional argument of the same call) reads the message from the database (not the cache), applies `fn` to the target slice and writes it with `dbhandler.MessageUpdateTargetsIf(id, prevTMUpdate, targets)`, an update whose `WHERE` compares `tm_update` (`IS NULL` when the message was never updated; the update sets a new `tm_update`). Zero affected rows means a concurrent write: read again and retry with a random delay of 0 to 50 ms, at most 12 tries, then return an error. Each round at least one writer wins, and at most 10 dispatcher writers run at the same time (plus a few receipts), so 12 tries cover the expected contention; the total delay stays below about 0.6 seconds (a broadcast with many targets can produce many concurrent receipts; a single target atomic `JSON_SET` is not used because MariaDB and MySQL differ and the CAS works on both). The `tm_update` comparison depends on the `datetime(6)` round trip of the driver; it is proved on the MariaDB and MySQL scratch engines, not on sqlite, and an ABA within the same microsecond is accepted as a very low risk. After a successful write the cache entry is refreshed as `MessageUpdate` does today, and the `message_updated` event is published by the existing path.
- Dispatcher merge rule: the dispatcher no longer overwrites the whole slice at the end. As each target is accepted, `fn` sets its `ProviderReferenceID`, `ProviderParts` and status only if the stored status is still `queued` (a receipt that arrived first is kept; for Telnyx this rule only matters when a receipt finds the id, which exists only after this write, so it protects against the final merge write of the batch overwriting a newer status). The provider name and final `failed` marks use the same helper. Every provider call takes an `onResult(i, SendResult)` callback that the provider invokes inside the goroutine of target `i` right after its request returns; the dispatcher's callback calls `updateTargets` without publishing an event, so the id is stored per accepted target while the rest of the batch is still running, not after the whole batch. The callback is best effort: a failed write keeps the result in memory and the final merge write of the batch (same helper, one `message_updated` event for the whole batch) writes it again. At most 10 callbacks run at the same time (the concurrency of `sendMMSTargets`), which bounds the contention on the CAS. Receipts publish `message_updated` for each status change. For a receipt that lists several `to` entries, the status is read from the entry whose phone number equals the matched target's destination.
- Error contract (receipts). Inbound (`message.received`): unchanged, every error is logged and answered 200 (a redelivery would create a duplicate message). The event type is decided first, before the `len(To) == 0` check. Receipt events (`message.sent`, `message.finalized`) of a payload whose `direction` is not `outbound` are ignored. A database error, or an update conflict that is not resolved after the retries, is wrapped in the sentinel `ErrReceiptRetry`, and `processV1HooksPost` answers 500 when `errors.Is(err, ErrReceiptRetry)` (the pkg/errors wrapper supports `Unwrap`); the 500 reaches hook-manager's answer and the provider redelivers, and a receipt is safe to process twice because of the rank rule. No matching message is never an error: it is answered 200, logged and counted in `message_manager_receipt_unmatched_total`. This keeps a deploy (messages sent earlier have no stored id), other senders on the same account and targets whose result was unknown from answering 500 on the endpoint that also receives inbound messages, which could make the provider warn about or disable it. The cost is the residual risk that a receipt arrives before the id write of its target (the write is per target and right after the provider answer, and a receipt follows an accepted message by much longer than that) or that all 12 tries of the id write fail (the id is then written by the final merge of the batch, up to 5 minutes later, and a receipt in between is lost, leaving the target `queued`); the unmatched counter makes both visible. The provider retry count and interval are not documented in the sources read, so the design does not depend on redelivery for correctness. hook-manager calls message-manager with a 3 second timeout, so the receipt path keeps its own work below about 1 second; if hook-manager still times out, the second processing is a no-op by the rank rule. Messages sent before this change have no stored id and are not corrected (out of scope).

  | Case | Answer | Log or counter |
  |---|---|---|
  | `meta.attempt` missing (0), future `occurred_at` | not used by any rule, processed normally | none |
  | `to` empty in a receipt | 200, nothing to update | debug log |
  | id is not a UUID | 200 | debug log |
  | no message with the id | 200 | `message_manager_receipt_unmatched_total` |
  | id matches but no `to[]` entry equals the target destination | 200, the status of the first entry is not used | warn log |
  | matched target already in a final state | 200, no write, no event | none |
  | database error or conflict not resolved after 12 tries | 500 | error log |
  | `direction` not `outbound` | 200 | debug log |

### 6. Dispatch and provider order (defect B)

Per target outcomes, as the MMS path already has: `SendResult{Outcome, ProviderReferenceID, ProviderParts}` with `Accepted`, `Rejected` (definitive 4xx other than 408, `requestexternal.IsDefinitiveRejection`) and `Failed` (result unknown: timeout, network, 5xx). `MMSProvider.SendMMS` changes from `[]MMSOutcome` to `[]SendResult` and both SMS and MMS providers take the `onResult` callback of decision 5 (the mocks are regenerated and the tests of `dispatchMMS` and `provider_mms` are updated). The SMS providers return the same type. Telnyx SMS reuses `sendMMSTargets` (at most 10 requests at a time, 30 second timeout each) instead of an unbounded goroutine per target; Messagebird sends one request for its targets and matches the recipients of the response by digits (a target missing from the response is treated as accepted with status `queued`, because the request as a whole was accepted; the Messagebird status strings are kept as they are today).

- SMS (type `sms`): an explicit ordered slice `[]namedSMSProvider{telnyx, messagebird}` built in `NewMessageHandler` (order: Q4). The remaining targets go to the first provider. `Accepted` is recorded; `Rejected` targets go to the next provider; `Failed` targets are marked `failed` and are not retried (a retry could duplicate a message that was in fact accepted); after the last provider the `Rejected` targets are marked `failed`. The goroutine uses a timeout context (as `dispatchMMS`) and writes the final results with `context.WithoutCancel` and its own timeout, so a result is always written. The accepted target status stays `queued` for Telnyx (a receipt moves it) and the provider status for Messagebird.
- Promoted (type `mms`, no media): the existing MMS chain of `dispatchMMS` runs first. `mmsFallbackEligible` stays in the core (it is the existing rule) and is reused: for a promoted message a target that is not +1 to +1 skips the MMS stage and goes straight to the SMS chain, which removes the request that Telnyx answers with 40301 for a Korean destination. An attached MMS keeps today's behavior (Telnyx is always tried first), so no behavior of VOIP-1679 changes. Targets that no MMS provider accepted use the SMS chain above as segments. If the SMS chain also rejects (for example a provider limit on the number of segments) the target is `failed`. A message can contain destinations on both sides of this rule; the message `type` stays `mms` for all of them and each target is dispatched on its own. The cases are: sender that is not a +1 number (alphanumeric sender id, short code, a number of another country) or destination that is not a +1 number: no MMS request is made, the target goes straight to the SMS chain; +1 to +1: the MMS stage runs, and a `Rejected` answer (including a sender the provider refuses for MMS) falls back to the SMS chain; a `Failed` answer (result unknown) is not retried. `message_manager_promoted_fallback_total{reason,segments}` counts targets of a promoted message that were sent as SMS segments, by segment count (at most 10 values). `dispatchMMS` gets a `promoted` parameter and an SMS-chain hand-over, because today it marks a `Rejected` ineligible target `failed` (`send_mms.go:175-180`) and says in its comment that an MMS is never sent as text only. With `promoted == true`: (1) before stage 1 the targets are split; a target that is not +1 to +1 goes directly to the SMS chain; (2) a `Rejected` outcome of the Telnyx stage goes to the Messagebird MMS stage when `mmsFallbackEligible`, and every target that no MMS stage accepted with `Rejected` goes to the SMS chain; (3) `Failed` (unknown) is never retried. With `promoted == false` (an attached MMS) the function is unchanged, and a regression test asserts it. Worst case for a +1 to +1 promoted target: Telnyx MMS, Messagebird MMS, Telnyx SMS, Messagebird SMS, four requests; to keep it simple, the reason of a `Rejected` answer is not inspected (a 4xx caused by a wrong number is refused again by the next stages, which costs requests but no money because a rejected request is not billed by the provider as far as the documentation says).
- `media_urls` is left out of the Telnyx MMS body when the list is empty. Until a text only MMS has been accepted by Telnyx and by Messagebird (neither is verified, Q7), each promoted message from a +1 sender to a +1 number may spend up to two rejected MMS requests before the SMS fallback. Two metrics make Q7 observable: `message_manager_promoted_mms_total{provider,outcome}` (outcome `accepted`, `rejected`, `failed`: the text only MMS acceptance) and `message_manager_promoted_fallback_total{reason,segments}` (reason `ineligible` for a target that skipped the MMS stage, `rejected` for a target whose MMS stage was refused; segments 2 to 10), which also separates the cost from non +1 traffic from the cost of refused MMS. The alert rule is a proposal for the operations side: a `rejected` share above 50 percent of `promoted_mms_total` over a day means the text only MMS is not accepted.
- The provider recorded for the message is the provider that accepted the most targets, as `dispatchMMS` does today.
- Implementation order: the `*ProviderError` conversion of both SMS providers comes first, because `IsDefinitiveRejection` is false for the current `fmt.Errorf` errors and the whole chain depends on it. 429, 402 and 403 are 4xx and count as `Rejected` (the provider did not accept the message, so the next provider may); a 2xx answer whose body cannot be parsed counts as `Failed` (unknown, the target is marked `failed` as the MMS path does today, even though the message may have been sent). A very large recipient list is bounded by the concurrency of 10 and the 5 minute limit of the MMS path; targets not tried in time are `failed` (the same rule as the MMS path, new for SMS).
- Provider errors become `*ProviderError{Provider, StatusCode, Detail}` for both SMS providers. `Detail` is the provider error `code` and `description` only (parsed from the JSON body, digit runs of 6 or more replaced by `<num>`, at most 200 characters), never the raw body, and is written to the log only. The Messagebird 422 reason is therefore visible in the log, and it settles whether the cause is the length, a sender or the +1 destination.

### 7. API, OpenAPI and RST

- `MessageManagerTarget.parts`: description changed to the platform segment count of the text, computed from the standard whatever the provider counts. It is 1 for an SMS of one segment and for an MMS with attached media, and 2 to 10 for a text that was promoted to `mms` (it stays the segment count even when the MMS stage accepts the message, and it is not the charged unit: a promoted message is charged one MMS rate per recipient). An inbound SMS can have more than 1. No new field. `provider_parts` and `provider_reference_id` are not in the spec.
- `MessageManagerMessage.type`: description states that a text longer than the limit is returned as `mms`. Customer facing note (no announcement is needed, maintainer decision): a text of 161 or more GSM-7 septets or 71 or more UCS-2 units now appears as `mms` in the API, the usage and the invoice, with the MMS rate for every recipient whatever the destination country.
- RST (`message_overview.rst`, `message_struct_message.rst`, `message_tutorial.rst`, billing pages): segment rules with the 160/70 and 153/67 table, the promotion limit and the 2000 character limit, the flat MMS charge for a promoted text (the charge does not depend on the segment count or on the final sent form), and that `type` can be `mms` for a text only message, and that a customer who subscribes to message webhooks now also receives `message_updated` when the delivery status of an SMS changes (previously the status of an outbound Telnyx message never changed). Rebuilt HTML is committed with the sources (root rule). The RST also states that `parts` is the segment count and not the charged unit.

## Decisions (resolved and open)

Reference prices (current rate table, provisional MMS rate): customer price per recipient: SMS of one segment (up to 160 GSM-7 septets or 70 UCS-2 units) = 0.01; promoted MMS = 0.03 flat, whatever the segment count and whatever the provider finally sends. All cost figures below are US reference figures for Telnyx (0.0075 to 0.009 per segment including the carrier fee, research report section 7; a text only MMS 0.015 to 0.025, unverified). The Messagebird price for this route and every Korean cost are not known, and the Korean byte rules are not applied here (they stay inside the provider path).

Consequence of plan C on cost (information). ## Part B. Schema impact analysis

There is no schema change: no migration file, no column, no index. The new `targets` keys live inside an existing JSON column. The analysis below is the proof for the five items of the schema rule.

- a-1 Destructive: none. No DDL and no data statement; the code adds optional JSON keys.
- a-2 Rolling deploy: old code ignores the new keys (Go `encoding/json`); new code reads missing keys as zero. Old code on rows written by the new code and new code on old rows both work. There is no schema step and no contract change between the services, so there is no deploy ordering.
- a-3 Lock and duration: none, there is no DDL. Table size: measured read only (one `START TRANSACTION READ ONLY` count, no personal data); the table is very small, so the receipt lookup reads a small number of small rows. The exact figures stay in the work card, not in this public document.
- a-4 Rollback: revert the code. Rows written by the new code keep the extra JSON keys, which old code ignores.
- a-5 Data loss: none.
- Verification of the `LIKE` and the `tm_update` guarded update runs against scratch MariaDB and MySQL 8.0 containers (not sqlite), because the `datetime(6)` round trip and the JSON column behave per engine. The result is added to the PR body. `scripts/verify-service-migrations.sh` is not needed because no migration changes.
