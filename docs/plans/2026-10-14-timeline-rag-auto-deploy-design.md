# Auto deploy for bin-timeline-manager and bin-rag-manager (VOIP-1595)

Follows `2026-10-14-main-auto-deploy-phase2-design.md`. Those two services were kept out of the auto-deploy list because they apply database migrations at startup. They now deploy automatically as well; the human approval click is replaced by a stronger review of database schema changes (see F3).

## Findings (measured 2026-10-14, read-only)

- F1. Both workflows in `config_work.yml` still have the approval-gated shape `build-approval -> test -> build -> deploy` (deploy job `<svc>-deploy` with `deploy_filters`, no `serial-group`, no stale-deploy guard).
- F2. Newest deployed commit per service (image tag of the running Komodo stack, listed by the Komodo read API `ListStacks`): bin-timeline-manager `d82c03073`, bin-rag-manager `ec3d0790e`. Commits that touch each service directory after that revision on `main`: 0 for both, and 0 of them touch `<svc>/migrations`. A service image also compiles the packages of other modules it imports (more than 130 package directories, resolved through the `replace` lines in `go.mod`; the exact count depends on how test-only packages are counted), so the delta that a first automatic deploy ships is the change of those packages, measured with `go list -deps` and `git diff <deployed revision> HEAD` on their non-test Go files (`_test.go` and `mock_*.go` files and documentation are excluded; mock files are linked into the binary but only used by tests). bin-timeline-manager: 0 changed files. bin-rag-manager: 32 changed non-test files in 17 dependency package directories (1,467 lines added and 96 deleted; mostly request-handler client methods and model fields for the AI builder and contact features in `bin-common-handler`, `bin-ai-manager`, `bin-flow-manager`, `bin-pipecat-manager`, `bin-hook-manager`, `bin-direct-manager`, `bin-contact-manager`, `bin-call-manager`), all merged to `main` with their own tests. One of them, in `bin-common-handler/pkg/rabbitmqhandler`, is on a path bin-rag-manager runs (`ConsumeRPC`); it only rewrites an error string used in logs. bin-rag-manager calls a single request-handler method (`StorageV1FileGet`) and none of the changed ones. We did not review these 32 files for runtime behavior beyond that; this is the same code that an approval click on today's `main` would deploy, so the first automatic deploy of bin-rag-manager is not a deploy of unchanged code and must be reported that way.
- F3. Both services run `migrate.Up` at startup, so a merge that adds a migration becomes a production schema change right after the merge. That risk is handled by the schema change verification described in `CLAUDE.md` (written impact analysis, independent re-verification, upgrade and downgrade run on a scratch database, destructive operations stay with a human, and a check for earlier unapplied migrations), not by an approval click.
- F4. `check-auto-deploy-config.rb` hard-codes both services in `DENY`, and `check-auto-deploy-config.bats` uses `bin-timeline-manager` as its approval-kept example in nine test cases.
- F5. Old `on_hold` approval workflows of these services exist in older main pipelines (2 for bin-timeline-manager within the 90 day window of the API). Approving one later would run the old, unguarded job definitions for its old revision.

## Change

1. `config_work.yml`: convert both workflows to the pilot shape used by the other auto-deploy services (`build-approval` and `<svc>-test` use `non_main_filters`, `<svc>-test-auto` uses `deploy_filters`, build requires both, deploy uses `deploy_filters` plus `serial-group`), and add `DEPLOY_REQUIRE_LATEST_FOR_PATHS="<svc>"` to each deploy command. Nothing else in the file changes (verified by parsing both versions and comparing every workflow and job).
2. `auto-deploy-services.txt`: add both names, keep the list sorted, and drop them from the never-allowed comment.
3. `check-auto-deploy-config.rb`: remove both names from `DENY`. The remaining deny list is `bin-trigger-sender`, `voip-asterisk-proxy`, `voip-rtpengine-proxy`, `voip-kamailio-proxy`.
4. Policy text: the human-confirmation paragraph in `CLAUDE.md` and the two merge-rule passages in `docs/workflows/git-workflow-guide.md` now match the new behavior (destructive or ambiguous schema changes and `monorepo-monitoring` stay with a human; other migration PRs are merged by QA after the strengthened verification; production apply of `bin-dbscheme-manager` stays manual). The Deploy paragraphs of the two service READMEs still describe a manual deploy; they are left unchanged on purpose, because any change under a service directory arms that service workflow and would deploy it at the merge of this change.
5. `check-auto-deploy-config.bats`: no real service remains approval-kept in the standard shape, so the approval-kept cases run on a fixture workflow (`tests/fixtures/keep-workflow.yml`, `keep-deploy-job.yml`, inserted by `add_keep_fixture`). Two cases are added: removing either service from the allowlist fails, and removing either guard line fails.

## What the merge does

This change touches `.circleci/`, `docs/` and `CLAUDE.md` only. The path mapping arms only `shell-tests` and `lint-config-check` for those paths, so the merge itself deploys nothing. That is derived from the mapping and the file list; the throwaway branch pipeline of the verification plan (step 2) is the required evidence of how CircleCI really loads the merged configuration. Each service gets its first automatic deploy on the next merge that touches its directory. Do not add any file under `bin-timeline-manager/` or `bin-rag-manager/` to this change.

## Out of scope

- Migration logic of the two services and the production apply step of `bin-dbscheme-manager` (a separate design).
- The four services that stay approval-kept.

## Risks and mitigations

- First automatic deploy ships unexpected code: F2 shows 0 pending service commits and, for bin-rag-manager, 32 changed files in dependency packages (one on a path it runs, a log string). Re-run the dependency measurement from F2 immediately before merge (`go list -deps` of the service, then `git diff <deployed revision> origin/main` over those package directories); any new change must be listed and accepted.
- A later migration reaches production without a human: covered by the schema change verification in `CLAUDE.md`; destructive or ambiguous changes still need a human.
- Two replicas run the migration at the same time: both services run with two replicas in the Komodo compose files that production uses (the old Kubernetes manifest of bin-rag-manager is not a deploy path). For bin-rag-manager (PostgreSQL) golang-migrate takes a database advisory lock. For bin-timeline-manager (ClickHouse) the driver lock is only an in-process flag, so both replicas can run the same pending migration at once; a statement that is not idempotent (for example an `ADD COLUMN` without `IF NOT EXISTS`) can fail on one replica and leave the version dirty. The schema verification therefore requires ClickHouse migrations to be idempotent. The two services use different databases, so a simultaneous deploy of both has no shared-database conflict; their `serial-group` values are per service.
- Stale old `on_hold` workflows: cancel them right after the merge (F5).
- Rollback of this change: remove the two names from the allowlist and revert the workflow blocks. Later pipelines are approval-gated again; a pipeline already running is not stopped.
- Rolling back a bad deployment: redeploying an older image does not work after a migration was applied. The older image does not contain the newer migration files, so `m.Up()` cannot find the database's current version in its source and returns an error; both services return that error from startup and exit (`cmd/timeline-manager/main.go`, `cmd/rag-manager/main.go`). Rollback is therefore a forward fix: a revert commit that touches the service directory, which builds and deploys a new image that still carries the migration files, or a human adjusting the migration version table. Re-running an old pipeline is also blocked by the stale-deploy guard (`DEPLOY_SUPERSEDED`), and a revert that touches only a dependency package does not arm the service workflow through the path mapping. The verification of a schema change therefore asks for compatibility in both directions during a rolling deploy (old replicas running against the new schema and new replicas against the old one), not for a safe rollback.
- Failed or interrupted migration: golang-migrate marks the version dirty and the service cannot start until a human repairs it. For bin-rag-manager (PostgreSQL) that means fixing the schema by hand and forcing the version. For bin-timeline-manager (ClickHouse) the service documentation (`bin-timeline-manager/docs/operations.md`) describes the repair of the version table. The deploy script's running check (three consecutive running samples after Komodo reports the deploy complete) catches a crash loop that begins at startup; a failure that happens later than that window is not detected by the pipeline and is found by the post-merge verification and service health checks.
