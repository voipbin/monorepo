# MMS send support, P2 (conversation, flow action and AI tool)

Supplement to `2026-11-06-mms-send-design.md` (P1 sending core, merged). P2 adds three callers of the P1 RPC `MessageV1MessageSendMMS`. P3 (receiving MMS) is independent of P2. Media is always given as storage file ids (uploaded with type `media`); arbitrary URLs are not accepted anywhere.

## Part 0. Ticket review and analysis

Every claim was assumed wrong and re-checked on `origin/main` (`5a0cb17ec`, no newer commit). No open or merged pull request other than P1 touches MMS.

### Claims that hold
- `smshandler.Send` takes only `text` and calls `MessageV1MessageSend` (`bin-conversation-manager/pkg/smshandler/send.go`). `messagehandler.sendSMS` stores `medias` in the message record but does not hand them to `smsHandler.Send`.
- `actionHandleMessageSend` (`bin-flow-manager/pkg/activeflowhandler/actionhandle.go`) and `toolHandleMessageSend` (`bin-ai-manager/pkg/aicallhandler/tool.go`) both unmarshal `fmaction.OptionMessageSend{Source, Destinations, Text}` and call `MessageV1MessageSend`. The AI tool definition (`toolhandler/definitions.go`, `send_message`) and the prompt line (`builderhandler/prompt.go`, "send an SMS text message") describe SMS only.
- P1 provides `MessageV1MessageSendMMS(ctx, id, customerID, source, destinations, text, medias []uuid.UUID)` (30 second timeout). message-manager enforces: at most 10 files, owner equals the sender customer (not found, deleted and foreign all give `MEDIA_NOT_FOUND`), upload type `media`, extension and size limits, duplicates, nil ids. So an id invented by an LLM or a flow author cannot reach another customer's file.

### Corrections and additions
1. How a file id travels through the conversation media has a direct answer: conversation `media.Media` embeds `commonidentity.Identity` (`ID`, `CustomerID`). `Media.ID` carries the storage file id. `message.Medias` is a json column (`db:"medias,json"`), so the id is stored with the message and no schema change is needed. `Type` and `Filename` stay informational.
2. The public API drops the medias: `server/conversations.go` (`PostConversationsIdMessages`) and `server/service_agents_conversations.go` always pass `[]cvmedia.Media{}`, although the spec already has a required `medias` array in the request. Changing only conversation-manager would make the feature unreachable for customers. Both handlers must pass the medias on. This is part of the requested "conversation" integration, not a new feature.
3. `ConversationV1MessageSend` already uses a 30 second timeout, so no change in `bin-common-handler` is needed (the timeout is longer than the P1 media check deadline of 10 seconds).
4. `fmaction.OptionMessageSend` is shared by the flow action and the AI tool, so one new field serves both. The Flow AI Builder clears every `ref:"resource"` field that the model writes and never shows it back (`builderhandler/flow_option.go`, `flow_reconstruct.go`), because such ids belong to the customer; `email_send` is kept out of the builder entirely for its file attachments. `medias` is therefore tagged `ref:"resource"`. That needs one case for `[]uuid.UUID` in `RefFieldsOf` (`models/action/ref.go`, a list field of kind resource) and the matching case in the drift test `Test_EveryUUIDFieldIsTagged`. With the tag the builder cannot keep an invented file id.
5. `bin-ai-manager/pkg/actioncatalog/main.go` lists the options of each action for the Flow Builder LLM, and `main_test.go` fails when a field of the option struct is missing there. The new field must be added to the catalog.
6. `engine_openai_handler/tool.go` defines an older tool named `message_send` that does not match the real tool name `send_message`. It is not touched (out of scope, proposed only).
7. Other callers of the conversation send RPC are checked and stay unchanged because they pass no media: `servicehandler/case_message.go` (`nil`), `bin-ai-manager/pkg/messagehandler/event.go` (empty list, two places), and the flow action `conversation_send` (`actionhandle.go`, empty list, two places).
8. `Media.ID` is used as a record id only by the table `conversation_medias`, whose insert method `MediaCreate` has no production caller (grep of the module). For an outgoing `sms` message the id is stored inside the json column `conversation_messages.medias` and means the storage file id; `TMCreate` stays nil there. There is no other reader of that json that treats the id as a record id (messages are only returned to clients).
9. Event path: conversation-manager subscribes to message-manager `message_created` and `MessageEventSent` creates a conversation message with an empty media list when none exists. For an MMS sent through the conversation, `sendSMS` creates the conversation message before it calls message-manager, so the event only updates the status and the stored `medias` survive. This order (create, then send) is relied upon and pinned by a test. An MMS sent outside a conversation (`POST /messages`, flow, AI) that lands in an `sms` conversation is recorded there as text only; showing its media is part of P3 (receiving) and of the P4 screens.
10. Status meaning: the `message_created` event can mark the conversation message `done` before the asynchronous provider dispatch finished; a later provider failure is not reflected there. This is the existing SMS limit.
10b. Timeouts: the conversation RPC and the message RPC both use 30 seconds. The message-manager media check has a 10 second deadline, so the inner call normally ends first; if both ever time out together the caller sees an error although the message may exist, and a retry could send twice. This is the P1 limit and is stated in the documentation (check the message list before a retry after a timeout).
11. Flow variable substitution runs on the option before it is unmarshalled; `medias` is typed `[]uuid.UUID`, so a variable placeholder in `medias` fails the action. Variables are not supported for `medias`, and the documentation says so. A JSON `null` element becomes a nil id and is rejected by message-manager (`INVALID_MEDIA_ID`); flow passes `uuid.Nil` as the message id, which message-manager replaces with a new id (`send_mms.go`).
12. Silent degrade window: an old conversation-manager, flow-manager or ai-manager ignores an unknown `medias` field and sends a text only SMS. This cannot be closed in the old code, so it is handled by deploy order (Part A, decision 7).
13. External client: `monorepo-javascript/square-talk` (`ChatInput.jsx`, also used by the case screen) already sends `medias` to `POST /service_agents/conversations/{id}/messages` for every conversation type. Each item has `file_id`, `type: "file"` and other fields but no `id`, and the file is uploaded with type `talk`. Today the API drops them and the text is sent without the attachment. The cli clients send `medias: []` only. This is why the API must stay lenient (decision 4) and why rejecting media for the other conversation types is a proposal and not part of this change (decision 3).

### Verdict
Valid, with the scope addition of item 2. Nothing is solved or duplicated already.

## Part A. Design

### Decisions
1. **File id carrier.** Conversation: `Media.ID` is the storage file id. Flow action: `medias` is an array of file ids. AI tool: `medias` is an array of file id strings. No URL field exists in any of them.
2. **Branching.** Every caller uses the old SMS method when the media list is empty and `MessageV1MessageSendMMS` otherwise. A request without media follows exactly the old code path and old tests. An empty array means SMS. No flag is added.
3. **Conversation.** `smshandler.Send` gets a `medias []media.Media` parameter. With media it calls `MessageV1MessageSendMMS` with the ids; message-manager validates everything else (count, owner, type, size, duplicates). `messagehandler.sendSMS` (conversation type `message`) rejects, before any record is created, a media whose `ID` is `uuid.Nil` with a typed `INVALID_ARGUMENT` (`MEDIA_ID_REQUIRED`, message "a media needs a valid storage file id in `id`"): an attachment without a storage file id cannot be sent, and sending the text alone would be a silent degrade. Behaviour change that must be reported: square-talk sends attachments without `id` (Part 0, item 13), so in an `sms` conversation such a request now fails with 400 instead of sending the text without the attachment; the square-talk change (P4) is outside this change and has a prerequisite that is also outside it: square-talk uploads through `POST /service_agents/files`, which accepts only type `talk` (`server/service_agents_files.go`), and `POST /storage_files` (the only upload that accepts type `media`) needs admin or manager permission. A file of type `talk` is rejected by message-manager (`MEDIA_FILE_TYPE_INVALID`). For the other conversation types (LINE, WhatsApp, webchat, email) the observable behaviour stays what it is today: the media is ignored. To keep it that way once the API passes media on, `messagehandler.Send` replaces the media list by an empty list for these types (with a warning log), so that no stored message record claims an attachment that was never sent (`sendLine` would otherwise store the list in the record). Rejecting it would be more correct but would also break square-talk sends whose text is delivered today, so it is a proposal for a decision. Typed errors from message-manager (media validation, balance) are returned unchanged and the listen handler maps them to their status; an untyped error (for example the identity verification gate of message-manager) becomes a 500 as for SMS today. In every case the existing handling marks the already created conversation message `failed`; only the nil id check runs before the record is created, because it is the one check that needs no other service. Checks that message-manager owns (count, duplicates, owner, type, size) are not duplicated here, so such a rejection leaves a `failed` record in the conversation, the same as any other send failure of an `sms` conversation today.
4. **Public API.** `PostConversationsIdMessages` and `PostServiceAgentsConversationsIdMessages` convert `req.Medias` (generated type with pointer fields) into `[]cvmedia.Media` through one helper that never fails: it copies only `id` (parsed; a missing or malformed value becomes `uuid.Nil`), `type` and `filename` (a client cannot set `customer_id` or timestamps), nil pointers give empty values, the generated type is converted to `media.Type`, and an absent, `null` or empty list gives a non nil empty slice (existing tests match `[]cvmedia.Media{}`). The API does not reject anything new, so no existing client request starts to fail at the gateway; the rejection of an unusable media for an `sms` conversation happens in conversation-manager (decision 3). Permission checks are unchanged.
5. **Flow.** `OptionMessageSend` gets `Medias []uuid.UUID` with tag `json:"medias,omitempty"`. `actionHandleMessageSend` calls `MessageV1MessageSendMMS` only when `len(opt.Medias) > 0`. Errors (including `MEDIA_NOT_FOUND`) fail the action as any send error does today. The flow builder catalog entry gets the field with the text that the user attaches files after the draft, never invent an id.
6. **AI tool.** `toolHandleMessageSend` uses the same branch. The `send_message` definition gets `medias` (array of uuid strings; `maxItems: 10` is only a hint for the LLM, the limit is enforced by message-manager; description: file ids of files the customer uploaded with type `media`; never a URL, never invent an id), and the description and prompt wording change from "SMS" to "SMS, or MMS when medias are given". A URL or any non uuid string in `medias` fails the JSON unmarshal of the arguments, so the tool result is a failure and nothing is sent. A JSON `null` element becomes a nil id and is rejected by message-manager. The prompt line of `builderhandler/prompt.go` is aligned. Prompt injection that makes the LLM send a file of the same customer to another number is the same class of risk as the existing text and destination arguments; message-manager's owner check bounds it to the customer's own files.
7. **Deploy order (documented in the PR).** Preconditions (not verified here, to be confirmed before deploy): billing-manager, message-manager and storage-manager run the P1 images. Then deploy conversation-manager and flow-manager, then ai-manager (the Flow Builder in ai-manager can store flows with `medias`, so flow-manager must understand the field first), and api-manager last; publish the customer documentation after every replica runs the new images. A new api-manager in front of an old conversation-manager would pass media that the old service drops and send a text only SMS; the order closes that window. An old api-manager keeps dropping medias, so it is harmless for the new services. An old conversation-manager also stores the received `medias` in the message record while it sends the text only. Do not roll back conversation-manager, flow-manager or ai-manager while MMS is live: rollback reopens the silent text only window for a short time. This window cannot be closed in the old code, is limited to deploy order violations and rollbacks, and is stated in the PR description.
8. **Billing, limits, providers.** Unchanged and owned by P1 (MMS billing type, Telnyx first, Messagebird fallback per target, limits).
9. **Cost safety.** No test sends anything; all tests use gomock for `RequestHandler`.

Latency: a flow action or an AI tool that sends an MMS waits for the synchronous part of the P1 call (media check, up to the 10 second deadline, normally milliseconds), the same pattern as the SMS call with a longer worst case; the AI tool result is delayed by that time in a voice call.

### Alternatives not taken
- A `url` field in conversation `Media`: arbitrary URLs are forbidden (SSRF, expiring links).
- Rejecting media (400) in the API for a bad id, or in conversation-manager for the other conversation types: breaks square-talk sends that deliver their text today (Part 0, item 13). Kept as a proposal.
- Leaving `medias` untagged and only telling the builder not to invent ids: the builder would keep ids that the model made up and save them in a flow.

### Impact
Code: `bin-conversation-manager` (smshandler, messagehandler, mocks), `bin-api-manager` (two server handlers, helper, tests, generated server types, the tracked redoc files `gens/openapi_redoc/api.html` and `openapi.json` (regenerated only when `npx` is available, checked separately), RST and built HTML), `bin-flow-manager` (option, handler), `bin-ai-manager` (tool handler, definitions, prompt, action catalog, docs), `bin-openapi-manager` (spec and generated types). Not changed: `bin-common-handler`, message-manager, billing-manager, storage-manager. Service docs: `bin-conversation-manager/docs/domain.md` and `architecture.md`, `bin-flow-manager/docs/domain.md`, `bin-ai-manager/docs/domain.md` (tool table).

### Open decisions
1. **Open question for the owners (not blocking implementation).** In an `sms` conversation, square-talk attachments (no `id`, uploaded with type `talk`) start to fail with 400 `MEDIA_ID_REQUIRED` when api-manager with this change is deployed, where today the text is sent and the attachment is silently lost. A working path for agents needs a further api-manager change that is not part of P2: let `POST /service_agents/files` accept type `media` (with an agent permission rule) and the square-talk change to send that file id as `id`. Until then, square-talk cannot attach files to `sms` conversations at all, with or without this change (a `talk` file is always rejected by message-manager); the only difference is that the failure becomes visible and the text of that message is not sent either. Options: (a) accept and plan the follow-up (recommended: the old behaviour loses the attachment without telling the agent); (b) keep sending the text and drop the attachment for `sms` conversations (the old silent degrade), which needs a different rule; (c) include the `service_agents/files` change in P2 (scope increase, needs approval of the agent permission rule). Recommendation: (a).
2. Proposals only: (a) reject media for the conversation types that cannot send it, together with the square-talk change; (a2) remove or fix the legacy `message_send` tool of `engine_openai_handler`; (b) a separate change that lets agents upload type `media`; (b2) let the Flow Builder pick uploaded files by name once a listing tool exists; (c) show the media of an MMS sent outside a conversation in the `sms` conversation (P3 and P4).

## Part B. Detailed design

### bin-conversation-manager
- Interface in `smshandler/main.go`: `Send(ctx context.Context, cv *conversation.Conversation, messageID uuid.UUID, text string, medias []media.Media) error`. `len(medias) == 0` (nil or empty): unchanged call to `MessageV1MessageSend`. Otherwise `ids` from `medias[i].ID`, then `MessageV1MessageSendMMS(ctx, messageID, cv.CustomerID, &cv.Self, destinations, text, ids)`. The new log lines carry the count only; existing log lines are not edited.
- `messagehandler.Send`: before the type switch, for `cv.Type != conversation.TypeMessage` a non empty media list is replaced by `[]media.Media{}` with a warning log (no error). `messagehandler.sendSMS`: before `Create`, a media with `ID == uuid.Nil` returns `cerrors.InvalidArgument(commonoutline.ServiceNameConversationManager, "MEDIA_ID_REQUIRED", ...)`; then `Create`, then `smsHandler.Send(..., medias)` (this order is relied upon by the event path, Part 0 item 9). `cerrors` is `monorepo/bin-common-handler/models/errors`. Mock `mock_smshandler.go` regenerated. `sendLine` and the other senders are not changed.
- Existing tests that gain the extra argument: `smshandler/send_test.go`, `send_coverage_test.go`, `messagehandler/send_test.go`, `error_paths_test.go` (the `Send` expectations). Existing sendSMS expectations keep the exact media value that was passed (gomock `Eq` distinguishes nil from empty). ai-manager shows a media with an empty `type` as `[media: unknown]` in conversation summaries; acceptable, documented.

### bin-api-manager
- `server/conversations_media.go` (new): `convertConversationMedias(in []openapi_server.ConversationManagerMedia) []cvmedia.Media` as in decision 4; used by both handlers after the body is parsed. Tests use `"abc"` as the malformed id (a 32 digit hex string without hyphens or a braced uuid is accepted by the uuid parser and is not malformed).

### bin-flow-manager
- `models/action/option.go`: field added with `ref:"resource"`. `models/action/ref.go`: `RefFieldsOf` returns `[]uuid.UUID` tagged fields as a list of kind resource; `Test_EveryUUIDFieldIsTagged` and `Test_RefFieldsOf` cover it. `actionHandleMessageSend`: branch. ai-manager builder tests pin that `medias` written by the model is cleared and is not shown back.

### bin-ai-manager
- `tool.go`: branch (`len(tmpOpt.Medias) > 0`); the message id from `UUIDCreate` is passed as the `id` of the MMS call, as for the SMS call (an unmarshal failure test expects no `UUIDCreate`). `definitions.go`: `medias` property and wording. `prompt.go`: wording. `actioncatalog/main.go`: `medias` entry (optional, type "array of uuid") and the `Summary` text ("Send an SMS text message, or an MMS when medias are given."); the drift test `main_test.go` fails without the entry, the summary wording is not pinned by a test and is reviewed by hand. `docs/domain.md`: tool table. There is no existing test for the `send_message` definition; a new one is written.

### bin-openapi-manager and docs
- `FlowManagerActionOptionMessageSend.medias`: array of uuid strings (`format: uuid`, `x-go-type: string`, `maxItems: 10`, realistic example, provenance "returned from POST /storage_files with type media"). `ConversationManagerMedia.id` description: for an `sms` conversation it is the storage file id. Request description of the two conversation message endpoints. `go generate` in openapi-manager and api-manager; generated files committed.
- RST: `flow_struct_action` (message_send), `ai_struct_tool` and `ai_overview` (send_message), `conversation_overview`, `conversation_tutorial` and `conversation_struct_message` (MMS in an `sms` conversation, ids, limits pointer to the message pages, error reasons, type of conversation behaviour). Clean sphinx rebuild, built HTML added with `git add -f`.

### Verify items (unit tests with gomock only; nothing is ever sent)
1. SMS unchanged: existing tests of smshandler, sendSMS, flow action and AI tool pass without edits except the added parameter; new tests pin that empty and nil media call `MessageV1MessageSend` and never `MessageV1MessageSendMMS` (conversation, flow, AI).
2. Media path: each caller calls `MessageV1MessageSendMMS` once with exactly the ids, source, destinations, text and customer id (gomock argument match), and never `MessageV1MessageSend`.
3. Errors: `MessageV1MessageSendMMS` typed error is returned unchanged; an untyped error is returned as is (the handler test asserts the returned error; the 500 mapping belongs to the existing `errorResponse`); (conversation: record set `failed`; flow: action error; AI: failed tool result). Nil id in conversation: no record created, no RPC.
4. AI and flow: JSON inputs `"medias":[]` and absent go to `MessageV1MessageSend` (pins `len > 0` instead of `!= nil`); a URL, `""` and a malformed id fail the unmarshal and send nothing; `[null]` reaches `MessageV1MessageSendMMS` with a nil id (message-manager rejects it). A new tool definition test pins the `medias` property (`maxItems` is only a hint, the limit is enforced by message-manager).
5. API: both handlers pass ids, type, filename only (a `customer_id` in the body is dropped); a nil, empty or malformed (`"abc"`) id becomes nil uuid with no gateway error; a square-talk shaped item (`file_id`, no `id`) is passed on as a nil id; nil `type` and `filename` pointers work; absent, `null` and empty lists give a non nil empty slice (existing gomock expectations unchanged). Conversation: nil id in an `sms` conversation gives `MEDIA_ID_REQUIRED`, no record and no RPC; create is called before the send (gomock `InOrder`); an `sms` conversation with valid ids calls the MMS method once; LINE with media: the stored record has an empty media list and the LINE sender gets an empty list (unchanged from today); `case_message` still passes `nil` and stays on the SMS path.
6. Catalog drift test and flow ref/meta tests pass.
7. Contract: `go generate` leaves no diff in the generated Go files (the redoc files need `npx`; checked separately); RST builds without new warnings; the documents do not list media types that the product does not support (no `video`).
8. Gates: per changed module `go mod tidy`, `go mod vendor`, `go generate ./...`, `go test ./...`, `golangci-lint run -v --timeout 5m`; root `scripts/check-*.sh`.

### Size and risk
About 800 to 1000 lines including tests, generated code and built HTML. Main risk is the silent degrade window of decision 7, handled by order.
