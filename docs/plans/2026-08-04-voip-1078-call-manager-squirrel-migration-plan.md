## 1. Key findings from investigation

1. **This is not a dbhandler-only change.** `models/bridge` and `models/channel` have no `db:` struct tags and no `field.go` (Field constants) at all. `models/outboundconfig` has **one** existing `db:` tag (`DefaultOutgoingSourceNumberID`) but no `field.go` and no tags on its other fields — it is partially prepped, not unprepped. `ScanRow`/`GetDBFields`/`PrepareFields` (the shared squirrel-migration helpers in `bin-common-handler/pkg/databasehandler/mapping.go`) skip any field lacking a `db` tag (`mapping.go:235-238, 283-286, 534-537`). **Model-layer prep is most of the actual work and must land before any dbhandler code references the new field constants.**
2. **Tests use SQLite round-trip, not SQL-string assertions.** `main_test.go` loads an in-memory SQLite DB from `scripts/database_scripts_test/*.sql` and runs real queries. Squirrel's generated SQL text can differ freely from the current raw SQL without breaking tests — refactor risk from SQL-shape changes alone is lower than expected.
3. **15 MySQL JSON-function call sites have zero unit test coverage today**, because SQLite lacks `json_array_append`/`json_insert` (see existing exclusion comments at `call_test.go:1549`, `confbridge_test.go:419-420`). This is the single largest risk in this migration — no automated regression signal for those sites. Exact list (verified by direct read, not grep count):
   - `bridge.go`: `BridgeAddChannelID`, `BridgeRemoveChannelID` (2)
   - `call.go`: `CallAddChainedCallID`, `CallRemoveChainedCallID`, `CallAddExternalMediaID`, `CallRemoveExternalMediaID`, `CallAddRecordingIDs`, `CallTXAddChainedCallID`, `CallTXRemoveChainedCallID` (7)
   - `confbridge.go`: 5 sites (`:327`, `:350`, `:375` `json_remove`, `:407` `json_insert`, `:431`)
   - `channel.go`: `ChannelSetDataItem` (`:339`, `json_set`) (1)
   - **Total: 15**, not 12 or 13. R1's "review every site" mitigation only works if this count is right — treat 15 as the checklist size.
4. **`squirrel.Expr` has sanctioned precedent in 5 services already** (verified by `grep -rn "squirrel.Expr\|sq.Expr" bin-*/pkg/dbhandler/`, excluding tests): `bin-agent-manager/pkg/dbhandler/agent.go:709` — `squirrel.Expr("JSON_CONTAINS(tag_ids, JSON_QUOTE(?))", id.String())`, in `WHERE` position, in a file that uses `PlaceholderFormat(squirrel.Question)` throughout (`agent.go:62,110,196,294`) — this is an **exact precedent** for a MySQL JSON function + `?` arg + `WHERE` + Question placeholders, the same combination this migration needs. `bin-conversation-manager/pkg/dbhandler/conversation.go:160-163` — 4 more `JSON_EXTRACT`/`JSON_UNQUOTE` sites in `WHERE`. `bin-rag-manager/pkg/dbhandler/document.go:355` — `"retry_count": sq.Expr("retry_count + 1")` **inside `SetMap()`**, an exact precedent for the arithmetic `Expr`-in-`Set` pattern `groupcall.go`'s `Decrease*` functions need. `bin-billing-manager/pkg/dbhandler/billing.go:154` and `bin-schedule-manager/pkg/dbhandler/execution.go:360-369` (the latter has an explicit "sanctioned exception" comment citing squirrel's inability to express the subquery). **This migration is applying an existing, already-sanctioned monorepo pattern to a new service — not pioneering one.** Phase 2 (below) is retained as a same-service sanity check (does it produce the expected SQL against *this* schema), not as first-ever-use validation.

## 3. New pattern: `squirrel.Expr` in `Set()` and `WHERE`

squirrel's `UpdateBuilder.Set(col, value)` inlines `value`'s SQL and merges its args when `value` implements `Sqlizer` (verified against `github.com/Masterminds/squirrel@v1.5.4/update.go:83-101`):

```go
Set(string(bridge.FieldChannelIDs),
    squirrel.Expr("json_array_append(channel_ids, '$', ?)", channelID))
```

Per `docs/conventions/database.md` §7.1, raw SQL via `Expr` is permitted for "computed expressions squirrel cannot express" (§7.1's own example is `cost_per_unit * ?`, an arithmetic case — the text does not currently name MySQL JSON functions explicitly). §7.1's exception list must be extended in Phase 8 to explicitly cover MySQL JSON functions (`json_array_append`, `json_insert`, `json_set`), since this migration introduces the monorepo's largest concentration of JSON-function `Expr` sites (15) and the convention doc should name the pattern it's sanctioning rather than leave it implied by cross-service precedent alone. Each `Expr` call site **must carry a `WHY` comment** explaining why the builder form doesn't work (e.g. "squirrel has no JSON-function builder; using Expr for json_array_append, precedent: bin-agent-manager/pkg/dbhandler/agent.go:709"). This is not a blanket allowance — every `Expr` call site in this migration must have that comment.

**Phase 2 (see §4) validates, before Phase 3 onward proceeds:**
- `Expr` used inside `Set()` — precedented by `bin-rag-manager/pkg/dbhandler/document.go:355` for arithmetic; this migration's JSON-function case is new *within `Set()`* specifically (the existing MySQL-JSON precedent in `bin-agent-manager` is `WHERE`-only), so it's still worth a same-service check even though the underlying builder mechanics are proven.
- `Expr` used inside `WHERE` combined with `PlaceholderFormat(squirrel.Question)` — this exact combination already exists in `bin-agent-manager/pkg/dbhandler/agent.go:709` (which also uses `PlaceholderFormat(squirrel.Question)` service-wide), so this check confirms call-manager's own `PlaceholderFormat` setting behaves the same way, not that the combination itself is untested.
- The exact `ToSql()` output on one real function (`BridgeAddChannelID`, since it needs a model-layer field constant only from `models/bridge` — see Phase reordering in §4) matches the current raw-SQL statement byte-for-byte (modulo whitespace), with args in the same order.

## 5. Risks

| # | Risk | Mitigation |
|---|---|---|
| R1 | 15 JSON-function sites have no automated regression coverage | 1:1 SQL diff review against pre-migration raw SQL for all 15 (see §1 item 3 for the authoritative list) + `ToSql()` golden-output test per site. **The golden test is a pure string-assertion test** (asserting `ToSql()`'s returned SQL string and arg slice match expected values) — it does **not** execute against SQLite (which lacks these JSON functions) or MySQL, since this service has no golden-test harness today and none is being introduced beyond this string-comparison form. **MySQL integration test evaluation**: given zero existing coverage on these exact sites and that the golden test alone doesn't prove the SQL is valid/behaves correctly against real MySQL, evaluate adding a `testcontainers`/`dockertest`-based MySQL integration test suite scoped to just these 15 functions before Phase 4 starts. If rejected (e.g. no existing precedent for MySQL integration tests in this service, CI time budget), record the reason explicitly in the PR description — do not silently rely on "manual smoke test" alone given the severity. |
| R-A | **Scope: read-side AND write-side, per (field × call site) — not per field alone — for every JSON/slice/map field this migration touches (not just `bridge.go`/`channel.go`).** Read-side: empty-collection normalization is silently dropped by `ScanRow`'s `copyJSON` (leaves Go zero-value/nil on NULL or empty JSON), while today's hand-written scan code normalizes selectively — **not uniformly**. Confirmed per-field read behavior today: `bridge.go:76-78` normalizes `ChannelIDs` (nil → `[]string{}`); `channel.go:117-119` normalizes `Data` (nil → `map[string]interface{}{}`); `channel.go:134-136` normalizes `StasisData` (nil → `map[StasisDataType]string{}`); **`SIPData` is NOT normalized today** (left nil on NULL). Write-side (newly identified, applies starting Phase 3, not just Phase 5-6): `confbridge.go:451-453` normalizes `Flags` (nil → `[]confbridge.Flag{}`) before `json.Marshal`; `groupcall.go:336-338,366-368` normalizes `CallIDs`/`GroupcallIDs` the same way; `outbound_config.go:93-95` (`OutboundConfigCreate`) normalizes `DestinationWhitelist` (nil → `[]string{}`, see B-2) — **but `OutboundConfigUpdate:193-199` does not**: it `json.Marshal`s `*req.DestinationWhitelist` directly with no nil-slice guard, so a caller passing a pointer to a nil slice already writes JSON `"null"` today at this specific call site. This is why the table must be keyed by (field, call site), not field alone — `DestinationWhitelist` has two write call sites with two different current behaviors, and collapsing them to one row would silently change one of the two. If any write-site that currently normalizes is routed through map-based `PrepareFields`/`SetMap` without preserving that normalization, a nil slice is auto-detected by `processMapValues`'s `reflect.Slice` branch and `json.Marshal`'d as `"null"` instead of `"[]"` — a write-path regression, not just a read-path one. Because struct-based `PrepareFields` emits every tagged field unconditionally (same mechanism as above), an omitted or copy-pasted-from-recording assignment here would either leave `tm_create` as its Go zero value (writing SQL `NULL`, since `TMCreate *time.Time` is a pointer field) or silently change the `TMUpdate` semantics. A NULL `tm_create` has a narrower but still real regression footprint on this table: `OutboundConfigList` (`outbound_config.go:229-233`) has no `tm_create` predicate at all on the first page (empty `pageToken`), so a NULL-`tm_create` row is still returned there — it only becomes excluded on a **subsequent** cursor page (`tm_create < ?` evaluates to unknown/false against NULL). ## 6. Incidental findings (reported, not silently fixed)

1. **SQL injection in `ChannelSetDataItem`** (`channel.go:339`) — `key` is interpolated via `fmt.Sprintf` with no escaping. Resolved naturally by the squirrel conversion (bind the path as a query argument, the same pattern `ConfbridgeAddChannelCallID` already uses).
2. **SQL injection in `ChannelList`** (`channel.go:757`) — the filter map's column-name key `k` is interpolated via `fmt.Sprintf` unvalidated into the `WHERE` clause (`and %s = ?`). Lower severity since `ChannelList` has **no production callers** (only mocks/tests reference it — confirmed via interface/call-site search), but it is the same injection class as item 1 and should be fixed in the same pass. Bonus: the current `for k, v := range filters` iteration order is non-deterministic, so the generated SQL (and any log of it) varies run to run — squirrel's builder fixes this incidentally once filters are passed as a typed, ordered structure.
3. **Suspected pre-existing bug in `ConfbridgeAddRecordingIDs`** — passes `recordingID.Bytes()` to `json_array_append`, while the semantically identical `CallAddRecordingIDs` and `ConfbridgeAddExternalMediaID` use `.String()`. Since `recording_ids` unmarshals as `[]uuid.UUID` (a JSON string array), `.Bytes()` likely stores a malformed value. **Recommendation: carry the existing behavior over as-is during this refactor and file it as a separate ticket**, and that ticket must include a **data backfill/integrity check** — this may have already written corrupted `recording_ids` entries into production rows, which a code-only fix would not repair.
4. **`ChannelList` has no production callers** (only referenced by mocks/tests) — changing its `filters map[string]string` signature to `map[channel.Field]any` (matching the other `List` functions) costs almost nothing and improves consistency. Requires `go generate ./...` to regenerate the mock (`mock_main.go:639`) and updating the `DBHandler` interface (`main.go:77`). The sanctioned helper for this shape is `commondatabasehandler.ApplyFields` (`bin-common-handler/pkg/databasehandler/main.go:61-110`) — note it hardcodes the `deleted` filter key to `tm_delete IS NULL`/`IS NOT NULL`, which happens to match `channel.go:749-754`'s current behavior exactly, but would be wrong if applied to a `9999-01-01` sentinel table (see §6 item 6's soft-delete split) — call this constraint out explicitly in Phase 6 so it isn't copy-pasted into a sentinel-convention table later.
5. **Three locations claim call-manager is a raw-SQL exception, not two**: `bin-call-manager/CLAUDE.md`'s "Database Pattern" section ("This service uses direct SQL — no Squirrel query builder"), `docs/conventions/database.md:42`'s "Exception — bin-call-manager", **and** `docs/conventions/database.md:86`'s "Raw SQL paths (the exception in `bin-call-manager`) must call `.Bytes()` explicitly" (this third one also needs review for whether it's still accurate post-migration, since raw SQL paths shrink to only the 15 `Expr` sites plus any genuinely-unconvertible statements). All three must be updated in Phase 8.
6. **The service has two co-existing, non-unified soft-delete conventions**: `bin-call-manager/CLAUDE.md` documents the `tm_delete = "9999-01-01 00:00:00.000000"` sentinel pattern, but `bridge`/`channel`/`outbound_config` actually use `tm_delete IS NULL` (confirmed: `channel.go:751`, `outbound_config.go:118,132,157,211,226`). **This migration must preserve each table's existing soft-delete semantics exactly as-is — do not unify them.** Unifying soft-delete conventions across tables is a separate, higher-risk change (touches query predicates across every caller) and belongs in its own ticket if pursued at all.
7. **`ChannelList`'s `LIMIT` argument is currently a pre-formatted string** (`strconv.FormatUint(size, 10)` at `channel.go:763`), while squirrel's `Limit()` takes a `uint64` directly — this is an expected, intentional simplification during the SQL-diff review in Phase 6, not a regression; call it out explicitly in that phase's PR commit so reviewers don't flag it as an unreviewed behavior change.
8. **Beyond `bridgeSelect` (`bridge.go`), the scope also includes `channelSelect`(`channel.go:18-61`) and each file's `*GetFromRow` scan helper** — all should be deleted once `ScanRow` replaces them. §2's per-file scope table undercounted this by naming only `bridgeSelect`; Phases 5-7 estimates should account for removing the equivalent helpers in `channel.go` and `outbound_config.go` too.
