# Self-hosted OpenAI-compatible LLM support (VOIP-1599)

Status: design, revision 16 (design review loop closed). This change implements Layer 1 only; Layer 2 is an unimplemented gate (proof of concept, its own design round and an earlier schema change come first, section 4). Scope: bin-ai-manager, bin-pipecat-manager (Go service and Python runner), bin-openapi-manager, bin-api-manager docs.

## 1. Issue analysis (current state, verified on main)

- `models/ai/main.go` has `EngineModelTargetOllama` only as a constant and a list entry. Nothing outside tests reads `EngineModelTargets`, `GetEngineModelTarget` or the Ollama constant: no behavior.
- `scripts/pipecat/run.py` `create_llm_service` handles `openai`, `grok` (fixed `base_url`), `gemini`, `platform_openrouter`, `openrouter.<id>`; anything else raises `Unsupported LLM service`.
- `models/ai/catalog.go` has `RouteDirect`, `RouteOpenRouter`, `RouteCustomOpenRouter` (the virtual entry `custom.openrouter`, which `ResolveEngine` skips). `ResolveEngine` is shared by ai-manager validation (`aihandler/chatbot.go`, `cmd/ai-control`) and pipecat-manager (`llmresolve.go`), and is fail-closed.
- pipecat `OpenAILLMService` accepts `base_url` (grok path). Tools use the shared `_openai_tools_to_standard` path, so a server that implements OpenAI chat completions with tools works.
- Deployment topology: the Python runner is a separate container (`pipecat-script-runner-1/2` in `bin-pipecat-manager/komodo/docker-compose.yml`), not the Go pipecat-manager container. The platform key `OPENROUTER_API_KEY` is injected into the runner containers only.
- `ai_ais.engine_key` is plaintext; `WebhookMessage` returns it (`webhook.go`).
- `mcpserverhandler.ValidateURL` checks scheme and literal IPs only; hostnames are checked at dial time by a Go `net.Dialer.Control` hook, which does not apply to the Python runner.

## 2. Layering

Layer 1 (operator): the operator registers endpoints and models by configuration. Customers pick a model from `GET /ai_models`; the URL is never exposed. Private IPs and plain http are allowed (trusted boundary). Entries exist only when configured; no global on/off flag.

Layer 2 (customer inline endpoint): the customer supplies base URL, model ID and an optional key in the AI configuration. Untrusted input. Delivery is gated, see section 7.

## 3. Layer 1 design

### 3.1 Configuration: catalog and connection are separate
Two variables, so that no secret reaches services that do not need it.

- `LOCAL_LLM_MODELS` (no secret): JSON list given to ai-manager and Go pipecat-manager (and read by `ai-control`).

      [{"endpoint":"vllm-a","id":"qwen3-8b","label":"Qwen3 8B","capabilities":["tool-calling"],"default":false}]

- `LOCAL_LLM_ENDPOINTS` (secret): JSON object given to the runner containers only.

      {"vllm-a":{"base_url":"http://llm.internal:8000/v1","api_key":""}}

Validation: the pure parse function in the shared model package validates the whole value and returns the accepted models plus a skipped count; `SetLocalModels` only stores the result; the service logs the summary after the call. Rules: `endpoint` matches `^[a-z0-9][a-z0-9-]{0,31}$`; `id` matches `^[A-Za-z0-9][A-Za-z0-9._:/-]*$`; the final engine model `local.<endpoint>.<id>` is at most 255 bytes (column width); duplicate `(endpoint, id)` rejected; `label` matches `^[A-Za-z0-9][A-Za-z0-9 ._()-]{0,63}$` (ASCII only) (it is customer-visible; the description is a fixed text, `Local model.`); unknown capability dropped. Invalid entries are skipped and a startup summary line logs loaded, skipped and default counts (error level when anything is skipped); the service still starts. Keys and URLs are never logged.
The runner validates only what it needs: the endpoint name exists, `base_url` is http or https without userinfo or query. A missing endpoint fails the session start with a generic message.

Why two variables: the runner sidecar is a different container with its own environment, and ai-manager must not hold URLs or keys. Trade-off: the model list and the endpoint list can drift. Drift is fail-closed (a model the runner cannot connect to fails at session start, a model unknown to pipecat-manager is rejected), and because models are visible only when `LOCAL_LLM_MODELS` is set, the operator sets `LOCAL_LLM_ENDPOINTS` first, then `LOCAL_LLM_MODELS` on pipecat-manager Go, and on ai-manager last (the catalog is exposed only by ai-manager). pipecat-manager Go and the runner use the same image tag and are replaced together, and the two replicas are replaced one after the other, so `LOCAL_LLM_MODELS` is set only after every container runs the new image; a model visible before that would fail on an old replica with `Unsupported LLM service`. The startup summary log makes a mismatch visible.
Alternative rejected: ai-manager serves the list to pipecat-manager over RPC (new RPC, startup ordering).

Config transport. The shared model package exposes a pure parse function only. `cmd/ai-manager`, `cmd/ai-control` and `bin-pipecat-manager/cmd/pipecat-control` (its `Start` goes through `classifySessionLLM`), and the pipecat-manager service itself, each read `LOCAL_LLM_MODELS` through their own `internal/config` (a new key that does not fail startup) and pass the string to the parse function and then `SetLocalModels`; without that call in `ai-control` local models would be rejected as invalid. `LOCAL_LLM_ENDPOINTS` is one secret variable holding the whole JSON value, injected as a single Komodo variable (JSON quoting and `$` characters in compose interpolation are checked in the real run; a nested array `[[` would collide with the `[[VAR]]` substitution syntax, so the documented value avoids it). Secrets are injected through Komodo variables or the environment file, not committed JSON in the compose file. Manifests to update (`komodo/docker-compose.yml` is the current manifest; the `k8s/` directory of ai-manager is stale and unchanged): ai-manager, pipecat-manager (Go) and both runner containers; the separate operator install repository must carry the same variables (not part of this change).

### 3.2 Catalog and routing
- `RouteLocal`; entry ID `local.<endpoint>.<id>`. The first-dot split in `create_llm_service` yields service `local` and model name `<endpoint>.<id>`; the runner splits once more at the first dot (endpoint names have no dot). A type with a colon and no dot cannot reach this branch because the ID always contains a dot.
- Registry: local models live in their own registry, separate from the static `catalog` slice, so existing loops over `catalog` and their tests are unaffected. `SetLocalModels` is called once at startup (the registry is then read-only) and is the injection point for tests (they restore it with `t.Cleanup` and do not use `t.Parallel()`); before it is called the registry is empty. `ResolveEngine` checks the registry after the `catalog` loop and returns a pointer into the registry entry; `CatalogView` appends registry entries after the built-in ones. The `KeyMode` switch and the `PlatformManaged` expression inside `CatalogView` treat `RouteLocal` as platform managed (`key_mode=platform`, vendor `Local`); `ModelInfo` has no URL field. `ResolveEngine` returns `OutcomeCatalog`, `BlankKey=true` (the customer key is never forwarded).
- Runner `local` branch: `OpenAILLMService(base_url, api_key)` from the parsed `LOCAL_LLM_ENDPOINTS` (parsed once per process). An empty `api_key` becomes a fixed placeholder, never `None`, so the SDK cannot fall back to `OPENAI_API_KEY`. Tools and aggregator as in the grok branch. The team-member path (`_member_llm_type`) goes through the same function; its fallback guard (used only when the Go side sends no `llm_type`; function `_member_llm_type` in `run.py`) is extended so a `local` service name from customer data is never honored as an internal routed service, the same invariant as `platform_openrouter` (test).
- Customer-visible strings: the engine model ID (`local.<endpoint>.<id>`) and label reach customers through the catalog and call variables, so operators must not put internal host or rack names in `endpoint`, `id` or `label` (documented in the operator docs).
- Text conversation: `aicallhandler/send.go` sends text through `PipecatV1MessageSend`, so a local model works for text sessions too. `engine_openai_handler.MessageSend` and `StreamingSend` (which strip the prefix with `GetEngineModelName` and use one OpenAI client) have no production caller (grep), so no guard is added; if a caller appears, it must reject `local.` and `customendpoint.` models first.
- Existing catalog tests that scan the public view for banned terms (`Test_CatalogPublicViewHidesInternals`, `Test_CatalogCustomerFacingTextHasNoBannedTerms`) run with an empty registry and keep their meaning; registry labels are operator-chosen and covered by the label rule only (ASCII only; the operator docs say so).
- Error handling: see 4.5 for what is logged and notified; Layer 1 keeps the existing `pipeline_error` behavior unchanged.

### 3.3 Capability tags (requested: operator-defined capability expression)
Operator `capabilities` whitelist: `tool-calling`, `low-cost`; shown in the existing `tags`. Informational only. Rejecting AIs with tools on a model lacking `tool-calling` is not done (would be a new policy). Cost: the OpenAPI/RST text "Currently `low-cost` only" is updated.

### 3.4 Default model
"Default" = the model preselected for a new AI. Backend scope: a configured default is exposed as the single `recommended` model, which is the contract field clients use. Checked in the admin frontend (`square-admin`): the AI create form starts with an empty model and falls back to a hard-coded template model, and the model picker uses `recommended` only to show a "Recommended" group, so a configured default does not preselect anything today. Making the form preselect the recommended model is a frontend change outside this backend change; it is reported as a proposal and as an open decision (section 7), and until it ships the effective behavior is the Recommended group placement only.

Rule: the API requires `engine_model`, so the backend does not default. Only an explicit operator setting changes anything: a model with `"default": true` is the only entry returned with `recommended=true` while configured (the built-in flag is cleared by `CatalogView` while it builds the response, and the static `catalog` slice is never mutated, so `recommended=true` still appears exactly once, matching the existing test contract and the API description 'the platform recommends this model'; `catalog_test.go` gets a configured-case test next to the unchanged unconfigured one). A second default only loses its flag (the model stays listed) and is counted in the startup log. Without configuration nothing changes. Making a self-hosted model the preselected one is an operator cost and capacity choice, made by setting the flag. The frontend preselect is the open point in section 7.
Known limitation of Layer 1: when a local server is down, a voice session gets no customer-visible notice, because the existing `pipeline_error` classifier (`pipelineerror.go`, VOIP-1542) classifies `Connection error.` as unknown, and unknown is notified only for sessions without STT. A hung server can stall a session for the openai SDK default read timeout (minutes). The runner uses the default client, which also honors proxy environment variables (`trust_env`); operators who run the runner behind a proxy variable must add the local host to `NO_PROXY`. Runner client for local models: pipecat defaults (no custom client, no extra timeouts) because the endpoint is inside the operator trust boundary. An unresponsive local server stalls only that session; hardening (timeouts) is not added without a measured signal.
Local failure fallback to OpenRouter is out of scope. Trigger to design it later: repeated local session start failures observed in production logs.

### 3.5 Ollama constant
Left unchanged (unused, outside the request).

### 3.6 Billing
No billing code references `platform_managed` or the catalog routes (grep). Local models add no cost line. Whether self-hosted usage should be priced is a product decision, open.

### 3.7 Operations
- Existing contract tests: `Test_CatalogViewPlatformManagedMatchesRoute` compares the view with `catalog` by index and length, `Test_CatalogKeyModeMatchesRoute` and `Test_CatalogInvariants` enumerate routes, `Test_CatalogViewShape` asserts `len(view)==len(catalog)` and exactly one recommended model (both assertions are handled: the length assertion is updated to include registry entries, and the single-recommended assertion gets an unconfigured case unchanged and a configured case), `Test_ResolveEngineAllOpenRouterEntriesBlankKey` walks `catalog`. Because local entries are not in `catalog`, these keep their meaning; they are updated to compare against `catalog` plus the registry where the view length is asserted, and local entries get their own contract tests (platform managed, key mode `platform`, blank key). The `wantKeys` test is unchanged. Python tests that expect `Unsupported LLM service` use non-local values and are unaffected.
- A running call keeps the engine model snapshotted in its aicall, so catalog changes do not affect calls in progress.
- If the operator removes or renames a model, existing AIs that store it still save (unchanged value) but session start fails closed with `engine model is not available`. The operator procedure: list AIs using the model before removal (`ai-control` list) and move them first. No automatic migration.
- `ai-control` runs where the ai-manager environment is available and reads `LOCAL_LLM_MODELS` the same way; `bin-ai-manager/docs/operations.md` documents it.
- The runner logs the number of loaded endpoints at start. A missing endpoint variable with models configured shows up as that count being 0 plus session start failures; no health flag is added.

## 4. Layer 2: constraints and gates

Values in this section (timeouts, file lists) are working assumptions that the proof of concept and the detailed round may change; the gates and invariants are the fixed part.

Layer 2 depends on a proof of concept (4.2) and on a schema change that must be its own earlier change. Its detailed design (write chain, validator placement, request DTO, key update semantics, exact files) is therefore a separate design-and-review round started after the proof of concept passes, not part of this document's approval. This section fixes what that design must satisfy.

### 4.1 Constraints
- Customer-supplied fields: `engine_base_url` on the AI and an engine model of the form `customendpoint.<model id>` (reserved prefix; different from the virtual `custom.openrouter` entry; the id follows the same character and length rule as `local.` ids). A `customendpoint.` model requires a valid `engine_base_url`; a base URL with any other model is rejected. `ResolveEngine` gets a new outcome for it.
- URL validation at create/update returns a typed 400 through the existing `engineValidationError` pattern. Rules: https only, no userinfo or query, hostname resolved and every address checked against an explicit block table with tests: private (RFC 1918, IPv6 ULA), loopback, link-local, carrier-grade NAT 100.64.0.0/10 (includes a cloud metadata address), benchmarking 198.18.0.0/15, 192.0.0.0/24, multicast, unspecified, NAT64 64:ff9b::/96 and 6to4 (checked on the embedded IPv4), IPv4-mapped IPv6. The existing helper checks literal IPs only and is not reused. The validator lives in the ai-manager model package, is a network-dependent function separate from the pure `ValidateEngine`, and is repeated in pipecat-manager Go before a session starts (stored rows and `ai-control` can bypass the API check).
- Key routing invariant: for `customendpoint.` the legacy `engine_key` is never forwarded to the runner (`llmresolve.go` forwards it when neither `BlankKey` nor `RequireKey` is set, so an OpenAI key stored before a model switch would reach a customer-chosen host). Only the dedicated encrypted key is used. The runner receives `base_url` and the dedicated key only when `ResolveEngine` returns the custom-endpoint outcome for the session's own snapshot type. Switching away from `customendpoint.` clears the base URL and the encrypted key in the same update. A changed base URL discards the stored key unless a new key is sent in the same call. The key is write-only: how `PUT` (whole replacement; omitted key currently means empty) distinguishes keep, replace and clear is decided in the detailed design.
- Key storage and exposure: encrypted in a new `varbinary` column, never returned by the API. The decrypted value travels in the internal AI get response (same internal trust level as `engine_key`), is cleared in `publishAIEvent`, excluded from `WebhookMessage` (whitelist copy), excluded from struct log output; tests assert each surface. The encryption code is the existing MCP secret mechanism with its own key setting so MCP key rotation does not touch AI keys; the new setting needs sign-off before implementation.
- Log and error hygiene: extend `loggableEngineModel` (api-manager `servicehandler/ai.go`) and `errEngineModelNotAvailable` (`llmresolve.go`) to `customendpoint.` (not to `local.`); never log the base URL; runner `main.py` `run_request` masks `llm_type`; pipecat-manager `runner.go` logs the session struct (`LLMKey` is a session field); `str(e)` in `main.py` and non-200 bodies in `pythonrunner.go` must not carry the URL or key; for `customendpoint.` sessions `runnerHandlePipelineError` logs only the category, not the raw text (an upstream 401 body can echo key fragments).
- Customer notice reuses `pipeline_error` (VOIP-1542). A refused, blocked or unresolvable connection surfaces as `Connection error.`, which the classifier maps to unknown, and unknown is not notified in voice sessions. Required: a connection category (phrase `error during completion: connection error`) with a fixed notice text, notified always. It touches `models/message/pipeline_error.go`, `pipelineerror.go`, ai-manager `messagehandler/pipeline_error.go` text map, `ai_struct_message.rst` category table, and the pipecat-manager docs. It applies to every OpenAI-compatible provider. Timeout already maps to the timeout category.
- Write chain and runtime path are enumerated in the detailed design: api-manager `servicehandler/ai.go`, `requesthandler` AI create/update (and mocks), ai-manager request DTO, `listenhandler`, `aihandler`, `dbhandler`, then AI get, `pipecatcallhandler` (single and team-member paths), `PythonRunner.Start`, runner request model, `create_llm_service`.
- Private ranges are not allowed in Layer 2; those users use Layer 1. No allowlist flag.

### 4.2 Proof of concept (precondition)
The runner subclasses `OpenAILLMService` and overrides `create_client` to pass an `httpx` client whose `httpcore` network backend resolves the host, validates every address, and connects to the validated IP while TLS uses the original host name (SNI and certificate check unchanged). Checked: pipecat-ai 1.12.0 `services/openai/base_llm.py` has an overridable `create_client` that builds its own `AsyncOpenAI` with `DefaultAsyncHttpxClient`. Notes for the proof of concept: the base class calls `create_client` inside its constructor, so the override must not depend on state set after `super().__init__`; the default client follows redirects, so the override disables it; `httpx.AsyncHTTPTransport` does not expose the network backend, so a transport built on an `httpcore` pool with a custom backend is needed; pooled connections must be re-validated or not reused across hosts; `trust_env=False` (no proxy); `httpx.Timeout` with connect 5 s and read 30 s, and the SDK `max_retries` set explicitly (default 2 would triple the worst case); pipecat's `retry_on_timeout` is not a first-token timeout. Success: a name that resolves to a public address first and a private one second is refused at connect, SNI and certificate verification use the original host, redirects are refused, pooled reuse is re-validated. Failure: Layer 2 is not shipped and no schema is added. The range is `>=1.12.0,<1.13`; the result must hold for the locked version, and release pins it. Alternative if the approach fails: an egress proxy applying the same address rules (more infrastructure; not preferred).

### 4.3 Order
Proof of concept, then the detailed Layer 2 design round, then the schema change as its own earlier change (ai-manager and pipecat-manager deploy automatically on merge and production schema is applied separately), then code. Rollout: pipecat-manager Go and the runner together (same image), then ai-manager (which opens validation for `customendpoint.`).

## 6. Verification plan
- Unit: config parse and validation, length and duplicate rules, registry, `ResolveEngine`, `CatalogView` (hidden without config, no URL or key in JSON), `ai-control` validation, runner `local` branch (placeholder key never `None`, env `OPENAI_API_KEY` set must not leak), endpoint missing.

## 7. Delivery order and open points
1. Layer 1 first. It needs no schema change. In scope for this change: `LOCAL_LLM_MODELS` and `LOCAL_LLM_ENDPOINTS`, registry, catalog and resolve changes, runner `local` branch, `ai-control` and `pipecat-control` wiring, OpenAPI and RST and service docs.
2. Layer 2: proof of concept (4.2), then its own detailed design round, then the schema change as its own earlier change, then code (4.3).
3. Must be decided before Layer 2 implementation starts: the separate encryption key setting for Layer 2 keys; the connection category and its fixed notice text; key update semantics on `PUT`. Other open items: the admin form does not preselect the `recommended` model today (3.4); a frontend change is proposed, and the owner decides whether the requirement 'default = preselected for new AI' is met by the backend marker alone for this change; the picker also groups `key_mode=platform` models together with OpenRouter models under the platform-provided heading and shows unknown tags as raw text (only `low-cost` has a label), both frontend-side; encrypting existing `engine_key` rows (not planned); capability-based enforcement (not planned); pricing of self-hosted usage (no billing code depends on the catalog route today).
4. Documentation wording: `platform_managed=true` means only that the platform supplies credentials. The docs state that it does not imply OpenRouter routing or zero data retention routing, and describe local models separately from OpenRouter models.

## 9. Layer 1 implementation plan (this change)
Files and steps, each with its check.

1. `bin-ai-manager/models/ai/local.go` (new): `RouteLocal`, `LocalModelsEnv` input parsing. `ParseLocalModels(raw string) (LocalParseResult, error)` with `LocalParseResult{Entries []ModelEntry, Skipped, DuplicateDefaults int}`; empty or blank input gives an empty result; malformed JSON returns an error (the caller logs it and starts with no local models). `SetLocalModels([]ModelEntry)` replaces the registry; `ConfigureLocalModels(raw)` = parse + set, used by the four entry points. Check: table tests for every rule in 3.1 (endpoint, id, label, 255 bytes, duplicate, unknown capability dropped, default handling, malformed JSON).
2. `catalog.go`: add `RouteLocal`; `CatalogView` appends registry entries, treats `RouteLocal` as `key_mode=platform`, `platform_managed=true`, vendor `Local`, description `Local model.`, and clears the built-in `Recommended` flag only when a local default exists. Check: configured and unconfigured view tests; JSON contains no URL or key.
3. `resolve.go`: after the `catalog` loop, look up the registry; return `Resolved{Entry, RunnerType: string(m), BlankKey: true}, OutcomeCatalog`. Check: resolve tests, key never forwarded (`resolveSessionLLM` test in pipecat-manager).
4. Config: `LOCAL_LLM_MODELS` key in `bin-ai-manager/internal/config` and `bin-pipecat-manager/internal/config`; call `ConfigureLocalModels` and log the summary (counts only) in `cmd/ai-manager`, `cmd/ai-control`, `cmd/pipecat-manager`, `cmd/pipecat-control`. Check: config tests, build.
5. Runner `run.py`: `local` branch (endpoint lookup from `LOCAL_LLM_ENDPOINTS`, parsed once; placeholder key; `OpenAILLMService(base_url, api_key)`), `_member_llm_type` guard for `local`. Check: pytest cases for success, missing endpoint, key placeholder never None with `OPENAI_API_KEY` set, member guard.
6. `komodo/docker-compose.yml`: `LOCAL_LLM_ENDPOINTS` for both runner containers, `LOCAL_LLM_MODELS` for both pipecat-manager containers, and for ai-manager's compose if present. Check: `docker compose config` style parse.
7. Docs/spec: OpenAPI tag text, `go generate` in `bin-openapi-manager` and `bin-api-manager`, RST files in section 5, service docs, docsdev rebuild.
8. Real run: a stub OpenAI-compatible server and `create_llm_service` plus a streamed completion through the runner code path; real model latency and tool-call quality stay unverified.

Not touched: frontend, billing, the Ollama constant, Layer 2 code and schema.
