# Service-owned migrations

A service that owns its tables applies its schema migrations itself at startup (golang-migrate, SQL files embedded with `go:embed`) instead of through Alembic. The shared code lives in `bin-common-handler/pkg/migrationhandler`; `bin-tag-manager` is the reference service. Tested engines: MariaDB 12.3 and MySQL 8.0, so migration files avoid engine specific syntax. The `bin-manager` Alembic stream is frozen (see `bin-dbscheme-manager/CLAUDE.md`); the list of converted services is `bin-dbscheme-manager/docs/schema-ownership.md`.

## What a service holds

- `migrations/embed.go`: `const VersionTable = "<prefix>_schema_migrations"` and `//go:embed *.sql` `var FS embed.FS`
- `migrations/NNNNNN_<description>.up.sql` and `.down.sql` (six digits from 000001 without gaps; the first pair is `000001_baseline`)
- `cmd/<name>-manager/main.go`, right after the database connection and before the cache and the message broker:
  `migrationhandler.Run(cfg.DatabaseDSN, migrations.FS, migrations.VersionTable)`
- `cmd/<name>-control/main.go`: `migrationhandler.NewMigrateCommand("migrate", open)`, where `open` returns `migrationhandler.New(dsn, migrations.FS, migrations.VersionTable)`. The command (`status`, `up`, `down`, `force <version>`) opens only the database, so it works while the cache or the broker are down. A service whose control binary already has a `migrate` command registers it under another name.
- `migrations/migrations_test.go`: `migrationcheck.Check(FS, migrationcheck.Options{TableOptions: ..., ColumnCharsets: ...})` and a test that no non-.sql file sits next to the embedded files. For a migration directory below the service root pass `fs.Sub(FS, "<dir>")`.

## Rules for the files

- One DDL statement per file. Only the baseline may hold several `CREATE TABLE IF NOT EXISTS` statements.
- Every up has a down. A down that cannot restore data starts with `-- DOWN-LOSSY: <reason>`; an up with a destructive operation starts with `-- DESTRUCTIVE: <reason>` and its PR body starts with `[DESTRUCTIVE]`.
- Merged files are immutable and numbers are never reused. Fix a mistake with a new number.
- Expand/contract: the old code must work on the new schema. Drop a column in a later PR than the one that stops using it; replace instead of rename or retype.
- The baseline down is the no-op `SELECT 1`.

## Baseline from the Alembic head

The baseline of a converted service must create what the Alembic head created.

1. `CREATE TABLE` becomes `CREATE TABLE IF NOT EXISTS`; `ENGINE=InnoDB` is dropped (database default). `ROW_FORMAT=DYNAMIC` is kept only when Alembic wrote it, as part of the table option (rule 2).
2. Table options: only these are written, and only as one of the five strings of `migrationcheck` (`OptionUTF8MB4`, `OptionUTF8MB4UnicodeCI`, `OptionUTF8MB4UnicodeCIDynamic` (with `ROW_FORMAT=DYNAMIC`), `OptionUTF8MB4Collate0900AI` (`COLLATE=utf8mb4_0900_ai_ci` written out, for a table that must keep the collation of an existing database where the Alembic text named only the charset), `OptionUTF8MB3`). The service test lists the table names that use one; a table that is not listed must have no table option. A collation that exists only in MariaDB (`*_uca1400_*`) is not copied. A baseline that names a collation the Alembic head does not name differs from it in the dump; accept that only through `E1_ALLOWED_DIFF` (see Checks).
3. JSON columns are written as `json`; expression defaults are written as `DEFAULT (expr)`. Column comments are kept.
4. Generation expressions are taken from the Alembic source, not from `SHOW CREATE TABLE` (MariaDB and MySQL print them differently).
5. Foreign keys without a name stay without a name (MariaDB names them `1`, `2`, which MySQL rejects), unless the baseline has to reproduce existing names: `migrationcheck` accepts `CONSTRAINT <name> FOREIGN KEY`, and the `CON`, `KCU` and `FK` lines of the dump are the final guard of the names; a name that differs from the Alembic head is accepted only through `fk-name` in `E1_ALLOWED_DIFF` (see Checks). CHECK constraints are named the same way: a baseline that has to reproduce the CHECK names of an existing database (they differ from the Alembic head) names them with `CONSTRAINT <name> CHECK (...)`, and the name difference is accepted only through `check-name` in `E1_ALLOWED_DIFF`; give every check of such a table an explicit name.
6. Seed rows are not part of the baseline; a seed is its own file with one statement.
7. A new database must be created with `CHARACTER SET utf8 COLLATE utf8_general_ci`, like the install scripts do, otherwise most tables differ from the Alembic head.

The result is accepted only when the extended normalized dump of the service tables is identical to the one of the Alembic head (`scripts/verify-service-migrations.sh`), except for the collation, foreign key name, CHECK name and column order differences that the service lists in `E1_ALLOWED_DIFF` on purpose. `migrationcheck` is a deny list for the baseline text; the dump comparison is the final guard. `migrationcheck` also expects the statement to start with `CREATE TABLE IF NOT EXISTS <name> (` with an unquoted name (strip the backticks and the database prefix of `SHOW CREATE TABLE` output) and rejects the words of its deny list even as unquoted column names (quote such a column with backticks). A column level `CHARACTER SET` or `COLLATE` is rejected by `migrationcheck` unless the service declares the column in `Options.ColumnCharsets` (`"<table>.<column>"` mapped to `ColumnCharsetUTF8MB4GeneralCI`, the only allowed string, which Alembic `f46d9c5c4438` set on `ai_messages.content`); the column definition must then contain exactly that string outside quotes and parentheses, and a declaration for a table or column the baseline does not have is an error. Any text outside the deny list that changes a collation (for example the `BINARY` column attribute) is not caught; the dump comparison catches it.

## Checks

- `scripts/check-service-migrations.sh <service-dir> [<migrations-subdir>]` (after `git fetch origin main`): merged `.sql` files are not modified, deleted, renamed or changed in mode; the added files are regular files `NNNNNN_<description>.(up|down).sql` in pairs whose numbers continue origin/main without gaps (from 000001 when origin/main has none there). `--self-test` runs it on synthetic branches. A changed `VersionTable` is not detected.
- `ALEMBIC_VENV=<venv> scripts/verify-service-migrations.sh <service-dir> [<migrations-subdir>]` starts scratch containers of both engines and checks: the dump of the Alembic head plus the service migrations equals the dump of an empty database plus the service migrations; applying them to the Alembic database keeps the row counts (not checked when an up file carries a `-- DESTRUCTIVE:` marker); up, down, up; concurrent start; dirty refusal and force; a database ahead of the image; a restricted account; a password with special characters; the daemon applies the migrations before it connects the cache; the structure test. `HELPER_TESTS=1` also runs the `migrationhandler` integration tests; run it for every change of the helper. Output with SKIP lines or with `ENGINES_OVERRIDE` is not evidence for the default engines (the SKIP line of a reference dump on the engine it was not made with is the one expected exception).
  Variables for services that differ: `CONTROL_BIN`, `SERVICE_BIN`, `VERSION_TABLE`, `MIGRATE_CMD`, `DSN_VAR`, `DAEMON_ENV`, `EXISTING_ROWS_SQL`, `SEED_COMPARE_SQL` (see the header of the script).
- E1 versus E2 with an intended difference: `E1_ALLOWED_DIFF=<file>` (not `ALLOWED_DIFF`, which belongs to `REFERENCE_DUMP`) lists what the service accepts; nothing else is accepted, and without the variable E1 versus E2 stays a strict diff 0. A line of the file is a `#` comment, a pair line, or a directive; `check_allowed_file` refuses anything else (free text, a typo, a table that is not a table of the service, a duplicate, a carriage return) before a container starts.
  - Pair lines (`< E1`, `> E2`) of the `TBL` and `COL` dump lines whose two sides differ only in the collation field. The dump lines carry no table name, so an accepted line is accepted for every table and must be listed once per table that shows it. For a table under `column-order` the `COL` pair line is written with an empty ordinal (second) field, for example `< COL<TAB><TAB>name<TAB>varchar(10)<TAB>YES<TAB><TAB>utf8mb4<TAB>utf8mb4_uca1400_ai_ci<TAB>`.
  - `fk-name <table>`: the foreign keys of the table may differ from the Alembic head in the name only, for example the `<table>_ibfk_N` names of an existing database against the numbers MariaDB gives an unnamed key. Kind, columns, referenced table and columns and the ON UPDATE and ON DELETE rules must be equal per key; a swap of the names of two keys is accepted too. An index that carries the name of a key still fails, and a later migration that drops a key by name can act differently per engine.
  - `column-order <table>`: the column ordinals of the table may differ from the Alembic head. The column set and every column definition (type, nullability, generation, charset, collation, comment, default, generation expression) must be equal; an added, removed or changed column fails. Use it only when no code depends on the column positions (an `INSERT` without a column list, a positional `SELECT *`), and say so in the service PR.
  - `check-name <table>`: the CHECK constraints of the table may differ from the Alembic head in the name only (the `CON` line of type `CHECK` and the `CHK` line); the multiset of check expressions must be equal, so a changed, added or dropped check, a check of another kind and an unpaired line fail. A name that exists in both E1 and E2 must belong to the same table and expression (`CHECK-NAME-GUARD`): a swap of names, also between two listed tables, fails, because a check is dropped by name (`DROP CHECK <name>`), unlike a foreign key name in `fk-name`, where a swap is accepted. The directive needs the comparison with the existing table: the run refuses `check-name` without `REFERENCE_DUMP`, and an `ALLOWED_DIFF` with `CON` or `CHK` lines. The reference comparison runs on the engine of `REFERENCE_ENGINE` only and the script cannot see whether the dump is genuine, so say in the service PR which database the dump comes from, that every check of the table is named explicitly (unnamed checks get engine specific names, `<table>_chk_N` on MySQL and `CONSTRAINT_N` on MariaDB) and that every check is ENFORCED (the dump has no field for it). MariaDB names column level checks (also the `json_valid` check of a `JSON` column) after the column; their expressions stay compared. Two checks with the same expression are interchangeable. Example: `check-name contact_cases`.
  - Used entries are printed as `ALLOWED-DIFF`, entries no engine needed as `UNUSED-ALLOWED-DIFF` (not a failure; an engine without the difference, for example MySQL 8.0 for `fk-name`, leaves them unused). An entry unused on both engines is stale: remove it. The PR body states why each accepted entry is intended and attaches that output for both engines. A service whose baseline keeps the names or the order of an existing database still compares that database through `REFERENCE_DUMP` and `ALLOWED_DIFF`, which are unchanged (a list with `check-name` only adds the preconditions described above).
- Comparing with an existing database: `REFERENCE_DUMP=<file>` (with `REFERENCE_ENGINE`) compares an externally produced dump with the empty database built by the service migrations, `ALLOWED_DIFF=<file>` lists accepted differences (printed as `ALLOWED-DIFF`); any other difference fails. A reference file is engine specific (MariaDB and MySQL 8.0 print column defaults differently): make it with the engine of the database it describes and name that engine in `REFERENCE_ENGINE` (required); the comparison runs on that engine and is skipped, with a SKIP line, on the other one; the allowed lines apply to every table of the dump, not to one table. The run prints `reference dump not given` when no reference was compared. `scripts/verify-service-migrations.sh --dump <service-dir> <database> [<migrations-subdir>]` produces the dump from a database through `SQL_CMD` (client option file for the credentials).
- `scripts/verify-service-migrations.sh --self-test` exercises the dump queries (generated column, comments, foreign key rules, check expressions) on a synthetic schema.

## Impact analysis for a migration PR

Every PR that changes a migration file or the migration runner states, with evidence, for each point: destructive operations one by one (DROP of any object, TRUNCATE, data changing UPDATE/DELETE/INSERT SELECT, type narrowing or change, default removal or change, rename, NOT NULL/UNIQUE/FK/CHECK on existing data, enum value removal, NOT NULL column without default); compatibility of the old code with the new schema and of the new code with the old schema (grep results); lock and duration with the table size source; rollback (the helper skips a database version that is ahead of the image, so an older image still starts; a rollback of a baseline is the previous image); data loss. A PR with a destructive or ambiguous operation starts its body with `[DESTRUCTIVE]`. Attach the output of the two engine verification.
