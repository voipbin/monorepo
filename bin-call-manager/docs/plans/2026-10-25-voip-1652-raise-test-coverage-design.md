# VOIP-1652: raise bin-call-manager unit test coverage to 75%

Ticket: VOIP-1652. Base: origin/main accc03e (the branch was rebased onto it; bin-call-manager had no other change). Scope: unit tests (and test helpers inside test files) in bin-call-manager only. No behavior change in non-test code.

## 1. Ticket review

Verdict: valid. Baseline re-measured in the worktree with `GOFLAGS=-mod=mod go test -count=1 -coverprofile=cp.out ./...` (no vendor directory, 0 test failures): hand-written 70.63% (8287 of 11733 statements), the same as the ticket. Statements still needed: 513 for 75.0%, 631 for 76.0%.

Checked against the code and history:
- Hand-written filter: files under `/gens/`, `mock_*.go` and files whose header before `package` has `Code generated` and `DO NOT EDIT` are excluded; duplicate blocks keep the maximum count.
- `git log` for the service shows no coverage work in flight; no open PR touches bin-call-manager.
- `cmd/call-control/main.go` (256) and `cmd/call-manager/main.go` (174) are 0% and count in the hand-written total (430 statements, 3.7 points). Their `main`, `runCommand`, `run` and `initHandler` connect to RabbitMQ, Redis and the database, so those parts cannot be unit-tested without refactoring non-test code, which is out of scope. `runSubscribe` (6) and `runRequestListen` (6) take interfaces and are the only mock-able candidates there; `initCallHandler` connects to RabbitMQ and `initProm` registers on the global HTTP mux and starts an endless retry goroutine, so both stay out. The command functions `runCommand`, `run` and the per-command `run*` functions that call `initHandler` stay out too. `resolveUUID` reads global viper state, so tests that touch it reset it with `t.Cleanup`. Of the helpers that need no infrastructure, `initCommand` (33) and the `cmdGet`/`cmdList`/`cmdDelete`/`cmdUpdateStatus`/`cmdHangup` constructors (72) only assemble command and flag declarations, and a test of them would compare copied literals, so they are not counted as a reserve; `resolveUUID` (7), `printJSON` (5) and the signal helpers (5) hold about 17 statements of real logic and are the last resort. Excluding the two cmd packages, the other 11303 statements are 73.3% covered with 3016 uncovered; the 75% goal needs 513 of those 3016 (the covered share of that range must reach about 77.9%, and about 78.9% for 76%); this is feasible (section 2). The 631 figure is the need for 76%, not a pool size.
- Not refuted: the ticket numbers (baseline, per-package table, exclusion method). Claims the ticket did not make (testability, dependencies, asynchrony) are analyzed in section 2.

Testability findings (read from the code):
- Handler packages use interfaces for the database, cache, request, notify and channel/bridge collaborators and already have generated gomock mocks; tests in this service build the private struct directly. Every partially covered function listed in section 3 can be reached with those mocks.
- `pkg/cachehandler` has no test at all. Its methods call `go-redis` directly through the `handler.Cache` field; an in-process Redis (`miniredis`) makes them testable. `NewHandler` and `Connect` (13 statements) can be exercised against the loopback address of the same fake server (success) and a closed address (failure); they are part of wave 1, not of the cmd reserve.
- `pkg/callhandler/recoveryhandler_homer.go` `getSIPMessages` issues an HTTP POST to a configurable endpoint; a loopback `httptest` server tests it without external network.
- `models/call`, `models/bridge`, `models/outboundconfig` contain pure functions (`Matches`, `String`, `CalculateHangupReason`, `ConvertHangupReasonToChannelCause`, webhook conversion, `ValidateCodecs`) that have no test for the listed functions (the packages have other tests).
- `pkg/dbhandler` tests run against sqlite with the table scripts under `scripts/database_scripts_test`; JSON-function expressions are covered by golden `ToSql()` tests, so those are not to be round-trip tested.
- Dependency: `github.com/alicebob/miniredis/v2` is not in bin-call-manager's go.mod today (it has go-sqlmock, go-redis v8 and go-sqlite3). Using it is a test-only addition: go.mod and go.sum change, non-test code does not, and the root verification (`go mod tidy`, `go mod vendor`, `go test`, lint) covers it. If it were not acceptable, the fallback is a go-redis hook or `redismock`, which is weaker; it is not planned.

Asynchronous code: several paths start goroutines (`groupcallhandler/start.go`, `hangup.go`, `dial.go`, `listenhandler/v1_calls.go`, `callhandler/hangup.go` and `recovery.go`, `recordinghandler/db.go`, `confbridgehandler/leaved.go`, `channelhandler/db.go`). Measured against `go func` ranges, only about a quarter (55 of 236) of the uncovered groupcallhandler statements are inside goroutine bodies; the rest is synchronous. Tests must wait deterministically (a `sync.WaitGroup` or channel released inside a `DoAndReturn`, then wait before the controller finishes) and must not rely on a fixed sleep to decide coverage or assertions; mock expectations for calls that depend on timing use `AnyTimes` only where the count is genuinely nondeterministic (the retry goroutines in `channelhandler/db.go` and `bridgehandler/db.go` run once per 150 ms until the deadline, so a deadline shorter than that gives one deterministic call and a wait of the full existence timeout does not). The existing `checkNoGetWithTimeoutGoroutine` helper in `channelhandler/db_test.go` is reused to prove no goroutine leaks.

Not unit-testable without infrastructure: the two `cmd` mains and the infrastructure wiring listed in section 1. The constructors `NewEventHandler`, `NewBridgeHandler` and the cache and database `NewHandler` only build structs or lazy clients, and `cachehandler.Connect` only pings, so they can be exercised with mocks or the fake server. Left out on cost, not on impossibility: `LoadGlobalConfig` (9 of the 12 uncovered statements of internal/config, global viper state).

dbhandler: most 0% functions (not all; `CallSetStatusRinging`, `CallSetStatusProgressing`, `ChannelSetSIPData`, `ChannelSetPlaybackID`, `ConfbridgeSetBridgeID`, `ConfbridgeDelete`, `RecordingSetStatus` and the recording status setters are plain updates and use sqlite) use MySQL JSON functions through `squirrel.Expr` (call chained-call, external-media and recording id add/remove, confbridge add/remove, bridge channel add/remove, channel data item). SQLite cannot run them (see `pkg/dbhandler/json_expr.go`), so they are reached with `go-sqlmock`, as `call_tx_ctx_test.go` already does (`newTXTestHandler`): assert the executed statement shape and arguments and the cache refresh, not a round trip.

Channel and bridge handlers retry with `time.Sleep(defaultDelayTimeout)` (150 ms) in `channelhandler/db.go` and `bridgehandler/db.go`; error-branch tests there use a short context deadline so they stay fast and deterministic.

Feasibility: the listed functions of waves 1 to 3 hold about 292 + 355 + 353 uncovered statements as a ceiling (about 730 at a realistic 70 to 85 percent) against the 513 needed for 75% and 631 for 76%; wave 4 is in reserve.

## 3. Design

Rules for every wave:
- New tests go in new files named `<source>_cov_test.go` (one per source file, in the same package), so the change does not collide with other work in the large existing `_test.go` files. Function names are `Test_<Func>_cov` or `Test_<Func>_<case>_cov` in the existing table-driven style (in callhandler the files and functions use the suffixes `_covA` and `_covB`; they keep the same collision avoidance and are selected by `-run '_cov[AB]?$'`) (the suffix avoids redeclaring names that the existing files already use and lets the mutation runs select exactly the new tests with `-run '_cov$'`); the gomock controller variable is `mc` (not `ctrl`); results are checked with `reflect.DeepEqual` and `t.Errorf`, not testify. The `scripts/check-test-conventions.sh` gate is run locally (it inspects the added lines only); helper functions must not be named `TestXxx(`.
- Every test asserts an observable result: a returned value or error (with `errors.Is` where the code wraps a cause), the exact arguments of the mock calls, and side effects on the fake cache or database. A path that logs and swallows an error is asserted on both sides: the return value is what the function documents and the following calls do (or do not) happen. Error-path tests make the injected collaborator fail and register no expectation for the later collaborators, so a call to them fails the test as an unexpected call.
- No empty-call tests and no tests that compare a value with itself. Expected keys, TTLs, queries and URLs are literals written in the test, never read back from a source helper or constant.
- Synthetic data only: zero-padded UUIDs, numbers in the 555 range, `example.com`, addresses in 203.0.113.0/24 or 198.51.100.0/24 (loopback is the one exception: the `httptest` server, the miniredis server, and a closed loopback port for connection-failure cases, obtained by listening on port 0 and closing the listener at once, never a fixed port), plain fake tokens such as `test-token` (no high-entropy strings, no `Bearer` with a long value). A password or token is assigned in a separate statement and not placed in the same literal as an address. No `user:pass@host` strings. No network beyond loopback and no PSTN, SMS or email calls.
- Time: miniredis TTL checks use `FastForward`, never a real sleep. Goroutine paths whose spawn order follows map iteration (ring-all and linear start) are asserted as a set with argument matchers, not as a call order. Goroutine paths wait on a channel or `sync.WaitGroup` released from a mock `DoAndReturn` before the controller finishes; the new goroutine tests run with `go test -race -count=5`.

At the checkpoints the hand-written total is re-measured; a wave that ends below its checkpoint is not closed: the shortfall is made up first in the same wave (more error branches of the same files) until the candidates in those files are exhausted or two further passes add under 10 statements each, and then the work continues with the next wave; wave 4 never starts before wave 3 is finished and is used only if the total after wave 3 is below the 76.0% line (631 statements gained); the 75.0% line (513) is the floor, never the goal. With the plan column, waves 1 and 2 give about 480, which is short of the 75% line (513), so wave 3 is needed in practice; the plan for waves 1 to 3 is about 730 against the 631 needed for 76%.

Wave 1 detail. cachehandler uses an in-process Redis (miniredis): for each getter and setter pair, the stored raw value is read with the miniredis API and compared with a literal JSON string, the key name is a literal, and the TTL is a literal taken from the source behavior: 24 hours for the generic setter, 30 minutes for `OutboundConfigSet`, 1 minute for `OutboundConfigSetNotFound`, and the caller-supplied value for `CallRecoveryClaim` (and `FastForward` past each gives a miss); a missing key returns the redis nil error; a stored non-JSON value makes the getter fail; `ExternalMediaDelete` removes both the id key and the reference key; `OutboundConfigSetNotFound` stores a sentinel that `OutboundConfigGet` returns as `(nil, nil)`, a missing key returns the redis nil error, `AsteriskAddressInternalGet` and `OutboundConfigDelete` are covered, `ExternalMediaSet` is checked for both keys it writes, the first-call error branches of the setters, `Del`, `HGetAll` and `SetNX` are reached by closing the miniredis server (`Close`) before the call (a second `Del` or second `setSerialize` after a successful first call cannot be reached this way and is left out), and after `FastForward` past the one-minute TTL the sentinel is a miss; `CallRecoveryClaim` returns true then false within the TTL and true again after `FastForward`; `KamailioMetadataGet` decodes a hex value and falls back to the raw value; `NewHandler` plus `Connect` succeed against the fake server and `Connect` fails against a closed loopback port. This adds `github.com/alicebob/miniredis/v2 v2.36.1` to go.mod and go.sum (same version as bin-sentinel-manager, bin-ai-manager, bin-message-manager, bin-registrar-manager and bin-transfer-manager; test import only). The real go.mod and go.sum diff after `go mod tidy` is checked and must show only miniredis and its transitive modules. `Call.String` and `Bridge.String` are asserted against a literal built from a small struct, not by re-running the same formatting call; the expected string is written out in the test as it prints (`<nil>` for nil pointers, canonical text for uuid values). Hangup-reason tables for models/call map each documented direction and reason pair to its exact expected value.

dbhandler detail (wave 4). The golden tests of `json_expr.go` already pin the generated SQL text, so the value of the sqlmock tests is the error propagation of `ExecContext` and the cache update that follows a successful update (the cache update re-reads the row with a SELECT, so the sqlmock gives a result row with the full column list written as a literal in the test, and the mock expects `CallSet` and the like; the caller discards the cache-update error, so the test asserts that the update result is returned unchanged when the cache update fails). sqlmock tests set the query matcher so the core of the expected SQL (the JSON function name and the WHERE condition) is a literal in the test, fix the arguments with `WithArgs`, and call `ExpectationsWereMet`.

Per wave completion conditions: the five-step verification of the repository (`go mod tidy`, `go mod vendor`, `go generate ./...`, `go test ./...`, `golangci-lint run -v --timeout 5m`); `scripts/check-test-conventions.sh`, which inspects committed lines only and exits 0 with "no changed test files" when nothing is committed, so the wave is committed first, `origin/main` is fetched, and the reported file count must equal the number of test files in `git diff --name-only <merge-base> HEAD -- '*_test.go'`; and a review of the added lines for the hygiene rules above.

Mutation checks. The mutation list is fixed in advance and recorded in a script kept in the scratch area, one line per mutation (file, line, change). For every wave at least five mutations, and for every new test file at least one, are applied in a scratch copy: flip an error check, drop a mock-visible call, ignore a returned error, change a literal key, TTL or constant, invert a condition. Only the new tests are run against each mutation (`-run '_cov$'` with `-timeout 60s`). A mutation that fails to compile is invalid and is replaced by another; a mutation that ends in a timeout is re-run with `-run` narrowed to the one test that targets it and counts as killed only if that run fails or times out on its own. Pass criterion: every mutation is killed, or a surviving mutation is explained and the test is strengthened. The pull request notes carry the number of mutations applied, how many were killed, and the file and mutation description of each survivor with the reason; nothing else.

Final measurement: the command of section 1, run twice (the second run with `-race` on the packages with new goroutine tests), reporting the lower of the hand-written totals as the result and, next to it, the raw total including generated code and mocks. Target at least 76.0% and never below 75.0%; the same total is also computed once with a vendor directory to confirm it equals the `-mod=mod` result. `git diff --stat origin/main...HEAD` must list only files under `bin-call-manager/`; go.mod and go.sum changes are limited to miniredis and its transitive dependencies. If after wave 4 the total is still below 75.0%, the work stops and the achieved value is reported.

Defects found while writing tests are not described in this repository; tests that pin such behavior carry only a neutral comment.

## 4. Result

Waves 1 to 3 were carried out together by package and wave 4 was not needed as a separate step. Measured with the section 1 command on the final HEAD: hand-written 83.23% (9765 of 11733 statements), raw total including generated code and mocks 71.3%, against the 75.0% floor and the 76.0% target. The sqlmock tests of the JSON-expression functions assert the executed statement, its arguments and the propagation of an `ExecContext` error and of a failed cache refresh; the successful cache refresh after such an update is not asserted by the sqlmock cases. The cmd packages stay at 0%.
