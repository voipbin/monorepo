# Remove the RECOVERY_ENABLED gate: call recovery is unconditionally active

Status: Approved, revision 5 (design review: 2 consecutive full-approval rounds, R5 and R6)
Date: 2026-10-03
Ticket: NOJIRA (CEO instruction, chat 2026-10-03; supersedes VOIP-1560, closed Won't do).

## 1. Problem and decision

VOIP-1553 added a gate (`RECOVERY_ENABLED`, default false) in front of every call-recovery path, because the path had verified defects at the time. VOIP-1556 then redesigned and fixed the recovery path itself (design rev 10, 9 design-review rounds, 3 code-review rounds, merged `ea1b948dc`), but the gate was left in place pending a separate go-live decision; the original plan (VOIP-1556 analysis) was to ship VOIP-1560 (drain the Asterisk before a planned recreate) first, then enable recovery only for a gated crash test, because without a drain every planned deploy would trigger recovery on every live call on that instance, not just rare real crashes.

CEO decision, 2026-10-03: skip the drain. Rely on the recovery module for both unplanned crashes and every planned recreate; if a defect surfaces, fix the recovery module. The CEO also directed removing the on/off flag itself, not just setting it to true: there is to be no global enable/disable switch for this path going forward. VOIP-1560 is closed Won't do; the stale-call defect it found (F5, 97 non-final calls) moves to a separate new ticket.

This document covers only the flag removal (a call-manager code change). It does not touch recovery's own logic (VOIP-1556 scope) or file the F5 ticket (separate action).

## 2. What changes

Recovery runs unconditionally from both of its existing entry points: `EventSMContainerDied` (automatic, on a sentinel-reported container death) and `POST /v1/recovery` (manual). No code outside this change decides whether recovery is allowed to run.

## 3. Risk, made explicit for the record

- **Scope gap, unchanged by this PR**: recovery (VOIP-1556) only ever recovers answered, single-leg Flow calls (no confbridge, chained, master, groupcall, or external-media relation). Connect/forwarding, queue, conference, AI/streaming calls are not recovered; they end the same way they do today on every planned recreate and every unplanned crash. This PR does not change that; it only removes the switch that was keeping recovery itself off.
- **Recovery now runs on every planned deploy**, not only on rare real crashes: call Asterisk alone was recreated 13 times in the last 30 days (VOIP-1560 analysis, section 2). From this PR onward, every live, in-scope call on the recreated instance goes through the recovery path at every one of those deploys. Recovery has passed design review (9 rounds) and code review (3 rounds) for VOIP-1556, including mutation-tested unit coverage, but has not yet been exercised against a real Asterisk crash or recreate in production (no gated crash test has been run).
- **No kill switch remains after this PR.** If a defect appears in production, the only mitigation is a code fix and redeploy (this is the CEO's explicit instruction: fix the recovery module when a problem surfaces, rather than keep a flag to fall back on). Recorded here so the trade-off is on paper, not implied.
- Mitigations already in place, unaffected by this change: VOIP-1556's own safeguards (Redis claim before Homer lookup, commit-first conditional switch, owner-conditioned hangup write) and its design/code review history (`bin-call-manager/docs/plans/2026-10-02-voip-1556-call-recovery-core-design.md`, which mentions `RECOVERY_ENABLED` twice as a historical fact, not as something this PR must edit: its opening summary line 7 ("Recovery stays disabled in production (`RECOVERY_ENABLED` unset)...") and its "## 7. Rollout and risk" section around line 371 ("Recovery is disabled (`RECOVERY_ENABLED` unset...)"). Both record the state of the world when that design was written and reviewed; this document is not rewritten for the same reason VOIP-1553's design doc is only annotated, not edited, per 2.6).

## 4. Out of scope

- Recovery's own selection/skip/dialog logic: VOIP-1556, already shipped, not touched here.
- F5 (97 calls stuck in non-final states, found during the VOIP-1560 analysis): separate new ticket, to be filed after this PR.
- Widening recovery's scope to connect/queue/conference/groupcall/AI calls: not requested; would be a new design if it becomes necessary.
