## 2. 설계

범위는 `bin-common-handler` 의 신규 `_test.go` 뿐이다. 제품 코드, go.mod, go.sum 은 바꾸지 않는다(새 모듈 없음). 테스트는 시간, 네트워크, 외부 상태에 의존하지 않으며 시각은 고정 리터럴을 쓴다.

### 2.1 requesthandler (error_paths_test.go)

`requestHandler` 의 exported 메서드를 reflect 로 열거(이름 정렬, 순서 의존 없음)하고 인자는 영값으로 호출하되 `context.Context` 는 `context.Background()` 로, 포인터는 영값을 가리키게 한다. 허용하지 않는 인자 타입(func, chan)을 가진 메서드가 생기면 그 서브테스트를 실패로 보고하고, 호출 중 panic 은 `recover` 로 해당 서브테스트의 실패 한 건으로만 보고한다(반환값 없음 오류를 중복 보고하지 않음). 영값 UUID 사용은 이 표의 의도된 예외임을 파일 주석에 적고 단언 메시지는 저장소의 `Wrong match` 형식을 쓴다. sentinel 비교는 모두 `errors.Is` 로 하고 400, 404, 409, 500 은 기대 sentinel 일치와 함께 다른 sentinel 이 아님도 단언한다. 이 표는 gomock 을 쓰지 않고 손으로 쓴 결정적 대역을 쓰며 그 이유(publish 횟수와 요청 필드를 한 곳에서 검사)를 파일 주석에 한 줄 적는다. 테스트 값(host_id 등)은 `pod-a` 같은 비주소 합성 문자열을 쓴다. 오류와 함께 반환되는 다른 값은 `reflect.Value.IsZero` 로 판정한다(nil 슬라이스는 영값, 빈 슬라이스는 아님). `t.Parallel` 을 쓰지 않고 케이스마다 독립된 대역 인스턴스를 만든다. 결정적 sockhandler 대역은 publish 를 세고 정해 둔 응답과 오류를 돌려주며, 각 publish 에서 queueName, `req.URI`, `req.Method` 가 비어 있지 않음도 단언한다. 인자를 그대로 전달하는 `SendRequest` 는 (a) 표에는 유지하되 영값 인자로는 이 비어 있음 단언을 만족하지 못하므로 그 단언만 건너뛰고, 비어 있지 않은 인자를 주는 별도 케이스를 추가한다(전송 오류가 전파됨, 404 응답은 오류 없이 그대로 반환됨. `SendRequest` 는 응답을 그대로 돌려주는 것이 계약이라 이 단언은 현재 동작 고정이 아니라 계약 검증이다).

- (a) 전송 오류: `errors.Is` 로 전파, publish 정확히 1회, 오류와 함께 반환되는 다른 값은 영값.
- (b) 응답 status 404, 500(`Data` 는 JSON `null`): 오류 반환과 영값. 본문을 비워 두면 일부 래퍼가 빈 본문 파싱 오류로 우연히 통과해 status 검사 제거를 못 잡으므로 `null` 을 쓴다(제외 목록 산정은 구현 시 이 응답으로 직접 실행해 확정한다). 오류의 종류(sentinel)는 래퍼마다 다르게 감싸므로 이 표에서는 단언하지 않는다. sentinel 매핑과 경계는 `getResponseStatusCodeError` 를 직접 호출하는 신규 `status_error_test.go` 의 `Test_getResponseStatusCodeError_Sentinels` 표로 따로 단언한다: 기존 `common_test.go` 의 표에는 400, 500, 499, 599 만 있어 404, 409 와 `< 300` 경계(200, 299 는 nil, 300 은 `ErrUnknown`)가 없으므로 400, 404, 409, 500 은 기대 sentinel 을 리터럴로, 200, 299 는 nil, 300 은 `ErrUnknown` 으로 둔다.
- (c) 영값 인자를 거부하는 `AgentV1AgentGetsByTagIDs`, `...AndStatus`(tag 1개와 2개를 모두 사용해 목록 결합 루프 경계를 넘음): 별도 표로 빈 목록(publish 0회), 전송 오류(`errors.Is`), 404(`errors.Is(err, ErrNotFound)`)를 검증한다.
- (e) 지연 전송: `delay` 인자를 받는 래퍼 하나(`ConferenceV1ConferenceDeleteDelay` 또는 같은 성격의 래퍼 중 구현 시 확정)를 골라 `delay > 0` 으로 호출하고 `RequestPublishWithDelay` 의 오류가 전파됨을 검증한다(영값 호출로는 이 경로에 도달하지 않음). 나머지 래퍼의 지연 경로는 같은 `sendRequest` 분기를 공유하므로 대표 1건으로 한다.
- (d) `PipecatV1Ping` 별도 표(기존 `pipecat_ping_test.go` 의 5개 케이스는 줄 커버리지를 채우지만 non-200 불일치 본문, `{}` 본문, 파싱 불가 본문, nil 응답이 없어(queueName 형식, URI, 메서드는 기존 테스트가 이미 정확히 비교하므로 (vii)의 queueName 변이는 기존 테스트가 죽임) 신규 파일의 신규 함수로 둔다): 응답 200 과 일치하는 host_id(성공), 빈 본문(성공), 다른 host_id(오류, 메시지에 요청 host_id 포함), 200 이 아닌 status 와 불일치 host_id 본문(성공, status 분기), 파싱 불가 JSON 본문(성공), `{}` 본문(host_id 비어 있음, 성공), 전송 오류, 응답 자체가 nil(성공). `{}` 본문 케이스는 요청 host_id 가 비어 있지 않아야 한다. 대역이 받은 queueName 이 `QueueNamePipecatRequest` 와 host_id 를 `.` 로 이은 형식인지 단언한다. 이 메서드는 status 를 응답 해석 대상으로 삼지 않으므로 404 는 단언하지 않는다.
- 이 표가 보장하는 것은 "실패가 호출자에게 전파된다"까지이며 성공 경로와 요청 형태(URI, 본문)는 기존 래퍼별 테스트의 몫이다. 성공 경로 테스트가 없는 래퍼는 이 표로 검증되지 않는다는 한계를 파일 주석에 적는다.
- 표 적용 규칙: 영값 인자를 거부하는 두 메서드는 (a), (b)에서 빼고 (c)에서 다루며, 이벤트를 발행하는 `CallPublishEvent` 는 전부 뺀다(기존 테스트 있음). `Data=null` 의 404, 500 양쪽에서 오류를 반환하지 않는 메서드 전부는 (a)에는 적용하고 (b)에서만 뺀다(`SendRequest` 의 비어 있음 단언 예외와 별도 케이스는 위와 같음). 이 집합은 구현 시 프로토타입을 그 응답으로 실제 실행해 확정하며, 문서와 PR 본문과 코드 주석 어디에도 이름별 사유를 적지 않고 제외 목록을 `var excludedFromStatusCheck = map[string]bool{...}` 형태로만 코드에 둔다(주석은 \"이 표의 (b) 가정을 적용하지 않음\" 한 줄만). 새 래퍼가 이 표의 가정(영값 인자 허용, publish 1회, 응답 해석)을 깨면 표가 실패하며 이는 의도된 마찰이고 개발자가 이유와 함께 제외 목록을 갱신한다. 제외 목록의 모든 키가 실제 메서드인지 단언하는 테스트를 둔다(삭제나 개명이 조용히 통과하지 않게). 제외 사유가 계속 유효한지는 기계로 검증하지 않고 항목별 주석으로만 관리한다. 제외 대상의 현재 응답 처리를 역으로 단언하는 테스트는 두지 않는다. 이벤트를 발행하는 `CallPublishEvent` 는 전부 뺀다(기존 테스트 있음, 이 메서드는 상태 코드 처리 여부와 무관하므로 이름을 적어도 위생 문제가 없다).

### 2.2 databasehandler (scan_row_test.go)

`sql.OpenDB` 와 `driver.Connector`(메모리 내 대역, 열과 값 행을 주입)로 실제 `*sql.Rows` 를 만든다. `sql.Register` 는 쓰지 않는다(중복 등록 패닉으로 `-count`, `-shuffle` 에서 깨짐). `rows.Next()` 후 `ScanRow` 를 호출한다. NULL 케이스의 기대값은 필드 종류별로 다르다: `*uuid.UUID` 는 코드가 nil 을 명시 대입하고 `uuid.UUID` 는 `uuid.Nil` 을 명시 대입하므로 대상 필드를 비영 센티널로 미리 채워 두고 되돌아옴을 단언하며, string, int, uint, float, bool, json, `*time.Time` 은 NULL, 빈 문자열, 파싱 불가에서 필드를 건드리지 않으므로 영값 dest 에서 영값(nil)이 유지됨을 단언한다(센티널 유지는 운영 경로에서 관찰되지 않는 구현 세부이므로 단언하지 않는다). `db` 와 `rows` 는 `t.Cleanup` 으로 닫는다. 대역은 열 이름 목록과 `driver.Value` 가 허용하는 타입(int64, float64, bool, []byte, string, time.Time, nil)의 값만 돌려주며 열 수를 열 이름 개수로 알린다. 기대값은 리터럴이고 `-race` 에서도 통과해야 한다.

- 값 변환: NULL 과 비 NULL 의 string, int(SetInt), uint(SetUint), float32/64, bool(0 과 1 입력), `uuid`/`json` 태그, 널 가능 `*uuid.UUID`(NULL, 빈 문자열, 16바이트), 널 불가 UUID 의 NULL(`uuid.Nil`), `json` 의 NULL 과 빈 문자열(필드 유지)과 정상 JSON(변이 (viii)를 죽이는 쪽은 비 NULL 케이스이므로 그 string, int, uint, float, bool 값은 영값이 아닌 리터럴을 쓴다), `*time.Time`(`*time.Time` 필드는 NullString 경로로 스캔되므로 입력은 문자열과 드라이버 `time.Time` 값 두 형태. 문자열은 MySQL 형식, ISO 형식, 오프셋이 붙은 `2024-01-15 10:30:45+09:00`(MySQL 변환 정규식에 맞지 않아 오프셋 레이아웃으로 파싱) 와 `T` 형식 오프셋 `2024-01-15T10:30:45+09:00`(RFC3339 레이아웃) 둘 다 UTC 로 변환됨, 빈 문자열은 nil, 파싱 불가는 오류).
- 오류 경로: UUID 바이트 길이 15, 17 의 오류와 16 의 정상 경계, 파손된 JSON 오류, 열 수 불일치(열이 더 많음, 더 적음)의 scan 오류, 널 불가 `time.Time` 필드에 NULL 이 올 때의 scan 오류, 비 포인터 dest 와 포인터이지만 구조체가 아닌 dest 의 거부.
- 구조: 내장 구조체 재귀, 내장 nil 포인터 구조체(대상 없음, 열 수는 내장 필드 몫을 뺀 값), `db:"-"`, db 태그 없는 필드 건너뛰기, db 태그 필드가 없는 구조체(열 0개이면 성공, 열 1개 이상이면 scan 오류).
- `prepareFieldsFromMap`, `convertValueForDB`: UUID 값과 포인터, 비 UUID 값의 uuid 변환 오류, `json` 태그 변환(nil 입력은 `(nil, nil)`, nil 슬라이스, map, 직렬화 불가 값 chan 은 `json` 태그에서만 오류), 태그 없는 경로의 `[]byte` nil, `time.Time` 통과, 원시 값을 리터럴 기대값으로 검증한다. `prepareFieldsFromMap` 의 비 map 입력 거부, 비 문자열 키 map, 직렬화 불가 구조체 값의 `field <키>:` 오류 감싸기도 포함한다.

### 2.3 sockhandler (main_test.go)

신규 `pkg/sockhandler/main_test.go` 에서 `NewSockHandler` 는 `TypeRabbitMQ` 에서 nil 이 아닌 핸들러를(uri 인자는 빈 문자열, 구체 타입은 비공개이므로 `reflect.TypeOf` 로 `rabbitmqhandler.NewRabbit("")` 의 반환 타입과 비교), 알 수 없는 타입에서 인터페이스 값이 `== nil` 인 진짜 nil 을 반환함을 검증한다(연결을 만들지 않으므로 네트워크 없음).
