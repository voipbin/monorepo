# Pipecat 1.4.x -> 1.12.0 upgrade (runner: `scripts/pipecat/`)

Status: Design approved (12 review rounds, rounds 11 and 12 consecutive APPROVED). Ticket VOIP-1544. Branch `VOIP-1544-Upgrade-pipecat-to-1.12.0`. Class: hardening (dependency bump), not a feature.

## 1. Issue analysis

Behavior deltas, found by diffing resolved service settings and constructor/param defaults between a pipecat 1.4.0 venv and the 1.12.0 venv with the runner's exact constructor calls:

- Deepgram `profanity_filter`: True -> None (Deepgram default = off). 1.9.0 change. Customer-visible (transcript text fed to the LLM).
- Cartesia `model`: sonic-3.5 -> sonic-3.6. 1.9.0 default change. Customer-audible (voice).
- ElevenLabs `model`: eleven_turbo_v2_5 -> eleven_flash_v2_5. 1.6.0 default change. Customer-audible (voice).
- `LLMUserAggregatorParams.empty_user_turn`: None -> `EmptyUserTurnConfig(interrupted_prompt=..., idle_prompt=None, max_consecutive_recoveries=1)`. 1.12.0 addition, on by default. When a user turn that interrupted the bot ends with no transcript (cough, line noise, unrecognized speech), the aggregator appends a `developer` message and runs the LLM so the bot asks the caller to repeat. Customer-audible on noisy phone lines, and it writes a new message into the conversation context.
- `PipelineTask` `setup_timeout_secs` / `start_timeout_secs`: none -> 20 s. A processor blocking in setup/StartFrame for more than 20 s now tears the pipeline down instead of hanging. Our processors (websocket connect to the local Go server, service setup) finish well under that. Protective, not audible.
- `WebsocketClientParams.audio_out_write_timeout_secs`: none -> 10 s. A transport write that never returns now marks the transport unusable instead of hanging the audio task. Protective.
- `PipelineTask.processor_unusable_policy`: new, default `CONTINUE` (pipeline keeps running, application decides). No prior equivalent; our disconnect/error handlers still cancel the task. The unusable state it reacts to is neutralized for STT/TTS by section 2.5c.
- `LLMContextAggregatorPair` `realtime_service_mode`: False -> None (auto). Only realtime speech-to-speech services flip it on; we use text LLMs. No effect.
- `PipelineTask.enable_rtvi`: True -> None, which resolves to True for an unbridged pipeline. No effect.
- OpenAI, Gemini model settings: unchanged.

Flows registration model (verified by probe and by reading the flows wheels): flows 1.2.0 `FlowManager` called `self._llm.register_function(...)` per node, which is why `run.py` swaps `flow_manager._llm = routing_llm` (fan-out to every member). **Standalone flows 1.3.0 already stopped doing this**, and 1.12 built-in flows is the same: `FlowManager` builds `FunctionSchema(handler=transition_func)` and queues `LLMSetToolsFrame`, and each `LLMService` auto-registers handlers from the advertised tools on every `LLMContextFrame` (`_sync_registered_tool_handlers`, present since pipecat 1.4.0). If prod runs flows 1.3/1.4 (see 1.2), this model is already live and is not a new risk from this change. Probe with `RoutingLLMService({A: OpenAI, B: Gemini})`: member A had the handler (auto_registered=True) after its context frame; member B did not until it processed its own first context frame, after which it did. `RoutingLLMService.process_frame` hands each `LLMContextFrame` only to the active member, so the member that runs inference always syncs first. Team tool routing keeps working. `self._llm` still exists and is read only by `generate_summary` (unused here), so the swap is harmless and the existing `hasattr` guard does not trip.

Team-path regressions found in design review round 1 (both reproduced against the real 1.12.0 install; neither exists on 1.4.0):

- **STT latency metadata lost behind `RoutingSTTService`.** In 1.4.0, `STTService.process_frame(StartFrame)` pushed the `STTMetadataFrame` (TTFS p99 latency) itself, through the instance `push_frame` that `RoutingSTTService` overrides, so it reached downstream. In 1.12.0 the broadcast moved into `AIService.push_frame` (class method, `ai_service.py:236-242`), which the router's per-instance `push_frame` replacement (`routing_stt.py:17-21`) bypasses. Probe (Pipeline with a dummy STT, `ttfs_p99_latency=0.7`): 1.12.0 direct = 1 frame, routed = **0 frames**. Impact: the default user-turn stop strategy keeps `_stt_timeout = 0`, so in team voice calls the turn closes as soon as VAD reports silence, without waiting for the last transcript (clipped utterance ends, double bot replies). Largest for Google STT members (p99 about 1.6 s). Single-AI path unaffected. The same bypass drops the new `LLMServiceMetadataFrame` behind `RoutingLLMService` (only `is_realtime_service=False`, which is also the aggregator's default, so no behavior impact, but restored for parity).
- **Flows now renders `{{ key }}` placeholders in `task_messages`.** Built-in flows (since 1.9.0) runs `_render_node` on every node entry: any `{{ identifier }}` in a `task_messages` content string is looked up in `flow_manager.state`, and a missing key raises `FlowError`, which `initialize()` wraps into `FlowInitializationError`. `team_flow.py:119-120` puts the caller's conversation history (`llm_messages`: user utterances, chat text, tool results) into the start node's `task_messages`. A history message containing e.g. `{{ name }}` therefore fails the whole team session at start (run.py except path cancels the task), and `\{{ x }}` silently loses its backslash. Standalone flows 1.2/1.3/1.4 had no rendering. `role_messages` (carrying `init_prompt`) is not rendered in 1.12, only `role_message` / `task_messages` / `tts_say` text.

Other upstream deltas checked and judged not affecting this runner: openai SDK 3 uses the OS trust store (`python:3.12-slim` ships `ca-certificates`, verified); function calls past `timeout_secs` are now cancelled (runner sets no timeout); `LLMSetToolsFrame` no longer accepts bare provider dicts (runner always uses `ToolsSchema`); flows transition frames are now uninterruptible (a fix; strictly safer for barge-in during a member transition); `ErrorFrame(fatal=True)` deprecated (no service we use emits it); sentence splitter for TTS aggregation changed from NLTK Punkt to sentencex in 1.12.0 (Korean samples split identically; a few English abbreviations and some Japanese sentences split at different points, so TTS chunk boundaries can differ slightly; not pinnable, negligible audible effect); `idle_timeout_frames` now also counts transcription / user-started-speaking frames and `PipelineTask(handle_flush_frame=...)` is new (both protective, runner uses neither); `LLMService.push_frame` speculation gate and `TTSService.push_frame` text pts stamping are bypassed behind the team routers (known limitation: no eager turn strategy in use, only RTVI text ordering affected, not audible); Speechmatics/LMNT/Rime/Sarvam/Soniox/Grok-realtime changes (unused providers).

Other 1.12 deltas recorded (checked, accepted):
- Reconnect latency after a dropped connection, surveyed for every connected component (fake servers, 1.4.0 vs 1.12 with this design): Cartesia, ElevenLabs, Google STT (including stream-limit rollover), Google TTS, OpenAI/Gemini HTTP connection reuse after FIN/RST, and the Go input/output WebSockets all recover as fast as 1.4.0 or faster (ElevenLabs recovers after a mid-turn drop where 1.4.0 stayed silent). Deepgram is the only regression and is handled by 2.5c (1b). Pre-existing limits unchanged from 1.4.0 and left as separate hardening candidates: ElevenLabs stays silent after three quick disconnects, Gemini waits indefinitely on a half-open connection.
- Gemini adapter: history function calls without a thought signature get the documented `skip_thought_signature_validator` placeholder (required by Gemini 3); parallel function responses are grouped into one user turn right after the grouped call (matches Gemini's expected shape, previously scattered); `ensure_last_message_is_user` is inert for every Gemini model VoIPBin offers (all match `_PREFILL_SUPPORTED_PATTERNS`). Team and resume request bodies otherwise identical to 1.4.0 + flows 1.3 (OpenAI byte-identical, Gemini `system_instruction` and function call/response pairs identical).
- Go's `pipecatcall_initialized` event is published when the output WS is accepted. 1.12 connects the output during `setup`, before the other services finish connecting, so the event moves earlier by the setup time. Effect: ai-manager stops call media sooner (slightly longer silence before the first bot utterance) and timeline `FirstResponseMS` rises by the same amount. Watch in the live smoke.
- Deepgram now pushes an error frame on a 4xx handshake ("Deepgram rejected the connection (status 401)"); the Go classifier maps it to an authentication notice published to the customer. In 1.4.0 it was only a retry log. Correct signal, new visibility. With 2.5c, a 429 handshake rejection surfaces as "connection error: Deepgram transient rejection (status 429)", which the Go classifier maps to rate_limited and notifies the customer once per session even on voice sessions (1.4.0: log only); 408 and 503 map to unknown and do not notify on STT sessions. Accepted (true signal, deduplicated per session); watch in the live smoke.
- Google STT results are now marked `finalized=True` (1.6, #5018), so a turn can close without the fallback timeout; the bot answers slightly sooner.

Pre-existing, out of scope (same on main, filed separately): `WebsocketClientParams` has no `session_timeout` field, so the runner's `session_timeout=` is silently ignored on both 1.4.0 and 1.12. Since pipecat 1.0, `WebsocketClientParams` silently drops the `vad_analyzer` / `turn_analyzer` the runner passes (run.py `create_websocket_transport`), and the user aggregator is built without them, so `build_vad_params` / `smart_turn_enabled` have no effect. This PR does not change that wiring.

Deprecations (warn only, removal in 2.0; our `<2.0` cap keeps them working): `FlowManager(task=)` -> `worker=`; NodeConfig `role_messages` -> `role_message`; service `model=` kwarg -> `settings=Service.Settings(model=)`; system prompt as first `LLMContext` message -> `system_instruction`; `AudioContextTTSService` base (upstream-internal).

Also noted (not a regression of this PR): since flows 1.3 the first node uses `LLMMessagesAppendFrame`, so the team start context carries `init_prompt` and history twice (run.py `start_messages` plus the start node). Already true on the flows 1.3 combination; out of scope. 1.12 also changes how an async tool result lands in context: 1.4 inserted `async_tool` running/finished developer envelopes, 1.12 overwrites them with a plain tool result when the result arrives first. Observed in both provider requests; checked and judged benign (cleaner context, same result content). Resolved patch versions of transitive deps can differ between `uv.lock` and the Docker pip resolve (e.g. openai 3.21 vs 3.22); both are inside pipecat's bounds.

### 1.4 Proceed decision

Proceed. (a) The shipped image cannot move past 1.4.x, so no pipecat fix (including the Gemini tool-schema and thought_signature fixes in 1.9 to 1.11) reaches prod without this change. (b) The breaking surface is small and fully mapped: one import repoint plus pin files. (c) The real risk is behavioral: default drift (section 2.3 pins it back), four team-path regressions (section 2.5), one input-transport race that affects every voice call (section 2.5b), a new permanent 'unusable' state and new give-up paths that turn transient provider failures into a mute or deaf call (section 2.5c), a new Gemini first-chunk timeout (section 2.5d), and a Gemini single-system-message ordering change (section 2.5e).

## 2. Design

Principle: upgrade = no customer-audible behavior change. Upstream default changes a caller could notice are pinned back to current behavior in this PR; adopting new defaults is a separate product decision. Protective, non-audible defaults (timeouts) are adopted as-is.

### 2.1 Pin files (all three in sync)

- `requirements.txt`, `pyproject.toml`: `pipecat-ai[silero,deepgram,openai,cartesia,websocket,google,local-smart-turn]>=1.12.0,<2.0`; remove `pipecat-ai-flows` (its presence makes pipecat log an ERROR at import and, under pip, caps pipecat `<1.5`). Keep `onnxruntime>=1.24.3,<1.25` (1.12 resolves 1.24.4).
- `uv.lock`: regenerate with `uv lock`. No extra caps on openai / deepgram-sdk; pipecat's own `requires_dist` bounds them.
- `Dockerfile`: keep the CPU torch pre-install at the current pins (`torch==2.12.1`, `torchaudio==2.11.0`). pipecat 1.12's `local-smart-turn` extra requires `torch>=2.5,<3` / `torchaudio>=2.5,<3`, so the existing CPU wheels satisfy it and pip does not pull a CUDA build. Not bumping torch keeps this PR free of an unrelated runtime change. Only the comment wording ("pipecat-ai 1.4.0") is generalized.

### 2.2 Imports

- `run.py:52`, `team_flow.py:8`: `from pipecat_flows import ...` -> `from pipecat.flows import ...`.
- `conftest.py`: stub key `"pipecat_flows"` -> `"pipecat.flows"`; `test_team_flow.py` comment updated.

### 2.3 Preserve current audible behavior (explicit settings)

- Deepgram: add `profanity_filter=True` to the existing `LiveOptions(...)` call (probe: honored by 1.12, resolves to True).
- Cartesia: pass `model="sonic-3.5"`.
- ElevenLabs: pass `model="eleven_turbo_v2_5"`.
- Empty user turn recovery: build every `LLMContextAggregatorPair` (single-AI openai / grok / gemini paths and the team path) through one helper `_make_aggregator(ctx)` in `run.py` that passes `user_params=LLMUserAggregatorParams(empty_user_turn=None)`, so the four call sites cannot drift.

Constructor style stays as today (keyword `model=`), deprecated-but-working under `<2.0`. Migrating to `settings=` is deferred with the other 2.0 deprecations.

### 2.4 Flows registration model

- No code change for correctness. Update the stale comments in `run.py` (Step 3 "create_adapter()", Step 7 swap rationale) and `routing_llm.py` to describe current behavior: flows advertises handlers via `FunctionSchema`; each member LLM auto-registers on its own context frame; the `_llm` swap is kept only as a harmless reference, and the `hasattr` guard stays.
- `RoutingLLMService.register_function` gains pass-through of `cancellable_by_llm` (optional kwarg added upstream) so a future caller using it is not rejected by the `**kwargs` guard. Covered by one unit test.

### 2.5 Team-path fixes (required for 1.12)

- `routing_stt.py` and `routing_llm.py` `process_frame`: after propagating `StartFrame` to every member, call `await svc.broadcast_service_metadata()` on each member that has it (`hasattr` guard, so a stub or a future rename does not crash). The member's `broadcast_frame_instance` goes through the member's instance `push_frame`, i.e. through the router, so the frame reaches downstream exactly as the 1.4.0 per-member push did (every member broadcasts once per StartFrame the router receives; with the StartFrame dedupe below, that is once per member, same as 1.4.0). Verified with a real 1.12 Pipeline: original router = 0 frames, fixed router = `[0.35, 1.57]` (both members, in member order). The aggregator keeps the last value it sees, so a team uses the last member's latency rather than the active member's; this matches 1.4.0 exactly (parity, not a new behavior) and a per-member re-broadcast on member switch is left as a follow-up. `routing_tts.py` needs nothing: TTS services return no metadata frame.
- `team_flow.py`: add `_escape_flow_placeholders(messages)` and apply it to the history injected into `start_node["task_messages"]`. For each message whose `content` is a `str`, prefix every match of the flows placeholder pattern `(\\?)\{\{\s*ident(\.ident)*\s*\}\}` with one backslash. Flows' renderer strips exactly one backslash from an escaped match, so both `{{ x }}` and `\{{ x }}` render back to the original text. Non-string content (multimodal parts) is passed through untouched. The helper is non-mutating: it returns new dicts (`{**m, "content": escaped}`) and never edits the input, because `run.py` Step 3 `start_messages` and `start_node["task_messages"]` share the same message dict objects (`filter_valid_messages` builds a new list but keeps the dicts); an in-place edit would leak backslashes into the initial `LLMContext`. A unit test asserts the input is unchanged. The regex is a local copy of flows' private `_PLACEHOLDER` (kept in sync by a real-library test, below). Verified against the real 1.12 `_render_node`: `{{ name }}`, `\{{ x }}`, `\\{{ y }}`, dotted keys, and non-matching braces all round-trip byte-identical; non-string content is untouched; unescaped `{{ name }}` raises `FlowError`.

- StartFrame dedupe in all three routers (`routing_stt.py`, `routing_llm.py`, `routing_tts.py`). Each router forwards `StartFrame` to every member and each member pushes it downstream through the router, so N members produce N copies per stage and N^3 reach the output transport (2 members: 8). 1.4.0's `WebsocketClientOutputTransport.start` had an `if self._initialized: return` guard; 1.12.0 removed it, so every copy calls `set_transport_ready` and starts a new `MediaSender` clock/audio task pair. Reproduced with a real 1.12 Pipeline (2 members, STT+LLM+TTS routers): 1.4.0 = `set_transport_ready` 1, no leftover tasks; 1.12.0 = 8, and 7 `_clock_task_handler` + 7 `_audio_task_handler` tasks left dangling after the run ("dangling tasks detected" ERROR). Audio is unaffected (3 sends per frame in both), but the runner is a long-lived uvicorn process, so each team call leaks N^3-1 task pairs. Fix: in each router's `routing_push`, forward only the first `StartFrame` downstream and drop later copies (a per-router boolean). Verified: `set_transport_ready` 1, no leftover tasks, no warning. EndFrame/CancelFrame duplication is unchanged from 1.4.0 (parity) and not touched. Fixing at the router rather than restoring the guard in `UnpacedWebsocketClientOutputTransport.start` is chosen because it removes the root duplication for every downstream processor, not just the transport, and also makes the metadata broadcast above exactly once per member.
- Suppress the auto-composed async-tool system instruction on team member LLMs. Since 1.8.0, `LLMService._compose_system_instruction()` appends the English `ASYNC_TOOL_INSTRUCTIONS` block whenever `_has_async_tools()` is true, i.e. any registered tool has `cancel_on_interruption=False`. Flows' `FlowsFunctionSchema.cancel_on_interruption` defaults to `False` (`flows/types.py:395`), and those options are carried into the auto-registered handlers, so every team member counts as having async tools. Effect captured on the outgoing provider request: Gemini member `system_instruction` = `"ASYNC TOOLS:..."` instead of the member `init_prompt` (the adapter then discards the leading context system message, so the persona is demoted); OpenAI member gets an extra leading system message. The single-AI path registers tools with the default (`True`) and is unaffected (identical requests 1.4 vs 1.12). Fix: in `init_team_pipeline`, right after each member LLM is created, set `svc._has_async_tools = lambda: False` (private API; the real-library test asserts `type(svc)._has_async_tools` exists and that a Gemini member request has no `ASYNC TOOLS` text, so an upstream rename fails the check instead of silently disabling the override). Verified: Gemini `system_instruction` back to `PROMPT_A`, OpenAI request identical to 1.4. Rejected alternative: `cancel_on_interruption=True` on the flows schemas, which restores the prompt but lets a barge-in cancel a transition handler mid-switch.

Known, not changed: routers call member `setup()` sequentially and 1.12 services (Deepgram/Google STT, Cartesia) connect during `setup`, so connect times add up inside the 20 s `setup_timeout`. Not an issue at current team sizes; noted for larger teams.

### 2.5b Input transport connect timing (required for 1.12, single-AI and team)

- Problem: 1.12 `WebsocketClientInputTransport.setup()` dials the input WebSocket (`client.py` ~261), but the audio queue `_audio_in_queue` is only created in `start()` -> `set_transport_ready()`. Go's `RunSender` drains the pre-filled `RunnerWebsocketChan` (150 frames, about 3 s of Asterisk media) the moment the input WS is accepted, so the first audio frame arrives before StartFrame: `push_audio_frame` raises `AttributeError`, the session's receive task exits, `on_disconnected` fires and `run.py` cancels the task. In 1.4.0 `start()` did `session.connect()` then `set_transport_ready()` back to back, so this window did not exist. Reproduced with the runner's real `init_pipeline` / `execute_pipeline` against a local WS server that sends audio immediately: 1.4.0 alive, 150/150 frames; 1.12.0 crashes at first audio delay 0 ms and 200 ms, survives at 1500 ms. Every STT-enabled voice call (single-AI and team, both use `create_websocket_transport("input")`) is exposed. Upstream fixed the same race only for the MoQ transport (1.8.0, PR #5451).
- Fix: keep the 1.12 setup-time connect and hold early audio instead of crashing or dropping it. Add `EarlyAudioBufferingInputTransport(WebsocketClientInputTransport)` with two overrides: `push_audio_frame(frame)` appends the frame to an instance list while `self._audio_task is None` (respecting the same `audio_in_enabled` / `_paused` checks as upstream) and otherwise calls `super()`; `set_transport_ready(frame)` calls `super()` (which creates the queue and audio task) and then replays the held frames in arrival order through `super().push_audio_frame`. A `BufferingInputWebsocketClientTransport(WebsocketClientTransport)` overrides `input()` to return it, and `create_websocket_transport("input")` uses that subclass (same pattern as the existing `UnpacedWebsocketClientTransport.output()`). No upstream method body is copied (`setup`/`start` are untouched), so upstream changes to them still apply. The list is bounded by the setup window and the short window between `stop()`/`cancel()` clearing the audio task and the session disconnect (frames held there are discarded with the transport); in practice bounded by setup duration (50 frames/s, `setup_timeout` 20 s caps it near 1000 frames) and is discarded with the transport if the task is cancelled before start.
- Verified (1.12): real runner e2e with first audio at 0 ms stays alive with no error; race probe 150/150 frames with 0 ms and 300 ms slow setup; Go-buffer probe (2000 ms of Asterisk media queued before accept, 1500 ms slow setup) 300/300 frames, 0 dropped, input accepted at 2.01 s like 1.4.0.
- Alternatives rejected, same probes: (a) drop audio while `_audio_task is None`: survives but loses early caller speech (149/150, 135/150); (b) defer the input connect to `start()` (1.4.0 order): survives, but because 1.12 services connect during `setup`, the input is accepted a whole setup later than in 1.4.0 (team: grows with member count), Go's 150-frame (about 3 s) channel overflows and drops frames (294/300 in the Go-buffer probe) and it copies the upstream `setup` body.
- If the input connect itself fails (refused, 4xx, handshake timeout), behavior is unchanged from 1.4.0: a non-fatal error, the pipeline continues without input until idle timeout or Go terminates it.

### 2.5c Keep services usable after transient provider failures (required for 1.12, single-AI and team)

- Problem: 1.12 adds a per-processor "usable" flag. Once a processor is marked unusable it never recovers within the call: `TTSService` skips synthesis (`tts_service.py:1425`, "service is no longer usable, not speaking") and `STTService` drops audio (`stt_service.py:443`, `:936`). Nothing in 1.4.0 had this state. With the default `processor_unusable_policy=CONTINUE` the call stays connected with a mute or deaf bot until the caller hangs up. Triggers that reach it on the runner's services:
  - Any error classified as a permanent category, including a single HTTP 400/404/422 on one request (`utils/errors.py`, `push_error_frame` -> `set_usable(False)`). Probe: one 400 from TTS, then the provider is healthy: 1.12 synthesizes nothing for the rest of the call (1 attempt, 0 audio); 1.4.0 speaks every later turn.
  - `max_consecutive_zero_audio_contexts=3` (new TTS default: Cartesia, ElevenLabs, Google TTS). Probe: 3 failed turns then recovery: 1.4.0 speaks turns 4 to 6; 1.12 speaks none.
  - Deepgram STT `QuickFailureTracker` (3 quick reconnect failures). Probe with a 20 s provider outage (503): 1.4.0 reconnects after recovery and transcribes; 1.12 gives up at about 18 s and never reconnects. A 12 s outage recovers on both.
- Fix (restores 1.4.0 retry-every-turn behavior, applied in the service factories so single-AI and team members are covered). The usable flag and the retry loops are two separate mechanisms and each needs its own fix:
  - Flag. One helper `_keep_usable(svc)` in `run.py`, called on every STT and TTS service the factories create: it wraps the instance's `set_usable` so `set_usable(False)` is ignored and `set_usable(True)` passes through. `_is_usable` is only written in `FrameProcessor.__init__` and inside `set_usable` (`frame_processor.py:290`, `:352`), so for the flag this is the single choke point. The error frame itself still flows, so Go's error classification and customer notices are unchanged (RTVI forwards only `error` and `fatal`, neither changes).
  - TTS zero-audio counter: TTS factories pass `max_consecutive_zero_audio_contexts=0` (public parameter; Cartesia/ElevenLabs verified, Google via `**kwargs`, checked in the real-library test). Recovery itself is already guaranteed by `_keep_usable`; this parameter stops the extra "N consecutive TTS contexts completed with no audio" error frame that would otherwise repeat every silent turn after the third (a notice candidate on TTS-only sessions).
  - Loops, per service (checked individually, since a loop that exits is not revived by the flag):
    - Deepgram STT, in one helper `_harden_deepgram(svc)`: (1) `svc._quick_failure_tracker = QuickFailureTracker(max_consecutive_failures=sys.maxsize)`, so 5xx and dropped connections keep retrying with the existing capped backoff; (1b) immediate first reconnect after a stable connection drops (stable = the connection stayed up at least 5.0 s, upstream `QuickFailureTracker.min_stable_duration`; since only a connection that lasted >= 5 s resets the count, back-to-back immediate reconnects are at least 5 s apart, measured worst case 0.2 handshakes/s at exactly 5.0 s; repeated 408/429/503 rejections and sub-5 s drops measured at 0.13 to 0.17 handshakes/s): 1.12 always sleeps `exponential_backoff_time(tracker.count)` before reconnecting, and its `min_wait=4` makes even the first retry after a healthy connection (count 0) wait 4 s while `run_stt` drops audio (measured: server closes the socket at 7 s, reconnect gap 4.0 s, about 195 frames / 3.9 s of caller speech lost; 1.4.0 reconnected in 0.0 s). The sleep uses a module-level name, so this cannot be done per instance: once, at runner import, `run.py` rebinds `pipecat.services.deepgram.stt.exponential_backoff_time` to a wrapper that returns 0 for attempt 0 and delegates otherwise (idempotent, only that module's binding, other services keep upstream backoff). Measured with the wrapper: gap 0.0 s, 727/727 frames. Any failure after that (count >= 1: a failed handshake is always a quick failure) keeps the upstream 4 s to 10 s backoff, which replaces 1.4.0's backoff-free tight loop (thousands of handshakes per second during an outage); the accepted cost is that after a longer outage the reconnect can lag provider recovery by up to 10 s (measured: 25 s outage from start, reconnect at 31 s); (2) wrap `svc._client.listen.v1.connect` with a function that returns an async context manager, entering the SDK's context manager in `__aenter__` (where the SDK raises `ApiError` at the handshake) and delegating `__aexit__` unchanged, so an `ApiError` with status 408 or 429 at the handshake is re-raised as `ConnectionError`, which the handler's generic branch retries with backoff, while every other 4xx still reaches the upstream give-up branch (401/403/400 are real configuration errors; 1.4.0 retried them in a backoff-free tight loop, so stopping is an improvement); (3) override the instance `setup` to call the parent `STTService.setup`, start `_connect()` as a task, and wait for it at most 2 s (`asyncio.wait({task}, timeout=2.0)`, the task is not cancelled on timeout). Upstream 1.12 `setup` awaits `_connect()` unbounded, which waits on `_connection_settled`; with give-up disabled that would block pipeline setup until the provider recovers or `setup_timeout` (20 s) ends the call. Fully non-blocking (as in 1.4.0) was measured and rejected: on a healthy connection the 2.5b replay burst (the caller's first words) reaches Deepgram before the socket is up and `run_stt` drops it (0/100 frames, same as 1.4.0), whereas unfixed 1.12 delivers 100/100. The bounded wait keeps that improvement on the healthy path (100/100 at handshake 0.05/0.4/1.5 s) and caps an outage at 2 s per Deepgram member; team routers set members up sequentially, so the worst case is 2 s x Deepgram members, far below `setup_timeout` 20 s at current team sizes (2 members, 25 s outage: StartFrame at 4.3 s, both members reconnect after recovery). Audio arriving during an outage is dropped, as in 1.4.0. Boundary, stated explicitly: a healthy handshake that takes longer than 2 s loses the replayed burst and the live audio until the socket opens (measured at 2.5 s and 3.0 s handshakes), which is the same as 1.4.0; a shorter handshake loses nothing. An EndFrame or cancel that arrives inside the 2 s wait is processed when the wait ends (at most 2 s later); no task leaks (measured).
    - Cartesia / ElevenLabs: `WebsocketService` reconnect exhaustion ends the receive loop, but `run_tts` reconnects when the socket is closed, so each new turn retries (1.4.0 parity). No change beyond the flag.
    - Google STT: `_stream_audio` retries every second without a give-up (1.4.0 parity). Google TTS is per request. No change beyond the flag and counter.
    - LLM services are not wrapped: `LLMService` has no usable gate on inference (only STT, TTS, output transport, worker, service switcher and observers read `is_usable`). A permanent-category LLM error still logs "can no longer do its job" once; behavior is unchanged under `CONTINUE`.
    - Output transport: `audio_out_write_timeout` (10 s) marks the output transport unusable and it then drops audio (`base_output.py:997`). 1.4.0 waited forever in the same situation, so this is not a regression and is not changed.
- Verified (1.12, real services, fake provider servers): TTS with one 400 then healthy: 6 attempts, 5 audio turns; 3 failed turns then recovery: turns 4 to 6 spoken (1.4.0 parity). Deepgram with all three fixes: 25 s and 10 s 503 outage from call start: StartFrame reaches downstream at about 2.4 s with the 2 s bounded wait (one Deepgram member; 2 members through the router: 4.3 s) (1.4.0: 1.0 s; unfixed 1.12: 8.5 s then permanently deaf; tracker-only fix: setup timeout at 20.4 s ends the call) and transcription resumes after recovery; 429 for 8 s mid-call and 6 s from start: reconnects and streams after recovery (1.4.0 parity; unfixed and tracker-only 1.12: 0 reconnects); 503 for 8 s mid-call: recovers; 401: stops retrying, as intended.
- New visibility, accepted: every TTS context that ends with no audio now emits a non-fatal "completed with no audio" error frame (absent in 1.4.0). Go classifies it as unknown; on a TTS-only session (no STT) it can produce one customer notice.
- Trade-off, stated explicitly: a truly permanent TTS failure (for example a revoked key) now retries every turn for the rest of the call, exactly as in 1.4.0, instead of going silent. A permanent Deepgram 4xx other than 408/429 stops retrying (better than 1.4.0's tight loop). Choosing to end such calls (`processor_unusable_policy=CANCEL`) is a product decision that needs a caller-facing message and is deferred.

### 2.5d Gemini first-chunk timeout

- 1.12 `GoogleLLMService` adds `stream_idle_timeout_secs=20.0`, applied to the first chunk when `retry_on_timeout=False` (`google/llm.py:220`, `:650`). Probe with a first chunk at 25 s: 1.4.0 speaks the answer at 25.6 s; 1.12 produces nothing and emits "LLM completion timeout" at 20.3 s, which Go classifies as timeout and always notifies the customer. VoIPBin offers `gemini-2.5-pro` and `gemini-pro-latest`, which think dynamically and emit no chunk while thinking (frequency not measured). Fix: `create_llm_service` passes `stream_idle_timeout_secs=None` to `GoogleLLMService`, restoring 1.4.0 behavior. `None` disables both the first-chunk and the between-chunk idle timeout (1.4.0 had neither), which is also why the pre-existing half-open-connection wait noted in 1.3 remains. Adopting a timeout is a separate decision once real first-chunk latency is measured. OpenAI/Grok: `retry_on_timeout` default unchanged (False), no equivalent new timeout.

### 2.5e Gemini lone system message ordering

- 1.4.0's adapter (`base_llm_adapter.py:222-236`) converted the initial `system` message to `user` in place, and only when it was the sole message in the context (`len(messages) == 1`); with any following message it extracted it into `system_instruction` instead. Since 1.7 (PR #5027) the same conversion runs on a per-request copy. For a single-AI Gemini session whose context starts as exactly one system message (an AI with an empty `init_prompt` and `parameter` `{}`, for which `bin-ai-manager` `start.go` writes one system row and no other row) and whose first turn calls a tool, the request after the tool result becomes `[model function_call, user function_response, user <system text>]` and every later request starts with a model function call; 1.4.0 sends `[user <system text>, model function_call, user function_response]` because its in-place conversion persisted. Reproduced with the runner's real `init_pipeline` (single-AI integrated probe). Gemini requires a function call turn to follow a user or function response turn, so the expected effect is a 400 on every later turn of that call (inferred; no live API key in the probe).
- Fix: in the Gemini branch of `create_llm_service`, when `len(valid_messages) == 1 and valid_messages[0]["role"] == "system"`, replace it with a new dict with role `user` (input not mutated) before building the `LLMContext`. This is exactly 1.4.0's condition. A lone system row followed by a user row (conversation AIcall) or by history (resume / reuse) is left untouched, so it is still extracted into `system_instruction` as in 1.4.0. A broader "exactly one system role" condition was measured and rejected: it demoted the platform system prompt from `system_instruction` to a user turn for those sessions, a new behavior change. Verified against 1.4.0 over six context shapes (lone system; system + user; system + history; system + tool history; two or more systems; developer messages) at three inference steps (first request, after tool result, next turn): identical. Team members are built with empty messages and the team context always carries two or more system messages, so the branch never applies there. 1.4.0 converted at the first inference and the fix converts when the context is built; these are equivalent because `init_pipeline` always queues the warmup `LLMRunFrame` first.
