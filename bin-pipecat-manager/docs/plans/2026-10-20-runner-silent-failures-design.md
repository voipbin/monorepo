# VOIP-1633: runner silent failures (empty completion, malformed tool call, tool call without id)

## 1. Ticket review

Verdict: valid, with corrections. Base: origin/main 4d1084ad3. No open PR covers the area; the last change to `scripts/pipecat` is #1462 (tool timeouts), which does not change the premise. Evidence is a local run of real pipecat 1.12.0 and openai 2.15.0 against a local OpenAI compatible stub (no external call, no cost). The real library tests of section 4 are new files added by this PR under `scripts/pipecat_realtest/`.

| Item | Observation before the fix |
|---|---|
| (a) empty completion | The stream ends with `finish_reason: stop` and empty content. The pipeline sees `LLMFullResponseStart`, `LLMFullResponseEnd`, no `ErrorFrame`. |
| (b) malformed tool call | Invalid argument JSON and a tool call without a name end in the same empty response (pipecat logs a WARN for the first, nothing for the second). A name absent from `service._functions` is only logged by `register_missing_tool_logging` (`tools.py`). No `ErrorFrame` in any of the three. |
| (c) tool call without id | The handler runs with `tool_call_id=None`. The next provider request of the same session carries `tool_calls[].id = null` and `tool_call_id = null`. The next turn through `/run` is rejected: `body.llm_messages.1.tool_calls.0.id:missing`, HTTP 422 (`ToolCall.id` is required in `main.py`). |

Corrections: a name-less tool call is dropped without any log in this stack (the worker saw a pydantic error with another server). Team pipelines replace `push_frame` of each member service (`RoutingLLMService`), so a per service `on_before_push_frame` handler would not fire there.

## 2. Design

No new flag, enum value, config, schema or Go change. The existing `ErrorFrame` -> RTVI `error` -> `runnerHandlePipelineError` -> `pipeline_error` event path is reused; its notice text is fixed plain text, never the raw error. The ErrorFrame is non fatal, has no explicit category and no exception, so pipecat classifies it `UNKNOWN`, which is not permanent: the processor stays usable and the default policy only logs it (`frame_processor.py`, `utils/errors.py`). `fatal=True` and `force_treat_as_permanent` are never used and a test pins that. The Go notice policy is not touched: this card is the runner side only (see the known limits).

All new runner logic is in `scripts/pipecat/llm_guard.py` (about 130 lines). `tools.py` only gains one `push_error` call and `message_filters.py` gains the legacy pairing (about 60 lines).

### 2.1 Empty output (a, b): an observer

`EmptyOutputObserver` is a pipecat observer created with `observe_every_push=False` (pipecat then reports each frame once, by frame id, which also covers an End frame that a TTS with word timestamps pushes again later). It is passed as an inline `observers=[...]` list to the two `PipelineTask` calls (single and team). PipelineTask adds its own RTVI observer whenever RTVI is enabled and no external RTVI processor exists, however many other observers are passed; only a user supplied `RTVIObserver` would duplicate it (`pipeline/worker.py`), and that is what the test keeps out. `test_run.py::test_pipeline_task_not_called_with_observers` forbids every `observers` keyword to keep `RTVIObserver` out; it is narrowed to allow only lists made of `EmptyOutputObserver(...)` calls and, new, to require them on every `PipelineTask` call (a missing wiring fails a test); the RTVI import checks stay.

It tracks one LLM response. `LLMFullResponseStartFrame` opens it. These mark it as having produced something: an `LLMTextFrame` with non blank text (other `TextFrame` subclasses such as transcriptions do not count), a `FunctionCallsStartedFrame`, an `ErrorFrame` whose `processor` is an `LLMService` (an STT or TTS error does not count), an `InterruptionFrame`, `CancelFrame`, `EndFrame` or `EagerEndOfTurnCancelFrame`. `LLMFullResponseEndFrame` closes it; if nothing was produced the observer logs `[empty_completion] pipecatcall_id=...` (no content) and calls `source.push_error(error_msg="LLM returned no usable output")`. Excluded as legitimate: interruption, session end, an error the service already pushed (a 5xx gives one error, not two), and a response that follows a tool result: the tail role of the `LLMContextFrame` seen before the Start is `tool`, because after a tool action saying nothing is a normal model choice; that case only logs `[empty_completion] after_tool=true`. The tail role is read when the context frame is observed and consumed at the next Start; observers run on a queue and the frame holds the live context, so a change between push and observation could be misread, which is accepted because the delay is far shorter than a tool run. If the role cannot be read the observer fails open (not after a tool). The observer's own error is seen again by the observer but arrives after the response closed, so it opens nothing (a test pins this). The observer body is wrapped in a try/except that logs one line without content: an exception would kill the observer's proxy task and silently stop all later detection (a test pins this).

Why an observer: it sees every frame of every processor in order, works for the team router (the observer then sees the router as `source`), and needs no change to pipecat internals.

### 2.2 Tool without a registered handler (b)

`register_missing_tool_logging` additionally calls `await service.push_error(error_msg="LLM called an unadvertised tool")` (fixed text, no tool name) once per batch, after its existing log lines. A name absent from `service._functions` covers a name the model invented and an advertised tool whose handler was not registered. The response contains `FunctionCallsStartedFrame`, so 2.1 adds no second error.

### 2.3 Tool call without id (c)

Source, `normalize_tool_call_ids(llm_service)` wraps the instance `run_function_calls`:
- A call whose id is empty (None or "") gets `call_<uuid4 hex>` before pipecat records it in the context and before `tool_execute` posts it. Only an empty id is touched, so a service that dedups on ids (pipecat's Mistral service does) is not defeated; the runner wires only OpenAI compatible and Google services, and Google already fills ids.
- A call with an empty name is dropped (it can reach `run_function_calls` when a name-less call precedes a valid one in the same stream; it is unregistered so it never ran, but it would stay in the context as an empty named call and poison later requests). Only the count is logged. If all calls are dropped the response is empty and 2.1 reports it. A name-less call after a valid one makes pipecat drop the whole batch, which 2.1 reports too.
- Applied to the single service (next to `register_missing_tool_logging`) and to every member service of a team (the loop that already registers it). In the team path the id posted to Go stays `team-tool-<name>` (existing); Go stores it as plain text and the only reader that matches on it is `filter_valid_messages`, which compares for equality, so the generated in session id causes no mismatch.
- Security: nothing new becomes executable. A registered tool ran with an empty id before (Go does not validate the id: `RunnerToolHandle` forwards it to `AIV1AIcallToolExecute`); an unregistered name still goes to pipecat's missing handler, which does not look at the id; broken arguments never reach `run_function_calls`; a name-less call is removed. Tests assert that an unregistered name with an empty id and a name-less call never call a handler. Refusing id-less calls was rejected: it would change tools that work today and the context would still hold an id-less pair.

Stored history, `filter_valid_messages` (legacy data written before this fix, or from a server that omits the id), and `main.py` `ToolCall.id: Optional[str] = None` (missing, `null` and "" are all accepted, so no more 422):
- One `ToolHandle` call in ai-manager writes the call row first and the result row after the tool ran (`aicallhandler/tool.go`), so an executed call is a single-call assistant row directly followed by its tool row. Parallel calls are written `[A1, A2, R1, R2]`, where `A2, R1` merely look adjacent.
- Rule, on the list that already passed the existing candidate filter (rows with a role and content or tool calls; adjacency means adjacent in that list, so an id'd row between two rows breaks adjacency): take the id-less rows (assistant rows with an id-less call, tool rows with an empty `tool_call_id`) as a subsequence and walk it in order. Expect `call, result` pairs: a call row must hold exactly one call and its result row must be the very next row in the list. Each accepted pair gets the same deterministic id `legacy_call_<n>` (n is the pair order in the list; unique inside a request, idempotent, shifts if the history window moves). One unpaired call row at the end of the id-less subsequence (an id'd row may follow it) is just dropped (its result is pending or lost) and earlier pairs stay. Any other violation (a result where a call is expected, which covers a leading orphan result after a window cut and `[A2,R1,R2]`; two calls in a row; a row mixing id and id-less calls; non adjacent rows) means the history cannot be trusted, so all id-less rows of the request are dropped and no pair is kept. Examples: `[A1,R1,A2,R2]` kept and `[A1,R1,A9(id),R9(id),A2,R2]` kept; `[A1,A2,R1,R2]`, `[A1,A2,R2,R1]`, `[A1,text,A2,R1]`, `[A2,R1,R2]`, `[A1,A2,R1,A3,R2]` all dropped.
- Evidence for the rule: an exhaustive enumeration in scratch (every order of up to 4 parallel calls, with and without filler rows) found no wrong pairing with a window cut alone or with lost result rows alone. A window cut together with a lost result row can still produce a wrong pair, for example `[A2,R1]` after A1 was cut: a single `call, result` pair carries no mark that tells it apart, so this is a known residual. The same enumeration is kept as a unit test (the "no wrong pair" property for cut only and for lost results only).
- Why keep the clean pairs instead of dropping everything id-less: dropping hides an executed call from the model, which could then repeat a side effect tool. Why drop the rest: a wrong pairing is worse than none.
- Behaviour change, intended: today an id-less call and an id-less tool row are kept together because `None in result_ids` matches them, and `None` ids reach the provider; after the change clean pairs are kept with ids and the rest is dropped. Complete valid history is returned unchanged and the existing `test_message_filters.py` cases stay green. The function does not mutate its input and is idempotent (the team path calls it twice). Counts of renamed and dropped rows are logged, never content. The existing `[missing_tool]` log line (which names the tool) is left as it is. The team path calls the function twice per request and a third call site exists in the single path; all of them get the same result because the function is idempotent.

### 2.4 Not changed

Normal path behaviour (regression tests: text answer, valid tool call, interrupted response, response after a tool result, complete valid history), Go notice texts, category enum, config, schema.

### 2.5 Known limits (reported, not fixed here)

- The error is classified `unknown`; by the VOIP-1542 policy `unknown` is notified only for sessions without STT, so voice sessions get the log and the metric but no aicall notice. Fixing that needs a policy change on the Go side.
- `MarkPipelineErrorSeen` keeps one notice per category per session and `unknown` is shared with every other unknown error, including the 2.2 error when the model recovers on its own. A later empty completion in that session is counted and logged but not noticed again; the ai-manager 10 minute window only applies to foreign pipecatcalls. The metric counts every one. The fixed `unknown` text ("An AI service provider returned an error.") is generic for these causes; adding a category is forbidden by the card.
- Partial failures are not detected: a call with broken arguments next to a valid call or next to answer text (pipecat drops only the bad call, with a WARN inside the parser).
- In every session type the silence after a tool result (deliberately not reported) and the cases above stay silent for the caller; only the log (and for reported cases the metric) show them.
- Legacy history, cascade: one lost result row early in the id-less subsequence (for example after a timeout, `[A1,A2,R2]`) makes the whole request's id-less rows dropped, including later clean pairs. This is the price of never guessing a pairing. A call and its result separated by assistant text are dropped as well.
- Legacy history residual risk: calls that cannot be paired (interleaved parallel calls, a call row without a result row after a timeout, a result row with empty content, which the existing candidate filter drops first) are dropped, so the model no longer sees them and could repeat a side effect tool. The frequency is not measured (no production access in this card).
- Calls that only use pipecat's cancel tool would show no `FunctionCallsStartedFrame`; the scripts never set `cancellable_by_llm` or `cancel_on_interruption`, so this does not occur today.
- Rolling deploy: an old runner's id-less history is read by a new runner as above; a new runner's history has ids and is read by an old runner unchanged. The Go side is unchanged in both directions.

## 3. Impact

Python runner only. Logs add `[empty_completion]` with the pipecatcall id only. `pipecat_manager_pipeline_error_total{category="unknown"}` can rise by the number of formerly silent failures, which is intended. Docs: `docs/domain.md` (Pipeline errors) and `docs/operations.md` get the log, the two fixed texts and the reason `unknown` can rise (service docs sync rule).
