# VOIP-1729: remove the environment fallback of the ai-manager MCP OAuth app credentials

## 1. Background (verified against origin/main 41517e3b0)

- `aiconfig.New` hands `os.LookupEnv` to `confighandler.NewHandler`; the eight MCP OAuth keys (`mcp_oauth.<vendor>.client_id` and `.client_secret` for github, linear, asana, hubspot) declare an `Env` name; the compose file, the operations doc, the service CLAUDE.md, the architecture doc, the `ai-control config` help text and the public Service Config docs describe the fallback.
- With no stored app and no environment value the connect start does not fail today. It creates a state row and returns an authorize URL with an empty `client_id`, which the vendor refuses (`pkg/mcpoauthhandler/start.go`).
- `confighandler.SourceEnv`, the `Env` field of `confighandler.Key` and `EnvLookup` stay: `bin-pipecat-manager/internal/pipecatconfig/main.go` still passes `os.LookupEnv`. The other five services pass `nil`.
- The only consumers of `MCP_OAUTH_<VENDOR>_CLIENT_*` are bin-ai-manager (code, tests, compose, docs). `RATE_LIMIT_MCP_OAUTH_*` in api-manager is an unrelated flag. No k8s manifest and no install file mention them.

## 2. Principle and decisions

Principle: one source of truth for a secret. The app of a vendor is read from the database only.

D1. `aiconfig.New` passes no environment lookup (`nil`), and the eight keys declare no `Env`. A key without an `Env` is resolved from the database only (same as the two platform LLM keys). The environment variables are ignored even when they are set.
D2. Fail closed. When the resolved pair is empty (either value empty), `Start` and `Complete` stop with a new error `MCP_OAUTH_VENDOR_NOT_CONFIGURED` (`cerrors.Internal`, HTTP 500, the same family as `MCP_OAUTH_VENDOR_UNAVAILABLE` and `MCP_OAUTH_CREDENTIALS_UNAVAILABLE`: a platform side condition the customer cannot fix). The check runs right after `resolveVendor` returns without error. `Start` therefore creates no state row, and `Complete` fails before it deletes the state row (the single use delete comes after the resolution). The refresh path (`exchangeAndStore`, which calls `h.credentials` directly and never `resolveVendor`) is unchanged: an empty pair is sent to the vendor, which refuses it, exactly as today.
D3. A half stored pair keeps its current error (`ErrMCPOAuthIncomplete`, reported as `MCP_OAUTH_CREDENTIALS_UNAVAILABLE`). A `client_id` row without a `client_secret` row reads as "not configured" because the group is anchored on the secret (`confighandler/resolve.go`): this is the middle state of the documented write order (client_id first) and ends in D2's error.
D4. `ai-control config list` keeps its JSON shape (`env_shadowed` stays, always false; billing, email and message controls keep it too). The admin config API (`/service_configs/ai`, served by the shared `configrpc`) copies `Key.Env` into `env_name` (`configrpc/server.go`, `omitempty`), so `env_name` is no longer returned for the eight keys. The OpenAPI description already says it is omitted when a key has no environment variable, so no spec or generated code changes; the tests that assert `env_name` for these keys change (`pkg/listenhandler/v1_configs_test.go`). Help text and docs no longer say the list reads an environment. Sources that can appear are `db`, `none`, `db_undecryptable`, `db_invalid`.
D5. No change to common `confighandler`, `SourceEnv`, the OpenAPI enum, generated code, pipecat, billing, install, the Komodo variables or the master key.
D6. Public docs: the Service Config pages stop saying that the `mcp_oauth` keys of `ai` use the environment; the error table gets `MCP_OAUTH_VENDOR_NOT_CONFIGURED` and the already published but undocumented `MCP_OAUTH_CREDENTIALS_UNAVAILABLE`; the HTML build is regenerated.

Docs: `bin-ai-manager/CLAUDE.md`, `docs/operations.md`, `docs/architecture.md`, `bin-common-handler/CLAUDE.md`, `bin-api-manager/docsdev/source/service_config_overview.rst`, `service_config_struct_service_config.rst`, `restful_api_errors.rst`, plus `docsdev/build`.
Tests: `aiconfig` (main and mcpoauth tests), `configkeys`, `cmd/ai-manager` credentials adapter, `internal/config` provider keys, `cmd/ai-control` config, `pkg/listenhandler` configs, `pkg/mcpoauthhandler` (new error).
`MCPOAuthClient` keeps the retry branch for a write that lands between its two reads; it is a race guard and is unchanged apart from its comments.

## 4. Rollout, mixed state, rollback

- Order: the eight values must be stored in the database before this image runs, otherwise connect start and completion fail with D2's error for every vendor that has no stored row. This is an operational precondition and is checked without printing values: `ai-control config list` must show source `db` for the eight keys. The `LogSources` start-up lines log each key without a stored value as a warning, which will be the case for the keys that are not stored yet.
- After deploy, deleting a stored row no longer returns to an environment value: the vendor fails with D2's error at once.
- Rolling deploy (two replicas): credentials are resolved per request and nothing is cached (`MCPOAuthClient` reads the store on every call; `mcpoauthhandler` resolves in `Start`, `Complete` and the refresh exchange only). With the eight keys stored, an old image (database first, and a stored secret row means database only) and the new image (database only) use the same values, so the restart order does not matter. A vendor without a complete stored pair would differ (old image: environment value, new image: D2 error), including the middle state of the write order where only the `client_id` is stored; that is why the store comes first and is complete before the deploy.
- Rollback: reverting to the previous image brings the environment fallback back, but the previous image needs the environment lines that this change removes from the compose file. Roll back the image and the compose file together. The Komodo variables are not deleted by this change and must stay until the rollback window has ended (their deletion is a separate, later step). This rule is written in `docs/operations.md`.
- Conflicts with the open pipecat change (VOIP-1728): both edit the same sentences in `bin-common-handler/CLAUDE.md`, `bin-ai-manager/CLAUDE.md`, `docs/operations.md` and the two Service Config rst pages. Whichever merges second rebases and the merged sentences must state that no service reads an environment variable for these keys.

## 5. Alternatives considered

- Keep the old behavior for a vendor without a stored app (empty `client_id` authorize URL): rejected, an operator who forgets to store a value would hand customers an unreadable vendor error page.
- Fail in `Start` only: rejected, `Complete` would still burn the state row and call the vendor with an empty app.
- Fail in the credentials adapter or `aiconfig.MCPOAuthClient`: rejected, it would also change the refresh path.
- Remove `SourceEnv` / `Env` from common now: rejected, pipecat still uses them; a later cleanup can drop them once nothing does.

## 6. Detailed design

### 6.1 Code

1. `internal/configkeys/main.go`: delete `mcpOAuthEnvName` and the `strings` import it alone uses (compile error otherwise); fix the package doc ("from the environment otherwise"), the `Keys` comment and the `maxClientIDLen` comment ("It applies to a value read from the environment too"); the two keys of `mcpOAuthKeys` lose `Env`. Descriptions change: the secret says "A stored value makes the pair read from the database; without a stored client_secret the vendor is not configured" instead of describing a client_id fallback; the client_id says "Write it before the client_secret". The comment of `Keys` says that no key declares an environment name.
2. `internal/aiconfig/main.go`: `confighandler.NewHandler(reg, store, crypto, nil, opts...)`; drop the `os` import if unused afterwards; the `New` doc says that no key reads the environment. `MCPOAuthClient` doc: "The pair comes from the database only. A stored client_secret needs a stored client_id (ErrMCPOAuthIncomplete). Neither stored is not an error: the result is an empty pair, meaning not configured. A read error or an undecryptable value is ErrKeyUnavailable." The switch keeps its three branches (the `default` branch now covers "nothing stored" only; comment fixed, behavior unchanged). `ErrMCPOAuthIncomplete` doc drops "the environment value of the client_id is not used".
3. `cmd/ai-manager/mcp_oauth_credentials.go`: comment only ("the pair comes from the database; an error is passed on as it is").
4. `pkg/mcpoauthhandler`: a new sentinel-free helper in `vendors.go` (imports `cerrors "monorepo/bin-common-handler/models/errors"` and `commonoutline "monorepo/bin-common-handler/models/outline"` are added):

   ```go
   // notConfiguredError builds the error of a vendor whose app is not stored.
   func notConfiguredError() error {
       return cerrors.Internal(commonoutline.ServiceNameAIManager, "MCP_OAUTH_VENDOR_NOT_CONFIGURED", "the oauth app of the vendor is not configured")
   }
   func (vc vendorConfig) configured() bool { return vc.ClientID != "" && vc.ClientSecret != "" }
   ```

   `Start`: after the `resolveVendor` error branch and before `generateRandomToken`: `if !vc.configured() { return "", "", notConfiguredError() }`. `Complete`: after the `resolveVendor` error branch and before `McpOAuthStateDelete`: `if !vc.configured() { return nil, notConfiguredError() }`. `exchangeAndStore` (refresh) is not touched. `CredentialsFunc` doc in `vendors.go` gets one line: Start and Complete fail closed on an empty pair, the refresh path does not. The package comment of `mcpoauthhandler/main.go` has no environment wording (checked) and stays. The message carries no value and no vendor secret; the vendor name is not added (the reason code is the contract).
5. `cmd/ai-control/config.go`: `Long` text: "The LLM keys and the OAuth apps of the MCP vendors are stored in the database only; a key that is cleared is not configured. Store the client_id before the client_secret, and clear both. A vendor whose app is not stored refuses a connection with MCP_OAUTH_VENDOR_NOT_CONFIGURED." The sentence about "list reads the environment of this process" is deleted. `config list` short help is unchanged; `env_shadowed` stays in the output struct (always false).
6. `internal/config/main.go` comment: "are config keys read per request through internal/aiconfig from the database".
7. `komodo/docker-compose.yml`: remove the eight `MCP_OAUTH_*` lines; keep `AI_CONFIG_ENCRYPTION_KEYS` and the other lines untouched (the `ENGINE_KEY_CHATGPT` and `GOOGLE_API_KEY` lines of the earlier removal stay as they are).
